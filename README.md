# النظام المحاسبي متعدد الشركات

نظام مالي عربي قيد التطوير، مبني كمستودع موحد بأسلوب Modular Monolith. يحتوي المستودع على API باستخدام Express وPrisma، وواجهة React، وعقد OpenAPI مرجعي.

## الحالة الحالية

أصبحت النواة الخلفية تدعم:

- المصادقة الآمنة، CSRF، تدوير الجلسات، قفل الحساب، تسجيل الخروج وإدارة الجلسات، واستعادة كلمة المرور برمز أحادي الاستخدام مع إلغاء الجلسات السابقة.
- تسجيل ذاتي عام ينشئ طلبًا قابلًا للاستئناف، ويتحقق من البريد قبل تجهيز المؤسسة والشركة والمدير الأول ودليل الحسابات ذريًا، مع منع تعداد الحسابات وحد محاولات وسجل أمان.
- الشركات وسياق الشركة والعزل الكامل للبيانات بينها.
- المستخدمين والأدوار والصلاحيات وسجل التدقيق.
- شاشة تشغيلية لسجل التدقيق مع البحث والتصفية حسب المستخدم والإجراء والكيان والتاريخ، وعرض التفاصيل، وتصدير CSV آمن ومسجل تدقيقيًا.
- سجل أمان مستقل للمصادقة وقفل الحسابات والجلسات، مع درجات خطورة، تنبيهات غير مقر بها، مرشحات، وسجل لمن راجع التنبيه.
- السنوات والفترات المالية مع مساحة إقفال مراجع: قائمة جاهزية للأستاذ والذمم والبنوك والمخزون والعملات، وتحضير وحزمة إقفال ثابتة البصمة تُرسل إلى Checker مستقل عبر محرك الموافقات، ثم إقفال شهري أو تصفير نتيجة السنة إلى الأرباح المبقاة، وعكس قيد النتيجة ذريًا عند إعادة الفتح.
- محرك موافقات مشترك يملك `ApprovalRequest/ApprovalDecision` فقط، مع صندوق طلبات معزول حسب الشركة وفصل Maker/Checker وقرار immutable وسبب رفض؛ أول تطبيق على مراجعة الإقفال عبر منفذ Fiscal، من دون امتلاك حالة المستند أو الكتابة في Ledger.
- وحدة خدمات مهنية ومشاريع تدعم القضية القانونية والتكليف الاستشاري والمشروع العام، وتربط العميل والفريق وتسجل الوقت الشخصي القابل للفوترة مبدئيًا مع حالات وتدقيق وعزل؛ تقرأ العميل والهوية عبر منافذ المالكين ولا تنشئ فاتورة أو حركة مخزون أو خزينة أو قيدًا.
- أساس موارد بشرية غير مالي يملك الأقسام والمناصب والموظف المستقل عن حساب الدخول والعقد المؤرخ، مع ربط اختياري بعضوية الشركة عبر منفذ Identity ومنع دورات المدير والعقد النشط المكرر. لا يخزن راتبًا أو هوية وطنية أو حسابًا بنكيًا ولا يكتب في المشاريع أو الموافقات أو الأنظمة المالية؛ اعتماد Timesheets ثم فوترة الخدمات هما المرحلتان التاليتان.
- التسلسلات الذرية لأرقام المستندات.
- دليل حسابات افتراضي عام للمنشآت الصغيرة يُنشأ تلقائيًا للشركة الجديدة، ويمكن إكماله للشركة القائمة وتخصيص أرقامه وأسمائه وبنيته أو حذف الحسابات غير المستخدمة، مع أنواع الحسابات ومراكز التكلفة.
- عملات مستقلة لكل شركة مع كتالوج مرجعي وإمكانية إنشاء عملات خاصة معزولة، وأسعار صرف مؤرخة ومدققة، واقتراح السعر النافذ تلقائيًا حسب تاريخ المستند.
- دعم مرجعي للريال اليمني `YER`، مع تفعيله للشركة عبر إعدادات العملات بعد تشغيل Seed المرجعيات.
- القيود اليومية اليدوية: المسودة، التعديل، الترحيل، الإلغاء والعكس.
- العملاء وعناوينهم والصناديق والحسابات البنكية وطرق الدفع، مع توليد رموزها المرجعية تلقائيًا وثباتها بعد الإنشاء.
- سندات القبض وتوزيعاتها وترحيلها المحاسبي وإلغاؤها وعكسها، مع إلزام سند العميل بتسوية كاملة ومنع الرصيد غير الموزع، واحتساب فروقات العملة المحققة تلقائيًا من القيمة الدفترية للفاتورة وسعر التسوية وإظهار الربح أو الخسارة بعملة الأساس.
- فواتير المبيعات والإشعارات الدائنة ببنود يدوية أو مرتبطة بصنف ومستودع من الكتالوج ولقطات تاريخية، مع الخصومات وضريبة القيمة المضافة والترحيل والعكس وربط التحصيلات وتقارير الأرصدة وأعمار الديون.
- نقاط بيع نقدية في شاشة واحدة تنسق فاتورة مبيعات مرحلة وحركة صرف مخزون وسند قبض كامل التخصيص وقيديهما ذريًا، وتملك رابط المستندين فقط من دون نسخ حقائق الفاتورة أو المخزون أو الكتابة المباشرة في Ledger.
- فواتير المشتريات والإشعارات المدينة ببنود مصروفات أو أصول يدوية أو مرتبطة بصنف ومستودع من الكتالوج ولقطات تاريخية، مع ضريبة المدخلات والترحيل والعكس وربط سندات الصرف بالفواتير المفتوحة وتقارير الموردين.
- محددات مرجعيات قابلة للبحث الخادمي والتصفح المتدرج في محرري الفواتير وتقارير الأعمار وإدارة الضرائب؛ لا تقيد العميل أو المورد أو الحساب أو الضريبة أو المستودع أو الصنف بأول 100 سجل، وتبقي التصفية والعزل داخل API.
- الموردون وعناوينهم وحساباتهم الدائنة، مع توليد رموز الموردين ومراكز التكلفة ومعدلات الضريبة والأدوار المخصصة تلقائيًا، وسندات الصرف وتوزيعاتها وترحيلها وإلغاؤها وعكسها وفروقات العملة المحققة، وإلزام سند المورد بتسوية كاملة بدل إنشاء رصيد ذمم غير موزع.
- لوحة تحكم مالية مرتبطة بالبيانات الفعلية تعرض المقبوضات والمدفوعات وصافي التدفق والمسودات وأحدث النشاطات.
- تقارير مالية حسب نطاق تاريخي تشمل التدفق النقدي الشهري في لوحة التحكم، وقائمة التدفق النقدي بالطريقة غير المباشرة مع مطابقة الرصيد وتصنيف الحسابات، وملخص ضريبة داخليًا حسب الاستخدام والمستند وحالة الحدث مع عكس مؤرخ، وحركة مراكز التكلفة الفعلية حسب المركز والحساب مع الانتقال إلى كشف الأستاذ، وميزان المراجعة.
- تقرير دفتر يومية تشغيلي بمرشحات التاريخ ونوع المستند والحالة والحساب والبحث، مع الترقيم والإجماليات المتوازنة وتصدير CSV عربي مدقق.
- المركز المالي وقائمة الدخل مع المقارنة وفحص المعادلة المحاسبية، وكشف حساب مستقل للعميل أو المورد أو حساب الأستاذ مع الرصيد الافتتاحي والحركات والختامي، وتصدير CSV وExcel وPDF عربي مدقق.
- واجهة تشغيلية بالعربية والإنجليزية والأردية والهندية تشمل لوحة التحكم وPOS والمشاريع والقضايا المهنية والموافقات والتقارير والعملاء والموردين وفواتير المبيعات والمشتريات وسندات القبض والصرف والسنوات والفترات المالية والقيود اليومية ودليل الحسابات ومراكز التكلفة والخزينة وطرق الدفع والمستودعات، مع دعم RTL/LTR والشاشات الصغيرة.
- واجهة إدارية للمستخدمين والبحث والتصفية والترقيم والإنشاء والتعديل والتعطيل، وإسناد الأدوار، وإدارة الأدوار المخصصة وصلاحياتها، ومراجعة الجلسات الشخصية وإلغائها.
- إعدادات الشركة الأساسية وضابط فصل منشئ القيد اليدوي عن مرحّله، مع حماية الأدوار النظامية وإبطال الجلسات المتأثرة وتسجيل جميع التغييرات الحساسة.
- طباعة PDF عربية لسندات القبض والصرف والقيود اليومية وفواتير البيع والشراء وإشعاراتها من لقطة تاريخية ثابتة، مع بصمة SHA-256 وعدّاد إعادة الطباعة وصلاحيات مستقلة وسجل تدقيق.
- `PostingEngine` مركزي يملك إنشاء القيود المرحلة وعكسها، و`TransactionExecutor` موحد بمهلة مشتركة وbackoff+jitter وتصنيف صريح لتعارضات MariaDB/MySQL، مع Idempotency واختبارات تزامن وعزل على المحركين.
- عناصر `ReceivableItem` و`PayableItem` مملوكة لـAR/AP تحمل الرصيد بالعملة الأصلية وقيمته الدفترية الدقيقة بعملة الأساس والحالة والنسخة؛ تخصص Treasury القبض والدفع إليها عبر منافذ داخل المعاملة بدل كشف معرفات أسطر الأستاذ، وتحفظ لقطة القيمة المسحوبة وقيمة التسوية وفرق العملة كي يكون العكس حتميًا.
- وحدة `Tax` مالك وحيد لنسب الضرائب وحسابات المدخلات والمخرجات؛ تستهلكها المبيعات والمشتريات عبر `TaxQuotePort` وحاسبة Decimal واحدة، وتحمي التعديلات بـ`version` متفائلة.
- وحدة `Treasury` مالك وحيد لحسابات الصندوق والبنك وطرق الدفع؛ يستهلك القبض والدفع أدواتها عبر `TreasuryInstrumentPort`، وتحمي التعديلات والتعطيل بـ`version` متفائلة مع عزل الشركة.
- Backend المطابقة البنكية 1:1 داخل `Treasury`: معاينة واستيراد CSV وCAMT.053 ببصمة وIdempotency، جلسات واقتراحات محلية حتمية واعتماد/ربط يدوي/فك وتصنيف وإقفال مدقق، مع عزل الشركة وتفرد يمنع اعتماد السطر أو حركة الدفاتر مرتين. يقرأ Ledger المنشور عبر `ReconciliationLedgerQueryPort` فقط؛ لا يكتب القارئ أو محرك المطابقة أو الجلسة أي قيد، وأي حركة محاسبية مفقودة تنشأ عبر خدمات القبض/الصرف/القيد الحالية و`PostingEngine`.
- وحدة `Inventory` مستقلة تملك المستودعات والكتالوج ودفتر حركة كميًا وقيميًا immutable وأرصدة حالية مقفلة؛ تدعم المتوسط المرجح المتحرك والرصيد الافتتاحي والاستلام والصرف والتحويل والتسويات، وتولد حركة الفاتورة وعكسها ذريًا مع Idempotency ومنع المخزون السالب أو القيمة غير المتسقة. تُنشئ الفواتير أثر المخزون وCOGS عبر `PostingEngine`، كما تُرحّل الحركات اليدوية ذات القيمة تلقائيًا إلى مستند `INVENTORY_ADJUSTMENT` وتوفر عكسًا منظمًا يعيد الكمية والقيمة والقيد معًا؛ التحويل وحده بلا قيد لأنه لا يغيّر إجمالي القيمة.
- مركز استيراد جماعي للعملاء والموردين وفواتير البيع والشراء من قوالب CSV/XLSX: معاينة خادمية بأخطاء صفية، وربط اختياري للمستودع والصنف بالرمز عبر منفذ Inventory مع بقاء القوالب القديمة متوافقة، وبصمة ملف قصيرة العمر بدل تخزين محتواه، واعتماد ذري وIdempotent وعزل شركة؛ تنشأ الفواتير كمسودات فقط ولا يلمس الاستيراد دفتر الأستاذ.
- سياق طلب موحد ينقل `deadlineAt` و`AbortSignal` من HTTP إلى المعاملات من دون إعادة ضبط الميزانية، ويمنع النجاح المتأخر، مع مهلات Node صريحة وPrometheus metrics محمية وتنبيهات للـdeadlocks والـdeadlines وOutbox.
- حارس عقد آلي يطابق OpenAPI مع 241 عملية HTTP فعلية، وحدود طلب تعيد أخطاء تحقق آمنة بمعرّف تتبع بدل تحويل مدخلات المصادقة أو JSON غير الصالح إلى خطأ داخلي.
- OpenAPI 1.33.0 عقد JSON تنفيذي موحد: مولد حتمي يغطي أجسام الطلبات الـ125 ومخططات الاستجابة الـ1590 عبر العمليات الـ241، مع أنواع TypeScript وحراس Zod وتحويل BIGINT الآمن وبصمة SHA-256 وفحص CI يمنع التقادم أو رجوع مخطط يدوي موازٍ. يفحص التطبيق أجسام الاستجابة ورموز حالاتها في التطوير والاختبار.
- تعدد لغات مكتمل للواجهة بقواميس عربية وإنجليزية منفصلة ومفاتيح typed، مع حفظ الاختيار وتبديل RTL/LTR وتنسيقات اللغة وبوابة CI تمنع النصوص الصلبة ومفاتيح الإعداد المرئية؛ آلية إضافة لغة وأسماء المرجعيات موثقة في [دليل تعدد اللغات](docs/localization.md)، وقواعد النص والتجاوب الإلزامية في [سياسة محتوى الواجهة والتجاوب](docs/UI_CONTENT_RESPONSIVE_POLICY_AR.md).
- بوابة E2E بـPlaywright/Chromium تغطي التسجيل والتحقق والدخول وتبديل اللغة وإنشاء عملة وسعر صرف وسنة مالية وأول قيد يدوي متوازن، وتعمل على MariaDB وMySQL قبل إصدار الحزمة.
- بوابة متصفح مستقلة تعيد فحص الواجهات حتميًا، بما فيها أرصدة وحركات المخزون ومحرر الحركة، باللغات الأربع وعلى 390/768/1440/1920، وتمنع النشر عند تمدد الواجهة أو التفاف البحث والتبويبات أو تسرب نص تشغيلي.

التفاصيل المرحلية الكاملة موجودة في [حالة التنفيذ](docs/implementation-status.md)، وخطة العملات والتسجيل والترجمة والفحص البصري في [خارطة التطوير](docs/product-roadmap.md).

## بنية المستودع

- `apps/api`: خادم Express وخدمات الأعمال ومخطط Prisma والاختبارات.
- `apps/web`: واجهة React/Vite العربية الأولية.
- `packages/contracts`: عقد OpenAPI المرجعي.
- `docs`: حالة التنفيذ ووثائق التسليم.
- `output/pdf`: نموذج PDF مرجعي مولّد من القالب الفعلي لفحص التسليم البصري.

## المتطلبات

- Node.js 22 أو أحدث.
- npm.
- MariaDB من XAMPP للتطوير المحلي؛ ويدعم الإنتاج MySQL 8.4 LTS أو MariaDB 10.11 بعد اجتياز البوابة المطابقة.

MariaDB 10.4 في XAMPP مستخدمة للتطوير المحلي. سلسلة الترحيلات والـSeed وجميع اختبارات قاعدة البيانات يتم التحقق منها من قاعدة فارغة على MySQL 8.4.11، وتوجد بوابة مستقلة مطابقة لاستضافة iFastNet على MariaDB 10.11.11 وNode.js 22.23.2.

## التشغيل المحلي باستخدام XAMPP

1. شغّل MySQL/MariaDB من لوحة XAMPP.
2. انسخ `.env.example` إلى `.env` وعدّل بيانات الاتصال وكلمة مرور Seed.
3. ثبّت الاعتماديات:

   ```bash
   npm install
   ```

4. ولّد Prisma Client:

   ```bash
   npm run prisma:generate
   ```

5. طبّق الترحيلات وشغّل البيانات الأولية:

   ```bash
   npm exec -w @mcap/api -- prisma migrate deploy
   npm run prisma:seed -w @mcap/api
   ```

6. شغّل المشروع:

   ```bash
   npm run dev
   ```

- API: `http://localhost:3000`
- الواجهة: `http://localhost:5173`
- فحص الحياة: `GET http://localhost:3000/live`
- فحص جاهزية التطبيق وقاعدة البيانات: `GET http://localhost:3000/ready`
- القياسات التشغيلية عند تفعيل `METRICS_ENABLED`: `GET http://localhost:3000/metrics`

Backend المطابقة البنكية معطل افتراضيًا إلى أن تبدأ مرحلة الواجهة والإطلاق؛ يفعّل محليًا فقط عبر `BANK_RECONCILIATION_ENABLED=true`. لا يضيف هذا العلم رابطًا أو شاشة مستخدم، ولا يغير مسارات Ledger أو الترحيل المحاسبي.

حساب التطوير بعد تشغيل Seed هو `admin@mcap.local`. كلمة المرور تؤخذ من `SEED_ADMIN_PASSWORD` في ملف `.env` المحلي، ولا تدخل Git.

## التسجيل الذاتي واستعادة كلمة المرور والبريد

يكون التسجيل الذاتي مفعّلًا افتراضيًا في التطوير. يعرض رابط «إنشاء حساب وشركة جديدة» رحلة عربية/إنجليزية لا تنشئ أي مستأجر أو مستخدم قبل التحقق من البريد. يوضع رمز التحقق في جزء `#` من الرابط حتى لا يصل إلى سجلات HTTP، ولا يُخزن في قاعدة البيانات إلا كبصمة SHA-256. بعد التحقق تُجهّز الشركة والمدير والدور والصلاحيات ودليل الحسابات، ويُمسح Hash كلمة المرور من طلب التسجيل لأن النسخة المعتمدة أصبحت في سجل المستخدم.

يحفظ بدء التسجيل وإعادة الإرسال حدث `RegistrationVerificationRequested` في `outbox_events` داخل معاملة الطلب نفسها، ثم يرسله عامل داخلي بعد الالتزام مع lease ذري وretry محدود وexponential backoff مع jitter. لا يحتوي الحدث بريدًا أو رمزًا؛ يُشتق رمز ثابت لكل حدث بمفتاح `REGISTRATION_TOKEN_SECRET` مستقل، ولا يبقى في قاعدة البيانات إلا Hash الرمز. لهذا لا يُفقد البريد عند سقوط العملية بعد الالتزام، وتبقى إعادة المحاولة صالحة وآمنة.

في التطوير يحاكي `REGISTRATION_EMAIL_MODE=log` الإرسال من دون طباعة البريد أو رابط التحقق في السجل. عند الحاجة إلى الرابط للاختبار اضبط `REGISTRATION_EMAIL_CAPTURE_PATH` على ملف JSONL محلي محمي. في الإنتاج يفشل التطبيق مبكرًا إذا كان التسجيل مفعّلًا من دون `REGISTRATION_EMAIL_MODE=resend` و`REGISTRATION_EMAIL_FROM` و`RESEND_API_KEY` و`REGISTRATION_AUDIT_PEPPER` و`REGISTRATION_TOKEN_SECRET` عشوائيين مستقلين. يمكن تعطيل الميزة صراحةً عبر `SELF_REGISTRATION_ENABLED=false`. مدة الرابط وحد الطلبات تضبطان عبر `REGISTRATION_TOKEN_TTL_HOURS` و`REGISTRATION_RATE_LIMIT_MAX`، وسياسة العامل عبر متغيرات `OUTBOX_*` في ملف البيئة النموذجي.

تعيد «نسيت كلمة المرور» الاستجابة العامة نفسها سواء كان الحساب موجودًا أم لا، ثم تحفظ `PasswordResetRequested` مع الطلب داخل معاملة واحدة. يرسل العامل الرابط بعد الالتزام؛ لا يخزن الرمز الخام، ويلغي طلب جديد كل الروابط المعلقة الأقدم. الرمز أحادي الاستخدام، وبعد نجاح التغيير تلغى جميع جلسات المستخدم ولا يحدث دخول تلقائي. تضبط الميزة عبر `PASSWORD_RESET_ENABLED` و`PASSWORD_RESET_RATE_LIMIT_MAX` و`PASSWORD_RESET_TOKEN_TTL_MINUTES`. عند تفعيلها في الإنتاج تلزم إعدادات Resend وعنوان المرسل و`REGISTRATION_TOKEN_SECRET` حتى لو كان التسجيل الذاتي معطلًا.

تستخدم E2E ملف JSONL مؤقتًا لالتقاط رسالة التحقق عبر `REGISTRATION_EMAIL_CAPTURE_PATH`. هذا المتغير اختبار فقط، ويرفض محمل الإعدادات تشغيل الإنتاج إذا كان مضبوطًا؛ لا تضفه إلى ملفات بيئة النشر.

## تجهيز شركة جديدة

تدعم النواة هوية مستخدم عالمية مع إسناد وأدوار مستقلة لكل شركة. تُنشأ الشركة الإنتاجية بأمر إداري ذري ومتكرر التشغيل من دون بيانات Demo:

```bash
npm run company:provision
```

تُمرر قيم `PROVISION_*` مؤقتًا من مدير الأسرار، ويجب أن تطابق قيمة التأكيد `CREATE:<ORGANIZATION_CODE>/<COMPANY_CODE>`. لا يغير الأمر كلمة مرور مستخدم موجود عند إسناده إلى شركة إضافية، وينشئ للشركة الجديدة دليل الحسابات الافتراضي دون Demo Seed. أي PR مدمج إلى `main` ينشر تلقائيًا إلى iFastNet بعد بوابتي MariaDB وMySQL ونسخة إنتاج مشفرة؛ يرفض النشر Force Push أو التزامًا لا يطابق PR المدمج قبل قراءة الأسرار. التفاصيل وإعدادات PM2 وNginx موجودة في [دليل التشغيل الإنتاجي](docs/production-operations.md)، ومسار الاستضافة الحالية موثق في [دليل iFastNet cPanel](docs/ifastnet-cpanel-deployment.md). يسجل [تدقيق اعتماد بيئة الإنتاج](docs/PRODUCTION_ENVIRONMENT_AUDIT_AR.md) الضوابط المثبتة والفجوات المطلوب إغلاقها قبل اعتماد حوكمة البيئة نهائيًا.

مهلات HTTP والتطبيق والمعاملة مرتبة من الخارج إلى الداخل، و`/metrics` اختياري ومحمي برمز مستقل في الإنتاج. لا يعني `504` حتمًا أن Commit ذريًا لم يقع عند حافة المهلة؛ تحقق من حالة المستند وأعد الأمر بمفتاح Idempotency نفسه. تفاصيل الضبط والاستجابة للتنبيهات في [دليل المرونة التشغيلية](docs/operational-resilience.md).

## النسخ الاحتياطي والاستعادة

```bash
npm run db:backup
npm run db:restore
```

ينشئ أمر النسخ ملفًا مضغوطًا ومشفرًا مع SHA-256 وManifest ‏`mcap-backup-v2` منقح لا يحمل اسم قاعدة المصدر أو إصدارها أو أعداد الصفوف أو المجاميع المالية. ترفض الاستعادة الكتابة فوق قاعدة غير فارغة، وتتطلب `RESTORE_CONFIRM=RESTORE:<DATABASE_NAME>`، ثم تتحقق من سلامة الملف والتشفير والجداول والترحيلات واتزان إجمالي المدين والدائن في القاعدة المستعادة. تبقى استعادة Manifest القديم `mcap-backup-v1` مدعومة مع مقارنته الدقيقة. راجع [دليل التشغيل الإنتاجي](docs/production-operations.md) للمتغيرات وإجراء التجربة الدورية.

ينشئ Workflow `production-backup-dr.yml` نسخة إنتاج مشفرة يوميًا خارج حساب iFastNet كـGitHub Artifact immutable داخل محاولة التشغيل وباحتفاظ 90 يومًا، ويسجل `recoveryPointAt` لهدف RPO البالغ 26 ساعة مع بوابة Artifact محافظة 25.5 ساعة. في أول يوم من كل شهر يعيد Artifact الفعلي إلى MariaDB 10.11.11 معزولة، يقيس زمن تنفيذ الاستعادة التقني بحد 900 ثانية، ويحفظ دليلًا منقحًا؛ ويراقب مسار ساعي غياب أو تقادم النسخة ومرور 35 يومًا بلا تمرين ناجح وأي فشل في تمرين مطلوب أحدث من النجاح. يشرح [دليل التعافي من الكوارث](docs/production-disaster-recovery.md) التشغيل اليدوي ومصفوفة الفشل واستعادة الخدمة وتدوير المفتاح.

## التحقق قبل التسليم

```bash
npm run typecheck
npm run e2e:typecheck
npm run contracts:check
npm run i18n:check
npm run ui:check
npm run visual-qa:test
npm run test:db -w @mcap/api
npm run infra:test
npm run build
npm exec -w @mcap/api -- prisma migrate status
node node_modules/@playwright/test/cli.js install chromium
npm run e2e
```

بعد `npm prune --omit=dev --omit=optional` تنشئ CI حزمة الإصدار عبر `npm run release:create -- --source . --output release-root` وتعيد فحصها عبر `npm run release:verify -- --root release-root`.

لتشغيل اختبارات قاعدة البيانات الفعلية، عيّن `RUN_DB_TESTS=true` مع `DATABASE_URL` و`SEED_ADMIN_PASSWORD` صالحين، وطبّق الترحيلات والـSeed وابنِ التطبيق قبل E2E. تحتوي الحزمة الحالية على **449 تحققًا آليًا**: 289 اختبار API، و28 اختبار واجهة، و34 اختبار بنية تحتية، و96 حالة Playwright للمصفوفة المتجاوبة، ورحلتا E2E، إضافة إلى تجربتي نجاح وفشل آمن للرجوع داخل سكربت CI. طبقت الترحيلات الـ47 والـSeed من قاعدة فارغة على MariaDB 10.4.32 ونجحت حزمة API الكاملة 289/289، ومنها مسارات المطابقة البنكية والإقفال المالي والتدفق النقدي غير المباشر وملخص الضريبة المحايد، والعزل والتزامن وIdempotency والعكس المؤرخ وتغير دفتر الأستاذ بعد مراجعة الإقفال وقيد نتيجة السنة وعكسه. تعيد بوابتا MariaDB 10.11.11 وMySQL 8.4.11 إثبات المصفوفة الكاملة وE2E والنسخ والاستعادة قبل أي إصدار. تشمل الحزمة كذلك اختبارات البحث المتدرج لمرجعيات الفواتير، ودفتر المخزون الكمي والقيمي والاتجاهات الأربعة للفواتير وعكسها، وCOGS والتكلفة التاريخية وحد كمية المرتجع، وقيد الحركات اليدوية وعكس الكمية والقيمة والقيد ذريًا، وفروقات العملة المحققة واستعادة القيمة الدفترية، ومنع سند الطرف غير الموزع مع إبقاء السند المباشر للحساب، وطباعة فواتير البيع المؤرشفة، واستيراد الصنف والمستودع، وكشف الحساب، والتحقق من Artifact النسخة الخارجية، إضافة إلى الاستيراد الذري وملفات CSV/XLSX السلبية.

## ضوابط مهمة

- كل الاستعلامات المالية مقيدة بالشركة المختارة، وتدعمها علاقات مركبة داخل قاعدة البيانات.
- لكل مؤسسة وشركة رمز ثابت، وتجهيز الشركة ومديرها قابل لإعادة التشغيل دون مضاعفة الإسنادات أو الأدوار.
- الرموز المرجعية للعملاء والموردين ومراكز التكلفة وحسابات الصندوق/البنك وطرق الدفع الخاصة ومعدلات الضريبة والأدوار المخصصة يولدها الخادم لكل شركة، ولا يطلبها من المستخدم ولا يسمح بتعديلها؛ بقي رمز الحساب المحاسبي ورمز العملة يدويين لأنهما دلاليان.
- هوية حساب القالب تبقى ثابتة عند تغيير الرمز أو الاسم أو الحساب الأب؛ لذلك لا تضاعف إعادة التطبيق تخصيصات العميل، والحذف النهائي مقصور على الحساب غير المستخدم الذي لا يملك فروعًا.
- يفشل تشغيل الإنتاج مبكرًا إذا غاب HTTPS أو Secure Cookie أو إعداد reverse proxy، وتوفر الخدمة فحص جاهزية قاعدة البيانات وRate Limiting وإغلاقًا سليمًا؛ ويفرض نشر cPanel تحويل `308` خارجيًا إلى النطاق الآمن مع حارس CI يحفظ المسار والاستعلام.
- لوحة التحكم وميزان المراجعة مشتقان مباشرة من السندات والقيود، ولا يخزنان أرقامًا ملخصة كمصدر حقيقة مستقل.
- النطاق التفاعلي الواحد للتقارير لا يتجاوز 366 يومًا، وميزان المراجعة يعتمد القيود المرحلة والمعكوسة لضمان أثر العكس الصحيح.
- الحساب غير النشط أو التجميعي أو غير المسموح بالترحيل إليه لا يقبل قيودًا مرحلة.
- المبالغ وأسعار الصرف تنتقل كنصوص عشرية لتجنب فقد الدقة في JavaScript.
- الترحيل والعكس والعمليات الحرجة تستخدم Optimistic Version وIdempotency.
- الترحيل والعكس وإغلاق الفترات وحجز الأرقام والتسجيل تستخدم منفذ معاملات موحدًا يعيد المعاملة كاملة فقط عند `P2034` أو deadlock/lock-wait المصنف، ولا يعامل `P2002` أو أخطاء الأعمال كعطل عابر.
- الأرقام الضريبية وأرقام الحسابات وIBAN لا تحفظ كنص ظاهر؛ تحفظ اللقطة اللازمة للعرض المقنع فقط في المرحلة الحالية.
- المسودات قابلة للتعديل، بينما المستندات المرحلة لا تعدل ويجري تصحيحها بقيد عكسي.
- لقطة الطباعة للمستند المرحّل غير قابلة للتغيير؛ إعادة الطباعة تتحقق من البصمة ولا تعيد قراءة أسماء الشركة أو الحسابات المعدلة لاحقًا.
- اختيار صنف مخزني في فاتورة يتطلب مستودعًا ويحترم دقة وحدة القياس؛ عند الترحيل تنشئ فاتورة البيع صرفًا، وإشعارها الدائن استلامًا، وفاتورة الشراء استلامًا، وإشعارها المدين صرفًا، بينما ينشئ العكس الحركة المقابلة داخل المعاملة المالية نفسها.
- حركات المخزون لا تعدل ولا تحذف؛ الحركة اليدوية تُصحح بمسار عكس ينشئ حركة مقابلة ويعكس مستندها المحاسبي التاريخي ذريًا. أما الحركة التي أنشأتها فاتورة فلا تعكس منفردة، بل من مستندها المصدر حتى تبقى الذمة والقيد والمخزون متطابقة.
- الربط الحالي يستخدم الفاتورة المرحلة بوصفها مستند الكمية والقيمة لعدم وجود إذن تسليم/استلام مستقل؛ يحسب المتوسط وCOGS والتكلفة التاريخية للعكس، ولا ينشئ إشعارًا دائنًا أو مدينًا تلقائيًا.

## سياسة تحديث الوثائق

تحديث `README.md` و`docs/implementation-status.md` جزء إلزامي من إنهاء كل مرحلة تطوير. يجب أن يسبق التحديث أي commit يغلق مرحلة، وأن يشمل النماذج والمسارات والترحيلات والاختبارات والقيود أو الأعمال المتبقية.

## الأعمال التالية

- تفعيل إنفاذ حماية `main` عبر GitHub Pro أو مؤسسة Team/Enterprise بدل بقاء القاعدة معرفة وغير منفذة على المستودع الخاص.
- بناء تسوية ذمم ثنائية العملة تسجل فروق الصرف المحققة وتبقي AR/AP مطابقين للقيمة الدفترية بعد القبض والدفع.
- بدء الإطلاق مع `SELF_REGISTRATION_ENABLED=false`، ثم فتحه لعينة مراقبة بعد نجاح البوابتين، ومتابعة أخطاء البريد والتجهيز و429 وفق دليل التشغيل.
- اعتماد دورة أذونات استلام وتسليم مستقلة عند الحاجة التشغيلية ومنع مضاعفة الأثر مع الفاتورة؛ طريقة المتوسط وقيد تكلفة المبيعات للفواتير مكتملان محليًا، وتحتاج أي طريقة تقييم ثانية قرارًا مستقلًا.
