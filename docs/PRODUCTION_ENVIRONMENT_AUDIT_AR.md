# تدقيق اعتماد بيئة الإنتاج

- المنهج: بدأ التدقيق بقراءة فقط، ثم طُبقت ضوابط GitHub المحددة أدناه دون قراءة قيم الأسرار أو تغيير بيانات التطبيق أو cPanel.

- الحالة التشغيلية: **GO**؛ الإصدار `0.1.0-8895deca2a0e` نشط، والنطاق وAPI وقاعدة البيانات جاهزة.
- اعتماد حوكمة البيئة: **NO-GO مؤقتًا** حتى إغلاق P0-2 أدناه، ثم حسم بندي P1 أو قبول مخاطرهما صراحةً. أُغلق P0-1 تقنيًا في مسار النشر، ويثبت تشغيل الإصدار نفسه القبول على النطاق العام.

- أثبت تشغيل GitHub Actions رقم [78](https://github.com/ALMutasemObad/multi-company-accounting/actions/runs/32711130785) نجاح حارس منشأ PR قبل قراءة الأسرار ونشر الالتزام `114a22d`، وأثبت التشغيل رقم [81](https://github.com/ALMutasemObad/multi-company-accounting/actions/runs/32713855741) نجاح المسار نفسه بعد دمج أداة النقل المؤقتة.

- إعدادات الإنتاج الحرجة فعالة لأن التطبيق اجتاز fail-fast ويعمل: `WEB_ORIGIN` الآمن و`SESSION_COOKIE_SECURE` و`TRUST_PROXY`. كوكي PRE_AUTH المرصودة تحمل `HttpOnly; Secure; SameSite=Lax`.
- الاستجابات تتضمن HSTS وCSP و`X-Frame-Options: SAMEORIGIN` و`X-Content-Type-Options: nosniff` وCORS محصورًا في نطاق الإنتاج.
- التسجيل الذاتي مفعّل فعليًا؛ أعاد `GET /api/v1/auth/register/options` خيارات المرجعيات وسياسة كلمة المرور بنجاح.

## الفجوات مرتبة حسب الأولوية

### P0-1 — منع HTTP غير المشفر

الحالة: **مغلق ومثبت إنتاجيًا في التشغيل 75**. كانت المشاهدة الأصلية أن `http://accounting.doralashab.com/` يعيد `200` بدل التحويل؛ لذلك أضيف الضابط داخل مسار تفعيل CloudLinux نفسه، لا داخل تطبيق Express.

الإجراء المطبق:

- يضيف `switch-cloudlinux-registration.sh` كتلة Apache مُدارة مرة واحدة بعد إعادة إنشاء تسجيل Passenger، وتعيد `308` إلى النطاق المعياري الثابت مع الحفاظ على `REQUEST_URI` والاستعلام؛ لا تثق بقيمة `HTTP_HOST` الواردة.
- تحفظ العملية نسخة محمية من `.htaccess` وتستعيدها ذريًا مع تسجيل المصدر إذا فشل التفعيل، كما ترفض العلامات المكررة أو المعكوسة.
- يفحص CI بعد النشر طلب HTTP بلا تتبع تلقائي، ولا يقبل إلا `301/308` و`Location` المطابق تمامًا للمسار والاستعلام المطلوبين، ثم يعيد فحص `/live` و`/ready` عبر HTTPS.
- تغطي اختبارات البنية ثبات الكتلة ومنع `HTTP_HOST`، ويغطي اختبار CloudLinux التكاملي عدم التكرار والاستعادة المطابقة عند فشل الهدف.

معيار القبول: لا يقدم HTTP أي HTML أو JSON، ويعيد `301` أو `308` مع `Location: https://accounting.doralashab.com/...` مع الحفاظ على المسار والاستعلام. هذه بوابة إلزامية في وظيفة النشر ولا ينجح الإصدار دونها.

### P0-2 — حماية سلسلة النشر وأسرارها

الحالة: **مغلق جزئيًا، ويبقى NO-GO**. اكتمل تقييد البيئة وحارس منشأ PR ونقل الأسرار دون كشفها، لكن GitHub لا ينفذ حماية الفرع لهذا المستودع الخاص على خطة الحساب الحالية. يبقى إثبات نشر يستخدم أسرار البيئة وحذف النسخ الأوسع قبل إغلاق جانب الأسرار نهائيًا.

الإجراء المطبق:

- قُيدت بيئة `production` بسياسة `Selected branches and tags` وبقاعدة فرع واحدة هي `main`؛ لم تعد `No restriction`.
- أُنشئت Classic Branch Protection لـ`main` تفرض PR، وتحديث الفرع، ونجاح `verify` و`iFastNet compatibility (Node 22 / MariaDB 10.11)`، وحل المحادثات، وعدم تجاوز المسؤولين؛ وبقي Force Push والحذف غير مسموحين.
- يعرض GitHub القاعدة نفسها بالحالة `Not enforced`. المستودع مملوك لحساب شخصي على GitHub Free؛ ووفق متطلبات GitHub الحالية تحتاج حماية الفرع في مستودع شخصي خاص إلى GitHub Pro، أو نقل المستودع إلى مؤسسة Team/Enterprise. لذلك لا تُحسب القاعدة المغلقة شكليًا كحماية فعلية.
- أضيف ضابط تعويضي داخل `deploy-production` قبل قراءة أي سر: يستعلم عن PR المرتبط بالالتزام، ويرفض النشر عند Force Push أو إذا لم يطابق الالتزام PR واحدًا مدمجًا إلى `main`. لا يعوض هذا قدرة مسؤول يملك Push مباشرًا على تعديل Workflow نفسه.
- أُنشئ Fine-grained PAT مؤقت لمدة 7 أيام، مقيدًا بهذا المستودع وبصلاحية `Environments: write` فقط، وحُفظ كسر Repository مؤقت. استخدمه Workflow يدوي من `main` لنسخ `CPANEL_SSH_PRIVATE_KEY` و`BACKUP_ENCRYPTION_PASSPHRASE` إلى `production` عبر `stdin`، ثم تحقق من الاسمين دون قراءة القيم. يُحذف Workflow في التغيير التالي مباشرةً، ويُحذف الرمز ويُلغى بعد إثبات النشر.

المتبقي المثبت:

- السرّان موجودان الآن في `production` وفي Repository معًا عمدًا. تتقدم أسرار Environment عند تطابق الاسم؛ لذلك يشكل نجاح أول نشر تالٍ دليلًا على القيم المنقولة قبل حذف نسخ Repository.
- يبقى حذف سري Repository والسر المؤقت `P0_2_ENVIRONMENT_SECRET_MIGRATION_TOKEN` وإلغاء PAT بعد نجاح نشر القبول. لا تُحذف النسخ الأوسع قبل هذا الدليل.
- بيئة `production` لا توفر Required Reviewers في واجهة الخطة الحالية، فلا يوجد ضابط موافقة مستقل يعوض غياب حماية الفرع.

الإغلاق المطلوب:

- ترقية الحساب الشخصي إلى GitHub Pro، أو نقل المستودع الخاص إلى Organization بخطة Team/Enterprise، ثم إعادة التحقق من تحول القاعدة إلى `Active`/منفذة فعلًا.
- دمج حذف Workflow المؤقت وتشغيل نشر مراقب؛ نجاح النشر يثبت أن `deploy-production` قرأ سري Environment ذوي الأولوية.
- بعد النجاح فقط، حذف نسخ Repository والسر المؤقت، وإلغاء PAT من إعدادات الحساب، ثم إثبات نشر أخير لا يملك أي نسخة Repository بديلة.

معيار القبول: لا تستطيع أي وظيفة خارج `deploy-production` ولا أي فرع غير `main` الوصول إلى أسرار الإنتاج، ولا يصل تغيير إلى `main` دون البوابات المعتمدة.

### P1-1 — فصل مستخدم التشغيل عن مستخدم الترحيل

المشاهدة: يقرأ `deploy-cpanel-release.sh` قيمة `DATABASE_URL` نفسها من إعداد Passenger، ثم يستخدمها للنسخ و`prisma migrate deploy` وSeed، وهي القيمة نفسها التي يستخدمها التطبيق. لا يوجد `MIGRATION_DATABASE_URL` مستقل؛ لذلك لم يثبت مبدأ أقل صلاحية لمستخدم التشغيل.

الإغلاق المطلوب:

- إضافة مستخدم DDL منفصل أو توثيق قيد الاستضافة وقبول المخاطرة صراحةً.
- عند إمكان الفصل، تمرير عنوان الترحيل من قناة سرية مستقلة وعدم حفظه داخل Artifact أو السجل، وإبقاء مستخدم التطبيق بصلاحيات DML اللازمة فقط.
- توثيق ناتج `SHOW GRANTS` منقحًا دون أسماء مستخدمين أو مضيفين أو كلمات مرور.

معيار القبول: لا يملك مستخدم التطبيق `CREATE/ALTER/DROP/INDEX`، وتستخدم مرحلة الترحيل هوية مستقلة قصيرة النطاق.

### P1-2 — تفعيل القياسات والمراقبة

المشاهدة: يعيد `/metrics` واجهة SPA بدل `401`؛ وهذا يثبت أن مسار Prometheus غير مفعّل في التطبيق الحالي. نقاط الحياة والجاهزية متاحة، لكن قياسات deadlock وdeadline وOutbox غير قابلة للكشط.

الإغلاق المطلوب:

- تفعيل `METRICS_ENABLED` مع `METRICS_BEARER_TOKEN` مستقل، وتقييد الوصول من cPanel/Apache إن أمكن.
- ربط تنبيهات deadlock وretry exhaustion وrequest deadline وOutbox lag/dead letter بالمسؤول التشغيلي.

معيار القبول: يعيد `/metrics` دون رمز `401`، وينجح الكشط بالرمز من مصدر المراقبة فقط، ويصل تنبيه اختباري موثق.

## حدود التدقيق

- صفحة cPanel طلبت مصادقة جديدة؛ لم يُطلب إرسال رمز أو إدخال بيانات اعتماد ولم يحدث تسجيل دخول.
- استقلال قاعدة البيانات ومسار التطبيق مثبتان من سجل النشر، لكن صلاحيات مستخدم قاعدة البيانات لم تُقرأ مباشرة؛ الاستنتاج الخاص باتحاد مستخدم التشغيل والترحيل مبني على سكربت النشر المعتمد.
- وجود نسخة ما قبل النشر لا يثبت النسخ اليومي الخارجي أو تجربة الاستعادة الشهرية؛ يبقيان مهمة تشغيلية مستقلة.

## ترتيب التنفيذ المقترح

1. تفعيل إنفاذ حماية `main` عبر GitHub Pro أو مؤسسة Team/Enterprise، وإكمال نشر قبول أسرار البيئة وحذف نسخ Repository والاعتماد المؤقت.
2. فصل مستخدم DDL أو توثيق قبول المخاطرة.
3. تفعيل القياسات والتنبيهات.
4. بعد نجاح البنود السابقة، إعادة هذا التدقيق وإصدار اعتماد **GO** نهائي للبيئة.
