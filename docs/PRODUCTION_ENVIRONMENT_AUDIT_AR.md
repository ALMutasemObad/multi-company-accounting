# تدقيق اعتماد بيئة الإنتاج

- تاريخ التدقيق: 24 أغسطس 2026.
- النطاق: GitHub Actions وبيئة `production`، نطاق التطبيق العام، CloudLinux/Passenger، قاعدة البيانات ومسار النشر.
- المنهج: بدأ التدقيق بقراءة فقط، ثم طُبقت ضوابط GitHub المحددة أدناه دون قراءة قيم الأسرار أو تغيير بيانات التطبيق أو cPanel.

## الحكم التنفيذي

- الحالة التشغيلية: **GO**؛ أثبت تشغيل الإنتاج رقم 93 النطاق وAPI وقاعدة البيانات ومسار النشر والقياسات بأسرار `production` فقط.
- اعتماد حوكمة البيئة: **NO-GO مؤقتًا** حتى إغلاق P0-2 أدناه، ثم حسم P1-1 أو قبول مخاطره صراحةً. أُغلق P0-1 وP1-2 تقنيًا وإنتاجيًا، ويثبت تشغيل الإصدار نفسه القبول على النطاق العام.

## الفجوات مرتبة حسب الأولوية

### P0-1 — منع HTTP غير المشفر

الحالة: **مغلق ومثبت إنتاجيًا في التشغيل 75**. كانت المشاهدة الأصلية أن `http://accounting.doralashab.com/` يعيد `200` بدل التحويل؛ لذلك أضيف الضابط داخل مسار تفعيل CloudLinux نفسه، لا داخل تطبيق Express.

الإجراء المطبق:

- يضيف `switch-cloudlinux-registration.sh` كتلة Apache مُدارة مرة واحدة بعد إعادة إنشاء تسجيل Passenger، وتعيد `308` إلى النطاق المعياري الثابت مع الحفاظ على `REQUEST_URI` والاستعلام؛ لا تثق بقيمة `HTTP_HOST` الواردة.
- تحفظ العملية نسخة محمية من `.htaccess` وتستعيدها ذريًا مع تسجيل المصدر إذا فشل التفعيل، كما ترفض العلامات المكررة أو المعكوسة.
- يفحص CI بعد النشر طلب HTTP بلا تتبع تلقائي، ولا يقبل إلا `301/308` و`Location` المطابق تمامًا للمسار والاستعلام المطلوبين، ثم يعيد فحص `/live` و`/ready` عبر HTTPS.
- تغطي اختبارات البنية ثبات الكتلة ومنع `HTTP_HOST`، ويغطي اختبار CloudLinux التكاملي عدم التكرار والاستعادة المطابقة عند فشل الهدف.

معيار القبول: لا يقدم HTTP أي HTML أو JSON، ويعيد `301` أو `308` مع `Location: https://accounting.doralashab.com/...` مع الحفاظ على المسار والاستعلام. هذه بوابة إلزامية في وظيفة النشر ولا ينجح الإصدار دونها.

### P0-2 — حماية سلسلة النشر وأسرارها

الحالة: **مغلق جزئيًا، ويبقى NO-GO بسبب إنفاذ الفرع وحده**. اكتمل تقييد البيئة وحارس منشأ PR ودورة نقل الأسرار وإثباتها وحذف النسخ الأوسع، لكن GitHub لا ينفذ حماية الفرع لهذا المستودع الخاص على خطة الحساب الحالية.

الإجراء المطبق:

- قُيدت بيئة `production` بسياسة `Selected branches and tags` وبقاعدة فرع واحدة هي `main`؛ لم تعد `No restriction`.
- أُنشئت Classic Branch Protection لـ`main` تفرض PR، وتحديث الفرع، ونجاح `verify` و`iFastNet compatibility (Node 22 / MariaDB 10.11)`، وحل المحادثات، وعدم تجاوز المسؤولين؛ وبقي Force Push والحذف غير مسموحين.
- يعرض GitHub القاعدة نفسها بالحالة `Not enforced`. المستودع مملوك لحساب شخصي على GitHub Free؛ ووفق متطلبات GitHub الحالية تحتاج حماية الفرع في مستودع شخصي خاص إلى GitHub Pro، أو نقل المستودع إلى مؤسسة Team/Enterprise. لذلك لا تُحسب القاعدة المغلقة شكليًا كحماية فعلية.
- أضيف ضابط تعويضي داخل `deploy-production` قبل قراءة أي سر: يستعلم عن PR المرتبط بالالتزام، ويرفض النشر عند Force Push أو إذا لم يطابق الالتزام PR واحدًا مدمجًا إلى `main`. لا يعوض هذا قدرة مسؤول يملك Push مباشرًا على تعديل Workflow نفسه.
- أُنشئ Fine-grained PAT مؤقت لمدة 7 أيام، مقيدًا بهذا المستودع وبصلاحية `Environments: write` فقط، وحُفظ كسر Repository مؤقت. استخدمه Workflow يدوي من `main` لنسخ `CPANEL_SSH_PRIVATE_KEY` و`BACKUP_ENCRYPTION_PASSPHRASE` إلى `production` عبر `stdin`، ثم تحقق من الاسمين دون قراءة القيم. بعد تشغيل القبول حُذف Workflow والسر المؤقت، وأُلغي PAT من الحساب.

المتبقي المثبت:

- تعرض `production` الأسرار الثلاثة `CPANEL_SSH_PRIVATE_KEY` و`BACKUP_ENCRYPTION_PASSPHRASE` و`METRICS_BEARER_TOKEN`، وتعرض صفحة Repository secrets الحالة `This repository has no secrets` بعد حذف النسخ الأوسع والسر المؤقت.
- تعرض صفحة Fine-grained personal access tokens الحالة `No fine-grained tokens created` بعد إلغاء اعتماد النقل؛ ولا يوجد Workflow نقل في الفرع الافتراضي.
- بيئة `production` لا توفر Required Reviewers في واجهة الخطة الحالية، فلا يوجد ضابط موافقة مستقل يعوض غياب حماية الفرع.

الإغلاق المطلوب:

- ترقية الحساب الشخصي إلى GitHub Pro، أو نقل المستودع الخاص إلى Organization بخطة Team/Enterprise، ثم إعادة التحقق من تحول القاعدة إلى `Active`/منفذة فعلًا.

معيار القبول: لا تستطيع أي وظيفة خارج `deploy-production` ولا أي فرع غير `main` الوصول إلى أسرار الإنتاج، ولا يصل تغيير إلى `main` دون البوابات المعتمدة.

### P1-1 — فصل مستخدم التشغيل عن مستخدم الترحيل

الحالة: **مطبق تقنيًا، وينتظر الإثبات الإنتاجي**. كانت المشاهدة الأصلية أن `deploy-cpanel-release.sh` يستخدم `DATABASE_URL` نفسه للتشغيل والنسخ والترحيل والـSeed.

الإجراء المطبق:

- يتطلب النشر `MIGRATION_DATABASE_URL` من سر مستقل في بيئة `production`، ويمرره عبر `stdin` للنسخ السابقة للترحيل وMigration وSeed فقط؛ لا يضاف إلى Artifact أو Passenger أو لقطة CloudLinux.
- يفحص الإصدار المرشح الحسابين فعليًا عبر `CURRENT_USER()` و`SHOW GRANTS FOR CURRENT_USER()`، ويرفض اختلاف المضيف/المنفذ/القاعدة أو اتحاد الهوية أو امتلاك حساب التشغيل DDL أو نقص DML/DDL المطلوب.
- يطبع الفاحص تقريرًا منقحًا يثبت القاعدة المشتركة والهوية المستقلة وقائمة الصلاحيات المتحققة فقط، ولا يطبع أي اسم مستخدم أو مضيف أو عنوان اتصال أو كلمة مرور حتى عند فشل الاتصال.
- تثبت بوابتا MySQL وMariaDB حساب تشغيل DML فقط وحساب ترحيل DDL مستقلًا، وتثبتان فشل `CREATE TABLE` بحساب التشغيل ورفض الهوية المتحدة وعدم تسرب تفاصيل الاتصال.

المتبقي للإغلاق:

- إنشاء حساب DDL مستقل في cPanel وربطه بقاعدة الإنتاج، وخفض حساب Passenger إلى `SELECT/INSERT/UPDATE/DELETE` فقط.
- إضافة `MIGRATION_DATABASE_URL` إلى أسرار بيئة GitHub `production`، ثم توثيق تشغيل نشر ناجح يحتوي تقرير القبول المنقح.

معيار القبول: لا يملك مستخدم التطبيق `CREATE/ALTER/DROP/INDEX`، وتستخدم مرحلة الترحيل هوية مستقلة قصيرة النطاق.

### P1-2 — تفعيل القياسات والمراقبة

الحالة: **مغلق ومثبت إنتاجيًا في التشغيل 93 وتشغيلي المراقبة 1 و2**. كانت المشاهدة الأصلية أن `/metrics` يعيد واجهة SPA بدل `401`؛ أما الإصدار الحالي فيفعّل المسار برمز مستقل ويكشطه من مراقب خارجي.

الإجراء المطبق:

- تحفظ بيئة `production` رمزًا عشوائيًا مستقلًا باسم `METRICS_BEARER_TOKEN`. يمرره النشر عبر `stdin` وملف مؤقت `0600`، ويدمج `METRICS_ENABLED=true` والرمز في لقطة CloudLinux الهدف دون Artifact أو سجل ثم يحذف الملف في جميع حالات الخروج.
- يعيد المسار دون رمز `401` مع Bearer challenge ومنع التخزين المؤقت، ويستخدم مقارنة ثابتة الزمن. يثبت النشر الكشط الموثق ويُفشل التفعيل عند وجود تنبيه نشط.
- يضيف المقياس `mcap_operational_alert_last_fired_timestamp_seconds` ذاكرة منخفضة الكاردينالية للتنبيهات القصيرة، ويكشط Workflow خارجي كل ساعة التنبيهات النشطة أو المطلقة خلال 65 دقيقة.
- ترتبط قواعد deadlock وretry exhaustion وrequest deadline وOutbox lag/dead letter بـGitHub Actions annotations. أثبت الاختبار التركيبي ظهور التنبيه للمسؤول بعد كَشط إنتاجي ناجح، من دون حقن عطل في قاعدة البيانات.
- لم يضف Apache قيد IP لأن مصدر GitHub Actions لا يملك عنوان كاشط ثابتًا معتمدًا في هذا التصميم؛ الضابط الحالي TLS + Bearer مستقل، وتبقى إضافة Allowlist ممكنة عند اعتماد كاشط ثابت.

معيار القبول: **متحقق**؛ يعيد `/metrics` دون رمز `401`، وينجح الكشط بالرمز من مصدر المراقبة، ووصل تنبيه اختباري موثق ثم نجح تشغيل عادي.

## حدود التدقيق

- صفحة cPanel طلبت مصادقة جديدة؛ لم يُطلب إرسال رمز أو إدخال بيانات اعتماد ولم يحدث تسجيل دخول.
- استقلال قاعدة البيانات ومسار التطبيق مثبتان من سجل النشر، لكن صلاحيات مستخدم قاعدة البيانات لم تُقرأ مباشرة؛ الاستنتاج الخاص باتحاد مستخدم التشغيل والترحيل مبني على سكربت النشر المعتمد.
- وجود نسخة ما قبل النشر لا يثبت النسخ اليومي الخارجي أو تجربة الاستعادة الشهرية؛ يبقيان مهمة تشغيلية مستقلة.

## ترتيب التنفيذ المقترح

1. تفعيل إنفاذ حماية `main` عبر GitHub Pro أو مؤسسة Team/Enterprise ثم إعادة تدقيق P0-2؛ اكتملت دورة أسرار البيئة وحذف النسخ الأوسع والاعتماد المؤقت.
2. فصل مستخدم DDL أو توثيق قبول المخاطرة.
3. بعد نجاح البنود السابقة، إعادة هذا التدقيق وإصدار اعتماد **GO** نهائي للبيئة.
