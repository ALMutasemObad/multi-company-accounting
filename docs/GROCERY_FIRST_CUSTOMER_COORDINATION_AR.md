# أول عميل: بقالة — خطة تنفيذ متوازية

التاريخ: 2026-08-31. حدد المستخدم البقالات كأولوية تجارية أولى، وأذن بتوسيع
التنفيذ والواجهات والربط بينها وإنشاء مهام مستقلة. المقاهي والمطاعم والصيدليات
تبقى أهدافًا لاحقة؛ لا نصفها بالجاهزة بتغيير تخطيط الشاشة فقط.

## النتيجة المطلوبة

رحلة واضحة من تهيئة النشاط والأصناف والباركود وأسعار البيع، إلى اختيار الصندوق
والمستودع ثم بيع نقدي ذري وعرض الفاتورة والقبض. وضع الكاشير الأول كثيف المنتجات:
مسح وبحث سريع وسلة واضحة. يوضع أساس عرض مربعات قابل للتبديل للنشاط محدود المينو،
دون ادعاء إدارة مطعم أو دفعات وصلاحية أدوية أو ورديات وفروع غير منفذة.

الأساس المثبت `7412a2c` يحتوي تكامل الاشتراكات السابق وتحسين قراءة الاستهلاك.
إصلاحا تأكيد الاشتراك وتعافي الدفع يُجمعان بمعزل ولا يمنعان تحسين POS المستقل.
لا دمج main أو نشر أو تحميل/تحصيل حقيقي دون تفويض إصدار مستقل وبوابات ناجحة.

## أدلة البداية من المصدر

- `PosPage.tsx` يستخدم المسح المشترك وCheckout عبر POS Ports القائمة، لكنه
  محرر بنود طويل يطلب سعرًا وحساب إيراد لكل سطر، ولا يوفر كتالوج بيع سريعًا.
- `InventoryItem` لا يملك سعر بيع أو حساب إيراد أو ضريبة افتراضية؛ لا تخترعها
  الواجهة ولا تنسخها في localStorage أو تستخدم آخر فاتورة مصدرًا للحقيقة.
- `SystemHomePage` يعرض موديولات مسموحة، ولا يوجه مستخدم بقالة إلى ترتيب الإعداد.
- الفروع والمحطات والورديات وlot/expiry وOffline ما زالت أهدافًا مستقلة. لا توسع
  مخططها ضمن هذه الدفعة ولا تدّع اكتمال تشغيل المتجر قبل اختبار الأجهزة والرحلة.

## R1 — واجهة POS قابلة للاستخدام

- استخدم المهارة المتاحة للمتصفح عند الفحص البصري، وابدأ بقياس عدد الحقول والخطوات
  الحالية. تنفيذ فعلي مع اختبار، لا mockup تسويقي منفصل.
- وضع retail للبحث والمسح والمنتجات الكثيرة، ووضع tiles اختياري لنفس السلة؛ لا
  عناصر صورية أو أصناف مولدة تلقائيًا. القراءة بصفحات خادمية وبحث محدود وإلغاء
  وتجاهل الاستجابات القديمة، لا تحميل كل الأصناف ثم فلترتها محليًا.
- حافظ على InventoryBarcodeScanner وresolve والـFIFO ومنع Checkout أثناء المسح،
  وleading zeros وRBAC. النقر والمسح يمران بتحويل سطر واحد. لا parser موازٍ.
- السعر/حساب الإيراد/الضريبة يأتي من عقد R2 المعتمد. إلى وصوله أبق الحقول الصريحة
  اللازمة، ولا تخترع أسعارًا أو hide لحقول تؤثر محاسبيًا. اعزل قارئ الكتالوج خلف
  helper ليُربط بالعقد، ونسق DTO مع R2 قبل الاعتماد عليه.
- حسّن السلة والتحكم بالكمية والإزالة وحالة الإتمام وعرض مستندات النجاح. لا
  Float للمبالغ حتى في الملخص الجديد؛ الخادم يبقى مصدر الإجمالي النهائي.
- لا replay تلقائي لـCheckout أو مفتاح جديد عند نتيجة مجهولة، ولا تنظيف للسلة
  بعد نجاح غير مؤكد. اربط الفاتورة/القبض بروابط موجودة فقط؛ اطلب عقد التنقل إن لزم.
- تفضيلات العرض فقط يمكن حفظها مقيدة بالمستخدم والنشاط. لا أموال أو أسعار أو
  اختيارات محاسبية صامتة؛ سياق التشغيل يحتاج تحققًا ومراجعة صريحة وفق السياسة.
- أربع لغات، RTL/LTR،390/768/1440، لوحة مفاتيح ولمس، واختبارات مسح/سلة/عزل/
  تزامن/فشل/إلغاء. Barcode Impact لازم، ومحاكاة قارئ ليست قبول جهاز فعلي.

## R2 — أساس مصدر سعر البيع وإعداد الصنف

ابدأ باقتراح عقد صغير مبني على فحص Sales/Inventory/Tax والتزامن، وأرسله للمنسق
قبل تعديل schema أو OpenAPI أو توليد Prisma. يجوز تنفيذ domain/helpers/tests
والـPorts الجديدة المملوكة أثناء مراجعة العقد، دون افتراض موافقة ضمنية عليه.

- المالك Sales لملف بيع الصنف؛ Inventory يبقى مالك الصنف/الوحدة/الباركود. لا
  يكتب Sales جدول Inventory ولا يبني سجل مخزون/دفتر موازيًا.
- الحد المقترح: سعر بيع افتراضي بعملة محددة وحساب إيراد وضريبة اختيارية للصنف
  داخل النشاط، مع version وحالة وتدقيق وصلاحية صريحة. الأسعار Decimal نصي.
  اقترح تفاصيل الكيان ومفاتيحه وحدود الاستجابة والتفرد قبل تثبيتها.
- ليست قائمة أسعار متعددة الطبقات أو عروضًا/خصومات أو منع تعديل سعر جديدًا.
  وضح أنها افتراضات بيع يُعاد التحقق منها، لا سعر محاسبي نهائي أو Tax Engine جديد.
- كتالوج POS محدود بصفحات/بحث، واختيار بعد المسح بالمعرف دون تحميل الكل أو N+1.
  إعادة استخدام Inventory Query Port وTax/Accounts Ports؛ لا تسريب Prisma بين السياقات.
- محرر إعداد ملف البيع مكون منفصل جاهز للتركيب لدى المنسق؛ لا تعديل InventoryPage
  أو PosPage أو App أو types/shared locales مباشرة. اتفق مبكرًا مع R1 على DTO.
- انشر اختبارات أحمر/أخضر للعزل والصلاحيات/version/Decimal/البحث والحدود. المخطط
  إن اعتمد يكون توسعيًا ومتوافقًا، مع بوابتي DB fresh+upgrade. لا seed بيانات متجر
  حقيقية، ولا generate إلى node_modules المشترك؛ ينتظر runtime محليًا معزولًا.

## R3 — طريق واضح إلى أول عملية بيع

- حسّن الصفحة الرئيسية الموجودة: دخول واضح للكاشير ومسارات عملية للمخزون
  والمشتريات/توريد المخزون والمبيعات/القبض والتقارير حسب الصلاحيات الفعلية.
- أضف دليل تهيئة عمليًا داخل الواجهة مع أزرار تذهب للشاشات الحقيقية. لا fake
  readiness أو علامات اكتمال من مجرد زيارة الصفحة؛ الحقائق فقط من API متاح
  ومسموح، وغير القابل للتحقق يعرض «يحتاج مراجعة» لا «جاهز».
- لا اختيار تلقائي لنشاط آخر أو كشف صفحة/طلب محجوب. حافظ على الموديولات المختارة
  والصلاحيات والـmodule entitlement وواجهة المنصة منفصلة عن النشاط.
- خفف التشتت واجعل الإجراء التالي واضحًا؛ لا تعيد تصميم كل الشاشات عشوائيًا.
  وثق أين يمنع عقد التنقل الحالي deep-link لعنصر أو قسم، وأرسل ربطًا مقترحًا
  للمنسق بدل تعديل App/navigation المملوك له.
- لا تنفذ تغييرات مالية أو إعدادات تأسيسية بمجرد الضغط على «ابدأ»؛ التوجيه قراءة
  وتنقل فقط إلا أمر إنشاء موجود مؤكد من المستخدم في صفحته المالكة.
- اختبر الأربع لغات والهواتف والكمبيوتر وأدوار محدودة/موديولات مخفية وحالات الفراغ
  والخطأ، وثق عدد خطوات رحلة أول بيع قبل/بعد دون بيانات حساسة.

## موارد وضوابط

اقرأ AGENTS.md والمراجع السبعة بالكامل، ثم وثائق POS/Barcode/Contextual Defaults
قبل التعديل. Modular Monolith وPorts وملكية الكتابة وDecimal وCSRF/RBAC وOpenAPI
وIdempotency وACID وimmutability ثوابت لا تُختصر بسبب السرعة.

كل نسخة عمل مستقلة في `D:/CodexWorktrees`؛ الاعتماديات القائمة junction للقراءة
فقط. C شبه ممتلئ؛ TEMP/TMP والكاش ونتائج الفحص توجّه إلى D داخل النسخة/مجلدات
المهمة. لا npm install/ci/prune/update، ولا تنزيل أو حذف ملفات مستخدم. لا تكتب
اسمًا تجاريًا متقاعدًا أو مسار C القديم في ملفات Git. node/npm runtime كما هي.

- R1 منافذ3140/4190، R2 منافذ3141/4191، R3 منافذ3142/4192؛ R0 منافذ3143/4193.
- worker واحد، no video/trace، صور قليلة لازمة، strictPort وreuse=false.
- لا وكلاء/مهام إضافية داخل هذه المسارات. أرسل العوائق والعقد مبكرًا، ثم commits
  صغيرة وhandoff بنتائج واقعية. لا Push/PR/Merge/Deploy أو تعديل استضافة.
- المنسق ينتظر عقودًا واضحة قبل الربط. لا نعلن أول عميل جاهز قبل رحلة end-to-end
  فعلية وبوابتي MariaDB10.11/MySQL8.4 وفحص قارئ/طابعة ومراجعة فجوات الإطلاق.
