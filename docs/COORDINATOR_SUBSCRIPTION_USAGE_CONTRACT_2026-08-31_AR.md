# تسليم العقد المركزي لاستهلاك الاشتراك

الحالة: عقد محلي مختبر يُسلّم للمسار C؛ تنفيذ Router/Service في فرعه، ولم يُربط
في نسخة التكامل بعد. لا رفع أو دمج main أو نشر، ولا نجاح بوابتي DB لهذه الدفعة.

## القرار المبني على المصدر

- `companyUsage` في `prisma-platform-analytics-query-adapter.ts` يعد عضويات
  الشركة النشطة لمستخدم نشط لحظيًا، والموظفين ACTIVE/ON_LEAVE لحظيًا، والمستندات
  بمدى `postedAt >= start && postedAt < endExclusive` دون استبعاد المعكوس ذي
  postedAt محفوظ. يستخدم SQL count لا تحميل السجلات، ويعد أيضًا عمليات Audit
  رغم أن اللوحة الجديدة لا تعرضها؛ هذه كلفة إعادة استخدام معروفة، لا عداد جديد.
- `issueInvoice` يستقبل الفترة من المشغل ويحول تاريخ النهاية الشامل إلى حد
  اليوم التالي المستبعد. لا يوجد كاتب تشغيلي لحقلي فترة الاشتراك الحالية في
  المصدر. لذلك لا يصح استنتاج فترة حصة المستندات من الدورة الشهرية أو السنوية.
- الخطة الفعالة تطابق `companySnapshot`: أحدث APPROVED بسريان `effectiveAt <= now`
  وبترتيب effectiveAt DESC ثم id DESC، وإلا إصدار الاشتراك الأساس. لا pending/future.

## العقد

`GET /api/v1/subscription/usage`، العملية `getCompanySubscriptionUsage`، وصلاحية
`subscriptions.view` للشركة المثبتة في الجلسة قبل أي استعلام. لا query أو companyId
من العميل، ولا كتابة/دفع/إنفاذ حد. OpenAPI **1.45.0** مصدر الحقيقة الكامل.

- `plan.id` معرف إصدار الخطة النصي، لا معرف رأس الخطة؛ plan قد تكون null.
- `consistency=BEST_EFFORT`: ليست لقطة ACID أو فاتورة.
- فترة المستندات إحصائية من أول الشهر UTC حتى measuredAt حصريًا؛ وقت القياس
  ثابت للطلب، ولا تُسجّل اللحظة اللاحقة بوصفها نهاية النافذة الأصلية.
- `billingPeriodStatus=NOT_CONFIGURED` عند غياب حقلي الفترة، وإلا UNCONFIRMED.
- used/included/remaining/excess غير سالبة وآمنة في JSON أو null. للقياس اللحظي
  المؤكد، remaining=max(0,included-used) وexcess=max(0,used-included).
- included=null تعني NOT_CONFIGURED لا غير محدود. عند used=null مع حصة معلومة
  تكون UNKNOWN. في الحالتين remaining/excess=null.
- مقارنة المستندات UNCONFIRMED_PERIOD؛ حالتها UNKNOWN مع الحصة المعلومة أو
  NOT_CONFIGURED إن غابت، ولا رصيد أو تجاوز رقمي أو رسوم مستنتجة.
- العقد يرفض الحقول الإضافية، تبديل تعريفات العدادات، أرقام ID بدل النصوص،
  قيم العد غير الآمنة، التواريخ غير UTC، وادعاء تأكيد دورة غير مثبتة.
- الحالات: 200،400،401،403،404،429،500،503،504. لا CSRF لأمر GET، مع بقاء
  Session/RBAC وCache-Control:no-store وحدود المعدل والمهلة العامة.

## تصحيح مولد الحراس

أثبت اختبار سلبي أن تركيب كائن strict مع كائن passthrough عبر intersection
في الاعتمادية المقفلة قد يقبل حقلًا زائدًا، خلاف دلالة JSON Schema allOf.
لم يُثبت بذلك تسرب من Endpoint منشور؛ الدليل على قبول الحارس لقيمة اصطناعية.

يولّد المنسق preflight لكل قيد على **مدخل النقل الأصلي** قبل intersection والتحويل.
لا يعاد التحقق من BIGINT المحول بوصفه نصًا، ولا يعدل الملف المولد يدويًا، ولا
تغيّر الاعتماديات أو مخططات البيانات. يثبت اختبار المولد طلبًا يحوّل ID كبيرًا
إلى bigint ويرفض حقلًا إضافيًا، واستجابة صارمة ترفض الحقل الإضافي كذلك.

تبقى كلفة التحقق مضاعفة في التراكيب المتأثرة؛ ليست هذه معايرة حمل أو SLO، ولا
مبرر لتفعيل مدقق الاستجابة في الإنتاج خلاف الإعداد القائم. يجب إبقاء الحارس
الصارم واختباراته عند أي تحسين لاحق للتوليد.

## التسليم إلى C والمتبقي للمنسق

يسمح للمسار C بجلب التزام هذا العقد المركزي المحدد بعد حفظ تغييره المحلي بأمان؛
ليس تفويضًا لجلب فروع المهام الأخرى. يختبر استجابته الفعلية بـ
`parseOpenApiResponseBody('getCompanySubscriptionUsage', 200, body)` أو middleware
المدقق، مع الحالات السلبية والعزل وحدود الفترة واختيار الخطة الفعالة.

يبقى ربط `services.subscriptionUsage` وRouter وbootstrap عند المنسق بعد مراجعة
تسليم C. يلزم أيضًا تحديث mock الواجهات واختبار رحلة الاختيار الغائب الذي يملكه
A، ثم جمع A/B/C وفحص الرحلة الكاملة. لا تعني أرقام الاختبارات أعلاه اكتمال ذلك.

Barcode Impact: غير منطبق؛ لا تعريف صنف أو إدخاله أو إخراجه أو قارئ/ملصق جديد،
ولا تغيير في دعم الباركود القائم. لا جداول أو أحداث أو Ledger أو حسابات أموال.
