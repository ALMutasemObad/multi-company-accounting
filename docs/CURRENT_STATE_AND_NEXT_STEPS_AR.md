هذه وثيقة التسليم المختصرة للمحادثة أو مرحلة التطوير التالية. تجمع الواقع التنفيذي
والقرارات والخطط والفجوات من دون تحويل وثائق المراحل التاريخية إلى مصدر حالة حالي.

ترتيب مصادر الحقيقة:

2. ADR الأحدث داخل [فهرس الحوكمة](architecture/README.md).
3. هذه الوثيقة للحالة الإجمالية وترتيب العمل.
4. [حالة التنفيذ](implementation-status.md) كسجل زمني تفصيلي.
5. دراسات المصدر المفتوح وتدقيقات الإنتاج كأدلة مؤرخة، لا كحالة راهنة منفردة.

بُني الجرد على `c1bcc3d` قبل التزام مزامنة التوثيق الحالي. يجب في بداية أي محادثة
جديدة تشغيل `git status` و`git log -5 --oneline` وعدم افتراض أن آخر عمل منشور.

## 3. تعدد الشركات والمجموعة

### الموجود

- `Organization` تحتوي عدة سجلات `Company`.
- `User` هوية عالمية واحدة، و`UserCompany` يمنحه عضوية وأدوارًا مستقلة لكل شركة.
- يستطيع الحساب الواحد إدارة عدة شركات والتبديل بينها من الواجهة؛ تخزن الجلسة
  `selectedCompanyId` وتتحقق الخدمة من العضوية النشطة قبل التبديل.
- أمر `company:provision` يستطيع استخدام رمز المؤسسة نفسه لإنشاء شركة إضافية، ويعيد
  استخدام هوية المدير ذات البريد نفسه من دون تغيير كلمة مروره.
- يمكن تمثيل «مجموعة جوار القابضة» كـOrganization والشركات الأربع كشركات تابعة.
- إذا كانت القابضة نفسها تمسك دفاتر أو تبرم معاملات، تنشأ أيضًا كـCompany خامسة.

### غير الموجود

- لا `OrganizationMembership` أو أدوار مالك مجموعة/مدير مالي/مشاهد على مستوى المجموعة.
- لا واجهة ذاتية لإضافة شركة فرعية تحت مؤسسة قائمة؛ التجهيز الإضافي إداري حاليًا.
- لا لوحة مالك مجموعة. `#dashboard` للشركة المختارة فقط، و`#platform` لمشغل الشركة
  المطوّرة وليس لمالك المجموعة.
- لا معاملات Intercompany أو مطابقة حسابات متقابلة أو قيود إلغاء.
- لا قوائم مالية موحدة أو عملة تجميع أو نسب ملكية أو حقوق أقلية.

القرار الحالي: لوحة مجموعة إدارية للقراءة والمقارنة مهمة قريبًا لكنها لا توقف CRM.
أما التجميع المحاسبي الكامل فمشروط بوجود تعاملات فعلية أو طلب تقارير موحدة، ولا ينفذ
بجمع مبالغ الشركات مباشرة.

## 5. حدود معمارية لا تتغير

- كل حقيقة لها مالك كتابة واحد؛ FK لا يمنح سياقًا آخر حق التعديل.
- `PostingEngine` هو الكاتب الوحيد لـ`JournalEntry/JournalLine`.
- الأثر المالي المتزامن داخل معاملة ACID، والآثار اللاحقة فقط عبر Transactional Outbox.
- لا Network I/O داخل المعاملة، ولا Retry لأخطاء الأعمال أو تعارض النسخة.
- كل بيانات تشغيلية مقيدة بـ`companyId` وعلاقات مركبة عند العبور.
- Decimal وBigInt ينتقلان نصًا في JSON، ولا تستخدم Float للحساب المالي النهائي.
- Idempotency والنسخة المتفائلة والأقفال تخدم أغراضًا مختلفة ولا يستبدل أحدها الآخر.
- لا يكرر CRM المخطط Customer، ولا تكرر المشاريع Invoice أو Ledger، ولا يملك Approvals
  حقيقة الموضوع.

الاستثناءات الانتقالية المعروفة:

- `CompanyService` يفحص استخدام العملة في عدة سياقات مباشرة.
- Onboarding يكتب بعض إعدادات Identity/Tenant/Accounting أثناء التجهيز.
- CRUD العميل موجود انتقاليًا تحت وحدة `receipts/reference-service.ts` رغم ملكية Sales.
- بعض أسماء المرجعيات في API عربية فقط وتظهر كقيمة احتياطية في اللغات الأخرى.

هذه استثناءات موثقة، وليست نمطًا مسموحًا نسخه في موديول جديد.

## 6. أدلة التحقق وحدودها

- مرحلة تخطيط المشاريع اجتازت API `334/334` في 83 ملفًا، Web `30/30`، Infra

- مرحلة المنصة والصفحة الرئيسية اجتازت TypeScript والبناء، Web `30/30`، 66 اختبارًا

- OpenAPI `1.38.0` صالح، والحراس والمسارات والاستجابات متطابقة وفق آخر تحقق مسجل.
- آخر حزمة API كاملة من قاعدة MariaDB 10.4 نظيفة موثقة قبل المرحلتين الأخيرتين كانت
  `321/321` بعد 54 ترحيلًا. لذلك يجب قبل أي نشر جديد إعادة الحزمة الكاملة بعد الترحيلات
  الـ56 على MariaDB 10.11 وMySQL 8.4، لا استنتاج نجاحها من الاختبارات المركزة.
- لا تغير دراسة CRM الكود التنفيذي أو قاعدة البيانات.

## 7. ما هو مخطط أو ناقص

### الأولوية المعتمدة التالية

1. **CRM-1:** Lead وOpportunity وActivity وتحويل Customer عبر Sales Port وفق
   [ADR-014](architecture/ADR-014-crm-business-development-priority.md) و
   [خطة الشريحة](architecture/CRM_BUSINESS_DEVELOPMENT_SLICE_AR.md).
2. **F2 فحص تعارض المصالح:** أطراف وأسماء بديلة ومرشح تطابق وقرار بشري مدقق. هو
   شرط قبل أي `CRM → ProfessionalProject` قانوني.
3. **وصول المجموعة ولوحة المالك:** أدوار Organization صريحة ولوحة مقارنة وCompany
   switch، من دون ادعاء قوائم موحدة.

### فجوات أعمال مهمة بعد ذلك

- مصروفات الموظفين والعهد والسلف وربطها بـApprovals وPurchases/Treasury.
- الأصول الثابتة: الرسملة والإهلاك والاستبعاد والعكس.
- الموازنات ومقارنة Budget vs Actual.
- أذونات استلام وتسليم وجرد مستقلة عندما تختلف الحركة عن الفاتورة.
- المواعيد القانونية وتصنيف المستندات وRetention والتخزين الآمن.
- أموال العملاء/الأمانات القانونية بقرار محاسبي ورقابي مستقل.
- الإجازات والحضور والتوظيف والأداء والرواتب؛ الرواتب تحتاج Jurisdiction محددًا.
- أوامر وعروض البيع والشراء، المتكرر، المستحقات والمقدمات، والتصنيع والتجارة الإلكترونية.
- الفوترة الإلكترونية والضريبة الخاصة بالدولة بعد تحديد الجهة والتشريع والشهادات.

### التجميع والمعاملات بين الشركات

ليست P0 حاليًا. تصبح حرجة إذا بدأت الشركات قروضًا أو مبيعات أو مصروفات أو تحويلات
داخلية فعلية، أو طلب المراجع قوائم موحدة. قبلها يلزم ADR يحدد:

- عملة التجميع وتاريخ/نوع سعر التحويل.
- ربط دلائل الحسابات بين الشركات.
- تعريف الطرف المقابل ومعاملة Intercompany المتناظرة.
- الإلغاءات والأرباح غير المحققة والأرصدة المتقابلة.
- نسب الملكية وحقوق الأقلية والفترات وسياسة الإقفال.
- أثر الرجوع والتدقيق وعدم تعديل دفاتر الشركات الأصلية.

### فجوات تشغيل وحوكمة

- إنفاذ حماية `main` ما زال غير مفعل بسبب خطة GitHub الحالية.
- إعادة بوابتي MariaDB 10.11/MySQL 8.4 والنسخ والاستعادة والرجوع مطلوبة قبل النشر.
- توثيق ومراقبة الإطلاق التدريجي للتسجيل والاستعادة وOutbox بصورة دورية.
- مراجعة إصدار Prisma والتنبيه المقبول مؤقتًا في [سياسة التنبيهات](security-advisories.md).
