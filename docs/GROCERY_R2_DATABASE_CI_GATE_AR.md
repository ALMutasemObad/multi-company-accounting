# بوابة R2 الفعلية في CI

التاريخ: 2026-08-31. ربط CI فقط؛ لا يثبت هذا المستند نجاح قاعدة بيانات أو يأذن بالنشر.

تعيد البوابة استخدام خدمات CI المؤقتة الموجودة دون تنزيل محرك أو تشغيله محليًا:

| المسار | المحرك | الحالة |
|---|---|---|
| `hosting-compatibility` | MariaDB 10.11 المثبت بالبصمة | fresh |
| `verify` | MySQL 8.4 المثبت بالبصمة | fresh |
| `migration-upgrade-compatibility` | كلا المحركين | upgrade من baseline الإنتاج المثبت و38 ترحيلًا وبياناته التجريبية |

اسم قاعدة كل خدمة `test_mcap_finance`، وهي مستقلة لكل job وتزول مع الخدمة. تمرر
`R2_DATABASE_URL` صراحة بقيمة `DATABASE_URL` نفسها **داخل CI المؤقت فقط**؛ لا fallback.
يظل `RUN_R2_DB_TESTS=true` والوضع `fresh|upgrade` إلزاميين. يرفض runner اسمًا خارج
`test_`/`r2_test_` واتصالًا خارج loopback، ويتحقق من إصدار المحرك ومن مطابقة هدف
الترحيل. يرفض أيضًا query/hash التي قد تغير خصائص الاتصال. لم يخفف حارس اختبار R2.
صحح fixture عملته فقط إلى upsert على `GLOBAL/XTS` مع `update:{}` لأن scopeKey
العشوائي السابق خالف CHECK الفعلي للعملة GLOBAL؛ لا يعدل upsert عملة موجودة.

في upgrade ينفذ `database-upgrade-compatibility.sh` الترتيب التالي:

1. preflight للعنوان والوضع والمحرك قبل أي تعديل، ثم ترحيلات baseline المثبت،
   ثم seed وdemo-seed الخاصان به كما في البوابة السابقة.
2. `selling-profile-db-gate.mjs prepare-upgrade`: يتحقق من عدد وتكامل تاريخ baseline
   وغياب جدول R2، ثم ينشئ وحدة وصنف Inventory باسم `R2 upgrade sentinel` في معاملة
   fixture محدودة. لا يستخدم `db push` أو reset أو بيانات حقيقية.
3. يحفظ snapshot ومعرف الصنف قبل الترحيل، ويمرر المعرف إلى الاختبار وإلى خطوات CI
   اللاحقة عبر `GITHUB_ENV`؛ ثم يطبق candidate migrations.
4. يتحقق من بقاء snapshot نفسه وعدم إنشاء ملف بيع/سعر له، ويشغل ملف التكامل الحقيقي
   وحده. تستمر بعده اختبارات التطبيق السابق وتشغيله على المخطط المحدث.

يُرفض نجاح Vitest الشكلي: يلزم تقرير جديد للملف الصحيح، وستة اختبارات على الأقل،
وكلها `passed` مع صفر skipped/todo/failed. غياب التقرير أو sentinel أو التعارض في
المحرك/الوضع يفشل البوابة. ترفع تقارير Vitest وملف evidence وsnapshot السابق
للترقية ضمن artifacts `r2-database-*` لمدة7 أيام؛ لا تحتوي بيانات اتصال أو أسرارًا.
يبقى النشر مربوطًا بنجاح jobs الثلاثة كما كان، ولم يضف هذا التغيير صلاحية نشر.

أضيفت أيضًا في `verify` فحص أنواع grocery واختبارات Chromium عبر
`playwright.grocery-integration.config.ts` وملفات الفشل
`tmp/agent/grocery-integration-results/`. هذه اختبارات واجهة مع HTTP harness،
وليست Backend/DB E2E ولا إثبات قارئ باركود أو طابعة فعلية.

## التحقق والحدود

اختبارات `scripts/tests/selling-profile-db-gate.test.mjs` تتحقق من الحواجز وترتيب
CI والـsentinel والrollback والتقارير عبر fixtures/mocks فقط، وتدخل تلقائيًا في
`infra:test`. لا تستبدل التشغيل الفعلي لأربع حالات المحرك/الترحيل أعلاه.
لم تنفذ هذه الحالات محليًا لعدم توفر المحركين المعتمدين، ولا توجد صلاحية رفع أو
إطلاق CI ضمن هذه المهمة؛ لا يجوز إعلان بوابات R2 مغلقة قبل مشاهدة أدلتها الخضراء.
نجح فحص JavaScript البنيوي و44 اختبارًا محدودًا (12 جديدة و32 حارسًا سابقًا للترقية
والاشتراكات وهويات قاعدة البيانات وworkflow والنسخ الاحتياطي)، بلا skip.
لم يتوفر Bash فعلي لتنفيذ `bash -n`
محليًا، ويظل فحص shell الموجود في CI مطلوبًا.

الملكية والعقد وDecimal وLedger وOutbox وRBAC لا تغيير. Barcode Impact: لا parser
أو lookup أو بيانات باركود جديدة؛ البوابة تحمي ملف البيع وتربط اختبار واجهته فقط.
الكتابة المباشرة الوحيدة fixture اختبار مؤقت قبل الترحيل، وليست مسار مجال تشغيليًا.
