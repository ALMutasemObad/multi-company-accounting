# تصنيف البيئات وخط الأساس المنشور

## القرار الحالي

النسخة المنشورة الحالية **بيئة ما قبل الإنتاج (Staging)** وليست إنتاجًا حيًا. لا تعد
بياناتها أو زمن إتاحتها عقد خدمة لعملاء حقيقيين، ويجوز إعادة تجهيزها أثناء التطوير بعد
نسخة احتياطية وتحقق صريح من الهدف.

مصطلح «الإنتاج» في أدلة التشغيل وWorkflows يعني البيئة الحية المستقبلية فقط. الالتزام
المنشور الحالي `c1a5722` هو **staging deployment baseline**، ولا يصبح Production
baseline إلا بقرار إطلاق صريح لاحق. تحتفظ بوابة الترقية مؤقتًا بـfixture أقدم محمل
بالبيانات عند `c39b979` و38 ترحيلًا لإثبات مسار ترقية أطول وتوافق التطبيق السابق؛ لا
يجعله ذلك الالتزام المنشور الحالي ولا Production.

## ما الذي يتغير

- ينشر `main` بعد نجاح جميع البوابات إلى endpoint المصنف **Staging**. تستخدم مهمة
  `deploy-staging` مؤقتًا GitHub Environment ذات الاسم القديم `production` كنطاق
  للأسرار الموجودة فقط؛ لا يغير الاسم الإرثي تصنيف الهدف، ويمكن إعادة نشر التزام
  `main` الحالي فقط يدويًا. لا توجد مهمة نشر Production تلقائية أو endpoint إنتاجي
  معرف في CI.
- أي Production مستقبلي يحتاج Workflow مستقلًا يدويًا، وبيئة `production` محمية
  بمراجعين، وأسرارًا وendpoint منفصلين؛ ولا يجوز إعادة استخدام endpoint الحالي له.
- أوقفت جداول `production-metrics-monitor.yml` و`production-backup-dr.yml` التلقائية
  وحُوّلت مهامهما إلى تشغيل يدوي للهدف Staging مع إبقاء Environment ذات الاسم
  الإرثي `production` كنطاق أسرار مؤقت. بقي اسما الملفين ومعرّفات Artifacts القديمة
  `mcap-production-*` مؤقتًا لحفظ سلسلة الأدلة وعدم قطع الوصول إلى النسخ السابقة؛
  لا تعني هذه المعرّفات أن البيئة Production.
- يمكن تغيير اسم قاعدة Staging أو إعادة إنشائها باسم محايد بدل المحافظة على اسم
  تطوير قديم إلى الأبد.
- يمكن حذف بيانات Demo بعد جردها، ولا يلزم ترحيل تجاري معقد لبيانات لا قيمة لها.
- يمكن تنفيذ Breaking cleanup قبل الإطلاق الحقيقي إذا غُلق داخل Migration واختبارات
  وترقية واضحة ولم يكسر بيانات اختبار لازمة بلا نسخة.

## ما الذي لا يتغير

- لا نشر أو تبديل أسرار أو حذف قاعدة عن بعد دون طلب صريح وهدف محدد.
- يلزم backup واستعادة تجريبية وrollback قبل أي استبدال لقاعدة Staging.
- تبقى بوابتا MariaDB 10.11 وMySQL 8.4، والعزل والمعاملات وRBAC وOpenAPI وDecimal
  شروط إصدار؛ Staging ليست مبررًا لكود مؤقت يدخل `main`.
- لا يفترض خلو Staging من بيانات مهمة قبل جرد read-only؛ التصنيف يسمح بالتغيير ولا
  يثبت أن كل سجل قابل للحذف.

## دليل التحويل التشغيلي

- نجح نشر `main` عند `c1a5722` في تشغيل CI رقم `33248189854`.
- فشل تشغيل المراقب `33257686234` في freshness، وفشل تشغيل النسخ/الاستعادة
  `33242837726`. لذلك لا توجد حاليًا مطالبة صادقة بـRPO يومي أو تمرين شهري للبيئة
  الحالية؛ التشغيل اليدوي يبقى متاحًا لجمع دليل جديد عبر نطاق الأسرار الإرثي، ثم
  ينقل إلى Environment باسم `staging` في تغيير تشغيلي مستقل لاحقًا.
- تشغيل التطبيق بـ`NODE_ENV=production` داخل Staging مقصود لتفعيل fail-fast وHTTPS
  والكوكيز الآمنة وبقية حواجز Node، ولا يغيّر تصنيف البيئة التجاري.

## إعادة تسمية قاعدة Staging

لا يعتمد المسار على `RENAME DATABASE`. ينشأ Schema جديد باسم محايد مثل
`mcap_finance`، وتطبق عليه الترحيلات من الصفر أو تستعاد فيه نسخة منقحة، ثم:

1. تؤخذ نسخة مشفرة ويثبت نجاح استعادتها في قاعدة مؤقتة.
2. يوقف كتاب Staging وتوثق نقطة القطع.
3. تطبق الترحيلات والـSeed المرجعي على الهدف، وتنقل فقط بيانات الاختبار المطلوبة.
4. تحدث `DATABASE_URL` و`MIGRATION_DATABASE_URL` وGrants دون طباعة الأسرار.
5. تشغل `/live` و`/ready` والعقود وSmoke tests والعزل والنسخ الاحتياطي.
6. يحتفظ بالقاعدة القديمة read-only لفترة رجوع قصيرة، ثم تحذف بأمر مستقل بعد التحقق.

المستودع لا يملك قيمة سر Staging، لذلك لا يمكنه إثبات الاسم الفعلي من ملفات Git؛
يجب فحص اسم Schema من مدير الأسرار/الاستضافة وقت التنفيذ دون كشف بيانات الاتصال.
