# هدف تطبيقات الهاتف والباركود الشامل

## 1. القرار وحالة التنفيذ

يعتمد المنتج هدفين ملزمين للمستقبل:

1. نشر تطبيق رسمي للنظام على Apple App Store وGoogle Play، مع دعم الهاتف واللوحي.
2. دعم الباركود كقدرة ERP كاملة للمدخلات والمخرجات، لا كحقل منفرد في شاشة الصنف
   ولا كاختصار خاص بـPOS.

الحالة الحالية لا تحقق أيًا من الهدفين: واجهة الويب متجاوبة مع عرض الهاتف، لكنها ليست
تطبيق متجر، ولا يوجد نموذج باركود أو API للمسح أو التوليد أو الطباعة. تبقى هذه الوثيقة
هدفًا حاكمًا للتصميم اللاحق ولا تدعي وجود تنفيذ.

## 2. الحد المعماري لتطبيقات الهاتف

تطبيق الهاتف قناة عرض إضافية لنفس النظام، وليس Bounded Context أو منصة محاسبية
موازية:

- يستخدم نفس OpenAPI والخادم وقاعدة البيانات؛ لا ينشأ Backend مستقل أو مخطط بيانات
  خاص بالهاتف.
- يبقى الخادم مصدر عزل `companyId` وRBAC والتحقق والمعاملات والترحيل والعكس
  وIdempotency. لا تنقل قواعد الضرائب أو المخزون أو Ledger إلى التطبيق.
- أي Mobile SDK أو Plugin يعزل خلف adapter صغير، ولا يتسرب إلى خدمات المجال.
- قرار PWA/Capacitor أو واجهة Native مستقلة يتخذ بعد Spike قابل للقياس. فرضية البداية
  هي إعادة استخدام React عبر Capacitor، وليست اعتمادًا نهائيًا قبل بوابة المصدر المفتوح
  واختبار أجهزة حقيقية.
- إذا بنيت واجهة Native لاحقًا، يعاد بناء Presentation فقط وتستخدم عميلًا مولدًا أو
  متحققًا من OpenAPI؛ لا تنسخ منطق الأعمال.
- يجب أن يسبق الإتاحة عقد هوية/capabilities مثل `/auth/me` حتى تعرض الواجهة التنقل
  والأفعال المسموحة، مع بقاء إنفاذ الصلاحيات خادميًا في كل طلب.

## 3. الأمان والاتصال على الهاتف

- توثق جلسة الهاتف في Threat Model مستقل يشمل CORS وCSRF وdeep links وإلغاء الجلسة
  وتدوير الاعتماد وتسجيل الخروج من الأجهزة.
- إذا احتاج التطبيق credential أصلية، تحفظ في Keychain/Keystore فقط؛ لا تحفظ أسرار
  جلسة أو refresh token في `localStorage`.
- أذونات الكاميرا والملفات والإشعارات تطلب عند الاستخدام وبأقل صلاحية، وتوثق في
  سياسات الخصوصية والمتجر.
- لا يسمح مبدئيًا بترحيل أو عكس أو تسوية مالية Offline. أي كتابة مالية دون اتصال تحتاج
  ADR مستقلًا يحدد command queue وIdempotency وترقيم المستندات والتعارض والاسترجاع.
- يمكن إضافة cache قراءة محدود وغير حساس بعد تحديد العمر والإبطال، ولا يعد مصدر حقيقة.
- يجب دعم اللغات الأربع وRTL/LTR وإمكانية الوصول وأهداف اللمس على الهاتف واللوحي.

## 4. ملكية الباركود ونموذج الهوية

يملك Inventory تعريف باركود الصنف وحالته. تستهلك Sales وPurchases وPOS وData Import
هذه القدرة عبر Ports أو API منشور، ولا تكتب تعريفاته مباشرة.

المتطلبات الملزمة للنموذج اللاحق:

- يدعم عدة باركودات للصنف بدل عمود `barcode` وحيد.
- تحفظ القيمة كنص حتى لا تضيع الأصفار البادئة، مع `symbology` وقيمة مطبعة مركزيًا
  وحالة نشطة ونسخة للتزامن.
- يكون lookup والتفرد داخل الشركة على الأقل بواسطة `(companyId, normalizedValue)`،
  مع مفتاح أجنبي مركب وفهرس مناسب للمسح. يجوز للشركتين استخدام القيمة نفسها دون تسرب.
- الباركود لا يستبدل `InventoryItem.id` أو رمز Master Data، ولا يستخدم كإذن وصول.
- ربط باركود بوحدة بيع أو عبوة أو معامل تحويل لا ينفذ قبل نموذج واضح لوحدات التعبئة
  والتحويل؛ لا توضع دلالة كمية ضمن نص الباركود بصورة ضمنية.
- لا يحذف hard delete تعريف استخدم تاريخيًا. يعطل مع Audit، وتحفظ المستندات المرحلة
  لقطة الباركود المختار عندما يلزم ثبات الإخراج التاريخي.

## 5. الإدخال والمسح

يجب أن تدعم القدرة قنوات الإدخال التالية خلف boundary موحد:

- قارئ USB أو Bluetooth من نوع HID/keyboard wedge.
- كاميرا iPhone وAndroid من التطبيق الرسمي.
- إدخال أو لصق يدوي كمسار احتياطي قابل للتحقق.
- استيراد دفعي من القوالب الرسمية عند وجود حالة أعمال معتمدة.

يعيد scanner adapter القيمة الخام ونوع الرمز إن أمكن. يحل الخادم القيمة داخل الشركة
الحالية، ثم يتحقق من الصنف والنشاط والوحدة والصلاحية قبل تمرير `itemId` إلى أمر الأعمال
الموجود. المسح لا يرحل فاتورة أو حركة مباشرة ولا يتجاوز موافقة المستخدم وقواعد المجال.

تتعامل الواجهة صراحة مع الرمز غير المعروف أو المعطل أو الملتبس، وتمنع تكرار القراءة
السريع غير المقصود. لا تفتح محتويات QR كرابط تلقائيًا؛ تعاملها كبيانات غير موثوقة.

مواضع الإدخال المستهدفة تشمل على الأقل:

- كتالوج المخزون والبحث عن الصنف.
- POS وتأليف بنود المبيعات والمشتريات.
- الاستلام والصرف والتحويل والجرد عند إضافة مستنداتها التشغيلية.
- المرتجعات والتحقق من الملصق قبل اختيار الصنف.

## 6. التوليد والمخرجات

- تحفظ حقيقة الرمز وقاعدته في البيانات، بينما يولد SVG/PDF أو تمثيل الطابعة عند
  الإخراج؛ لا تصبح صورة PNG مخزنة هي مصدر الحقيقة.
- تدعم الملصقات مقاس الورق وDPI والـquiet zones والنص المقروء بشريًا وعدد النسخ، مع
  حدود دفعة صريحة تمنع توليد آلاف الملصقات داخل ذاكرة طلب واحدة.
- تكون PDF هي نقطة البداية المحمولة للطباعة. يمكن إضافة ZPL/EPL عبر printer adapter
  بعد Spike لأجهزة فعلية، لا داخل خدمة Inventory.
- يظهر الباركود في ملصق الصنف وملصق العبوة، وفي الفاتورة أو الإيصال أو مستند الحركة
  أو التصدير عندما تحدد حالة الأعمال ذلك. لا يضاف إلى كل تقرير بلا معنى.
- يستخدم المستند التجاري معرفًا مستقرًا لا رقم صف داخليًا، ولا ترمز مبالغ أو بيانات
  حساسة إلا عندما يفرض عقد أعمال أو تشريع موثق ذلك.
- لا يولد النظام GTIN عامًا عشوائيًا. إصدار GTIN الخارجي يتبع بادئة وسياسة GS1 الخاصة
  بالمنشأة، بينما يمكن إصدار Code 128 داخلي وفق sequence مملوك للشركة.

## 7. الأنواع المدعومة

الشريحة الأولى يجب أن تثبت مصفوفة تشغيلية قابلة للتوسع تشمل:

- EAN-13 وEAN-8 وUPC-A للرموز التجارية مع تحقق check digit.
- Code 128 للرموز الداخلية.
- QR للمعرفات أو الروابط الداخلية الموقعة عند وجود حالة أعمال معتمدة.
- GS1-128 أو GS1 DataMatrix في شريحة لاحقة عند إضافة lot/serial/expiry وقواعد Application
  Identifiers؛ لا يدعي النظام traceability قبل امتلاك هذه النماذج.

إضافة نوع جديد تكون في codec/adapter مركزي وعقد اختبارات، لا عبر شروط موزعة على
صفحات النظام.

## 8. شرائح التنفيذ

1. **B0 — قرار الأجهزة والعقود:** عينات أجهزة وملصقات، symbologies المطلوبة، سياسة
   GS1، نموذج البيانات، ADR، وSpike للمكتبة والطباعة.
2. **B1 — Master Data وResolve API:** عدة باركودات، RBAC وAudit والتزامن والعزل،
   إنشاء/تعديل/تعطيل، lookup مفرد ودفعي بعقد OpenAPI.
3. **B2 — إدخال ERP:** HID والإدخال اليدوي في Inventory وPOS وSales وPurchases، مع
   إعادة استخدام أوامر الأعمال الحالية.
4. **B3 — المخرجات:** توليد الرمز والملصقات وPDF واللقطات التاريخية وحدود الدفعات.
5. **M0/M1 — قناة الهاتف:** Spike ثم shell رسمي وتسجيل آمن وعميل OpenAPI وتوقيع CI
   ونشر تجريبي داخلي.
6. **B4 — كاميرا الهاتف:** ربط scanner adapter بالكاميرا واختبارات iOS/Android.
7. **B5 — اللوجستيات المتقدمة:** عبوات وlot/serial/expiry وGS1 فقط بعد اعتماد نماذجها.

لا تسمى القدرة «دعم باركود كامل» بعد B1 وحدها؛ يلزم نجاح مسار إدخال وإخراج فعلي.

## 9. بوابات القبول

- OpenAPI وحراس الطلب والاستجابة واختبارات route parity.
- عزل شركتين تستخدمان القيمة نفسها، ومنع الغموض داخل الشركة، ورفض foreign/inactive.
- الحفاظ على leading zeros والتحقق من الطول والمحارف وcheck digit لكل symbology.
- اختبار تنافس إنشاء الرمز وoptimistic concurrency وIdempotency للاستيراد/التوليد.
- round-trip يولد الملصق ثم يفك الرمز من artifact نفسه، مع عينات قياس وطباعة فعلية.
- اختبار HID والكاميرا والإدخال اليدوي، ومصفوفة iPhone وAndroid وأحجام الهاتف واللوحي.
- ثبات PDF التاريخي بعد إعادة تسمية الصنف أو تعطيل باركوده.
- قياس p50/p95/p99 لـlookup ودفعات الملصقات قبل تحديد حدود الإنتاج أو SLO؛ لا تخترع
  حدود نهائية بلا قياس.
- نجاح MariaDB 10.11 وMySQL 8.4، وفحص الترقية والنسخ والاستعادة والرجوع.
- مراجعة الرخصة والأمن وحجم الحزمة وخطة التحديث والخروج لأي مكتبة barcode/mobile.

## 10. ما لا يغيره هذا الهدف

- لا يغير ملكية `PostingEngine` أو أثر الفواتير والحركات داخل المعاملة.
- لا يمنح POS أو تطبيق الهاتف ملكية Inventory أو Sales أو Treasury.
- لا يحول الباركود إلى مفتاح شركة عالمي أو وسيلة مصادقة.
- لا يقرر التتبع بالدفعات والأرقام التسلسلية أو العمل Offline بمجرد اعتماد الهدف؛ لكل
  منهما قرار ونموذج وتزامن واختبارات مستقلة.
