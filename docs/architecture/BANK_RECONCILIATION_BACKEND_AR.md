# Backend المطابقة البنكية 1:1

## 1. القرار والنطاق

تنفذ المرحلة 2 Backend المطابقة البنكية داخل `Treasury` فقط، خلف `BANK_RECONCILIATION_ENABLED=false` افتراضيًا. تشمل المعاينة والاستيراد والجلسات والاقتراحات والربط اليدوي والاعتماد والفك والتصنيف والإقفال. توثق واجهة المستخدم والتصدير والإطلاق التدريجي المنفذة لاحقًا في [عقد واجهة المطابقة والإطلاق التدريجي](BANK_RECONCILIATION_UI_ROLLOUT_AR.md).

المبدأ الحاكم: القارئ ومحرك المطابقة ومنسق الجلسة لا يكتبون `AccountingDocument` أو `JournalEntry` أو `JournalLine`. يقرأ Adapter محلي القيود المرحلة عبر `ReconciliationLedgerQueryPort`. إذا كشف المستخدم رسمًا أو فائدة أو حركة ناقصة تحتاج أثرًا محاسبيًا، ينشئ المستند من خدمة Receipt/Payment/Manual Journal الحالية، ويظل `PostingEngine` الكاتب الوحيد للـLedger؛ بعدها يعاد توليد الاقتراح أو ينفذ الربط اليدوي.

## 2. الملكية والتخزين

يضيف الترحيل `20260827010000_bank_reconciliation_backend` الجداول التالية، وجميع روابطها التشغيلية تحمل `company_id` وعلاقات مركبة تمنع الربط عبر الشركات:

- `bank_statement_imports`: بصمة المصدر، حساب البنك، الفترة والعملة وملخص الأرصدة وحالة الاستيراد ونسخته.
- `bank_statement_lines`: التاريخ والمبلغ والمرجع والوصف والبصمة والتصنيف ونسخته؛ لا يخزن الملف الخام.
- `bank_reconciliation_sessions`: وارد واحد وحساب واحد ونطاق يطابق فترة الوارد كاملة في شريحة 1:1، ولقطات bank/book والفرق والحالة والنسخة.
- `bank_reconciliation_matches`: سجل تاريخي للاقتراح أو الربط اليدوي وحالته وقاعدته ودرجته وهوية المعتمد أو المفك وأسبابهما.

تفرض قاعدة البيانات تفرد بصمة المصدر داخل حساب بنك الشركة، وجلسة واحدة لكل وارد، وسطر واحد داخل الوارد، كما تفرض ألا يشارك سطر بنك أو مفتاح حركة دفاتر في أكثر من Match معتمد. ترفض الخدمة نطاق جلسة جزئيًا حتى لا تترك خطوطًا خارج جلسة لا يمكن إنشاؤها ثانية. وإذا حمل CAMT معرف حساب وكانت مرجعية البنك تحفظ آخر أربعة أرقام للحساب أو IBAN، تطابقها الخدمة قبل الحفظ. الفك يغير الحالة إلى `RELEASED` ولا يحذف السجل. الـPreview لا يحفظ شيئًا، والوارد المعتمد وخطوطه لا تحذف صلبًا. حالة `CANCELLED` محجوزة لسياسة إلغاء مستقبلية ولا يوجد مسار عام يفعّلها في هذه المرحلة.

## 3. المنافذ والمحرك المحلي

- `BankStatementParserPort`: عقد الـSpike القائم؛ يحول CSV أو CAMT.053 إلى حقائق محلية، ولا يرى Prisma.
- `ReconciliationLedgerQueryPort`: يعيد حركات حساب الأستاذ المرتبطة بحساب البنك من قيود `POSTED` فقط. المفتاح العام للحركة SHA-256 opaque، ولا يكشف معرف Ledger خامًا كعقد مجال.
- `ReconciliationMatcherPort`: محرك pure يستخدم `Prisma.Decimal` ومدخلات مرتبة ولا يقرأ قاعدة البيانات.

القواعد الأولى حتمية ومحافظة:

1. تطابق المرجع والمبلغ والعملة: درجة 100.
2. تطابق المبلغ والعملة ضمن نافذة التاريخ: درجة 70 واقتراح يحتاج اعتمادًا صريحًا.
3. الغموض أو تساوي أكثر من مرشح يترك السطر بلا اقتراح.
4. لا tolerance للمبلغ، ولا fuzzy amount، ولا FX، ولا اعتماد تلقائي.

## 4. حالات الاستخدام والعقد العام

يوفر OpenAPI 1.24.0 العمليات التالية تحت `/bank-statement-imports` و`/bank-reconciliation/sessions`:

- معاينة كشف، اعتماد وارد، قائمة الواردات وتفاصيل وارد.
- إنشاء جلسة وقائمتها وتفاصيلها وقراءة حركات الدفاتر المرشحة.
- توليد الاقتراحات، اعتماد اقتراح، ربط يدوي، وفك Match مع سبب.
- تصنيف السطر غير المطابق إلى `PENDING_TRANSACTION` أو `BANK_FEE` أو `BANK_INTEREST` أو `BANK_ERROR` أو `NEEDS_ACCOUNTING_DOCUMENT`.
- إقفال الجلسة إذا حُلت كل الخطوط وكان الفرق صفرًا، أو إذا حفظ تفسير معتمد لفرق غير صفري.

كل BIGINT وDecimal يخرج نصًا. لا يعاد رقم حساب أو IBAN خام؛ يخرج آخر أربعة أرقام مقنعة فقط. لا تدخل محتويات الملف أو أوصاف السطور أو المراجع في logs.

## 5. RBAC والتدقيق وIdempotency

الصلاحيات مستقلة:

- `bank_reconciliation.view`
- `bank_reconciliation.import`
- `bank_reconciliation.review`
- `bank_reconciliation.close`

يمنح الترحيل والـSeed الصلاحيات الأربع لدور `ADMINISTRATOR` النظامي فقط. لا تمنح `close` تلقائيًا لمن يملك `import`، ويمكن للدور المخصص امتلاك `view/import/review` من دون `close`. كل أمر كتابة يحتاج CSRF و`Idempotency-Key` ويستخدم `IdempotentCommandExecutor` ببصمة تشمل المعرف العام والمدخل ونسخة الجلسة. تسجل أوامر الاعتماد والاقتراح والربط والفك والتصنيف والإقفال في `AuditLog` داخل المعاملة نفسها.

## 6. التزامن وحدود المعاملة

يحدث parsing والتحقق من الملف قبل معاملة الحفظ؛ لا file parsing ولا Network I/O داخل Transaction. تستخدم الأوامر deadline الطلب وretry المحدود للأخطاء العابرة فقط، ولا تعاد أخطاء قاعدة الأعمال أو النسخة القديمة.

ترتيب الأقفال الثابت:

1. صف الجلسة.
2. خطوط البنك تصاعديًا حسب المفتاح الداخلي.
3. حركات Ledger المرشحة تصاعديًا حسب معرف السطر.

بعد الأقفال يستخدم الأمر conditional update على `companyId + id + version`. تحمي قيود التفرد النهائية من السباق حتى عند وصول طلبين متزامنين؛ ينجح اعتماد واحد فقط ويعاد تعارض للآخر. لا يعاد إقفال جلسة مغلقة أو ربط Match مفكوك من خلال تعديل التاريخ.

## 7. الترحيل والرجوع

الترحيل توسعي: يضيف أربعة جداول وأربعة أذونات ولا يعيد كتابة Ledger أو المستندات أو بيانات Treasury السابقة. يستطيع Binary أقدم تجاهل الجداول الجديدة. ترتيب الإصدار المستقبلي، بعد موافقة صريحة فقط، هو نسخة قابلة للاستعادة ثم `migrate deploy` ثم Artifact جديد مع بقاء العلم معطلًا حتى اكتمال المرحلة 3.

الرجوع التطبيقي يكون بإعادة Artifact السابق وتعطيل العلم؛ تبقى سجلات المطابقة محفوظة. لا يحذف الترحيل في الإنتاج كإجراء رجوع عادي. إذا ألغي المنتج نهائيًا، يحتاج حذف الجداول Migration مستقلة بعد retention/export وموافقة تشغيلية صريحة.
