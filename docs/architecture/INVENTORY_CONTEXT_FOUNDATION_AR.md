# أساس سياق المخزون ورحلة الصعود إلى ERP

## 1. القرار

يعمل `Inventory` كوحدة مستقلة داخل الـModular Monolith. تملك الشريحة الحالية بيانات `Warehouse` و`UnitOfMeasure` و`InventoryItem` كاملة من مخطط البيانات إلى API والصلاحيات والواجهة والتدقيق. لا تمنح العلاقة المستقبلية مع المبيعات أو المشتريات أي سياق آخر حق الكتابة المباشرة في جداول Inventory.

## 2. حدود المرحلة الحالية

تشمل المرحلة:

- إنشاء المستودع وعرضه والبحث عنه وتعديله وتعطيله.
- عزل جميع البيانات بالـ`companyId` المأخوذ من الجلسة.
- توليد رمز ثابت خادميًا بصيغة `WH-000001` وتسلسل مستقل لكل شركة.
- حماية التعديل والتعطيل بـ`version` متفائلة.
- صلاحيتين مستقلتين: `warehouses.view` و`warehouses.manage`.
- سجل تدقيق داخل المعاملة نفسها لكل إنشاء أو تعديل أو تعطيل.
- إنشاء وحدات القياس وعرضها والبحث عنها وتعديلها وتعطيلها، برمز دلالي ثابت داخل الشركة مثل `EA` أو `KG` ودقة كمية من صفر إلى ست منازل عشرية.
- إنشاء الأصناف وعرضها والبحث عنها وتصفيتها وتعديلها وتعطيلها، برمز خادمي ثابت مثل `ITM-000001` ووحدة قياس نشطة إلزامية.
- صلاحيتان لكتالوج المخزون: `inventory_catalog.view` و`inventory_catalog.manage`، مستقلتان عن صلاحيات المستودعات.
- قفل صف وحدة القياس عند إنشاء الصنف أو تغيير وحدته أو تعطيل الوحدة، لمنع سباق يترك صنفًا نشطًا مرتبطًا بوحدة معطلة.

ولا تشمل:

- التصنيفات أو المتغيرات أو الباركود.
- أرصدة افتتاحية أو حركات استلام وصرف وتحويل أو جرد.
- الحجز والتوفر والتكلفة أو طرق التقييم.
- ربط بنود فواتير البيع والشراء بالمخزون.
- إنشاء قيد يومية أو الكتابة في `JournalEntry/JournalLine` أو `AccountingDocument`.

هذا الفصل مقصود؛ وجود شاشة مستودعات لا يعني ادعاء اكتمال نظام مخزون.

## 3. Invariants

1. رمز المستودع فريد داخل الشركة، يصدر من `MasterDataCodeSequence` في معاملة الإنشاء نفسها، ولا يقبله عقد الإدخال.
2. كل قراءة وكتابة تشغيلية تقيد بـ`id + companyId` عند الوصول لكيان مفرد.
3. التعديل والتعطيل يستخدمان تحديثًا شرطيًا على `version` ويزيدانها مرة واحدة عند النجاح.
4. المستودع المعطّل يبقى مرئيًا للتاريخ ولا يعاد تنشيطه ضمن هذه المرحلة.
5. سجل التدقيق يلتزم أو يتراجع مع تغيير المستودع، ولا يستخدم كناقل أحداث.
6. لا يوجد حدث Outbox حاليًا لأن المرحلة ليس لها مستهلك لاحق للـcommit.
7. رمز وحدة القياس دلالي، يُطبّع إلى أحرف كبيرة عند الإنشاء، ولا يقبل في التعديل؛ أما رمز الصنف فيولده الخادم من تسلسل `INVENTORY_ITEM` داخل معاملة الإنشاء.
8. علاقة الصنف بوحدة القياس محمية بمفتاح خارجي مركب `(unit_of_measure_id, company_id)`، فلا يمكن ربط بيانات شركتين حتى في SQL.
9. لا يقبل إنشاء صنف أو تغيير وحدته إلى وحدة معطلة أو تابعة لشركة أخرى، ولا تُعطّل وحدة تستخدمها أصناف نشطة.
10. يتسلسل إنشاء الصنف وتعطيل الوحدة على قفل `FOR UPDATE` نفسه؛ ينجح أحد القرارين فقط إذا تزامنا على وحدة بلا أصناف.

## 4. خريطة التوسع

1. **المستودعات — مكتملة:** البيانات الرئيسية والعزل والصلاحيات والتدقيق.
2. **كتالوج المخزون الأساسي — الحالية:** وحدات القياس والأصناف وسياسة الرموز، دون كميات أو أرصدة.
3. **توسعة الكتالوج:** التصنيفات والمتغيرات والباركود بعد قرار أعمال مستقل.
4. **دفتر حركة المخزون:** أرصدة افتتاحية وحركات immutable وهوية طلب Idempotency وتحويل بين المستودعات.
5. **التكامل التشغيلي:** استلامات مشتريات وصرف مبيعات عبر منافذ Inventory صغيرة؛ لا كتابة مباشرة من سياقي Sales/Purchases.
6. **التكلفة والمحاسبة:** اختيار طريقة تقييم، ثم تمرير خطة القيد إلى `PostingEngine` المملوك لـCore Accounting.

كل خطوة لاحقة تحتاج عقدًا ومخططًا وترحيلًا واختبارات عزل وتزامن مستقلة؛ ولا تبدأ طريقة التقييم قبل قرار أعمال صريح.

## 5. معايير قبول الشريحة

- نجاح Prisma validation وClient generation وTypeScript والبناء.
- تطابق المسارات مع OpenAPI وحراس الأجسام المولدة.
- اختبار إنشاء متزامن يثبت تفرد الرموز، وعزل شركتين، وتعارض النسخة، والتدقيق، وتسلسل إنشاء الصنف مع تعطيل وحدته.
- نجاح ترحيل القاعدة الفارغة وترقية السلسلة السابقة على MariaDB وMySQL في CI.
- واجهة عربية وإنجليزية متجاوبة لا تسمح بإدخال رمز الصنف أو تعديل رمز وحدة القياس بعد إنشائها.
