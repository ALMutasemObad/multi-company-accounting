# ملكية سياق Tax وسياسة الحساب الضريبي

## 1. القرار

`TaxRate` مملوك حصريًا لوحدة `Tax`. لا تنفذ Sales أو Purchases قراءة Prisma أو كتابة مباشرة على جدول `tax_rates`، بل تستخدمان `TaxQuotePort` للحصول على لقطة النسبة وحساب الترحيل المناسب داخل المعاملة المالية نفسها.

تبقى مسارات HTTP العامة الحالية متوافقة مكانيًا:

- `/tax-rates` لضريبة المخرجات.
- `/purchase-tax-rates` لضريبة المدخلات.

تنفذ المسارات وحدة `TaxRouter` واحدة، ولا تعود جزءًا من راوترَي الفواتير. تحمل استجابة النسبة `version`، ويلزم PATCH بإرسال النسخة المقروءة؛ الطلب القديم من دون نسخة يرفض كطلب غير صالح بدل السماح بفقد تحديث متزامن.

## 2. حدود الملكية

| الوحدة | تملك | تستهلك |
|---|---|---|
| Tax | `TaxRate`، CRUD، صلاحية حسابات المدخلات والمخرجات، التقريب والحساب | الحسابات كمرجع مقيد بالشركة |
| Sales/AR | فاتورة المبيعات وبنودها ولقطة الضريبة المثبتة | `TaxQuotePort` باستخدام `OUTPUT` |
| Purchases/AP | فاتورة المشتريات وبنودها ولقطة الضريبة المثبتة | `TaxQuotePort` باستخدام `INPUT` |
| Core Accounting | قيد الأستاذ النهائي | Posting plans المبنية من اللقطة |

## 3. Invariants

- كل قراءة أو تعديل لـ`TaxRate` مقيد بـ`companyId`.
- النسبة بين صفر و100، وتثبت في بند الفاتورة بأربع منازل عشرية.
- النسبة الموجبة للمخرجات تحتاج حساب التزام نشطًا، ورقيًا، قابلًا للترحيل ومن الشركة نفسها.
- النسبة الموجبة للمدخلات تحتاج حساب أصل بالشروط نفسها.
- النسبة الصفرية يمكن أن تعمل بلا حساب ضريبي.
- كل تعديل يستخدم `WHERE id + companyId + version` ثم يزيد النسخة؛ عدم تحديث صف واحد يعني `VERSION_CONFLICT`.
- `P2034` وdeadlock يعادان عبر `TransactionExecutor` ضمن deadline واحد؛ بعد الإعادة تتحول النسخة القديمة إلى تعارض أعمال حتمي.

## 4. سياسة الحساب والتقريب

تستخدم المبيعات والمشتريات `calculateTaxDocument` نفسها و`Prisma.Decimal.ROUND_HALF_UP`:

1. يقرب إجمالي السطر والخصم والصافي والضريبة والإجمالي إلى أربع منازل.
2. يثبت `taxRateSnapshot` و`taxAmount` في السطر ولا يعاد تفسير المستند المرحل من إعداد حالي.
3. يحتسب `baseTotal` من مجموع صافي وضريبة كل سطر بعد تقريب كل تفصيل بالعملة الأساسية؛ يطابق ذلك أسطر Posting الفعلية ولا يستخدم تقريبًا ثانيًا لإجمالي مدمج.

## 5. الترحيل والتوافق

الترحيل `20260822233000_tax_context_ownership` توسعي فقط: يضيف `tax_rates.version` كـ`INT UNSIGNED NOT NULL DEFAULT 0`. لا يعيد كتابة النسب أو الحسابات أو روابط الفواتير، ويمكن تطبيقه بينما توجد بيانات تاريخية. اختبر من قاعدة فارغة وكترقية للترحيل السابق مع صفوف فعلية على MariaDB 10.4.32 وMySQL 8.4.11؛ بقي عدد الصفوف ثابتًا وأصبحت النسخ صفرًا.

يمكن للـBinary القديم قراءة الجدول بعد إضافة العمود، لكن PATCH القديم لا يشارك في حماية النسخة. لذلك ترتيب النشر المعتمد هو: نسخة احتياطية، `migrate deploy`، ثم Artifact الجديد. الرجوع البنيوي غير مطلوب؛ عند رجوع التطبيق مؤقتًا يبقى العمود الإضافي غير ضار، مع منع الكتابات الإدارية حتى إعادة Artifact الجديد.

## 6. بوابات القبول

- حارس معماري يمنع أي Prisma CRUD لـ`TaxRate` داخل Sales/Purchases.
- اختبارات وحدة للحساب والتقريب والعزل ونوع حساب المدخلات والمخرجات والنسخة.
- اختبارات تكامل للمسارين العامين ولرفض الحساب الخاطئ.
- اختبار تحديثين متزامنين يثبت نجاح واحد و`409 VERSION_CONFLICT` للآخر.
- حزمة API كاملة وبناء الواجهة وOpenAPI/Redocly على MariaDB وMySQL 8.4.
