# سياسة OpenAPI كعقد تنفيذي

## القرار

ملف `packages/contracts/openapi.yaml` هو مصدر الحقيقة لأشكال JSON العامة في HTTP. يولد `scripts/generate-openapi-guards.mjs` منه ملف `apps/api/src/generated/openapi-request-guards.ts` حتميًا؛ يمنع تعديل الملف المولد يدويًا أو إبقاء مخطط Zod موازٍ لجسم طلب في Router.

التغطية الحالية هي 213 عملية، و108 أجسام طلب JSON، و1429 جسم استجابة JSON مرتبطًا بالعملية ورمز الحالة. الاستجابات `204` والمحتوى الثنائي أو النصي لا تعامل كأجسام JSON.

## دلالات النقل والتوليد

- يحل المولد `$ref` و`allOf` و`oneOf` و`anyOf` و`not`، ويدعم الكائنات والمصفوفات والقيود والأنواع المقيدة و`readOnly/writeOnly`.
- معرف BIGINT العام يبقى نصًا في الاستجابة. في جسم الطلب يحوله الحارس المولد إلى `bigint` بعد التحقق من النمط الموجب؛ لا تستخدم `Number` لهذا الحد.
- قيم `DECIMAL` وأسعار الصرف تبقى نصوصًا مطابقة للنمط، والتواريخ تبقى نصوص ISO حتى تحولها طبقة التطبيق صراحةً عند الحاجة.
- `readOnly` مستبعد من الطلب و`writeOnly` مستبعد من الاستجابة.
- الامتداد `x-trim: true` هو التعبير الصريح عن تنظيف النص عند حد الطلب. لا يطبق القص ضمنيًا على كل نص.
- `additionalProperties: false` يعني جسم طلب صارمًا. أي توافق قديم مقصود، مثل قبول حقل الطرف المقابل بقيمة `null`، يجب تمثيله في JSON Schema واختباره.
- الحقول الاختيارية ذات `default` تحتفظ بالقيمة الافتراضية بعد التحليل، بينما تزال الخصائص الاختيارية ذات القيمة `undefined` من ناتج جسم الطلب.

## الاعتماد في التطبيق

تستخدم Routers حصريًا `openApiRequestBodySchemas` أو aliases المولدة لتحليل `request.body`. تبقى معاملات المسار والاستعلام والترويسات في حراسها المحلية حاليًا، وتمنع بوابة تطابق المسارات اختلاف الطريقة أو المسار عن OpenAPI.

في التطوير والاختبار يلف `createOpenApiResponseValidator` استجابات JSON ويطابق العملية ورمز الحالة مع المخطط المولد. يفشل الاختبار عند جسم غير مطابق أو رمز حالة JSON غير معلن، ويسجل اسم العملية والحالة ومسارات المشكلات دون تسجيل قيم الجسم. المدقق معطل في الإنتاج افتراضيًا، ولذلك لا يحل محل اختبارات التكامل على MariaDB وMySQL.

غلاف `Problem` يقبل مؤقتًا الأغلفة الأحدث والحقول القديمة المنفذة. يبقى `code` مطلوبًا، ويجب تقليص هذا التوافق في مرحلة مستقلة بعد توحيد جميع معالجات الأخطاء من دون كسر العملاء.

## بوابات منع الانحراف

1. `npm run contracts:generate` يعيد التوليد ويحدث بصمة SHA-256 والتغطية.
2. `npm run contracts:check` يفشل إذا كان الملف المولد مفقودًا أو متقادمًا.
3. اختبار المولد يثبت الحتمية عبر LF/CRLF وتأثر المخرج بتغير العقد.
4. اختبار `architecture-guardrails` يقارن العمليات الـ77 مع الحراس المعتمدة في Routers ويمنع مصدرًا يدويًا لجسم الطلب.
5. اختبارات الطلب والاستجابة تغطي التحويلات والقيود والحالات السلبية والحالة غير المعلنة.
6. اختبار تطابق المسارات وRedocly recommended يظلان بوابتين مستقلتين.
7. يجب تشغيل حزمة API كاملة على MariaDB وMySQL عند تغيير عقد تشغيلي مالي أو شكل استجابة فعلية.

## سير عمل التغيير

1. عدّل OpenAPI أولًا أو معه في التغيير نفسه.
2. أعد التوليد ولا تعدل الملف المولد يدويًا.
3. اعتمد الحارس المولد في Router، ثم حدّث نوع الخدمة إذا تغير حد BIGINT أو الاختيارية.
4. أضف اختبارًا إيجابيًا وسلبيًا، واختبار استجابة عند تغيير المخرج أو رمز الحالة.
5. شغل `contracts:check` وTypeScript وVitest وRedocly والبناء، ثم بوابتي قاعدة البيانات بحسب المخاطر.
6. حدّث حالة التنفيذ والوثائق الحاكمة قبل إغلاق المرحلة.

لا يجوز إصلاح فشل المدقق بتخفيف مخطط مشترك على نحو غير صادق. يحدد أولًا هل التنفيذ أم العقد هو السلوك المقصود، ثم يصحح المصدر الحاكم مع اختبار يمنع عودة الانحراف.
