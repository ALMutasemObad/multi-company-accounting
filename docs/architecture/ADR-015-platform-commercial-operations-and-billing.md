# ADR-015: التشغيل التجاري للمنصة وفوترة الشركات

## السياق

قدمت الشريحة الأولى من Platform Operations مؤشرات مجمعة للمنتج والصحة التشغيلية
فقط. تحتاج الشركة المطوّرة الآن إلى ملف تشغيلي لكل شركة، وتسعير اشتراكها، وإصدار
فواتير المنصة، وتسجيل السداد، ومعرفة الرصيد والمتأخرات. هذه العلاقة التجارية بين
الشركة المطوّرة والشركة المستأجرة، وليست جزءًا من دفتر الشركة المستأجرة أو مبيعاتها.

## القرار

- يتوسع السياق إلى **Platform Operations & Billing**. تبقى قراءات استخدام الوحدات
  خلف Query Port، ويملك السياق وحده `PlatformBillingAccount` و`PlatformBillingInvoice`
  وبنودها و`PlatformBillingPayment`.
- تعرض الشركة المطوّرة إحصاءات مجمعة لكل شركة: المستخدمون والموظفون والجلسات
  والعمليات والمستندات واستخدام الوحدات والاتجاه الزمني. لا تعرض أسماء أفراد أو
  بريدًا أو IP أو وصف مستند أو مبالغ من Ledger الشركة.
- فواتير المنصة مستقلة عن `SalesInvoice`, `ReceivableItem`, `JournalEntry` ودفاتر
  الشركات. أي تكامل مستقبلي مع دفتر مستقل للشركة المطوّرة يمر عبر Port وقرار لاحق؛
  لا تنشئ هذه الشريحة قيدًا أو ذمة داخل شركة عميلة.
- يحفظ حساب الفوترة دورة الاشتراك، عملته، الرسم الدوري، الشرائح المشمولة، أسعار
  الاستخدام الإضافي، نسبة الضريبة، مهلة السداد، وحالته بنسخة متفائلة.
- عند إصدار الفاتورة تثبت لقطة الاستخدام والتسعير والبنود والمبالغ. الفاتورة
  الصادرة immutable؛ يسمح بإلغائها فقط قبل وجود سداد، مع سبب وتدقيق. السداد سجل
  append-only ولا يتجاوز الرصيد القائم.
- الرصيد وحالة السداد والمتأخرات مشتقة من الفواتير غير الملغاة والسدادات، ولا ينشأ
  جدول أرصدة موازٍ. تستخدم كل الحسابات `Prisma.Decimal` و`ROUND_HALF_UP`.
- تعرِض قراءة التحليلات النطاقات اليومية المخصصة حتى 366 يومًا، والمقارنة بالفترة
  السابقة أو السنة السابقة، وتوزيع أعمار الرصيد والنشاط حسب الوحدة والشركة. تبقى
  القراءة مشتقة عند الطلب عبر Query Adapter، وتفصل العملات ولا تضيف Projection أو
  جدول تجميع مادي في هذه المرحلة.
- الوصول محصور في `PLATFORM_OPERATOR_EMAILS`. كل كتابة تحتاج جلسة مصادقًا عليها،
  CSRF، و`Idempotency-Key`، وتدقيقًا داخل المعاملة نفسها. لا يمنح أي دور داخل شركة
  هذا الوصول.
- لا Outbox في هذه الشريحة لعدم وجود مستهلك بريد أو تكامل خارجي. إصدار PDF وإرسال
  الفاتورة والتحصيل الإلكتروني خارج النطاق، ويمكن إضافتها لاحقًا بمستهلك وعقد واضحين.

## قواعد الفوترة

1. لكل شركة حساب فوترة واحد على الأكثر.
2. لا تصدر فترتان متطابقتان للشركة نفسها مرتين.
3. فترة الفاتورة صحيحة وغير معكوسة، وتاريخ الاستحقاق لا يسبق الإصدار.
4. بنود الاستخدام تحسب من لقطة الخادم، ولا يقبل العميل أعداد المستخدمين أو
   الموظفين أو المستندات كمصدر حقيقة.
5. إجمالي الفاتورة لا يكون سالبًا، والسداد موجب ولا يتجاوز الرصيد.
6. إلغاء الفاتورة يتطلب `version` وسببًا، ويرفض عند وجود سداد.

## النتائج

- تصبح المنصة قادرة على متابعة العقود والفوترة والتحصيل دون تلويث دفاتر العملاء.
- يضيف التغيير Migration توسعية وجداول مملوكة لسياق واحد، بلا Dependency جديدة.
- الرجوع مسموح قبل أول استخدام فقط؛ بعد وجود حساب أو فاتورة أو سداد يرفض rollback
  حذف التاريخ التجاري.
- التنفيذ محلي في هذه المرحلة؛ لا نشر ولا Push ضمن هذا القرار.
