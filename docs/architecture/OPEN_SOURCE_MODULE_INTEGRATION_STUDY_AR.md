# دراسة النواقص ودمج الموديولات مفتوحة المصدر

## 1. الخلاصة التنفيذية

النظام لا يحتاج استبدال قلبه المحاسبي أو إدخال ERP آخر. الموجود حاليًا يغطي دليل الحسابات والدفتر والترحيل والعكس والفواتير والذمم والقبض والصرف والضرائب الأساسية والعملات والمخزون بالتكلفة والتقارير الأساسية والتدقيق والاستيراد وتعدد الشركات.

أعلى نقص وظيفي حالي هو **المطابقة البنكية واستيراد كشوف البنك**، يليه **إقفال الشهر والسنة بصورة حاكمة**، ثم **استكمال حزمة التقارير النظامية والإدارية**. هذه قدرات تكمل دورة قائمة ولا تنشئ منتجًا جديدًا منفصلًا.

قرار الدراسة الأولي:

1. يبدأ أول Pilot بالمطابقة البنكية داخل `Treasury`، من دون أي ترحيل تلقائي ومن دون خدمة خارجية.
2. تعتمد مكتبتا `csv-parse` و`fast-xml-parser` كمكونات parsing مرشحة؛ لا تعد أي منهما مالكًا لبيانات البنك أو قواعد المحاسبة.
3. يبقى `ofx-data-extractor` مرشح Pilot اختياريًا لـOFX فقط بسبب صغر مجتمع المشروع مقارنة بالمرشحين الأساسيين.
4. يستخدم `XState` عند بناء سير الإقفال والموافقات بوصفه محرك انتقال حالات فقط؛ تبقى الحالة والمعاملات والصلاحيات محلية.
5. لا يعتمد Blnk أو Lerian Matcher أو Settler حاليًا: الأول يضيف PostgreSQL وRedis ودفترًا موازيًا، والثاني رخصته غير قابلة للتحقق كمفتوحة المصدر، والثالث لديه تضارب معلن في الرخصة ومتطلبات تشغيلية كبيرة.

لا تمنح هذه الدراسة موافقة تنفيذ أو تثبيت Dependency أو Migration أو نشر. كل موديول يجتاز Prototype وبوابة أمن ورخصة مستقلة قبل الدمج.

## 2. خط الأساس الموجود في النظام

اعتمد الجرد على مخطط Prisma وعقد OpenAPI والوحدات والاختبارات الحالية. القدرات الموجودة التي لا ينبغي إعادة بنائها أو استبدالها:

- الهوية والجلسات وRBAC وعزل الشركات والتدقيق والأحداث الأمنية.
- السنوات والفترات المالية ودليل الحسابات ومراكز التكلفة.
- `PostingEngine` والقيود اليدوية والترحيل والعكس ودفتر اليومية.
- فواتير المبيعات والمشتريات والإشعارات والذمم المدينة والدائنة.
- سندات القبض والصرف والتخصيص والقيمة الدفترية وفروق العملة المحققة.
- الضرائب الأساسية ومعدلاتها وحاسبة الضريبة الموحدة.
- المستودعات والأصناف والحركات والأرصدة والمتوسط المرجح وتكلفة المبيعات.
- القوائم المالية الحالية: المركز المالي، الدخل، ميزان المراجعة، دفتر الأستاذ، أعمار الذمم والتصدير.
- الطباعة التاريخية والاستيراد الجماعي والنسخ الاحتياطي والاستعادة والنشر الذري.

النتيجة: يمنع دمج أي موديول جاهز ينشئ Ledger أو مخزونًا أو هوية أو صلاحيات موازية لهذه المكونات.

## 3. قائمة الموديولات الناقصة مرتبة حسب الأولوية

### P0 — تكمل الرقابة المحاسبية الأساسية

| الترتيب | الموديول | النقص الفعلي | سبب الأولوية | قرار المصدر المفتوح |
|---:|---|---|---|---|
| 1 | المطابقة البنكية واستيراد الكشف | توجد حسابات بنك وسندات، لكن لا توجد خطوط كشف مستقلة أو مطابقة أو فروقات مفسرة أو إقفال كشف | رقابة يومية/شهرية على النقد، وتكشف القيود المفقودة والمكررة | ابدأ Pilot بالمكونات المقبولة في القسم 5 |
| 2 | الإقفال المالي للشهر والسنة | إغلاق وإعادة فتح الفترة موجودان، لكن لا توجد قائمة جاهزية موحدة أو carry-forward أو إقفال سنة أو إعادة تقييم عملة غير محققة | يمنع إغلاق فترة ناقصة ويكمل دورة السنة المالية | `XState` للانتقالات فقط؛ السياسات والقيد محليان |
| 3 | استكمال التقارير المالية والضريبية | لا يظهر تقرير تدفق نقدي أو ملخص/إقرار ضريبي أو حركة مراكز تكلفة مقارنة | التقارير الحالية لا تكفي حزمة إدارة/مراجع مكتملة | إعادة استخدام مكونات التصدير الحالية؛ لا حاجة ERP خارجي |

### P1 — ضرورية حسب طبيعة الشركة وحجم الرقابة

| الترتيب | الموديول | النقص الفعلي | شرط البدء | قرار المصدر المفتوح |
|---:|---|---|---|---|
| 4 | الموافقات وفصل المنشئ عن المعتمد | RBAC موجود، لكن لا توجد دورة Maker/Checker عامة للمستندات الحساسة | قبل المصروفات والأصول أو عند تعدد موظفي المالية | `XState` مناسب لمحرك حالات نقي خلف Adapter |
| 5 | الأصول الثابتة | لا يوجد سجل أصل أو رسملة أو جدول إهلاك أو استبعاد وربح/خسارة | عندما تملك الشركات أصولًا مادية أو برمجية ذات عمر | لا يوجد مرشح جاهز يطابق التقنية والدقة؛ راجع القسم 7 |
| 6 | مستندات المخزون التشغيلية | توجد حركات وفواتير، لكن لا توجد دورة استلام/تسليم/جرد مستقلة عن الفاتورة | عندما تختلف لحظة الاستلام/التسليم عن الفوترة | لا تدمج مخزون ERP موازٍ؛ استخدم workflow component فقط |
| 7 | المصروفات وعهد الموظفين والسلف | لا يوجد طلب مصروف أو إيصال أو عهدة وتسويتها | للشركات التي تصرف عبر الموظفين | `XState` للموافقة؛ الحساب والتسوية محليان |
| 8 | الميزانيات ومقارنة الفعلي | مراكز التكلفة موجودة من دون موازنات أو Budget vs Actual | عند الحاجة للرقابة الإدارية | لا يوجد محرك محاسبي خارجي مطلوب؛ Reporting read model محلي |
| 9 | التجميع والمعاملات بين الشركات | الشركات معزولة، لكن لا توجد تقارير مجمعة أو قيود إلغاء أو تسويات intercompany | فقط إذا كانت المؤسسة تدير مجموعة شركات مترابطة | لا يدمج قبل تعريف عملة التجميع وملكية الإلغاءات في ADR |

### P2 — يؤجل حتى يثبت احتياج تشغيلي

- القيود والفواتير المتكررة، والمصروفات المقدمة والمستحقة.
- أوامر البيع والشراء والعروض؛ هذه توسعة ERP وليست نقصًا يمنع المحاسبة الحالية.
- الفوترة الإلكترونية والتكامل الضريبي الخاص بالدولة؛ لا يبدأ قبل تحديد الدولة والجهة المنظمة والشهادة المطلوبة.
- الرواتب وPOS والتصنيع وCRM والتجارة الإلكترونية؛ ليست ضرورية لقلب النظام المحاسبي الحالي.

## 4. معايير التقييم المستخدمة

قيم كل مرشح وفق الآتي:

- رخصة OSI واضحة ومتوافقة، مع تفضيل MIT وApache-2.0 وBSD.
- مشروع نشط، إصدار مثبت، اختبارات وتوثيق ومجتمع استخدام قابل للقياس.
- يعمل مع Node.js 22 وTypeScript ولا يفرض PostgreSQL أو Redis أو خدمة دائمة جديدة.
- لا يستخدم `Number` للحساب المالي النهائي، ولا ينشئ Ledger أو قاعدة بيانات أو Tenant model موازيًا.
- يمكن عزله خلف Port/Adapter وحذفه أو استبداله من دون Migration على نوعه الداخلي.
- لا يرسل كشف البنك أو بيانات مالية خارج خادم النظام.
- له خطة ترقية ورجوع، وتوجد بصمة للحزمة المثبتة وملفات إشعار الرخصة.

## 5. المرشحون القابلون للدمج

بيانات الإصدارات والبصمات في هذا القسم هي لقطة بحث بتاريخ 26 أغسطس 2026، وتجب إعادة قراءتها من السجل قبل التثبيت.

### 5.1 `csv-parse` — قبول مبدئي لاستيراد CSV

- المصدر الرسمي: [adaltas/node-csv](https://github.com/adaltas/node-csv) و[وثائق CSV Parse](https://csv.js.org/parse/).
- الإصدار المقيم: `7.0.2`، رخصة MIT.
- المشروع يذكر تاريخًا يتجاوز عشر سنوات، واختبارات شاملة وESM/TypeScript. أظهر سجل npm نحو 76.6 مليون تنزيل في آخر شهر وقت الدراسة.
- بصمة الحزمة المقيمة: `sha512-uKZghv9UmPkMVLYy//KZ9HFAIJsl7wkhoEdIL0+rhuSY9pZQlhaeGEDPIe+/w7eh81MOql8Q/9+inAGWG6ZHYA==`.
- الاستخدام المسموح: قراءة CSV إلى صفوف نصية فقط؛ تحويل التاريخ والمبلغ والعملة والتوقيع يتم داخل `BankStatementParserAdapter` المحلي.
- القرار: **مرشح معتمد للـPrototype**.

### 5.2 `fast-xml-parser` — قبول مشروط لـCAMT.053

- المصدر الرسمي: [NaturalIntelligence/fast-xml-parser](https://github.com/NaturalIntelligence/fast-xml-parser).
- الإصدار المقيم: `5.11.0`، رخصة MIT، ونحو 3.1 آلاف نجمة وقت البحث. أظهر سجل npm نحو 346 مليون تنزيل في آخر شهر.
- بصمة الحزمة المقيمة: `sha512-9IGxMqvqLOnqP+Egi1nqDHKv5k8aZ7r9n558enxcucmyVGEBNPAU+MOg/8jPIS7rO7sSq4gFm1/nHtiaubMruw==`.
- توجد ثغرة DoS عالية في إصدارات أقدم من `5.3.6` وفق [GHSA-jmr7-xgp7-cmfj](https://github.com/advisories/GHSA-jmr7-xgp7-cmfj). الإصدار المقيم أعلى من الإصدار المصحح، لكن هذا لا يلغي ضوابط الإدخال.
- الضوابط الإلزامية: تثبيت الإصدار والبصمة، `processEntities: false`، رفض `DOCTYPE`، حد صارم للحجم والصفوف، parsing خارج المعاملة، واختبارات XXE/entity expansion وnamespace واختلاف إصدارات CAMT.
- الاستخدام المسموح: XML parsing فقط؛ Mapping من CAMT إلى العقد المحلي وقواعد المبلغ والعملة محلية.
- القرار: **مرشح معتمد للـPrototype بشروط أمنية**.

### 5.3 `ofx-data-extractor` — Pilot اختياري لـOFX/QFX

- المصدر الرسمي: [Fabiopf02/ofx-data-extractor](https://github.com/Fabiopf02/ofx-data-extractor).
- الإصدار المقيم: `1.5.0`، رخصة MIT، TypeScript ومن دون اعتماديات معلنة؛ يدعم strict/lenient والناتج normalized.
- بصمة الحزمة المقيمة: `sha512-Yjbx/Svqu18gItfd0D1GD23ibMB5cjZjTfNsJAcGFNHuTTLyIS8UDTM6RHi2QLXzjxa89MVFdYT+CUCuQ5uhCg==`.
- النشاط أفضل من مكتبات OFX القديمة، لكن المجتمع ما زال صغيرًا: نحو 23 نجمة و40 ألف تنزيل شهري وقت الدراسة.
- القرار: **لا يثبت مع المرحلة الأولى**. يدخل Prototype مستقل بملفات اصطناعية وله Adapter قابل للإزالة، ويعتمد فقط إذا طلبت الشركات OFX فعلًا.

### 5.4 `XState` — قبول مبدئي لسير الإقفال والموافقات

- المصدر الرسمي: [statelyai/xstate](https://github.com/statelyai/xstate).
- الإصدار المقيم: `5.32.6`، رخصة MIT، TypeScript، ومن دون اعتماديات تشغيلية معلنة. أظهر سجل npm نحو 22.1 مليون تنزيل في آخر شهر.
- بصمة الحزمة المقيمة: `sha512-WfA8WNrh6r9osuGwVm+aIPM4jmMW2LKHV1Yv9thYpOtL4HVF/kobh95K/O8v2jDCpDmP2EoY+6uvuqHXCZ6ZLw==`.
- الاستخدام المسموح: تعريف انتقالات صريحة واختبار المسارات فقط. Prisma هو مخزن الحالة، وRBAC هو صاحب قرار المستخدم، و`PostingEngine` وحده ينشئ القيد.
- لا تستخدم Actors أو effects لتنفيذ Network I/O أو كتابة قاعدة البيانات داخل آلة الحالات.
- القرار: **مرشح معتمد لـPrototype إقفال/موافقة نقي**.

### 5.5 `rrule` — مؤجل للمتكرر

- المصدر الرسمي: [jkbrzt/rrule](https://github.com/jkbrzt/rrule).
- الإصدار المقيم: `2.8.1`، BSD-3-Clause، TypeScript، ونحو 11.4 مليون تنزيل شهري وقت الدراسة.
- آخر تعديل منشور في npm كان في نوفمبر 2023؛ قد يعني الاستقرار أو انخفاض الصيانة، ويحتاج فحص issues/security قبل الاعتماد.
- الاستخدام المحتمل لاحقًا: توليد تواريخ مستندات متكررة فقط، لا إنشاء المستند أو ترحيله.
- القرار: **مؤجل إلى P2**.

## 7. دراسة الدمج الأولى: المطابقة البنكية

### 7.1 الملكية والحدود

- المالك: `Treasury`، كوحدة فرعية باسم `Bank Reconciliation`؛ لا ينشأ Microservice أو Bounded Context موزع.
- تظل `CashBankAccount` مملوكة لـTreasury.
- يقرأ الموديول الحركات النقدية والقيود من Query Ports، ولا يقرأ Prisma models لسياق آخر مباشرة.
- استيراد الكشف أو اقتراح Match لا ينشئ قيدًا ولا يعدل سندًا.
- أي رسم بنكي أو فائدة أو حركة مفقودة تتحول بعد قرار المستخدم إلى أمر Receipt/Payment/Manual Journal حالي، ثم تمر عبر `PostingEngine`.

### 7.2 نموذج البيانات المقترح للـPrototype

هذا تصور للدراسة وليس Migration معتمدًا:

- `BankStatementImport`: الشركة، حساب البنك، صيغة الملف، SHA-256، الفترة، العملة، الرصيد الافتتاحي والختامي، الحالة والنسخة.
- `BankStatementLine`: هوية البنك أو fingerprint، تاريخ القيد والقيمة، المبلغ الموقع كنص Decimal، العملة، المرجع والوصف، وحالة المطابقة.
- `BankReconciliationSession`: نطاق التاريخ، رصيد الدفاتر، رصيد البنك، الفرق، الحالة، المنشئ/المراجع، والنسخة.
- `BankReconciliationMatch`: اقتراح أو اعتماد، نوع `1:1` في الشريحة الأولى، درجة/سبب القاعدة، وروابط خطوط البنك وحركات النظام.

كل جدول يحمل `companyId` وعلاقات مركبة تمنع الربط بشركة أخرى. صفوف الكشف بعد اعتماد الاستيراد immutable؛ التصحيح يكون بإلغاء الدفعة واستيراد جديد لا بتعديل التاريخ المالي.

### 7.3 منافذ العزل المقترحة

```ts
interface BankStatementParserPort {
  sniff(input: Uint8Array): "CSV" | "CAMT053" | "OFX";
  parse(input: Uint8Array, profile: BankImportProfile): NormalizedBankStatement;
}

interface ReconciliationLedgerQueryPort {
  listTreasuryMovements(companyId: bigint, cashBankAccountId: bigint, range: DateRange): Promise<TreasuryMovementFact[]>;
}

interface ReconciliationMatcherPort {
  propose(statement: BankStatementFact[], books: TreasuryMovementFact[], rules: MatchRule[]): MatchProposal[];
}
```

لا تعبر أنواع أي مكتبة خارج Adapter، ولا تقبل المنافذ `number` للمبلغ؛ المبالغ نصوص canonical وتتحول إلى `Prisma.Decimal` عند الحد المحلي.

### 7.4 قواعد المطابقة للشريحة الأولى

1. مرجع فريد + مبلغ + عملة متطابقة.
2. مبلغ وعملة متطابقان مع نافذة تاريخ قابلة للضبط، ويظل الاقتراح للمراجعة عند غياب المرجع.
3. منع استخدام السطر أو الحركة في اقتراحين معتمدين.
4. لا fuzzy amount ولا نسبة tolerance ولا تحويل عملة في الشريحة الأولى.
5. لا auto-post ولا auto-adjust. الاعتماد يربط سجلات موجودة فقط.
6. تكتمل الجلسة عندما يصبح فرق البنك مفسرًا، وكل اعتماد يحمل Actor ووقتًا ونسخة وقاعدة.

تؤجل 1:N وN:1 وN:M إلى شريحة لاحقة بعد إثبات 1:1، لأنها تحتاج تخصيصات وتزامنًا أعقد وليست شرطًا لإطلاق الرقابة الأساسية.

### 7.5 الأمان والاعتمادية

- حد أولي: 512 كيلوبايت و5000 سطر، ويتغير فقط بقياس.
- رفض الملف المضغوط أو المشفر أو XML ذي `DOCTYPE` أو entities.
- parsing خارج Transaction، ثم إعادة التحقق من SHA-256 والمرجعيات داخل معاملة الاعتماد.
- تفرد `(companyId, cashBankAccountId, sha256)` لمنع إعادة الملف نفسه.
- لا يحفظ الملف الخام في الشريحة الأولى؛ تحفظ بصمته والصفوف normalized. إعادة الرفع يجب أن تنتج البصمة نفسها.
- لا يرسل الملف إلى AI أو SaaS أو API خارجي.
- Idempotency لكل اعتماد، وOptimistic `version` للجلسة، وقفل خطوط المطابقة بترتيب المعرف.
- Audit لكل استيراد واعتماد وفك ربط وإقفال، مع عدم تسجيل الوصف الكامل في السجلات التشغيلية.

### 7.6 خطة الـPrototype قبل أي Migration

1. تثبيت الحزم في فرع Spike منفصل بإصدارات وبصمات دقيقة وملفات NOTICE.
2. بناء Adapter بلا قاعدة بيانات يقرأ Fixtures اصطناعية لـCSV وCAMT.053؛ OFX اختياري.
3. اختبارات malformed/duplicate/XXE/entity expansion/encoding/timezone/negative amounts/decimal precision.
4. مقارنة ناتج Parser بعقد JSON محلي واحد وعدم تسريب نوع المكتبة.
5. Prototype matching نقي لـ1:1 على `Prisma.Decimal` مع نتائج حتمية قابلة لإعادة التشغيل.
6. قياس 5000 سطر على Node 22 وحد الذاكرة الفعلي في iFastNet.
7. بعد النجاح فقط: ADR صغير، مخطط Migration، OpenAPI، RBAC، Audit، واجهة مراجعة واختبارات MariaDB/MySQL.

### 7.7 معايير القبول

- نفس الملف والقواعد والدفاتر تنتج النتيجة نفسها.
- لا يمكن لشركة رؤية أو مطابقة كشف شركة أخرى.
- لا ينتج الاستيراد أو الاقتراح أي قيد محاسبي.
- لا يستخدم `Number` في المبلغ أو الفرق النهائي.
- إعادة الرفع/الأمر لا تضاعف الخطوط أو الروابط.
- فك الربط لا يحذف أثر المراجعة، وإقفال الجلسة لا يسمح بفرق غير مفسر.
- يستطيع النظام إزالة مكتبة Parser واستبدال Adapter من دون تغيير مخطط البيانات أو عقد API العام.

## 8. اتجاه دراسة الموديولات التالية

### الإقفال المالي

يبنى بعد Prototype المطابقة، لأن كشف البنك غير المسوى يجب أن يكون مانعًا أو تحذيرًا في قائمة الإقفال. يستخدم XState لوصف الحالات مثل `OPEN → PREPARING → REVIEWED → CLOSED` فقط. الفحص الفعلي للفترات والمخزون والذمم وفروق العملة والقيود يتم بخدمات النظام، وcarry-forward يمر عبر `PostingEngine`.

### الأصول الثابتة

لا يوجد مرشح JavaScript/TypeScript ناضج يجمع سجل الأصل والإهلاك والتصرف وDecimal وMySQL/MariaDB كحزمة قابلة للفصل. كود ERPNext وOpen Accounting مفيد لاستخراج حالات قبول، لكن دمجه المباشر غير مناسب للرخصة أو التقنية. القرار المرجح هو إعادة استخدام XState لدورة الأصل، مع حاسبة Decimal محلية صغيرة موثقة؛ يجب عدم استخدام Formula.js أو أي حاسبة تعتمد IEEE `Number` كنتيجة مالية حاكمة.

### مستندات المخزون

لا تدمج Medusa أو ERPNext أو Odoo كمخزون ثانٍ، لأن الرصيد والتقييم والحركة موجودة محليًا. يعاد استخدام محرك حالات للمستندات فقط، وتفوض لحظة الأثر إلى `Inventory` الحالي داخل معاملة `PostingEngine` عند وجود أثر محاسبي.

## 9. الترتيب التنفيذي الموصى به

1. Spike parsing والمطابقة البنكية بلا قاعدة بيانات.
2. موديول المطابقة البنكية 1:1 ومراجعة يدوية.
3. قائمة إقفال شهرية وسنوية مرتبطة بنتيجة المطابقة.
4. تدفق نقدي وملخصات ضريبية ومراكز تكلفة.
5. محرك الموافقات المشترك.
6. الأصول الثابتة.
7. مستندات المخزون المستقلة، ثم المصروفات والعهد.
8. الميزانيات والتجميع فقط عند وجود مستخدم فعلي لها.

هذا الترتيب يقلل المخاطر: يبدأ برقابة لا تنشئ قيودًا، ثم يستخدم نتيجتها لإغلاق الفترة، وبعدها يسمح بوحدات جديدة ذات أثر مالي.

## 10. قرار الانتقال إلى التنفيذ

الخطوة التالية الآمنة هي Prototype غير إنتاجي للمطابقة البنكية باستخدام `csv-parse@7.0.2` و`fast-xml-parser@5.11.0` فقط. لا ينشأ Migration أو endpoint أو شاشة قبل نجاح الـPrototype وفحص الرخص والبصمات والثغرات والحجم على بيئة Node 22.

لا يبدأ أي موديول آخر بالتوازي حتى تثبت حدود هذا النمط؛ الهدف اعتماد طريقة دمج قابلة للتكرار، لا فتح عدة سياقات غير مكتملة.
