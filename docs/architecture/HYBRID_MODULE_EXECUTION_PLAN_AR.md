# خطة تنفيذ المسار الهجين للموديولات

## 1. الهدف والقرار

تنفذ الموديولات الناقصة بمسار هجين:

- تبقى قواعد الأموال والحالات المحاسبية وملكية البيانات داخل النظام.
- تستخدم مكونات مفتوحة المصدر صغيرة للأعمال العامة مثل parsing وسير الحالات.
- يعزل كل مكوّن خلف Port/Adapter، ولا تعبر أنواعه أو مخططه إلى عقود النظام.
- لا يعتمد موديول خارجي كامل إذا أضاف Ledger أو قاعدة بيانات أو Tenant model أو خدمة دائمة موازية.
- ينفذ موديول واحد فقط في كل وقت حتى يكتمل ويثبت في الإنتاج؛ لا تفتح حلقات متوازية ناقصة.

أول مسار تنفيذ هو **المطابقة البنكية**، ثم **الإقفال المالي**، ثم **استكمال التقارير**. لا يبدأ P1 قبل إغلاق هذه المراحل الثلاث.

## 2. قواعد إدارة التنفيذ

### 2.1 حجم التغيير

- فرع مستقل لكل مرحلة قابلة للإصدار.
- PR واحد لا يخلط Prototype مع Migration إنتاجية.
- كل Migration لها توسعة واضحة، واختبار قاعدة فارغة وترقية من الإصدار المنشور.
- لا دمج لوحدة غير مكتملة خلف روابط ظاهرة للمستخدم؛ تستخدم Feature Flag عند الحاجة إلى إطلاق تدريجي.
- لا نشر إلا بطلب مباشر من المستخدم وبعد نجاح بوابات الإصدار كاملة.

### 2.2 بوابة اعتماد أي Dependency

قبل إضافته إلى `package.json`:

1. إعادة فحص الإصدار والرخصة والمستودع ووقت آخر تحديث.
2. تثبيت إصدار exact في `package-lock.json`؛ يمنع نطاق عائم للمكوّن المالي الجديد.
3. تسجيل رابط المصدر والإصدار وintegrity وسبب الاستخدام ومالك التحديث.
4. تشغيل تدقيق production dependencies وفحص Advisory خاص بالحزمة.
5. إثبات أن Adapter المحلي يمنع انتشار أنواع المكتبة.
6. إثبات خطة الإزالة: بديل Fake/Reference Adapter ينجح في اختبارات العقد نفسها.

### 2.3 تعريف الإنجاز العام

لا تعد أي مرحلة مكتملة قبل تحقق الآتي:

- كل وظائف النطاق مكتملة من API إلى الواجهة والتدقيق والصلاحيات.
- OpenAPI والحراس المولدة متطابقة، وDecimal/BigInt نصوص في النقل.
- لا كتابة جديدة إلى Ledger خارج `PostingEngine`، ولا وصول مباشر جديد بين السياقات.
- اختبارات Unit وIntegration وNegative وcross-company وIdempotency والتزامن مكتملة.
- Migration ناجحة من قاعدة فارغة ومن النسخة المنشورة على MariaDB 10.11 وMySQL 8.4.
- TypeScript والبناء والترجمة وعقد الواجهة وChromium وE2E والنسخ والاستعادة ناجحة.
- الرخصة وNOTICE وقرار التحديث والخروج موثقة.
- لا نشر قبل موافقة المستخدم المباشرة.

| 3 | واجهة المطابقة والإطلاق التدريجي | لا مكوّن أعمال جديد | M | 2 | E2E وإقفال كشف بفارق صفر |

## 4. المرحلة 0 — تجهيز نمط الدمج

### النطاق

- قالب تقييم موحد للحزمة: الرخصة، المصدر، الإصدار، integrity، النشاط، الثغرات، الاعتماديات وخطة الخروج.
- مجلد Fixtures اصطناعية خاص بالـSpike؛ يمنع استخدام كشف بنك حقيقي في المستودع.
- عقد Adapter Testing مشترك يتيح تشغيل مكتبة حقيقية وFake على الاختبارات نفسها.
- حارس معماري يمنع import مباشر للمكتبة خارج مجلد Adapter المعتمد.

### المخرجات

- `docs/architecture/adoptions/<package>.md` لكل Dependency مقبول.
- Test fixture policy تمنع أسرارًا وIBAN أو أسماء أو مبالغ حقيقية.
- أمر CI يفشل عند غياب إشعار الرخصة أو انتشار import خارج Adapter.

### معيار الخروج

يمكن إضافة أو إزالة Parser تجريبي من دون تعديل نوع Domain أو OpenAPI أو Prisma.

## 5. المرحلة 1 — Prototype المطابقة البنكية بلا قاعدة بيانات

### 5.1 الحزم المقيمة

- `csv-parse@7.0.2` لـCSV.
- `fast-xml-parser@5.11.0` لـCAMT.053 مع `processEntities: false` ورفض `DOCTYPE`.
- لا يثبت `ofx-data-extractor` في هذه المرحلة؛ يضاف Spike منفصل فقط إذا ظهر ملف OFX فعلي مطلوب.

### 5.2 التسليمات

1. عقد محلي `NormalizedBankStatement` لا يحمل أي نوع من المكتبتين.
2. اكتشاف الصيغة من المحتوى والامتداد مع رفض التعارض.
3. Adapter CSV بملف Profile يربط أسماء الأعمدة، ولا يخمن العملة أو اتجاه المبلغ بلا إعداد صريح.
4. Adapter CAMT.053 يقرأ الحساب والعملة والأرصدة وخطوط `BOOK` فقط ويحفظ المرجع الأقوى المتاح.
5. تطبيع التاريخ إلى تاريخ أعمال واضح والمنطقة الزمنية إلى metadata منفصلة.
6. مبالغ canonical strings؛ التحويل والحساب بـ`Prisma.Decimal` فقط.
7. fingerprint حتمي للسطر وSHA-256 للملف.

### 5.3 مصفوفة الاختبار

- CSV بفاصلة وفاصلة منقوطة وUTF-8 BOM وعناوين عربية/إنجليزية معرفة في Profile.
- مبلغ signed ومبلغ debit/credit منفصل، مع رفض وجودهما معًا بصورة متعارضة.
- CAMT.053 بإصدارات namespaces مختلفة، وأرصدة opening/closing، وعملة مخالفة.
- ملفات malformed، مكررة، أكبر من 512KB، أكثر من 5000 سطر، وXML يحوي DTD/entities.
- فروق decimal كبيرة وصغيرة، أرقام سالبة، صفر، أكثر من منازل العملة، وتاريخ غير صالح.
- قياس CPU والذاكرة والمدة على Node 22 للحد الأعلى.

### 5.4 قرار Go/No-Go

**Go** إذا:

- كل Fixtures تنتج العقد المحلي الصحيح حتميًا.
- لا يتجاوز Parser ميزانية الذاكرة/المدة، ولا يمكنه حجب العملية بمدخل صغير خبيث.
- تستطيع Fake Adapter اجتياز Contract tests نفسها.
- لا ثغرة غير معالجة أو ترخيص/نسخة غير مثبتة.

**No-Go** إذا فشل أي شرط؛ عندها يبنى CSV Adapter على مكوّن مقبول آخر أو يقتصر الإصدار الأول على CSV، ولا ينتقل الفشل إلى كود الإنتاج.

## 6. المرحلة 2 — Backend المطابقة البنكية 1:1

### 6.1 تصميم المجال

يضاف تحت `apps/api/src/treasury/reconciliation`:

- `BankStatementImport` و`BankStatementLine`.
- `BankReconciliationSession` و`BankReconciliationMatch`.
- `BankStatementParserPort` و`ReconciliationLedgerQueryPort` و`ReconciliationMatcherPort`.
- matching engine محلي pure، ويستخدم Decimal والمفاتيح المرتبة.

لا يكتب Parser في Prisma، ولا يقرأ Matcher Ledger مباشرة؛ كل قراءة تمر عبر Query Port مملوك.

### 6.2 حالات الاستخدام

1. Preview ملف بلا حفظ.
2. Commit استيراد validated مع Idempotency وبصمة.
3. إنشاء جلسة لحساب بنك ونطاق تاريخ.
4. توليد اقتراحات 1:1 بالقواعد المعتمدة.
5. اعتماد اقتراح أو ربط يدوي أو فك ربط مع Audit.
6. تصنيف سطر غير مطابق: حركة معلقة، رسم/فائدة، خطأ بنك، أو يحتاج مستندًا محاسبيًا.
7. إقفال الجلسة فقط عند فرق صفر أو تفسير معتمد لكل فرق وفق السياسة.

### 6.3 قواعد الشريحة الأولى

- Exact reference + amount + currency هو الاقتراح الأعلى.
- Exact amount + currency ضمن نافذة تاريخ لا يعتمد تلقائيًا.
- لا tolerance للمبلغ، ولا fuzzy amount، ولا تحويل عملة.
- لا يستخدم سطر بنك أو حركة دفاتر في Match معتمد آخر.
- لا ينشئ Match قيدًا أو سندًا.
- “إنشاء حركة مفقودة” يفتح أمرًا صريحًا في خدمة Receipt/Payment/Journal الحالية؛ اعتمادها يمر عبر `PostingEngine` ثم يعاد ربطها.

### 6.4 قاعدة البيانات والتزامن

- علاقات مركبة تحمل `companyId` في كل رابط.
- unique على بصمة الاستيراد داخل حساب الشركة.
- `version` للجلسة والاستيراد، وconditional updates للاعتماد والفك والإقفال.
- قفل الجلسة ثم خطوط البنك تصاعديًا ثم حركات النظام تصاعديًا.
- لا file parsing أو Network I/O داخل Transaction.
- Retention واضح للـpreview والدفعات الملغاة؛ الصفوف المعتمدة لا تحذف صلبًا.

### 6.5 API والصلاحيات

- `bank_reconciliation.view`
- `bank_reconciliation.import`
- `bank_reconciliation.review`
- `bank_reconciliation.close`

لا تورث صلاحية `close` تلقائيًا لكل من يملك `import`. يحدد Seed الدور الإداري، وتختبر الأدوار المخصصة.

### 6.6 معيار الخروج

- لا أثر Ledger ناتج من الاستيراد أو المطابقة وحدهما.
- شركتان لا تستطيعان رؤية أو ربط ملفات/حركات إحداهما بالأخرى.
- طلبان متزامنان لا يعتمدان السطر نفسه.
- إعادة الاستيراد أو إعادة الأمر تنتج أثرًا واحدًا.
- إقفال الجلسة يثبت فرقًا صفريًا أو تفسيرًا محكومًا قابلًا للتدقيق.

## 7. المرحلة 3 — واجهة المطابقة والإطلاق

### التسليمات

- صفحة اختيار حساب البنك والفترة ورفع/معاينة الملف.
- جدولان متقابلان: كشف البنك وحركات النظام، مع اقتراح واضح وسبب المطابقة.
- إجراءات اعتماد/فك/ربط يدوي، ومرشحات للحالة والمبلغ والتاريخ.
- ملخص opening/closing/book balance/difference، ومنع الإقفال عند عدم الجاهزية.
- العربية والإنجليزية أولًا مع اتجاه RTL/LTR، ثم تطابق مفاتيح اللغات الأربع الحالية.
- تصدير تقرير المطابقة والاستثناءات دون كشف بيانات حساسة في logs.

### الإطلاق التدريجي

1. Feature flag على مستوى البيئة والشركة.
2. شركة تجريبية واحدة وملفات اصطناعية/منزوعة الحساسية.
3. تشغيل Shadow: اقتراحات فقط دون اعتماد.
4. تفعيل الاعتماد اليدوي بعد مقارنة عينة كاملة.
5. تفعيل إقفال الجلسة بعد مراقبة معدل unmatched والتكرار والأخطاء.

### معيار الخروج

رحلة E2E من رفع كشف إلى إقفال جلسة بفارق صفر، وإثبات أن إزالة Feature Flag تعيد النظام إلى سلوكه السابق من دون أثر على Ledger.

## 8. المرحلة 4 — الإقفال الشهري والسنوي

### 8.1 Prototype `XState`

- تثبيت إصدار exact بعد إعادة بوابة الرخصة والأمن.
- آلة pure للحالات `OPEN → PREPARING → REVIEWED → CLOSED` مع مسارات رفض وتصحيح.
- Types المكتبة لا تعبر Context، ولا Actors/effects للكتابة أو الشبكة.
- الحالة المخزنة و`version` وActor وRBAC محلية.

### 8.2 قائمة الجاهزية

- الفترات الفرعية مفتوحة/مغلقة بترتيب صحيح.
- جلسات البنك مكتملة أو استثناء معتمد.
- فواتير/سندات/قيود مسودة أو غير مرحلة.
- أرصدة مخزون غير مقيّمة أو سالبة أو حركات غير معكوسة بصورة صحيحة.
- ذمم غير متوازنة مع Ledger.
- أسعار صرف لازمة وإعادة تقييم العملة غير المحققة.
- حساب أرباح مبقاة معتمد للإقفال السنوي.

### 8.3 الإقفال السنوي

- Close pack يحفظ أرقام/بصمات التقارير الحاكمة.
- إعادة تقييم FX تنشئ Posting Plan محليًا وتُعكس حسب السياسة في الفترة التالية.
- carry-forward يمر عبر `PostingEngine`، وله Idempotency وعكس صريح قبل السماح بإعادة الفتح.
- يمنع إعادة فتح سنة بعد carry-forward بلا عكس منضبط.

### معيار الخروج

سباق `post-vs-close` و`reconciliation-vs-close` و`carry-forward-vs-reopen` لا ينتج حالة جزئية، وتنجح الترقية والرجوع التشغيلي والنسخ والاستعادة.

## 9. المرحلة 5 — اكتمال التقارير

الترتيب داخل المرحلة:

1. التدفق النقدي بالطريقة غير المباشرة من Ledger مع Mapping محكوم للحسابات.
2. ملخص الضريبة حسب النوع والفترة وحالة المستند، ثم نموذج إقرار خاص بالدولة فقط بعد تحديد jurisdiction.
3. تقرير مركز التكلفة وحركته والفعلي، قبل إضافة الموازنة.
4. Close pack موحد يجمع ميزان المراجعة والمركز المالي والدخل والتدفق والمطابقة والاستثناءات.

كل تقرير مشتق من الحقائق الحالية ولا يملك دفترًا أو أرقامًا مالية قابلة للتعديل. تستخدم بنية CSV/XLSX/PDF الموجودة ولا يضاف مولد تقارير ثانٍ.

## 10. المرحلة 6 — محرك الموافقات

- يعاد استخدام `WorkflowStatePort` نفسه المبني حول XState.
- أول تطبيق: اعتماد إقفال الفترة والسنة؛ لا يبدأ بالمستندات المالية كلها دفعة واحدة.
- Maker لا يعتمد عمله عند تفعيل سياسة الفصل، ويثبت Checker مستقلًا.
- القرار محفوظ مع Actor ووقت ونسخة وسبب؛ لا يحل محرك الحالات محل RBAC أو Audit.
- بعد إثباته يطبق على الأصول والمصروفات ومستندات المخزون فقط بحسب احتياج كل Context.

## 11. مراحل P1 اللاحقة

### الأصول الثابتة

1. السجل والفئات والحسابات والعمر والقيمة المتبقية.
2. الرسملة من فاتورة أو قيد افتتاحي.
3. جدول إهلاك Decimal وحفظ Snapshot لكل تشغيل.
4. ترحيل الإهلاك عبر `PostingEngine` وعكسه.
5. نقل/تحسين/انخفاض قيمة/استبعاد واحتساب الربح أو الخسارة.

### مستندات المخزون

1. إذن استلام وتسليم وتحويل وجرد.
2. سياسة صريحة تحدد هل الفاتورة أم الإذن ينشئ حركة المخزون في كل شركة.
3. unique source event يمنع أثر الفاتورة والإذن معًا.
4. التقييم يظل في `Inventory` الحالي، والقيد يظل في `PostingEngine`.

### المصروفات والعهد

1. طلب مصروف وإيصال وموافقة.
2. عهدة موظف كذمة مستقلة لا كحساب حر فقط.
3. صرف العهدة عبر Treasury وتسويتها بفواتير/مصروفات ورد المتبقي.
4. منع إقفال الفترة عند عهد منتهية أو غير مفسرة وفق سياسة الشركة.

## 12. المخاطر وقرارات التوقف

| الخطر | الإشارة | الإجراء |
|---|---|---|
| Dependency غير ناضج | إصدار غير مثبت، ثغرة، صيانة متوقفة | أوقف الاعتماد واستخدم Adapter بديل أو نطاقًا محليًا محدودًا |
| انتشار أنواع المكتبة | Imports خارج Adapter أو Migration تعتمد على نوعها | ارفض PR وأضف حارسًا معماريًا |
| دفتر/بيانات موازية | خدمة خارجية تحتاج نسخ Ledger | أوقف التنفيذ واطلب ADR؛ الافتراضي الرفض |
| كلفة Adapter أكبر من البناء المحلي | تجاوز التكييف 30–40% من نطاق الموديول | أعد التقييم وابنِ الجزء المالي الصغير محليًا |
| أداء parsing غير آمن | تجاوز CPU/ذاكرة/وقت الحد | قلص الصيغ أو انقل parsing إلى worker مع deadline بعد ADR صغير |
| تضاعف أثر مالي | مصدران يستطيعان الترحيل لنفس الحدث | لا دمج قبل unique invariant واختبار التزامن |

## 13. مؤشرات النجاح

- زمن إضافة صيغة كشف جديدة يقتصر على Adapter وFixtures، من دون تعديل Domain/API.
- نسبة imports المكررة ذات الأثر الإضافي تساوي صفرًا.
- نسبة Match المعتمد خطأ في العينة التجريبية تساوي صفرًا قبل أي توسع تلقائي.
- لا قيود ينشئها Parser أو Matcher أو XState مباشرة.
- لا ثغرات High/Critical في production dependencies الجديدة عند الدمج.
- جميع بوابات MariaDB/MySQL والنشر والنسخ والاستعادة تبقى خضراء.
- كل مرحلة تقلل الأعمال اليدوية ولا تضيف مصدر حقيقة أو خدمة تشغيلية غير لازمة.

## 14. أول حزمة عمل عند بدء التنفيذ

عند طلب البدء بالتنفيذ، تكون الحزمة الأولى فقط:

1. قالب اعتماد `csv-parse` و`fast-xml-parser` وNOTICE.
2. تثبيت الإصدارين exact في فرع Spike.
3. عقد `NormalizedBankStatement` وPort محلي.
4. Fixtures اصطناعية واختبارات Contract/Security/Performance.
5. تقرير Go/No-Go.

لا تشمل هذه الحزمة Prisma أو Migration أو OpenAPI أو واجهة مستخدم، ولا تنشر. الانتقال إلى المرحلة 2 يحتاج نجاحها وتسجيل القرار.
