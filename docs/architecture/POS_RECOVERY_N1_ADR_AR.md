# N1 — استرجاع نتيجة POS عبر إعادة التحميل دون إعادة البيع

## تعديل W1 المعتمد محليًا — 31 أغسطس 2026

اعتمد المنسق `01a05783-e720-7ed0-a107-4a372bd53202` ربط هذه الشريحة في المنتج،
ثم اعتمد حالة `REJECTED` ثالثة للرفض النهائي المثبت. هذا القسم يحل محل القيود
التاريخية أدناه التي كانت تصف شريحة غير مركبة بعقد ثنائي فقط. لا تتغير الملكية
أو المخطط أو الاحتفاظ الافتراضي البالغ 24 ساعة، ولا تنفذ هذه الدفعة نشرًا.

العقد المركب `POST /api/v1/pos/checkouts/recovery` يقبل `attemptKey` UUIDv4 فقط؛
الهوية والشركة من جلسة الخادم. Infrastructure تبحث عن
`unique(companyId,userId,operation,keyHash)`؛ `keyHash=SHA256(attemptKey)`، بينما
`requestFingerprint` بصمة الجسم المالي المستقلة. يعاد التفويض الفعلي قبل القراءة
وبعدها: `pos.checkout`، واستحقاق POS، وCSRF. يحمل `CONFIRMED` الإقرار الأصلي
المطابق لحارس OpenAPI المولد، ويحمل `REJECTED` القيمة
`{code: POS_CHECKOUT_REJECTED, reason}` من قائمة مولدة محدودة. يشمل `UNKNOWN`
الغياب أو الانتهاء أو الحالة غير المكتملة أو الاستجابة التالفة أو الهوية المختلفة
أو الفشل المبهم. لا يُستخدم معرف مستند محاسبي بدل `result.invoice.id`.

حل الرفض ذو مرحلتين داخل `IdempotentCommandExecutor`، وباشتراك POS الصريح فقط:

1. بعد حجز المفتاح، يجوز لخطأ `SalesInvoiceError/ReceiptError` مسمى ومسموح
   خرج من `work` أن يصبح **مرشح رفض**. عودة `TransactionExecutor` بالخطأ نفسه
   ليست دليل rollback؛ قد يبتلع عميل Prisma فشل نقل rollback. لا يؤهل هذا المسار
   خطأ deadline أو إلغاء أو commit مبهم أو validation/auth أو P2002 أو idempotency/version.
2. بعد العودة، تبدأ معاملة Infrastructure ثانية بالموعد النهائي الأصلي نفسه.
   تقرأ المفتاح الكامل وتتنافس بـINSERT فقط لحفظ رفض؛ لا upsert أو update لسجل قائم،
   ولا أي إعادة للعمل المالي. غياب القراءة ليس دليلًا. INSERT الفائز يلتزم بعد
   تحرير قفل المعاملة القديمة، أو يفشل؛ وبهذا لا يمكنه تجاوز نجاح ملتزم سابق.
3. إذا فاز طلب مالي منافس، تُعاد نتيجته الأصلية. اختلاف البصمة يظل 409، والحجز
   غير المكتمل يبقى مبهمًا. بعد P2002 تُقرأ النتيجة خارج snapshot الفاشلة بقراءة
   جديدة، مع فحص deadline قبلها وبعدها. تبقى إعادة المحاولة عند deadlock لدى
   المنفذ المركزي، ضمن الميزانية نفسها.
4. سجل الرفض `COMPLETED/responseStatus=422` يحمل حصريًا
   `{kind:"POS_CHECKOUT_REJECTION",version:1,rejection:{code,reason}}`.
   يفحص `resolveExisting` الحالة ورمز الاستجابة وdecoder الرفض قبل استعادة النجاح؛
   لا يحوّل JSON الرفض إلى `T` ناجح. الحجز والمرحلتان يستخدمان تاريخ انتهاء واحدًا.
5. لا تخرج استجابة 422 المخصصة قبل commit السجل أو قراءة فائز ملتزم. يبقى فشل
   finalization أو ACK المفقود أو انتهاء المهلة خطأً مبهمًا، ولا يُستخدم خطأ المجال
   الأصلي وعدًا بعدم الأثر. لا تُعاد رسالة الخطأ الخام أو body أو scope أو المفتاح.

في الواجهة، لا تكفي استجابة HTTP 422 وحدها لتحرير العلامة، حتى بالكود المخصص.
يطلب الكود المخصص قراءة recovery واحدة؛ و`REJECTED` المتحقق من الخادم وحده يفتح
إجراء مراجعة صريحًا. يحذف هذا الإجراء العلامة تحت Web Lock ويحافظ على سلة الذاكرة
إن بقيت؛ بعد reload لا تُستعاد البنود. يرسل الضغط التالي فعلًا جديدًا بمفتاح UUID
جديد، ولا يوجد financial POST تلقائي أو replay بعد reload أو زر force-clear
لحالة `UNKNOWN`. تبقى FIFO وprofile والنطاق حاكمة.

**بوابة التفعيل والرجوع:** يتجاهل backend القديم `responseStatus`؛ يمنع تشغيله
بالتوازي مع كاتب tombstone الجديد. قبل أول تفعيل، يجب تصريف الطلبات وإيقاف الجيل
القديم كله، ثم تشغيل قارئ الجيل المتوافق وكاتبه معًا، وإغلاق تبويبات UI القديمة
التي لا تشارك Web Locks. لا rollback إلى backend لا يفك tombstones ما دامت موجودة؛
لا يحذفها rollback ولا يمتد احتفاظها تلقائيًا. هذه شروط تفعيل، وليست أعمال نشر نُفذت.

بوابة DB الحقيقية منفصلة: سباقات success/rejection وثلاثة متنافسين، وACK مفقود،
ومهل، وrollback لكل invoice وreceipt وledger وstock وaudit وarchive، ومحركا
MySQL 8.4 وMariaDB 10.11. لا يُنسب نجاح unit أو HTTP fixtures أو SSR أو hook harness
إلى قبول DB أو متصفح Web Locks. نتائج هذه الدفعة وحدودها التشغيلية في
`../W1_POS_RECOVERY_HANDOFF_AR.md`.

## القرار والملكية

تضاف قراءة نتيجة فقط؛ لا جدول أو عمود أو migration أو كتابة مالية أو Outbox.
يملك POS تفسير نتيجة Checkout، ويملك Application Infrastructure قراءة سجله عبر
`PosRecoveryQueryPort`. تنفيذ adapter وتسجيله من ملكية المنسق، وليس في هذه النسخة.

المنفذ في `apps/api/src/pos/recovery-types.ts`:

```ts
find({ companyId, userId, operation: "COMPLETE_POS_CHECKOUT", attemptKey }):
  Promise<null | {
    companyId: bigint; userId: bigint; operation: string; status: string;
    expiresAt: Date; responseBody: unknown;
  }>
```

يشتق adapter بصمة SHA256 من attemptKey ويبحث بالفهرس المركب الكامل. لا قائمة
عامة ولا scan للمبيعات ولا fallback إلى company+key أو أحدث عملية. يعيد scope
للدفاع الإضافي، ولا يعيد fingerprint أو keyHash أو المفتاح الخام في HTTP.

`PosRecoveryService.recover(authorize, attemptKey)` يستدعي callback التفويض قبل
القراءة وبعدها. يرجع callback سياق `ActorContext` من الجلسة الحالية فقط، ويفرض
`pos.checkout` والاستحقاق وCSRF في كل استدعاء. اختلاف المستخدم أو الشركة بين
القراءتين أو دليل لا يطابق نطاق الطلب يبقى UNKNOWN. رفض التفويض ينتقل إلى معالج
HTTP المعتاد، ولا يترجم إلى فشل البيع. لا تضاف صلاحية ولا ترث `pos.view` حق الاسترجاع.

## العقد المرسل للمنسق

- `POST /api/v1/pos/checkouts/recovery`، قراءة بلا أثر جانبي، مع جلسة وCSRF وno-store
  والحماية المركزية وحد المعدل والمهلة القائمة.
- جسم strict وحيد `{ "attemptKey": "UUIDv4" }`. المفتاح في الجسم لا URL أو query
  أو route param، ولا audit أو error أو log. المفاتيح الجديدة تأتي من crypto.randomUUID.
- الرد200 أحد شكلين فقط: `{ "outcome": "UNKNOWN" }` أو
  `{ "outcome": "CONFIRMED", "result": PosCheckoutResult }`.
- missing / IN_PROGRESS / منتهي الاحتفاظ / responseBody ناقص أو غير صالح كلها UNKNOWN.
  ليست 404 أو FAILED أو إذنًا لبيع بديل. التفويض والنقل لهما أخطاء HTTP العادية.
- النتيجة المؤكدة إقرار **الأمر الأصلي** من السجل؛ قد تكون الفاتورة/السند عُكسا لاحقًا.
  لا تعرض POSTED القديمة بوصفها الحالة الحالية، ولا تفترض أن النقد لا يزال غير معكوس.
- فحص النتيجة الحالي projection دفاعي محدود، ليس schema عامًا بديلًا. يحافظ على
  Decimal كنص، ويتحقق من BIGINT غير الموقع والوقت ISO والمستندين POSTED وحقولهما
  وقوائم القيود المحدودة، ويحذف أي حقول إضافية. عند التركيب يطابقه المنسق أو يستبدله
  بالـvalidator المولد لـPosCheckoutResult؛ لا تبقى نسختان مستقلتان من عقد عام.
  حراس الطلب/الرد وOpenAPI وتغطية operations لم تضاف هنا.

## آلة الحالة والمتصفح

| الحالة | ما يسمح به |
|---|---|
| initializing | لا إرسال ولا مسح سلة |
| ready | بدء محاولة جديدة صريحة بعد مراجعة السلة والصلاحيات |
| pending | callback إرسال واحد فقط؛ لا ضغط مزدوج ولا قراءة متوازية |
| unknown | قراءة النتيجة يدويًا فقط؛ لا replay أو new sale |
| checking | قراءة واحدة قيد التنفيذ؛ لا كتابة ولا قراءة مكررة |
| confirmed | عرض إقرار الخادم؛ newSale صريح فقط |
| blocked | توضيح مشكلة التفويض/التخزين/تنسيق التبويبات؛ لا بيع |

المفتاح المحلي `pos-recovery:v1:[userId,companyId]`، وقيمته فقط
`{version:1,attemptKey,startedAt}`. حدها256 محرفًا. لا جسم/أسطر/مبلغ/عميل/نتيجة/
كلمة مرور/CSRF/session token. لا يعد المفتاح إذن وصول. snapshot العلني للمكوّن لا
يحمل المفتاح أو النطاق؛ النتيجة المؤكدة تبقى في الذاكرة فقط.

قبل callback الإرسال يحصل controller على Web Lock خاص بالنطاق؛ يقرأ العلامة،
ويمنع بدء ثانية إذا وجدت، ثم يكتب العلامة ويعيد قراءتها قبل الإرسال. فشل القراءة
أو quota أو JSON تالف أو عدم حفظ الكتابة فعليًا يمنع الإرسال. القفل متطلب للمسار:
غياب Web Locks يفشل مغلقًا مع رسالة، دون fallback إلى مسار بيع غير محمي.
هذه ليست معاملة موزعة بين المتصفح والخادم: انهيار بعد حفظ العلامة وقبل الإرسال
يترك UNKNOWN محافظًا، لأن عدم وجود نتيجة ليس إثباتًا بأن الإرسال لم يحدث.

تستعيد إعادة التحميل العلامة في unknown، ولا يمكنها استعادة الجسم أو استدعاء
callback القديم. مرور23 ساعة أو تراجع الساعة يغير التوضيح فقط، ولا يمسح العلامة.
القراءة بعد23 ساعة ممكنة، لكن الخادم يرفض تأكيد سجل بلغ expiresAt. لا يقدم المسار
نفسه replay حتى داخل الذاكرة؛ جميع الإخفاقات بعد حجز العلامة، بما فيها رفض أول
422، تبقى مقفلة دون عقد خادمي يثبت فشل المحاولة. هذه كلفة أمان مقصودة للشريحة
الثنائية؛ تتطلب الحالات غير المحسومة مراجعة مسؤول، ولا يوجد زر تجاوز للقفل.

storage event إشارة لإعادة قراءة **النطاق الحالي** فقط؛ لا يقرأ newValue كحقيقة.
وجود علامة قد يقفل ready، لكن حذفها أو تبديلها لا يفتح قفلًا قائمًا ولا يؤكد بيعًا.
يتحقق newSale من العلامة نفسها تحت القفل ويحذفها فقط بعد إقرار خادمي متحقق.
تغيير المستخدم/الشركة/الصلاحيات أو logout يلغي الإشارات ويغير generation فورًا؛
لا تظهر النتائج المتأخرة في النطاق الجديد، وتبقى علامة النطاق القديم محفوظة.

## ربط PosPage المطلوب عند المنسق

1. إنشاء controller مرة واحدة لكل تجربة POS مصرح بها، وحقن read port بعد نشر
   OpenAPI محليًا في نفس حزمة التركيب. read يرسل attemptKey فقط مع signal ومدة
   محددة، بلا retry للكتابة أو مفتاح في عنوان الطلب.
2. تفعيل النطاق قبل عرضه، والاشتراك عبر useSyncExternalStore. عند تغيير الجلسة أو
   صلاحياتها/استحقاقها: activate بالنطاق الجديد أو null وإلغاء السابق فورًا؛
   يفضل الاحتفاظ بحد remount الحالي حسب الهوية والشركة والصلاحيات/الموديولات.
   dispose ينظف المستمع والإشارات ولا يحذف storage.
3. شرط تعديل السياق والسلة/إضافة مسح/Checkout هو ready بالإضافة لحراسة legacy
   attempts القائمة؛ لا تشغل مساري الإرسال معًا ولا تعتبر absence في أحدهما كفاية.
4. بعد انتهاء FIFO وكل قراءات profile، تجميد الجسم الحالي داخل closure ذاكرية،
   ثم `begin((key,signal) => api('/pos/checkouts', {method:'POST',body,
   idempotencyKey:key,signal,...}))`. القيمة الراجعة boolean تثبت هل استدعي الإرسال،
   وليست نجاح البيع. المصدر الوحيد للعرض هو state الحالية المؤكدة.
5. `PosRecoveryPanel` يتلقى state وlocale وcanCheckout وbarcodePending،
   وonCheck يستدعي check، وonNewSale يعيد فحص FIFO/profile ثم ينتظر newSale()؛
   لا يمسح السلة أو يعيد scanner إلى التركيز إلا إن أعاد true.
6. لا يعاد إنشاء سلة أو سعر من النتيجة بعد reload. يعرض الرقم والإجمالي النصي
   الخادمي فقط، ولا تُلحق عملة من سياق حالي قد لا يطابق الأمر الأصلي.

## Barcode Impact

لا يضيف الاسترجاع parser أو lookup أو تعريف باركود أو إخراجًا مطبوعًا. يجب أن
يبقى `InventoryBarcodeScanner` وFIFO وresolve المقيد بالنشاط ومراجعة الصلاحيات
وleading zeros كما هو. تعديل البنود/المسح ممنوع أثناء recovery، وبدء البيع
ونقل السلة إلى بيع جديد ينتظران المسح وقراءات ملف السعر. المكوّن يوفر حارس
barcodePending لزر البيع الجديد، لكن فحص scanner الحقيقي في callback مسؤولية
التركيب ويجب اختباره في PosPage. لا يعتبر اختبار SSR/port هنا إثبات HID أو
Bluetooth أو كاميرا أو طابعة أو رحلة Barcode فعلية.

## الحدود وبوابة القبول

لا schema أو ترحيل أو Ledger/Inventory/Treasury writes جديدة، ولا شبكة داخل معاملة،
ولا Outbox أو مكتبات جديدة. اختيرت واجهات المتصفح والمنافذ المحلية لأن مكتبة ERP
أو queue جديدة لا تحل إثبات النتيجة ولا تضيف مصدر حقيقة مناسبًا.

ليست هذه استعادة بعد تلف/حذف بيانات الموقع أو فقد الجهاز أو خارج المتصفح نفسه،
ولا من تبويب إصدار قديم لا يكتب marker، ولا ترميمًا لمحاولات قديمة ضاعت قبل
تفعيل الشريحة. يلزم المنسق خطة انتقال تمنع التبويبات القديمة من bypass الحراسة.
حد الاحتفاظ24h ليس SLO؛ correlation الدائم على PosSale مؤجل إلى ADR مستقل.

القبول النهائي يحتاج adapter كامل العزل واختبارات HTTP فعلية للـCSRF/RBAC/entitlement
والعقد والمهل وعدم التخزين، واختبارات متصفح حقيقية مع reload وتبويبين وتغيير النطاق
على أربع لغات و390/768/1440، وقبول Barcode الفعلي عند التركيب. بوابتا MariaDB10.11
وMySQL8.4 وDB E2E تبقيان شرطًا مستقلاً. لا تساوي unit/SSR هذه الأدلة.
