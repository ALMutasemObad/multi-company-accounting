# شريحة إنشاء المستخدم من الموظف

## نطاق المرحلة الأولى

1. قائمة موظفين مؤهلين معزولة بالشركة ومحدودة إلى 100 نتيجة: `ACTIVE` أو
   `ON_LEAVE` و`userId IS NULL`.
2. إنشاء حساب من الموظف مع بريد وكلمة مرور مؤقتة، دون حقول اسم في الطلب.
3. ربط حساب تأسيسي/قديم نشط بموظف غير مرتبط، مع توحيد لقطة الاسم.
4. إظهار رقم الموظف واسمه وحالته في قائمة المستخدمين.
5. إزالة الربط من نموذج إنشاء/تعديل الموظف وإبقاء الرابط الحالي للعرض فقط.

خارج النطاق: دعوات البريد، فرض تغيير كلمة المرور عند أول دخول، تعطيل عضوية الشركة
تلقائيًا عند إنهاء الخدمة، والمزامنة العامة لتغييرات الاسم بعد الربط. هذه تحتاج
سياسات دورة حياة مستقلة ولا يجوز افتراضها ضمن CRUD.

## نموذج البيانات والملكية

لا يضاف جدول أو عمود. تستخدم العلاقة الحالية:

```text
Employee(companyId, userId?)
    -> UserCompany(userId, companyId)
    unique(userId, companyId)
```

- HR يقرأ ويقفل ويحدث `Employee` عبر `EmployeeAccountPort`.
- Identity ينشئ ويقفل ويحدث `User/UserCompany` عبر `IdentityAccountPort`.
- `WorkforceAccessService` منسق تطبيق لا يملك جدولًا ولا يكتب Prisma models
  الخاصة بالسياقين مباشرة.

## حالات الاستخدام والأخطاء

- `GET /users/employee-options`: يتطلب `users.create`.
- `POST /users`: يتطلب `users.create` وCSRF و`Idempotency-Key`.
- `POST /users/{userId}/employee-link`: يتطلب `users.update` وCSRF وIdempotency.
- موظف غير موجود/شركة أخرى: `404 EMPLOYEE_NOT_FOUND`.
- موظف منتهي: `422 EMPLOYEE_TERMINATED`.
- موظف أو مستخدم مرتبط مسبقًا أو بريد مكرر: `409` بسبب واضح.
- إعادة المفتاح والجسم نفسيهما تعيد النتيجة نفسها؛ اختلاف الجسم يعيد
  `IDEMPOTENCY_MISMATCH`.

## العزل والتزامن

- تقيد كل قراءة وربط بـ`companyId`، ولا تقبل UUID من شركة أخرى.
- ترتيب الأمر: Idempotency ثم قفل Employee ثم قفل/إنشاء عضوية Identity ثم الربط
  والتدقيق. لا Network I/O داخل المعاملة؛ Argon2 ينفذ قبلها.
- قفل الموظف وشرط `userId IS NULL` يمنع حسابين متزامنين للموظف نفسه، والتفرد
  المركب يمنع ربط المستخدم بموظفين داخل الشركة.
- أي تعارض بريد يعيد المعاملة كاملة، فلا يبقى موظف مرتبطًا بحساب لم ينشأ.

## الواجهة والترجمات

- نافذة المستخدم الجديد تعرض الموظف أولًا، ثم البريد وكلمة المرور فقط.
- إذا لم يوجد موظف مؤهل تعرض إرشادًا للذهاب إلى HR بدل نموذج أسماء مكرر.
- الحسابات غير المرتبطة تعرض وسمًا وإجراء ربط انتقالي.
- الحساب المرتبط يعرض مرجع الموظف ولا يعرض تعديل الاسم من القائمة؛ تعديل حقيقة
  الموظف يتم في HR. تغطى العربية والإنجليزية والأردية والهندية.

## الترحيل والعكس

- لا DDL ولا backfill إجباري. الروابط الحالية تبقى، والحسابات القديمة تظهر
  كغير مرتبطة ويمكن ترحيلها تدريجيًا من الواجهة.
- نشر التطبيق يتطلب توليد حراس OpenAPI ثم الاختبارات. الرجوع يعيد نسخة التطبيق
  السابقة فقط؛ لا تسقط علاقة ولا بيانات.
- إذا فشل الربط بعد إنشاء المستخدم داخل المعاملة، يتراجع `User` و`UserCompany`
  وAudit وIdempotency معًا.

## بوابة الإغلاق

- عقد OpenAPI والحراس المولدة متطابقان.
- اختبارات إنشاء ناجح، replay، mismatch، بريد مكرر، موظف مرتبط/منتهي، وعزل شركة.
- اختبار تنافس طلبين لموظف واحد على MariaDB الفعلية.
- Typecheck وAPI/Web tests وbuild وi18n/UI/architecture guards وE2E ناجحة.

## نتيجة التنفيذ المحلي

- عقد OpenAPI صالح بلا تحذيرات، والحراس المولدة حالية: 269 عملية و144 جسم طلب
  و1768 جسم استجابة.
- مخطط Prisma صالح، و56 Migration مطبقة بلا DDL جديد لهذه الشريحة.
- نجحت حزمة API على MariaDB الفعلية `344/344`، واختبارات الواجهة `30/30`،
  والبنية `35/35`، واختبارا E2E لتدفق المستخدم وHR.
- نجح البناء وفحص TypeScript والترجمات الأربع وعقد UI والفحص الحي مع CSRF وسياق
  الشركة. لا Dependency جديدة، ولا نشر، ولا Push.
