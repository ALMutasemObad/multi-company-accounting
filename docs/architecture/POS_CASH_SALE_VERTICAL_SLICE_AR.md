# خطة أول شريحة رأسية لنقاط البيع

## 1. الهدف ومعيار الإغلاق

ينفذ الكاشير بيعًا نقديًا كاملًا من شاشة واحدة. لا يعود API بنجاح إلا بعد وجود فاتورة مبيعات مرحلة، وحركة مخزون للأصناف المخزنية، وسند قبض مرحل ومخصص بالكامل، وقيود متوازنة أنشأها `PostingEngine`، وسجل `PosSale` يربط المستندين.

## 2. نموذج البيانات

`PosSale` فقط:

- `id`, `companyId`, `salesInvoiceId`, `receiptId`.
- `completedById`, `completedAt`, `createdAt`.
- مفاتيح فريدة مركبة لكل رابط وعلاقات مركبة تمنع cross-company.
- لا `lines`, `total`, `tax`, `stockQuantity`, `cashAmount` أو حالة مستند منسوخة. الحالة والعرض مشتقان من المالكين عبر Query Port.

## 3. حالات الاستخدام والعقود

1. `POST /pos/checkouts`: Checkout نقدي أحادي التحصيل. يتطلب CSRF و`Idempotency-Key` و`pos.checkout`.
2. `GET /pos/sales`: قائمة حديثة paginated مشتقة من سجل الربط وملخصات المالكين. يتطلب `pos.view`.

جسم Checkout يحتوي الفترة والتاريخ والوصف والعميل والمستودع والعملة وسعر الصرف والصندوق وطريقة الدفع والمرجع والملاحظات وبنود الفاتورة. لا يحتوي الإجمالي أو مبلغ السند؛ كلاهما ناتج موثوق من Sales.

الاستجابة تعيد هوية POS ورقم/هوية/حالة الفاتورة وسند القبض والإجماليات النصية ومعرفات القيود. تبقى BigInt وDecimal نصوصًا canonical.

## 4. المنافذ

- `PosSalesCheckoutPort`: ينشئ ويرحل فاتورة `SALES_INVOICE` ويعيد عنصر الذمة والإجمالي، مستخدمًا Tax وInventory و`PostingEngine` الحاليين.
- `PosReceiptCheckoutPort`: ينشئ ويرحل سند قبض كامل التخصيص لعنصر الذمة، مستخدمًا Treasury وAR و`PostingEngine` الحاليين.
- `PosSaleQueryPort`: قراءة فقط لتجميع عرض المبيعات من المالكين؛ لا يكتب أي جدول.

لا يستورد `PosService` خدمات Prisma الخاصة بالمبيعات أو Treasury ولا يكتب نماذجها؛ يحصل على المنافذ بالحقن.

## 5. واجهة المستخدم والترجمات

- صفحة `#pos` في التنقل، lazy-loaded.
- محرر سريع متجاوب للبائع/الفترة/المستودع/الصندوق/طريقة الدفع/العملة والبنود.
- ملخص محسوب للعرض فقط؛ الخادم يعيد الحساب الحاكم.
- جدول أحدث المبيعات مع رقم الفاتورة والسند والإجمالي والحالتين.
- مفاتيح متطابقة للعربية والإنجليزية والهندية والأردية، مع RTL/LTR، ولا نص أعمال خام في JSX.

## 6. الاختبارات

- Unit: fingerprint حتمي، تحويل DTO، وعدم قبول مبلغ من العميل.
- Integration/API: الرحلة الكاملة، Idempotency replay/mismatch، rollback عند فشل التحصيل، نقص المخزون، الصلاحيات، CSRF، pagination، والعزل بين شركتين.
- Concurrency على MySQL/MariaDB: طلبان بالمفتاح نفسه ينتجان `PosSale` واحدًا؛ أو نجاح واحد/إعادة نتيجة واحدة من دون حركة مخزون أو قيد مكرر.
- Architecture: لا كتابة Ledger أو فاتورة أو مخزون أو Treasury داخل مجلد POS، وكل جسم طلب عام من الحارس المولد.
- Contract/UI: OpenAPI response validation، route parity، i18n parity، TypeScript، build، واختبار واجهة.

## 7. Migration والرجوع

- Migration توسعية تنشئ `pos_sales` والصلاحيتين وتمنحهما للأدوار الإدارية فقط.
- تطبق من قاعدة فارغة ومن آخر مخطط منشور.
- الرجوع الآمن يبدأ بتعطيل Router/واجهة الإصدار السابق، ثم يبقى الجدول للقراءة والتدقيق.
- ملف rollback SQL لا يسقط `pos_sales` إذا احتوى صفوفًا؛ يسقطه فقط في بيئة لم تستخدم الموديول، ويزيل صلاحيات POS بعد إزالة إسناداتها.

## 8. ترتيب التنفيذ

1. Schema وMigration وrollback guard.
2. منافذ Sales/Treasury و`PosService` والمعاملة الذرية.
3. Router وOpenAPI والحراس والصلاحيات والـcomposition root.
4. صفحة الويب والأنواع والترجمات الأربع.
5. اختبارات المجال والعقد والعزل والتزامن، ثم بوابات المشروع الكاملة.

## 9. نتيجة التنفيذ المحلي

- طبقت Migration 49 على قاعدة التطوير المحلية، وأنشأت الجدول والصلاحيتين من دون تعديل بيانات مالية قائمة.
- أثبت اختبار MariaDB فعلي أن طلبين متزامنين بالمفتاح والجسم نفسيهما يعيدان النتيجة نفسها وينتجان رابط POS واحدًا، وفاتورة واحدة، وحركة مخزون واحدة، وسند قبض واحدًا، وقيدًا واحدًا لكل مستند.
- أثبت سيناريو أداة خزينة غير صالحة أن فشل التحصيل يعيد الفاتورة وحركة المخزون والقيود والذمة وسجل Idempotency، ويبقي رصيد الصنف كما كان قبل المحاولة.
- أثبتت اختبارات الحدود أن مجلد POS لا يكتب في حقائق Sales أو Inventory أو Treasury أو Ledger، وأن قائمة POS تقيد القراءة بـ`companyId`.
- لا توجد Dependency خارجية جديدة، ولم يحدث نشر أو Push.
