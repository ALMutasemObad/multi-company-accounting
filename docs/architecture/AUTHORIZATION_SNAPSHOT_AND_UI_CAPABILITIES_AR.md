# لقطة صلاحيات الشركة ووعي الواجهة بالقدرات

## القرار

تعرض الهوية المصادق عليها لقطة واحدة محدودة عبر `GET /auth/me` تضم المستخدم الحالي،
والشركة المختارة من الجلسة إن وجدت، ورموز الصلاحيات الفعلية داخل تلك الشركة. لا يرسل
العميل `companyId` لاختيار نطاق اللقطة، ولا تعيد الاستجابة الأدوار أو أسرار الجلسة أو
إعدادات مشغل المنصة.

هذه اللقطة عقد عرض وتجربة استخدام فقط. يبقى الخادم مصدر الإنفاذ الوحيد: إخفاء رابط أو
زر لا يمنح صلاحية، وإظهاره لا يتجاوز فحص RBAC وعزل الشركة والمعاملة عند تنفيذ الطلب.

## دلالة الاستجابة

- `user` هو المستخدم النشط صاحب الجلسة، بمعرف عام واسم العرض والبريد فقط.
- `selectedCompany` تؤخذ من سياق الجلسة وتكون `null` عندما لا توجد شركة مختارة.
- `permissions` قائمة مرتبة وفريدة لعضوية نشطة في شركة نشطة ولمستخدم نشط؛ لا تقبل
  قيمًا يرسلها المتصفح ولا تستنتج من اسم الدور.
- الجلسة غير الصالحة تعاد وفق عقد المصادقة الحالي، ولا تتحول إلى لقطة فارغة توحي
  بصلاحية محدودة.
- قدرة منصة التشغيل تبقى في `/platform/capabilities` لأنها صلاحية عابرة للشركات وليست
  جزءًا من RBAC الخاص بشركة عميلة.

## سلوك الواجهة

يحمّل shell لقطة `/auth/me` مع شركات المستخدم وقدرة منصة التشغيل. ثم يطبق السياسات
نفسها على:

1. عناصر التنقل وبطاقات دليل الأنظمة.
2. الوصول المباشر عبر hash أو رابط محفوظ، بحيث يعاد المستخدم إلى أول صفحة مسموحة قبل
   تركيب الصفحة غير المصرح بها.
3. أفعال الصفحات عالية المخاطر، مثل الإنشاء والترحيل والإلغاء والعكس والطباعة، مع بقاء
   فحص الخادم قائمًا عند handler والطلب.

الصفحة المركبة التي تحتاج عدة مصادر تستخدم سياسة `allOf` مغلقة افتراضيًا إلى أن تفصل
أقسامها أو طلباتها حسب الصلاحية. ولا يسمح غياب سياسة أو تعذر تحميل اللقطة بإظهار ميزة
محميّة.

مشغل المنصة الذي لا يملك عضوية شركة يستطيع دخول shell خاص بالمنصة فقط عندما تعيد
`/platform/capabilities` القيمة الصحيحة. لا ينشئ النظام له عضوية Tenant صورية، ولا
تظهر له صفحات الشركات لمجرد كونه مشغلًا.

## حواجز التطوير

- كل رمز تستخدمه الواجهة يجب أن يوجد في كتالوج الصلاحيات المعياري والـseed.
- كل توسع جديد يحدد سياسة العرض وسياسة كل فعل إلى جانب إنفاذ الخادم واختبار 403.
- لا تستخدم أسماء الأدوار أو البريد أو `sessionStorage` لاتخاذ قرار صلاحية.
- لا تخزّن لقطة الصلاحيات كمصدر طويل العمر؛ تعاد قراءتها عند المصادقة أو تغيير الشركة،
  ويؤدي رفض الخادم بعد تغيير الصلاحيات إلى تحديث آمن للواجهة.
- تغييرات جسم `/auth/me` تخضع لـOpenAPI والحراس المولدة واختبارات العقد والتوافق.

## بوابات القبول

- اختبارات وحدة لتقاطع `permission` و`anyOf` و`allOf` والحالة الفارغة.
- اختبار أن شركة أو عضوية أو مستخدمًا معطلًا لا ينتج صلاحيات.
- اختبار عزل شركتين للمستخدم نفسه، وأن الشركة المختارة تأتي من الجلسة فقط.
- اختبار مسار مباشر غير مصرح به، وإخفاء التنقل والبطاقات والأفعال عالية المخاطر.
- اختبار shell لمشغل منصة بلا شركة، مع بقاء مستخدم Tenant العادي خارج المنصة.
- TypeScript وبناء الويب واختبارات API/Web وعقد OpenAPI ناجحة على بوابات الإصدار.

## العكس

لا يضيف هذا التغيير جدولًا أو Migration. يمكن عكس الواجهة والعملية معًا بإرجاع نسخة
التطبيق، لكن لا يجوز إبقاء عميل يعتمد على `/auth/me` مع حذف العقد الخادمي قبل نشر نسخة
متوافقة منه.
