# ADR-018: ملف المنشأة وطبيعة النشاط والاستكمال النظامي التدريجي

## السياق

يستخدم المجال الداخلي `Company` كوحدة قانونية ومحاسبية معزولة تملك دفاترها وفتراتها
وعملتها. أما المستخدم فيفكر في «منشأتي» أو «نشاطي التجاري»، وقد يكون الاسم التجاري
مختلفًا عن الاسم القانوني، وقد تمارس المنشأة أكثر من نشاط. كما تختلف بيانات التسجيل
والضريبة والعنوان المطلوبة حسب الدولة والقدرة المستخدمة ومرحلة نضج الحساب.

استبدال `Company` داخليًا باسم `BusinessActivity` سيخلط الكيان القانوني بتصنيف نشاطه،
ويكسر دلالة العزل المحاسبي. وفي المقابل، فرض كل البيانات النظامية عند أول تسجيل يرفع
الاحتكاك قبل أن يحتاجها المستخدم، بينما تركها اختيارية دائمًا يجعل الدفع والفوترة
النظامية والمستندات الرسمية غير قابلة للاعتماد.

## القرار

- يبقى اسم `Company` داخل Domain وSchema والعقود التقنية لأنه وحدة الدفتر والعزل.
- تستخدم الواجهة في رحلة التسجيل والإعداد تسمية مفهومة مثل **«المنشأة / النشاط
  التجاري»**، مع شرح أن كل منشأة تمسك دفاتر مستقلة.
- يفصل النظام الاسم التجاري وطبيعة النشاط عن الهوية القانونية، ولا يحشرها في حقل اسم
  واحد.
- يعتمد **Progressive Profiling**: يبدأ الحساب بحد أدنى، ويطلب الاستكمال قبل القدرة
  التي تحتاج البيانات، وفق سياسة دولة ونسخة متطلبات معلنة.
- لا توزع شروط الدولة داخل React أو Routers. يملك Tenant Configuration محرك متطلبات
  صغيرًا يعيد الحقول المطلوبة/الاختيارية/غير المنطبقة وأسبابها، ويبقى الخادم مصدر
  قرار readiness.

## النموذج المستهدف

### الملف التجاري

- `CompanyProfile`: `tradeName`, `legalName`, `countryCode`, `legalForm`, لغة التواصل
  ومعلومات اتصال العمل، بحالة اكتمال و`version`.
- `BusinessActivity`: كتالوج مرجعي قابل للترجمة، ولا يكون Enum مغلقًا على قطاعات قليلة.
- `CompanyBusinessActivity`: ربط متعدد مع نشاط أساسي واحد فقط ونشاطات إضافية مؤرخة.
- لا يعد النشاط فرعًا أو مشروعًا أو Service Offering، ولا يملك أي حقيقة مالية.

### التسجيل والعناوين

- `CompanyRegistration`: نوع الوثيقة ورقمها وجهة الإصدار وتواريخها وحالة
  `DECLARED/VERIFIED/REJECTED/EXPIRED`، مع عدم تغيير النسخة المتحققة بصمت.
- `CompanyTaxRegistration`: نوع التسجيل الضريبي والدولة والرقم والحالة والتواريخ؛ لا
  يفترض أن كل دولة تستخدم VAT أو الصيغة نفسها.
- `CompanyAddress`: عنوان `REGISTERED/NATIONAL/OPERATING/BILLING` بمكونات منظمة
  وعنوان عرض، مع صلاحية مستقلة عند احتواء عنوان منزل لمنشأة فردية.
- المستندات الإثباتية نفسها خارج الشريحة الأولى حتى اعتماد التخزين والتشفير وفحص
  الملفات وRetention؛ لا تحفظ Base64 في جدول الملف.

## سياسة الدول والاستثناء اليمني

- يختار المستخدم الدولة في الحد الأدنى الأول، ومنها تحل `JurisdictionRequirementPolicy`
  نسخة المتطلبات السارية وتاريخها ومصدرها.
- في السياسة الابتدائية لا تفرض اليمن (`YE`) الحقول السعودية الخاصة: رقم السجل
  التجاري السعودي، رقم ضريبة القيمة المضافة السعودي، أو العنوان الوطني السعودي.
  تظهر هذه الحقول `NOT_APPLICABLE` بدل خطأ أو قيمة وهمية.
- لا يعني ذلك منع تخزين رقم تسجيل أو ضريبة أو عنوان يمني إذا اعتمدت متطلبات محلية
  لاحقًا؛ تستخدم أنواع وثائق خاصة بالدولة بدل إعادة استخدام مسميات سعودية.
- لا تثبت تفاصيل إلزامية لدولة في الشفرة قبل مراجعة مصدر حكومي حديث وتسجيل تاريخ
  السياسة. القاعدة الفنية هنا ليست رأيًا قانونيًا ولا بديلًا عن التحقق النظامي.

## مستويات الاستكمال

1. `BASIC`: الاسم التجاري، الدولة، طبيعة النشاط الأساسية، العملة والمنطقة الزمنية.
   يكفي لبدء تجربة النظام وإنشاء بيانات غير نظامية.
2. `OPERATIONAL`: بيانات الاتصال وعنوان التشغيل والمسؤول؛ تطلب قبل دعوة واسعة أو
   إعداد فروع ومحطات حسب السياسة.
3. `COMMERCIAL`: الاسم القانوني والتسجيل وعنوان الفوترة والبيانات التي يطلبها مزود
   الدفع؛ تطلب قبل اشتراك مدفوع أو Checkout إذا ألزمها المزود.
4. `REGULATED`: متطلبات الفاتورة الإلكترونية والضريبة والمستندات الرسمية الخاصة
   بالدولة؛ تطلب قبل تفعيل القدرة المنظمة، لا قبل استخدام دفتر داخلي تجريبي.

يعيد API قائمة `missingRequirements` بأكواد ثابتة وسبب/قدرة مرتبطة، وتعرض الواجهة
Checklist واحدة وروابط مباشرة للحقول الناقصة. لا يعاد سؤال المستخدم عن بيانات صحيحة
ومتحققة في كل عملية.

## الأمن والملكية

- Tenant Configuration هو مالك الكتابة الوحيد؛ Platform Operations يقرأ نسبة اكتمال
  مجمعة فقط ولا يقرأ أرقام التسجيل أو العنوان عبر استعلاماته التحليلية.
- صلاحيات مستقلة مثل `company_profile.view/manage` و`company_compliance.view/manage`
  وصلاحية تحقق منصّية أضيق، ولا تمنح `settings.manage` كل البيانات الحساسة ضمنيًا.
- كل قراءة وكتابة مقيدة بـ`companyId`، وكل تعديل بنسخة متفائلة وتدقيق منقح لا يسجل
  أرقامًا كاملة أو عناوين في `details` أو logs.
- تعرض القيم الحساسة Masked في القوائم، وتمنع الصادرات العامة وبيانات القياس من
  حملها. تحدد سياسة التشفير والبحث قبل تخزين معرف عالي الحساسية.
- تغيير الدولة أو الهوية القانونية بعد استخدامها في مستند رسمي يحتاج Workflow
  معتمدًا وتاريخ نفاذ، ولا يعيد كتابة لقطات الفواتير السابقة.

## الواجهة والتسمية

- التسجيل: «اسم المنشأة أو النشاط التجاري» و«طبيعة النشاط» بدل مطالبة المستخدم
  بتفسير المصطلح التقني Company.
- الإعدادات: صفحتان واضحتان، «الملف التجاري» و«البيانات النظامية»، لا نموذج طويل واحد.
- مبدل السياق يمكن تسميته «تبديل المنشأة»؛ يبقى `companyId` في API لتجنب تغيير تقني
  واسع بلا قيمة.
- الاسم القانوني والرقم الضريبي لا يستخدمان كاسم عرض افتراضي إذا وفر المستخدم اسمًا
  تجاريًا.

## ترتيب التنفيذ

1. `BP-1`: عقد الملف التجاري والدولة والنشاط الأساسي وreadiness بلا حقول إلزامية
   جديدة على الحسابات القائمة.
2. `BP-2`: التسجيلات والعناوين وسياسة المتطلبات وإسناد `Grandfathered` آمن للحسابات
   الحالية.
3. `BP-3`: ربط readiness بصفحة الاشتراك والدفع، دون اختيار مزود قبل ADR-017/PAY-1.
4. `BP-4`: سياسات الفوترة الإلكترونية/الضريبة لكل دولة بعد توثيق رسمي منفصل.

لا تخلط هذه الشرائح مع Branch أو Service Catalog أو CRM في Migration واحدة.

## بوابات القبول

- عزل شركتين، وإخفاء البيانات الحساسة، وRBAC/Audit/CSRF/OpenAPI كامل.
- اختلاف سياسة `YE` عن سياسة دولة تتطلب حقولًا إضافية دون شروط UI خاصة بالدولة.
- الحساب القديم لا يتوقف بعد Migration، والقدرة المنظمة فقط هي التي تطلب readiness.
- تغيير النشاط لا يغير `Company` أو دفاترها، وتغيير الهوية لا يغير مستندًا تاريخيًا.
- ترجمات أربع وRTL/LTR وهاتف وإتاحة وChecklist لا تعيد طلب المكتمل.
- MariaDB 10.11 وMySQL 8.4 والترقية والعكس المحروس واختبارات التزامن.
