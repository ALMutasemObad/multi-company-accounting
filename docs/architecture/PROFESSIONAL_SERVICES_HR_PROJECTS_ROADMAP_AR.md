# خارطة خدمات الشركات المهنية والموارد البشرية والمشاريع

## مبدأ الترتيب

يرتب التنفيذ حسب أقصر دورة أعمال مكتملة وأقل مخاطرة محاسبية، لا حسب عدد الشاشات. لذلك يبدأ بالعمل المهني والوقت، ثم ملف الموظف، ثم الموافقات والفوترة، وتؤجل الرواتب وأموال العملاء حتى تتضح السياسة النظامية.

| الأولوية | المرحلة | الناتج القابل للإغلاق | الاعتماد | الحالة |
|---:|---|---|---|---|
| A | المشاريع/القضايا والوقت الشخصي | مشروع مرتبط بعميل، فريق، وقت خام، حالات وتدقيق | Sales customers + Identity users | منفذة محليًا |
| B | أساس HR | ملف موظف، رقم وظيفي، قسم، منصب، عقد/حالة عمل، إجازة أساسية | Identity reference only | التالية |
| C | Timesheets والموافقة | فترة وقت immutable عند الإرسال وقرار Maker/Checker | A + Approvals + B | مخططة |
| D | العقود والأسعار وفوترة الخدمات | أسعار مؤرخة ولقطة تسعير وفاتورة عبر Sales port | C + Sales + Tax | مخططة |
| E | تخطيط المشروع والمصروفات | مهام/معالم/ميزانية وقت ومصروفات معتمدة | B/C + Expenses/Approvals | مخططة |
| F | خصائص المكتب القانوني | تعارض مصالح، مواعيد، تصنيف مستندات وقيود وصول | A + Security/Audit | تحتاج قرارات نطاق |
| G | أموال العملاء/الأمانات | حسابات منفصلة، تسوية، منع الاعتراف كإيراد وضبط صلاحيات | Treasury + Ledger + Reconciliation | ADR مستقل إلزامي |
| H | الرواتب | دورة أجور واستقطاعات وترحيل ودفع وإلغاء | B + jurisdiction محدد | مؤجلة عمدًا |

## المرحلة B — أساس الموارد البشرية

### النطاق المقترح

- `Employee` كهوية عمل داخل الشركة، ويمكن ربطه اختياريًا بـ`UserCompany` دون مساواتهما.
- الأقسام والمناصب ومواقع العمل والمدير المباشر.
- رقم موظف محجوز من الخادم، تاريخ الالتحاق، حالة العمل، وعقد عمل مؤرخ.
- طلب إجازة ورصيد بسيط بعد تحديد سياسة الرصيد، مع Approval Subject خاص.
- صلاحيات منفصلة للعرض والإدارة والبيانات الحساسة؛ لا تعرض بيانات التعويض لكل مدير مشروع.

### خارج النطاق

الرواتب والحضور البيومتري والتوظيف وتقييم الأداء. لا يخزن الرقم الوطني أو البنكي بلا سياسة تشفير/وصول وRetention محددة.

## المرحلة C — Timesheets ومحرك الموافقات

- يجمع الوقت الخام في فترة أسبوعية/شهرية يملكها سياق المشاريع.
- عند الإرسال تثبت قائمة السجلات وبصمتها وإصدارها، ويمنع تعديلها حتى القرار.
- يرسل `PROFESSIONAL_TIMESHEET` إلى Approvals عبر `ApprovalSubjectPort`.
- يظل Approvals مالك `ApprovalRequest/ApprovalDecision` فقط؛ يعيد المالك فتح الفترة عند الرفض ويثبتها عند الاعتماد.
- تحدد السياسة هل مدير المشروع ثم مدير الموارد البشرية تسلسل واحد أو عدة مستويات قبل تنفيذها؛ لا يفترض ذلك في البيانات الحالية.

## المرحلة D — العقود والأسعار والفوترة

- عقد خدمات مؤرخ ونموذج فوترة: وقت ومواد، مبلغ ثابت، أو مراحل.
- Rate card حسب الموظف/الدور/المشروع والعملة، مع صلاحيات حساسة.
- لقطة سعر عند اعتماد الوقت حتى لا تغير الأسعار التاريخية الفاتورة.
- أمر فوترة يمر إلى Sales عبر Port ويولد `SalesInvoice` عادية؛ لا يملك سياق المشاريع Invoice أو Receivable أو Tax quote أو Journal.
- الدفعات المقدمة التجارية تعالج بتصميم عقد/خزينة واضح؛ أمانات العملاء القانونية لا تخلط بها.

## المرحلة E — إدارة المشروع العملية

- Work breakdown صغير: مراحل ومهام واعتماديات وتقدير ساعات ومسؤول.
- ميزانية وقت ومقارنة مخطط/فعلي، دون دفتر مالي موازٍ.
- مصروفات المشروع تطلب من موديول المصروفات وتربط مرجعيًا بعد اعتمادها.
- تنبيهات المواعيد عبر Outbox بعد commit، لا Scheduler خفي داخل الطلب.

## المرحلة F — احتياجات شركات المحاماة

- **Conflict check:** أطراف القضية وأسماؤها البديلة ونتيجة فحص قابلة للتدقيق قبل فتح القضية. يحتاج سياسة مطابقة وقرارًا بشريًا؛ لا اعتماد تلقائي fuzzy.
- **Matter deadlines:** موعد، منطقة زمنية، مصدر، مسؤول، وإقرار/إكمال؛ التنبيه أثر Outbox.
- **Document metadata:** تصنيف ووصف وRetention وقيود وصول؛ تخزين الملفات نفسه يحتاج قرار تخزين وتشفير وفيروسات منفصلًا.
- **Ethical walls:** صلاحيات على مستوى القضية قد تتجاوز RBAC الشركة العام، وتحتاج نموذج وصول واختبارات تسرب قبل التنفيذ.

## المرحلة G — أموال العملاء والأمانات

هذه ليست ميزة خزينة عادية. قبل التنفيذ يلزم ADR يحدد:

- فصل الحساب البنكي والدفتر المساعد لكل عميل/قضية.
- منع تسجيل الإيداع كإيراد أو Accounts Receivable settlement بلا سبب صحيح.
- المصالحة البنكية والتحويل إلى أتعاب بعد اعتماد وفاتورة.
- عدم السالب، والتسوية 1:1، وMaker/Checker، والتقارير والتدقيق والرجوع.

## بوابات الانتقال بين المراحل

- لا تبدأ مرحلة جديدة قبل اكتمال عقد وMigration وOpenAPI وواجهة واختبارات المرحلة السابقة أو فصلها خلف Feature Flag غير ظاهر.
- لا Dependency جديدة إلا بتقييم الرخصة والأمن وخطة الخروج؛ المراحل A وB وC لا تحتاج مبدئيًا مكتبة خارجية.
- لا كتابة مباشرة إلى Ledger؛ كل أثر محاسبي يمر عبر مالك المستند ثم `PostingEngine`.
- لا تكرار للعميل أو المستخدم أو الفاتورة أو قرار الموافقة أو حركة الخزينة.
- كل علاقة بين الشركات تحمل `companyId`، وكل أمر قابل للإعادة يملك Idempotency، وكل تعديل متنافس يملك version.
- لا نشر أو Push قبل طلب صريح وبوابات الإصدار الكاملة.
