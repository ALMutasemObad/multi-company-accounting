# أول شريحة رأسية لمحرك الموافقات: مراجعة الإقفال المالي

## 1. نطاق المرحلة الأولى

تشمل الشريحة:

1. إرسال حزمة إقفال جاهزة إلى الموافقات.
2. تجميد بصمة الحزمة وتحويل تشغيل الإقفال إلى `AWAITING_APPROVAL`.
3. صندوق طلبات حسب الشركة والحالة مع التاريخ والقرار.
4. اعتماد Checker مستقل بعد إعادة فحص الحزمة، أو رفض بسبب إلزامي يعيدها للتحضير.
5. متابعة الإقفال النهائي من Fiscal بعد الاعتماد.

خارج النطاق: درجات متعددة، تفويض مؤقت، مجموعات معتمدين، SLA وتصعيد وتنبيهات، إلغاء الطلب من API، اعتماد جماعي، مصمم تدفقات، موافقات الفواتير والمخزون والمصروفات، وسياسة شركة قابلة للتعطيل. لا تضيف المرحلة Event أو Outbox لعدم وجود مستهلك لاحق حقيقي؛ القرار وانتقال الموضوع حاكمان ومتزامنان.

## 2. نموذج البيانات والملكية

### `ApprovalRequest`

- UUID عام، و`companyId` للعزل.
- `subjectType=FINANCIAL_CLOSE_RUN` و`subjectId` العام؛ لا FK مباشر إلى جدول Fiscal ولا نسخة من الحزمة.
- `subjectVersion` وبصمة `SHA-256` فقط لحماية اللقطة.
- `status`, `requestedById`, `makerCheckerRequired`, `version`.
- `activeSubjectKey` nullable وفريد داخل الشركة: موجود فقط في `PENDING` لمنع طلب نشط ثانٍ.

### `ApprovalDecision`

- قرار واحد immutable لكل طلب: `APPROVE` أو `REJECT`.
- `actorUserId`, `decidedAt`, وسبب إلزامي بطول 10–500 عند الرفض فقط.
- علاقة مركبة بالطلب والشركة تمنع cross-company reference.

لا يخزن المحرك `FinancialCloseRun` أو قائمة الجاهزية أو حزمة الإقفال أو مبالغها، ولا يقرأ أو يكتب `AccountingDocument`, `JournalEntry`, `JournalLine`, الفواتير أو المخزون.

## 3. حالات الاستخدام

### الإرسال

يقفل Fiscal صف الفترة ثم صف تشغيل الإقفال على مستوى قاعدة البيانات، ويتحقق من النسخة والحالة والجاهزية، ويبني الحزمة والبصمة، وينقل التشغيل إلى `AWAITING_APPROVAL`. بعدها ينشئ Approvals الطلب النشط في المعاملة نفسها. أي فشل يلغي الحزمة والطلب وIdempotency والتدقيق معًا.

### الاعتماد

يتحقق المحرك من نسخة الطلب وحالته ومن اختلاف Maker وChecker، ثم يستدعي Fiscal. يعيد Fiscal حساب الجاهزية والحزمة تحت القفل ويقارن بصمة الطلب؛ عند التطابق ينتقل إلى `REVIEWED` ويسجل Checker في حقول المالك. بعدها يحفظ المحرك `ApprovalDecision(APPROVE)` ويغلق الطلب.

### الرفض

يتطلب سببًا، وينقل Fiscal التشغيل إلى `PREPARING` ويمسح الحزمة المختومة ويحفظ مرجع الإعادة، ثم يحفظ المحرك قرار الرفض ويحرر المفتاح النشط لإرسال طلب جديد.

### الإقفال والعكس

الاعتماد لا يرحل قيدًا ولا يغلق فترة. ينفذ Fiscal أمر الإقفال الحالي فقط عندما تكون الدورة `REVIEWED` وتبقى البصمة صحيحة. إعادة الفتح وعكس `PERIOD_CLOSE` يمران عبر Fiscal و`PostingEngine` كما قبل المحرك؛ لا يملك Approvals مسار عكس مالي.

## 4. OpenAPI والصلاحيات

الإصدار `1.31.0` يضيف:

- `GET /approval-requests`
- `POST /approval-requests`
- `GET /approval-requests/{approvalRequestId}`
- `POST /approval-requests/{approvalRequestId}/approve`
- `POST /approval-requests/{approvalRequestId}/reject`

كل أمر كتابة يتطلب CSRF و`Idempotency-Key`. أجسام JSON تستخدم الحراس المولدة من OpenAPI، ومعرفات BIGINT في الأشخاص تخرج نصوصًا. الصلاحيات هي `fiscal_periods.close` للإرسال، و`approvals.view` للقراءة، و`approvals.decide` للقرار.

## 5. الواجهة والترجمات

- تغير زر الإقفال من اعتماد مباشر إلى «إرسال للموافقة».
- تعرض مساحة الإقفال حالة `AWAITING_APPROVAL` ورابط صندوق الموافقات.
- يضيف `#approvals` صندوقًا بمرشح الحالة وبيانات Maker والوقت والقرار وأزرار الاعتماد والرفض.
- الرسائل والحالات والأخطاء موجودة بالعربية والإنجليزية والهندية والأردية، مع RTL/LTR والتخطيط المتجاوب وعناصر الجدول القابلة للتمرير.

## 6. الاختبارات والحواجز

تغطي الاختبارات:

- آلة الحالات العامة وحالات تشغيل الإقفال.
- إرسالين متزامنين بالمفتاح والجسم نفسيهما ينتجان طلبًا وحزمة واحدة.
- رفض المفتاح نفسه مع Payload مختلف بـ`IDEMPOTENCY_MISMATCH`.
- منع Maker من الاعتماد حتى مع امتلاك صلاحية القرار.
- الرفض بسبب محفوظ ثم إعادة الإرسال.
- اعتماد Checker مستقل ورفض الإقفال إذا تغيرت الحزمة.
- عزل طلبات شركة أخرى.
- تطابق OpenAPI مع Routers وحراس الطلب والاستجابة.
- حارس يمنع وحدة Approvals من كتابة حقائق Ledger أو Fiscal مباشرة.

## 7. الترحيل والرجوع

- Migration: `20260827150000_approval_engine_financial_close`.
- الترحيل توسعي للجداول والصلاحيات، مع توسيع Enum حالة موجودة.
- التطبيق السابق لا يعرف `AWAITING_APPROVAL`؛ لذلك الرجوع الآمن بعد الاستخدام هو إصدار وسيط يعطل الإرسال والقرارات لكنه يبقي Router قراءة أو يعالج الطلبات المعلقة قبل العودة.
- `rollback.sql` مدمر ومخصص لمرحلة ما قبل الاستخدام فقط؛ يرفض عند وجود طلب أو تشغيل معلق.
- اختبر المسار من قاعدة فارغة بكل الترحيلات الخمسين، واختبر رفض rollback مع سجل ثم نجاحه بعد إزالة سجل الاختبار واستعادة Enum القديمة.

## 8. اتجاه التوسعة

لا يضاف Subject جديد بمجرد توفر المحرك. يلزم لكل تطبيق تحديد المالك وحالات الإرسال والرفض والصلاحيات وترتيب الأقفال وبصمة اللقطة والعكس. المرشحون بعد الإثبات: طلبات المصروفات، الأصول الثابتة، ثم مستندات المخزون عند تنفيذها، وليس الفواتير الحالية دفعة واحدة.
