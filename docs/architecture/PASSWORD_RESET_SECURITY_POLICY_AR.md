# سياسة أمان استعادة كلمة المرور

## 1. حدود المجال

استعادة كلمة المرور حالة استخدام يملكها **Identity & Access**. يملك هذا السياق `PasswordResetRequest` وتغيير `User.passwordHash` وإلغاء `Session`. إرسال البريد أثر لاحق للـcommit ينفذ عبر `PasswordResetRequested` في Transactional Outbox، ولا يجوز تنفيذه داخل معاملة قاعدة البيانات.

## 2. عقد المسار العام

- يعيد طلب الاستعادة دائمًا `202 ACCEPTED` بالاستجابة نفسها للحساب الموجود وغير الموجود والمعطل؛ يمنع كشف هوية المستخدم أو حالته.
- يحمي بدء الاستعادة وإكمالها بـPRE_AUTH session وCSRF، وبـRate Limit مستقل.
- لا يسجل البريد أو الرمز أو الرابط أو كلمة المرور في Logs أو Outbox أو Audit.
- يوضع الرمز في URL Fragment (`#reset-password?token=...`) كي لا يدخل Access Logs أو Referer الخادمي.
- لا يسجل النظام المستخدم تلقائيًا بعد التغيير؛ يعود إلى شاشة الدخول ويجري مصادقة جديدة.

## 3. دورة حياة الرمز

- الرمز opaque عالي العشوائية، مشتق بـHMAC-SHA-256 من `eventId` مع domain separator مستقل عن رمز التسجيل.
- لا يخزن الرمز الخام مطلقًا؛ تحفظ بصمة SHA-256 فقط في `password_reset_requests`.
- الرمز أحادي الاستخدام، قصير العمر، وتحدد مدته بـ`PASSWORD_RESET_TOKEN_TTL_MINUTES`.
- طلب رابط جديد يلغي كل الطلبات المعلقة السابقة للمستخدم داخل المعاملة نفسها.
- استهلاك الرمز يتم بـconditional update داخل معاملة؛ طلبان متزامنان لا يستطيعان استهلاك الرمز نفسه.
- بعد النجاح تلغى كل جلسات المستخدم، وتصفّر محاولات الدخول الفاشلة والقفل، ويسجل `PASSWORD_RESET_COMPLETED` عالي الخطورة لكل شركة نشطة مسندة إليه.

## 4. المعاملات والتزامن والـDeadlines

- إنشاء الطلب وإلغاء الطلبات السابقة وإلحاق حدث Outbox عملية ذرية واحدة.
- يجري Argon2 hashing خارج المعاملة لتقصير مدة الأقفال، ثم تعيد المعاملة فحص حالة الطلب وانتهاءه ونشاط المستخدم قبل الالتزام.
- يستخدم قفل المستخدم عند إنشاء جيل جديد لمنع رابطين صالحين نتيجة طلبين متزامنين.
- تستخدم المعاملات `maxWait` و`timeout` محدودين؛ لا Network I/O ولا sleep داخلها.
- يعالج عامل Outbox البريد بسياسة at-least-once وlease وretry وdeadline القائمة. إعادة تسليم البريد قد تتكرر، لكن الرابط المشتق للحدث نفسه ثابت وآمن وأحادي الاستخدام.

## 5. متطلبات الإنتاج

عند `PASSWORD_RESET_ENABLED=true` يجب أن يفشل التشغيل مبكرًا ما لم تتوفر:

- `REGISTRATION_EMAIL_MODE=resend`
- `REGISTRATION_EMAIL_FROM`
- `RESEND_API_KEY`
- `REGISTRATION_TOKEN_SECRET` بطول وعشوائية مناسبين
- HTTPS وSecure Cookie وTrust Proxy وفق ضوابط الإنتاج

يجوز مشاركة **بنية النقل** ومفتاح الاشتقاق المخزن مع التسجيل في الإصدار الحالي، لكن domain separator يفصل الرموز تشفيريًا. عند فصل المفاتيح مستقبلًا يجب دعم تدوير مراقب للأحداث المعلقة وعدم إبطال روابط محفوظة بلا خطة انتقال.

## 6. بوابة أي تغيير مستقبلي

أي تعديل للاستعادة يجب أن يثبت باختبارات تكامل فعلية:

1. عدم تعداد الحسابات في الاستجابة والحالة.
2. رفض رمز منتهي أو مستخدم أو ملغى.
3. نجاح مستهلك واحد فقط تحت التزامن.
4. إلغاء الجلسات السابقة وعدم إنشاء جلسة جديدة تلقائيًا.
5. عدم وجود الرمز أو كلمة المرور أو البريد في Outbox وLogs.
6. فشل المعاملة بالكامل عند تعذر حفظ Outbox أو تعطيل المستخدم أثناء العملية.
7. صلاحية Migration من قاعدة فارغة ومن الإصدار السابق.

يمنع إضافة أسئلة أمان، أو إرسال كلمة مرور مؤقتة بالبريد، أو تخزين الرمز خامًا، أو كشف اختلاف الحساب الموجود وغير الموجود، إلا بقرار أمني موثق يحافظ على هذه الخصائص أو يحسنها.
