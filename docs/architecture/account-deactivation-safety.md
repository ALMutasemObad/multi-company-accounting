# سلامة تعطيل الحساب — بروتوكولات الكتّاب

## ما أُغلق في هذه الشريحة

أصبح `ManualJournalService` يستخدم `AccountReferenceLockPort` المملوك لسياق
Accounts والمحقون صراحة من composition. لا يستورد سياق Journals محول Prisma ولا
ينفذ SQL حسابات خاصًا به.

- إنشاء القيد يقفل الفترة ويعيد قراءتها، ثم يحجز رقم المستند داخل المعاملة، ثم
  يقفل حسابات السطور بعد إزالة التكرار وبترتيب رقمي، ثم يكتب المستند والأسطر.
- تعديل السطور يقفل الفترة المستهدفة أولًا بما يوافق ترتيب `PostingEngine`، ثم
  يقفل `AccountingDocument` ويعيد قراءة status/version والأسطر الحالية، ثم يقفل
  اتحاد الحسابات القديمة والجديدة بترتيب رقمي. بعد ذلك يقفل `JournalLine` الحالية،
  وينفذ CAS قبل حذف الأسطر واستبدالها.
- تعديل metadata دون `entries` لا ينشئ مرجع حساب جديدًا ولا يستبدل الأسطر، ولذلك
  لا يقفل الحسابات أو الأسطر. الإلغاء يقفل المستند ويعيد قراءته قبل CAS.
- أي حساب من شركة أخرى أو inactive أو non-posting أو له children يفشل مغلقًا قبل
  كتابة `JournalLine`. لا يعاد تشغيل الأمر المالي تلقائيًا عند تعارض المعاملة؛
  يبقى حكم CAS أو خطأ المعاملة ظاهرًا بلا إعادة إرسال ملتبسة.

أسطر قيد `DRAFT` تعد استخدامًا يمنع تعطيل الحساب، لكنها ليست تاريخًا immutable؛
التاريخ immutable يبدأ عند الحالات النهائية التي يغطيها Core usage adapter.

## بروتوكول شجرة الحسابات

تستخدم أوامر `AccountService` والقالب الافتراضي helper داخليًا مملوكًا لسياق
Accounts. يقفل helper مجموعة صفوف الحسابات بنطاق الشركة بعد إزالة التكرار وبترتيب
المعرّف الرقمي الصاعد مع `FOR UPDATE`. تعمل أوامر الشجرة التفاعلية بعزل
`READ COMMITTED` كي لا تنشئ قراءات الاكتشاف أقفالًا ضمنية تسبق الترتيب الصريح.

- إنشاء الطفل يقفل الأب ثم يعيد قراءته ويتحقق أنه active وغير posting قبل الكتابة.
- إعادة الأبوة تكتشف الشجرة مبدئيًا، ثم تقفل دفعة واحدة الجذر وكل descendants
  وسلسلة آباء الهدف. تعيد بناء closure تحت الأقفال؛ ظهور حساب خارج المجموعة
  المقفلة يفشل `VERSION_CONFLICT` ولا يمدد مجموعة الأقفال تدريجيًا.
- تحديث metadata يقفل الحساب الهدف فقط. تغيير `allowsPosting` إلى true يقفل
  subtree كاملة كي لا يتسابق مع إنشاء طفل.
- التعطيل والحذف يقفلان الهدف أولًا، ثم يعيدان قراءة version والأطفال والاستخدامات
  قبل CAS. لذلك لا يمكن لإنشاء طفل أو نقله إلى أب أن ينجح بالتزامن مع تعطيل الأب.
- القالب يخطط مسبقًا فقط للحسابات الموجودة التي سيربطها أو التي ستكون آباءً
  لحسابات مفقودة، ويقفلها دفعة مرتبة قبل أول كتابة ثم يعيد القراءة والتخطيط.
  الحساب الذي أنشأته المعاملة نفسها لا يحتاج إعادة قفل.

## بوابة التفعيل المتبقية

يبقى `AccountUsageGuard.enforcementEnabled=false` ولا يحقن في `AccountService`.
اكتملت handshakes لكتاب المراجع التشغيلية وكتابة القيود اليدوية وبروتوكول
`Account.parentAccountId`، لكن تفعيل الحارس قرار مستقل يحتاج مراجعة تكاملية نهائية.
اكتمال composition ‏7/7 وحده لا يمنح إذن التفعيل.

لا تغير هذه الشريحة schema أو OpenAPI، ولا تضيف retry للأوامر المالية.
