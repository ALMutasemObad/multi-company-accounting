# دفعة تأسيس قابلية التوسع للاستعلامات

التاريخ: 2026-08-29

خط الأساس: `origin/main` عند الالتزام `1b2159d0d6ab5f8a6ff43e738f85a3a4e9e89984`

الفرع: `perf/database-query-scalability-foundation`

## النطاق والقيود

هذه دفعة أداء قصيرة خارج نطاق Platform Operations & Billing. لم تغيّر عقود OpenAPI أو
ملكية الكتابة بين الوحدات أو دلالات العزل حسب `companyId`، ولم تضف قدرات أعمال جديدة.
كل العمل تم في Git worktree مستقل عن شجرة التطوير المتسخة.

## ما تغير

1. قوائم فواتير المبيعات والمشتريات تنفذ `where` و`count` و`skip/take` داخل قاعدة
   البيانات. مرشح `outstandingOnly` يعتمد سجل التسوية المملوك لـAR/AP، ويقيد النتائج
   بالفاتورة الأصلية المرحلة ذات رصيد موجب كما كان العقد السابق.
2. لوحة التقارير تجمع المقبوضات والمدفوعات شهريًا في SQL، مع تمثيل حركة العكس في
   تاريخ مستند العكس وبالإشارة السالبة نفسها.
3. كشف الأستاذ لا يحمل كل `JournalLine`. يحسب الافتتاحي والإجمالي والعدد في قاعدة
   البيانات، ويقرأ الصفحة فقط. نافذة SQL تحسب الرصيد التراكمي قبل `LIMIT/OFFSET` حتى
   تبقى أرصدة الصفحات اللاحقة مطابقة للترتيب `(entry_date, line.id)`.
4. ملخص الضريبة يقرأ فواتير المبيعات ثم المشتريات بدفعات keyset ثابتة من 250 سجلًا،
   ويحتفظ في ذاكرة الطلب بالمجاميع فقط. التجميع والتقريب ما زالا يستخدمان
   `Prisma.Decimal` و`ROUND_HALF_UP`.
5. إعدادات Connection Pool أصبحت بيئية وصريحة لكل عملية API. القيم الافتراضية نقاط
   بدء تشغيلية وليست SLO أو اختيار سعة نهائيًا؛ منهج المعايرة موثق في
   `docs/operational-resilience.md`.
6. أضيفت اختبارات سلوكية وحواجز معمارية تمنع إعادة `slice/filter` لقوائم الفواتير أو
   `journalLine.findMany` لكشف الأستاذ، وتفرض batching لملخص الضريبة.

## ثوابت محاسبية ومعمارية

- كل قراءة جديدة تقيد مباشرة بـ`companyId`؛ لا يوجد اعتماد على فلترة لاحقة في الذاكرة.
- الاستعلامات SQL للقراءة فقط وقيم المستخدم مربوطة كمعلمات. اسما جدولي الحركة فقط
  يختاران من اتحاد داخلي مغلق (`receipts | payments`).
- لا تغيير في ترتيب كشف الأستاذ أو دقة القيم النقدية أو دلالة المستند المعكوس.
- `outstandingOnly` يستند إلى `ReceivableItem.outstandingAmount` و
  `PayableItem.outstandingAmount`. ترحيل settlement items الحالي يعيد بناء هذه السجلات
  للفواتير التاريخية المرحلة/المعكوسة، وخدمات الترحيل والعكس تحدثها ضمن المعاملة نفسها.
- لا تغيير في OpenAPI؛ لذلك بقيت حواجز الطلب/الاستجابة المولدة كما هي.

الوحدة `BOX` الموجود مسبقًا في قاعدة التطوير المحلية، فتلقى `409` بدل `201`. لم تحذف

بوابتا الإصدار الإلزاميتان MariaDB 10.11 وMySQL 8.4 تنفذان في CI للـPR لأن Docker
غير متاح محليًا. يبقى PR مسودة حتى نجاح البوابتين، ولا يدمج أو ينشر بهذه الدفعة.

## مراجعة الدين التالي — بلا تنفيذ في هذه الدفعة

### فصل الاعتمادات الخرسانية

الخدمات تقبل بعض Ports بالفعل، لكن constructors ما زالت تنشئ fallbacks خرسانية:

- `SalesInvoiceService` و`PurchaseInvoiceService`: `TaxService` و
  `InventoryCatalogService` و`InventoryMovementService`، إضافة إلى settlement service
  داخلي.
- `ReceiptService` و`PaymentService`: settlement service و`TreasuryService` و
  `RealizedFxAccountService`.

الشريحة التالية المقترحة تجعل هذه الاعتمادات إلزامية كـPorts، وتبقي إنشاء adapters
الخرسانية في composition (`server.ts`) فقط، ثم تحدث test factories. يجب أن تكون PR
منفصلة حتى لا تختلط مخاطرة بنيوية بتغيير مسارات الاستعلام.

### هوية المستخدم ووعي الواجهة بالصلاحيات

لا يوجد حاليًا عقد `/auth/me`. الواجهة تقرأ `/auth/companies` ثم تضبط
`/auth/context`، وبعدها تعرض التنقل العام مع استثناء capabilities خاصة بالمنصة
والمطابقة البنكية. الخادم يبقى مصدر الإنفاذ عبر authorization الحالي.

الشريحة التالية المقترحة تضيف عقدًا company-scoped يعيد هوية المستخدم والسياق وقائمة
permission codes/capabilities، ثم تستخدمه الواجهة لإخفاء التنقل والأزرار غير المتاحة.
هذا تحسين UX فقط ولا يستبدل إنفاذ الخادم. يؤجل التنفيذ إلى PR منفصلة بعد نجاح بوابات
هذه الدفعة، وبعد مزامنة تغييرات Platform Operations & Billing لأنها تمس ملفات OpenAPI
والتركيب والواجهة المشتركة نفسها.
