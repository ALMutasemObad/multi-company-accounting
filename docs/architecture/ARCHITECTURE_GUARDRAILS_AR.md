# الضوابط المعمارية لنظام جوار المالي

## 1. طريقة قراءة القواعد

- **يجب / MUST**: قاعدة إلزامية لا تكسر إلا بقرار ADR مقبول.
- **ينبغي / SHOULD**: القاعدة الافتراضية؛ مخالفتها تحتاج تعليلًا موثقًا في المراجعة.
- **يمنع / MUST NOT**: سلوك محظور.

هذه الوثيقة تحكم التطوير الجديد. المخالفات الموجودة حاليًا موثقة كدين معماري انتقالي؛ لا يجوز زيادتها أو نسخها إلى وحدات جديدة.

## 2. ما نبقي عليه كما هو

| القرار الحالي | الحكم | سبب المحافظة عليه |
|---|---|---|
| Modular Monolith | نبقيه | يناسب حجم الفريق ويضمن معاملات محلية ونشرًا أبسط |
| قاعدة بيانات علائقية MySQL/MariaDB مع Prisma Migrate | نبقيه | مناسب لسلامة القيود والعلاقات والمعاملات |
| Strong consistency لدفتر الأستاذ | نبقيه إلزاميًا | الترحيل والعكس والتسويات لا تحتمل أثرًا ماليًا جزئيًا |
| معاملة واحدة للمصدر والقيد والحالة والتدقيق وIdempotency | نبقيها | تمنع نجاحًا جزئيًا أو سجل نجاح بلا أثر مالي |
| `companyId` والعلاقات المركبة للعزل | نبقيها | حاجز أساسي ضد تسرب بيانات الشركات |
| `Prisma.Decimal` و`ROUND_HALF_UP` | نبقيهما | يمنعان أخطاء الدقة في الأموال |
| Optimistic Version وIdempotency | نبقيهما | يحميان العمليات الحرجة من التكرار والسباق |
| عدم تعديل POSTED والتصحيح بالعكس | نبقيه | يحافظ على الأثر التاريخي وقابلية التدقيق |
| جلسات خادمة وCSRF وRBAC وسياق شركة مثبت | نبقيها | أساس العزل والأمان |
| Audit وSecurity logs منفصلان عن logs التشغيلية | نبقيه | لكل سجل غرض واحتفاظ مختلف |
| تقارير مشتقة من القيود الفعلية | نبقيه حاليًا | يمنع إنشاء مصدر حقيقة مالي موازٍ |
| لقطة طباعة ثابتة للمستند المرحل | نبقيها | تحافظ على المستند التاريخي عند تغير المرجعيات |

## 3. ما يجب إصلاحه أو تحسينه

### 3.1 أولوية P0 — حماية السلامة المعمارية

#### أ. مالك مركزي للترحيل المحاسبي

يجب إنشاء `PostingEngine` داخل Core Accounting ليكون المالك الوحيد لإنشاء وعكس `JournalEntry` و`JournalLine` وتغيير حالة `AccountingDocument` المالية.

الوحدات مثل Sales وPurchases وTreasury تبني `PostingPlan` فقط، ولا تحفظ القيود بنفسها.

تعريف الإنجاز:

- لا يوجد إنشاء جديد لـ`JournalEntry/JournalLine` خارج Core Accounting.
- جميع أنواع المستندات تمر عبر سياسات توازن وفترة وحساب موحدة.
- الترحيل والعكس يبقيان داخل معاملة ACID واحدة.
- اختبارات التكامل الحالية تستمر بالنجاح مع اختبارات parity لكل نوع مستند.

#### ب. تثبيت ملكية الـBounded Contexts

يجب إسناد كل Aggregate وجدول إلى مالك واحد وفق [خريطة السياقات](BOUNDED_CONTEXT_MAP_AR.md).

يمنع إنشاء وصول مباشر جديد من Service في Context إلى Prisma model يملكه Context آخر. يستخدم بدلًا منه:

- Application Port لاستدعاء متزامن.
- Query Port للقراءة.
- Domain/Integration Event للأعمال اللاحقة للـcommit.

#### ج. عدم استخدام معرفات Ledger كعقود بين المجالات

يجب التخلص تدريجيًا من جعل `targetJournalLineId` هو هوية الذمة بين Treasury وAR/AP. الهدف هو `ReceivableItemId` و`PayableItemId` أو مفهوم مجال مكافئ، مع إبقاء Journal Line تفصيلًا داخليًا في Core Accounting.

### 3.2 أولوية P1 — إزالة التكرار وتوضيح الملكية

#### أ. Treasury

يجب أن يملك Treasury:

- `CashBankAccount`.
- `PaymentMethod`.
- رؤوس `Receipt` و`Payment` وحركة النقد.

يجب إزالة منطق Treasury المكرر من Customer/Supplier services تدريجيًا.

#### ب. Tax Configuration

يجب وجود مالك واحد لـ`TaxRate` وسياسات حسابات ضريبة المدخلات والمخرجات. لا يجوز استمرار CRUD مستقل في Sales وPurchases لنفس الجدول دون واجهة مالك مركزية.

#### ج. خدمات البنية المشتركة

ينبغي توحيد ما يلي بدل نسخه داخل خدمات المستندات:

- `Money` والتقريب.
- Document numbering/sequence reservation.
- Master-data code reservation وفق [سياسة رموز البيانات الرئيسية](MASTER_DATA_CODE_POLICY_AR.md).
- Idempotent command execution.
- Fiscal-period validation.
- Posting-account validation.
- Event envelope وOutbox append.

التوحيد لا يعني إنشاء `shared` ضخم؛ توضع القاعدة عند مالكها الطبيعي وتُكشف عبر Port صغير.

#### د. تقليل الخدمات الضخمة والأنواع غير الآمنة

ينبغي تقسيم الخدمات الكبيرة حسب حالات الاستخدام والسياسات، وتقليل `any` لصالح أنواع Domain/Application صريحة. يمنع إدخال `any` جديد في منطق الأموال أو الترحيل أو العقود بين السياقات دون مبرر موثق.

### 3.3 أولوية P1 — موثوقية الأعمال اللاحقة للـcommit

يجب اعتماد Transactional Outbox وفق ADR-003، بدءًا من `RegistrationVerificationRequested` لأن البريد الحالي غير durable بعد commit.

حالة التنفيذ: اكتملت شريحتا بريد التسجيل واستعادة كلمة المرور بعامل داخلي durable؛ تطبق القواعد نفسها على أي حدث لاحق.

بعد ذلك تضاف أحداث الترحيل والعكس وإغلاق الفترة عندما يوجد مستهلك حقيقي أو Read Model واضح.

### 3.4 أولوية P0/P1 — التزامن والـDeadlocks والـDeadlines

يجب توحيد تصنيف أخطاء المعاملات وRetry وترتيب الأقفال والمهل وفق [سياسة التزامن والـDeadlock والـDeadlines](CONCURRENCY_DEADLOCK_DEADLINE_POLICY_AR.md).

الأولوية هي إصلاح الفرق بين سباق Idempotency والـdeadlock الحقيقي، وإعادة المعاملة كاملة عند الخطأ القابل للإعادة، وإضافة deadline موحد واختبارات post-vs-close والتسويات المتزامنة.

## 4. قواعد إلزامية للتطوير المستقبلي

### 4.1 قواعد الحدود والملكية

- يجب تحديد Bounded Context مالك قبل إضافة أي Feature أو جدول.
- يجب أن يكون لكل جدول تشغيلي مالك كتابة واحد.
- يمنع تعديل جدول Context آخر مباشرة من Service المجال.
- Reporting مسموح له بالقراءة عبر Query Layer فقط، ولا يكتب في مصادر المجالات.
- Onboarding ينسق بين Contexts ولا يصبح مالكًا لبياناتها.
- الأنواع المشتركة تقنيًا مثل `ActorContext` توضع في Application Kernel محدود، لا داخل وحدة أعمال عشوائية.
- يمنع إنشاء dependency cycle بين السياقات.

### 4.2 قواعد Core Accounting

- يمنع أي ترحيل أو عكس خارج `PostingEngine` بعد اكتمال نقله.
- يجب أن يبقى Ledger strongly consistent.
- يمنع نشر حدث ثم الاعتماد عليه لاحقًا لإكمال القيد المحاسبي الأساسي.
- يجب أن تشمل المعاملة: المصدر، القيود، الحالة، Audit، Outbox عند وجود حدث، وIdempotency.
- POSTED لا يعدل، والعكس مستند جديد في فترة مفتوحة.
- لا Float أو `Number` للحساب المالي النهائي.
- لا Network I/O داخل transaction.

### 4.3 قواعد الأحداث

- الأحداث للأعمال التي يمكن تنفيذها بعد commit، وليست بديلًا عن invariants المتزامنة.
- يجب حفظ Outbox Event في معاملة العمل نفسها.
- يجب أن تكون المعالجة At-least-once والـhandlers idempotent.
- يمنع استخدام `AuditLog`, `SecurityEvent`, أو logs التشغيلية كـOutbox.
- يجب إصدار `schemaVersion` لكل عقد حدث.
- يمنع نشر Prisma record كامل أو أسرار أو بيانات حساسة غير لازمة.
- يجب استخدام past tense في أسماء الأحداث.
- لا Broker خارجي أو Microservice دون ADR وقياسات تبرر القرار.
- لا Event Sourcing دون ADR مستقل؛ القرار الحالي لا يعتمده.

### 4.4 قواعد البيانات والعقود

- كل schema change عبر Migration واختبارات قاعدة فارغة وترقية.
- يجب تحديث Prisma وMigration والوثائق والعقد معًا حسب نطاق التغيير.
- يمنع `db push`, `MAX()+1`، وraw SQL غير parameterized.
- رموز البيانات الرئيسية المشمولة بالسياسة يولدها الخادم ذريًا، وتبقى ثابتة ولا تقبلها عقود الإنشاء أو التعديل.
- يجب المحافظة على company isolation في كل query واختبار cross-company.
- يجب ألا تعبر DTOs أو Prisma types حدود Context كعقد دائم؛ يستخدم عقد Application أو Event صريح.

### 4.5 قواعد المراجعة والتسليم

- يجب إكمال [قائمة مراجعة التغيير](CHANGE_REVIEW_CHECKLIST_AR.md) لأي تغيير ذي أثر معماري.
- أي استثناء جديد يحتاج ADR قبل الدمج.
- يجب تحديث خريطة السياقات عند تغير الملكية أو اتجاه الاعتماد.
- يجب إضافة اختبارات تمنع تكرار الخلل المعماري عند كل عملية نقل جوهرية.
- لا يعتبر التغيير منتهيًا إذا كانت الوثائق أو OpenAPI أو Migration غير متوافقة معه.

### 4.6 قواعد التزامن والمهل

- يجب أن تستخدم العمليات الحساسة Transaction Executor وسياسة Retry مركزية عند توفرها.
- يمنع Retry غير محدود أو Retry لأخطاء Business.
- يجب قفل الصفوف المتعددة بترتيب ثابت عالميًا.
- يجب أن تقع كل المحاولات ضمن deadline واحد، لا deadline جديد لكل محاولة.
- يجب تحديد `maxWait` و`timeout` للمعاملات الحساسة بدل الاعتماد الدائم على defaults.
- Idempotency تجعل إعادة المحاولة آمنة، لكنها لا تستبدل version أو locking.
- يجب اختبار التزامن على MySQL/MariaDB الفعليين للمسارات المالية الحرجة.

## 5. سياسة الانتقال من الوضع الحالي

لا يطلب إصلاح شامل دفعة واحدة. تطبق القواعد كالتالي:

1. **Stop the bleeding:** يمنع إدخال وصول مباشر أو تكرار جديد.
2. **Improve when touched:** عند تعديل مسار مخالف، يجب تقليل المخالفة أو توثيق سبب التأجيل وخطة إزالتها.
3. **Extract high-risk rules first:** الترحيل والعكس والأموال والتسويات قبل CRUD العادي.
4. **Preserve behavior:** كل نقل معماري يرافقه regression/integration tests.
5. **No distributed rewrite:** لا تُحوّل السياقات إلى Microservices لمجرد وجود حدود منطقية.

## 6. مؤشرات تستدعي مراجعة القرار

ينشأ ADR جديد فقط عند وجود واحد أو أكثر من الآتي:

- فريق مستقل ودورة إصدار مستقلة لسياق محدد.
- حاجة Scaling أو Availability مختلفة جذريًا ومدعومة بقياسات.
- تكاملات خارجية أو jobs طويلة لا يكفيها Outbox worker داخل المونوليث.
- حجم بيانات أو قفل معاملات يثبت بالقياس أن الحدود الحالية لم تعد مناسبة.
- متطلبات تنظيمية تفرض فصلًا تشغيليًا أو تخزينيًا.
