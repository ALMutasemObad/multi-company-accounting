# ADR-017: خطط الاشتراك واستحقاقات الموديولات والدفع الإلكتروني

## السياق

يملك النظام حاليًا حساب فوترة واحدًا لكل شركة مع `planName` وتسعير استخدام مباشر،
وفواتير منصة وسدادًا يسجله مشغل المنصة. لا يوجد كتالوج خطط مؤرخ، أو اشتراك ذاتي، أو
استحقاقات موديولات، أو دفع إلكتروني. كما أن صلاحية المستخدم الحالية تجيب عن «ماذا
يسمح لهذا المستخدم أن يفعل داخل شركته؟»، ولا تجيب عن «ما الموديولات التي اشتركت بها
الشركة أصلًا؟».

إضافة إخفاء واجهة فقط أو ربط الخطة بالدور سيخلط قرارًا تجاريًا على مستوى الشركة مع
قرار أمني على مستوى المستخدم، ويمكن تجاوزه باستدعاء API مباشرة.

## القرار

يعتمد موديول مستقل داخل النطاق المنصّي باسم **Platform Subscriptions & Entitlements**،
بواجهة منفصلة عن تحليلات التشغيل. يملك كتالوج الخطط، اشتراك الشركة، استحقاقات
الموديولات، ومحاولات الدفع الإلكتروني الخاصة بفواتير المنصة. تبقى فواتير المنصة
وسداداتها خارج Sales/Treasury/Ledger للشركة المستأجرة.

تبدأ الشريحة الأولى باشتراك على مستوى `Company` اتساقًا مع حساب الفوترة الحالي. لا
يفترض اشتراكًا موحدًا على مستوى `Organization` قبل قرار مستقل عن التسعير والفوترة
والحصص بين الشركات التابعة.

## النموذج المستهدف

- `PlatformModule`: كود ثابت للموديول، حالة إتاحته، واعتمادياته على موديولات أخرى.
- `PlatformPlan` و`PlatformPlanVersion`: هوية الخطة ونسخة immutable مؤرخة للاسم
  والوصف والدورة والعملة والسعر وسياسة التجربة والحدود المشمولة.
- `PlatformPlanEntitlement`: الموديولات والحدود التي تمنحها نسخة الخطة.
- `PlatformAddOn` ونسخته: موديول أو حصة إضافية يمكن لمدير الشركة اختيارها.
- `PlatformSubscription`: اشتراك الشركة وحالته ونسخة الخطة والفترة والتجربة وسياسة
  التجديد و`version`.
- `PlatformSubscriptionEntitlement`: الاستحقاق الفعلي المؤرخ، مع مصدره Plan/Add-on/
  Grandfathered وسبب التغيير.
- `PlatformCheckoutSession` و`PlatformPaymentAttempt`: مراجع مزود الدفع وحالة المحاولة
  فقط؛ لا رقم بطاقة أو CVV أو بيانات اعتماد دفع.
- `PlatformWebhookReceipt`: معرف حدث المزود وبصمته ووقت استلامه ونتيجة معالجته لضمان
  idempotency وعدم تطبيق الحدث مرتين.

لا تكون أسماء «تجريبي/مجاني/أساسي/احترافي» Enum في الشفرة؛ هي سجلات كتالوج قابلة
للترجمة والإصدار. تبقى حالات دورة الاشتراك ثابتة مثل `TRIALING`, `ACTIVE`,
`PAST_DUE`, `SUSPENDED`, `CANCELED` لأنها قواعد سلوك، لا أسماء باقات تسويقية.

## اختيار الموديولات والقدرات

- يختار مدير شركة مخول الخطة والإضافات المتاحة، ولا يغير مستخدم عادي اشتراك الشركة.
- قابلية رؤية أو استخدام موديول تساوي تقاطع:
  `company entitlement ∩ user RBAC permission ∩ rollout/feature safety gate`.
- إخفاء البطاقة والتنقل والأزرار نتيجة UX فقط. كل Router/Use Case حساس يعيد التحقق
  خادميًا من الاستحقاق والصلاحية والسياق؛ لا يكفي `#/route` أو React guard.
- يوسع عقد capabilities المبني على `/auth/me` ليعيد أكواد موديولات مستحقة ومزايا
  محددة، دون كشف تسعير داخلي أو صلاحيات شركات أخرى.
- لا تستخدم أكواد الصلاحيات نفسها كأكواد اشتراك؛ `sales_invoices.post` قرار RBAC،
  بينما `SALES` استحقاق تجاري. يربطهما Policy مركزي قابل للاختبار.
- تتحقق اعتماديات الموديولات قبل الشراء أو التخفيض؛ لا يمكن مثلًا تمكين POS دون
  المالكين اللازمين لدورة البيع والمخزون والخزينة، ولا تفعل الواجهة اعتمادًا ناقصًا.
- لا يؤدي انتهاء الاشتراك إلى حذف بيانات أو كسر التاريخ المحاسبي. تطبق Grace Period
  وسياسة قراءة/تصدير واضحة، وتبقى القيود والفواتير والدفاتر التاريخية قابلة للتدقيق.

## التوافق والترحيل من النموذج الحالي

لا يستبدل `planName` الحالي مباشرة ولا يعاد تفسير الفواتير السابقة. تنفذ الهجرة
تدريجيًا:

1. إضافة الكتالوج والنسخ والاشتراك والاستحقاقات دون حذف حقول الفوترة الحالية.
2. إنشاء خطة/نسخة legacy واشتراك `Grandfathered` لكل حساب قائم، مع منح الموديولات
   الحالية حتى لا تختفي وظائف العملاء عند الإطلاق.
3. حفظ `planVersionId` ولقطة اسم الخطة والسعر والاستحقاقات المؤثرة على كل فاتورة
   جديدة؛ تبقى الفاتورة immutable حتى لو تغير الكتالوج.
4. نقل إصدار الفاتورة إلى قراءة نسخة الاشتراك عبر Port، ثم إيقاف الكتابة في
   `planName` القديم قبل حذفه في Migration لاحقة مستقلة.

## الدفع الإلكتروني

- التكامل عبر `PlatformPaymentProviderPort` وAdapter لكل مزود؛ لا تنتشر SDK أو أنواع
  المزود داخل Domain أو OpenAPI العام.
- ينشئ الخادم Checkout لفاتورة منصة محددة ومبلغ/عملة مثبتين. لا يثق بمبلغ أو نجاح
  يرسله المتصفح.
- Webhook هو مصدر إثبات النتيجة، ويجب التحقق من التوقيع والطابع الزمني وبيئة
  test/live قبل أي كتابة.
- يحجز `providerEventId` بصورة فريدة ويطبق الحدث idempotently داخل معاملة؛ الآثار
  الخارجية اللاحقة تمر عبر Transactional Outbox بعد commit.
- لا Network I/O داخل معاملة قاعدة البيانات. الاستعلام عن المزود أو إنشاء Checkout
  يحدث خارجها مع state machine قابلة للاستئناف وحد زمني.
- لا تخزن المنصة PAN أو CVV. يهدف التصميم إلى hosted checkout/tokenization وتقليل
  نطاق PCI، لكن اختيار المزود والامتثال النهائي يحتاجان قرار الدولة والعملات والضرائب
  وسياسة الاسترداد وChargeback قبل التنفيذ.
- السداد الناجح ينشئ `PlatformBillingPayment` من Adapter المالك مرة واحدة ويربط مرجع
  المزود؛ لا ينشئ Receipt أو قيدًا داخل دفاتر الشركة العميلة.

## واجهات العرض

- `#subscription`: صفحة ذاتية لمدير الشركة تعرض الخطة الحالية، الموديولات المتاحة،
  الاستهلاك والحدود، الفواتير، وطريق الدفع/التغيير المسموح.
- `#platformSubscriptions`: واجهة مشغل المنصة لإدارة الكتالوج والنسخ والأسعار ومراقبة
  الاشتراكات والمدفوعات والاستثناءات، منفصلة عن `#platform` التحليلية.
- تطبيقات iOS وAndroid المستقبلية تستهلك العقود نفسها وتحترم الاستحقاقات نفسها؛ لا
  تنشئ مخزن اشتراك أو قرار صلاحية محليًا.

## ترتيب التنفيذ

بعد إغلاق دفعة أداء وأمان المنصة الحالية وبوابتي قاعدة البيانات:

1. `SUB-1`: كتالوج الموديولات والخطط والنسخ immutable واستحقاق Grandfathered، بلا دفع.
2. `SUB-2`: إنفاذ الاستحقاق خادميًا ودمجه مع capabilities والتنقل، مع اختبارات تمنع
   bypass المباشر وتثبت عدم اختفاء التاريخ.
3. `SUB-3`: اختيار الإضافات وQuote/Preview وترقية أو تخفيض مؤرخ بعد اعتماد سياسة
   proration والحدود والـGrace Period.
4. `PAY-1`: Spike لمزود دفع واحد بعد تحديد الدولة والعملات؛ تحقق Webhook وHosted
   Checkout في sandbox واختبارات replay/out-of-order/timeout/chargeback.
5. `PAY-2`: إطلاق مرحلي ومراقبة ومطابقة يومية واسترداد/نزاع وفق السياسة المعتمدة.

لا يخلط تنفيذ هذه الشرائح مع CRM أو Service Catalog أو نضج Projects في PR واحد.

## حالة التنفيذ

بدأت `SUB-1` في 30 أغسطس 2026 بدفعة تأسيسية توسعية لا تغيّر سلوك الفوترة أو الواجهة:

- أضيف كتالوج `PlatformModule` وأكواد تجارية مستقلة عن أكواد RBAC، مع اعتماديات
  صريحة تمنع تركيب POS بلا Sales وInventory وTreasury.
- أضيفت `PlatformPlan/PlatformPlanVersion`؛ تحفظ النسخة لقطة الدورة والعملة والسعر
  والحصص وسياسة التجربة، ولا يوجد مسار تعديل لنسخة منشورة.
- أضيف `PlatformSubscription` واستحقاق فعلي مؤرخ ومعزول بعلاقة مركبة مع الشركة،
  إضافة إلى Query Port للقراءة لا يمنح أي سياق آخر حق الكتابة.
- ينشئ الترحيل خطة Legacy ونسخة واشتراكًا لكل شركة قائمة، سواء كان حساب الفوترة
  مهيأ أم لا، ويمنح كل الموديولات المنفذة وقت الترحيل كمصدر `GRANDFATHERED`. لا يحدّث
  `planName` أو الفواتير أو السدادات السابقة ولا يختلق سعرًا لشركة بلا حساب فوترة.
- CRM وService Catalog موجودان في الكتالوج بحالة غير نشطة ولا يمنحان كقدرة منفذة.

لا تضيف هذه الدفعة API عامًا أو اختيار خطة ذاتيًا أو إنفاذًا على Routers أو دفعًا
إلكترونيًا. هذه وظائف `SUB-2/SUB-3/PAY-*` التالية، ولا يجوز تفعيل الإخفاء قبل أن
يتزامن مع إنفاذ `entitlement ∩ RBAC` خادميًا.

## بوابات القبول

- عزل شركتين، ومنع تغيير اشتراك شركة أو قراءته من شركة أخرى.
- إنفاذ `entitlement + RBAC` في الخادم والواجهة واختبارات API مباشرة.
- نسخة خطة وفاتورة تاريخية لا تتغيران بعد تعديل اسم الخطة أو سعرها أو موديولاتها.
- Idempotency وتزامن تغيير الخطة مع إصدار الفاتورة، وترتيب Webhooks المكررة والمتأخرة.
- Decimal نصي ودقة العملة، وعدم جمع عملات مختلفة.
- Audit لا يحتوي أسرار المزود أو payload كاملًا، والسجلات التشغيلية لا تحتوي توقيعًا
  أو token أو بيانات بطاقة.
- OpenAPI والحراس، TypeScript والبناء، E2E، وترجمات RTL/LTR والهاتف.
- MariaDB 10.11 وMySQL 8.4 والترقية والعكس المحروس والنسخ والاستعادة.

## خارج النطاق حتى قرار لاحق

- اختيار مزود الدفع أو رسومه من دون دولة وعملات مستهدفة وقياسات فعلية.
- اشتراك موحد للمؤسسة أو إعادة توزيع حصص بين الشركات.
- Marketplace لطرف ثالث، Revenue Recognition، أو قيود محاسبية في دفاتر العميل.
- حذف بيانات العميل تلقائيًا بسبب الإلغاء أو التأخر في السداد.
