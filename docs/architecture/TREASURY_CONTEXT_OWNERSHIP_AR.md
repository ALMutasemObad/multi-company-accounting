# ملكية سياق Treasury وسياسة أدوات الحركة النقدية

## 1. القرار

`CashBankAccount` و`PaymentMethod` مملوكان حصريًا لوحدة `Treasury`. لا تنفذ خدمات العملاء أو الموردين أو القبض أو الصرف Prisma CRUD مباشرًا عليهما. تستخدم حركتا القبض والصرف `TreasuryInstrumentPort` للحصول على حساب النقد وطريقة الدفع الصالحين داخل المعاملة المالية نفسها.

تبقى مسارات HTTP العامة الحالية بلا كسر:

- `/cash-bank-accounts` للصناديق والحسابات البنكية.
- `/payment-methods` للطرق العامة والخاصة بالشركة.

ينفذ المسارات `TreasuryRouter`، بينما تبقى `/customers` و`/currencies` في راوتر مراجع القبض و`/suppliers` في راوتر الموردين. أزيل التنفيذ الكامل غير المستخدم للخزينة من خدمة الموردين، وأزيل CRUD الخزينة من خدمة العملاء.

## 2. حدود الملكية

| الوحدة | تملك | تستهلك |
|---|---|---|
| Treasury references | `CashBankAccount` و`PaymentMethod` وCRUD وسياسة الصلاحية والتقنيع والنسخ | الحساب المحاسبي كمرجع مقيد بالشركة |
| Receipt | رأس القبض وحركة النقد وتخصيصاتها | `TreasuryInstrumentPort` و`ReceivableSettlementPort` و`PostingEngine` |
| Payment | رأس الصرف وحركة النقد وتخصيصاتها | `TreasuryInstrumentPort` و`PayableSettlementPort` و`PostingEngine` |
| Registration/Onboarding | تنسيق تجهيز الشركة | `upsertGlobalPaymentMethods` المملوك لوحدة Treasury بدل Prisma المباشر |
| Reporting | قراءة الحركات المنشورة | Query/read model فقط بلا كتابة |

`Receipt` و`Payment` خدمتا تطبيق داخل سياق Treasury، لكنهما لا تدمجان في خدمة ضخمة: تبقى قواعد العميل والذمة المدينة في Receipt، وقواعد المورد والذمة الدائنة في Payment. المشترك الوحيد المستخرج هو سياسة أداة النقد وطريقة الدفع.

## 3. Invariants المرجعيات

- كل صندوق أو حساب بنكي مقيد بـ`companyId` ويرتبط بحساب محاسبي من الشركة نفسها.
- حساب الأستاذ المرتبط نشط، ورقي، يسمح بالترحيل ولا يملك أبناء.
- نوع `BANK` يحتاج اسم بنك، ولا تعاد أرقام الحساب أو IBAN خامًا؛ تحفظ آخر أربعة أرقام وتخرج مقنّعة.
- طريقة الدفع العامة مرئية لكل الشركات وغير قابلة للتعديل من API.
- طريقة الدفع الخاصة مرئية وقابلة للتعديل داخل شركتها فقط.
- الطريقة التي تتطلب مرجعًا ترفض حركة قبض أو صرف بلا `referenceNumber`.
- كل تعديل أو تعطيل يستخدم `WHERE id + companyId + version` ثم يزيد النسخة؛ عدم تحديث صف واحد يعني `VERSION_CONFLICT`.
- يولد الخادم رموز `CB-...` و`PM-{companyId}-...` ذريًا وفق سياسة رموز البيانات الرئيسية.

## 4. حدود الحركة المالية

يعمل `resolveInstrument` باستخدام `Prisma.TransactionClient` الذي يمرره Receipt أو Payment، لذلك لا توجد قراءة عالمية خارج معاملة الحركة ولا Network I/O. يعيد العقد فقط:

- هوية حساب النقد.
- حساب الأستاذ النقدي.
- هوية طريقة الدفع.
- هل المرجع إلزامي.

تبني خدمتا الحركة Posting Plan مستقلًا؛ يبقى `PostingEngine` المالك الوحيد للقيود والحالة، وتبقى تسوية الذمم عبر `ReceivableItem/PayableItem` ومنافذ AR/AP داخل المعاملة نفسها. لا يغير نقل الملكية ترتيب أقفال الفترة والمستند وعناصر الذمم وLedger.

## 5. التزامن والأخطاء

تمر إنشاءات وتعديلات وتعطيلات مراجع Treasury عبر `TransactionExecutor` بمهلة واحدة وretry محدود لأخطاء قاعدة البيانات العابرة فقط. لا يعاد خطأ النسخة القديمة أو العزل أو المرجع العام؛ يعاد HTTP 409 للنسخة القديمة و404 للكيان غير المرئي و422 لقاعدة الأعمال.

اختبارا التحديث المتنافس على `CashBankAccount` و`PaymentMethod` يثبتان نجاح طلب واحد فقط وإعادة 409 للآخر على MariaDB وMySQL الفعليين.

## 6. الترحيل والتوافق والرجوع

الترحيل `20260822234500_treasury_context_ownership` توسعي فقط:

- يضيف `cash_bank_accounts.version` كـ`INT UNSIGNED NOT NULL DEFAULT 0`.
- يضيف `payment_methods.version` بالصورة نفسها.

لا يعيد كتابة المرجعيات أو حركات القبض والصرف أو التخصيصات. اختبر من قاعدة فارغة وكترقية للترحيل السابق مع صفَّي حساب خزينة وأربع طرق دفع على MariaDB 10.4.32 وMySQL 8.4.11؛ بقيت الأعداد ثابتة وأصبحت النسخ صفرًا.

يمكن للـBinary القديم قراءة الجدولين بعد إضافة العمود، لكنه لا يرسل النسخة في التعديل. ترتيب النشر المعتمد: نسخة احتياطية قابلة للاستعادة، `migrate deploy`، ثم Artifact الجديد. عند رجوع التطبيق مؤقتًا يبقى العمودان الإضافيان غير ضارين، مع إيقاف كتابة مراجع Treasury حتى إعادة Artifact الجديد.

## 7. بوابات القبول

- حارس معماري يمنع Prisma access لـ`CashBankAccount/PaymentMethod` خارج Treasury في كود التشغيل.
- اختبارات وحدة للعزل وصلاحية حساب الأستاذ والمرجع الإلزامي والنسخة والطرق العامة.
- اختبارات تكامل للـCRUD والتقنيع والتعطيل والتزامن وcross-company.
- استمرار اختبارات القبض والصرف والتسوية والعكس والـIdempotency عبر المنفذ الجديد.
- نجاح 178/178 اختبار API على MariaDB وMySQL 8.4، وبناء API والواجهة، وOpenAPI/Redocly.
