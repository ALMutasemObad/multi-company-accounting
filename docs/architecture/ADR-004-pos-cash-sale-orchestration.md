# ADR-004: اعتماد أول شريحة لنقاط البيع كمنسق لبيع نقدي

## السياق

اكتملت في النظام دورة فواتير المبيعات والذمم، ودفتر المخزون الكمي والقيمي، وسندات القبض، وملكية Treasury، و`PostingEngine` المركزي. كانت الخطة السابقة ترجح محرك الموافقات بوصفه المرحلة التالية، بينما صنفت دراسة الموديولات POS ضمن P2 لأنه لم يكن نقصًا يمنع المحاسبة الأساسية.

طلب المرحلة الحالي هو اختيار موديول أعمال جديد، مع تفضيل POS ما لم يظهر مانع جوهري موثق. لذلك أعيد تقييم المرشحين على أساس الجاهزية الحالية لا على ترتيب الدراسة السابق وحده.

## المفاضلة

| المعيار | POS — بيع نقدي | محرك الموافقات المشترك |
|---|---|---|
| قيمة مباشرة على النظام الحالي | عالية: يوحد البيع والمخزون والتحصيل في رحلة واحدة | متوسطة: بنية تمكينية قبل وجود مستند جديد يحتاج Maker/Checker |
| جاهزية المالكين | عالية: Sales وInventory وTreasury وCore Accounting مكتملة | عالية تقنيًا بعد اعتماد XState، لكن حالات الاستخدام الأولى غير محسومة |
| خطر تكرار الحقائق | مرتفع إن بُني كفاتورة/مخزون مستقل، ويمكن منعه بمنسق رفيع | منخفض، مع خطر تحول المحرك إلى مالك حالات المجالات |
| اعتماد خارجي جديد | لا يحتاج | لا يحتاج؛ يمكن إعادة Adapter XState الحالي لاحقًا |
| شريحة قابلة للإغلاق | بيع نقدي كامل أحادي التحصيل قابل للاختبار والعكس عبر المالكين | يحتاج اختيار مستند أول وسياسة Maker/Checker قبل إظهار قيمة أعمال كاملة |

## القرار

اعتماد **POS** الآن، لأن اكتمال المالكين الأربعة أزال المانع الذي كان يبرر تأجيله، ولأن شريحة بيع نقدي صغيرة تقدم قيمة تشغيلية مباشرة. لا يعد هذا رفضًا لمحرك الموافقات؛ يعاد إلى قائمة المراحل التالية قبل الأصول والمصروفات التي تحتاجه.

POS هو **Process Manager / Application Orchestrator** داخل الـModular Monolith، وليس مالكًا لفاتورة أو ذمة أو حركة مخزون أو حركة نقد أو قيد. يملك فقط سجل الربط `PosSale` الذي يثبت أن أمر Checkout واحد نتج منه فاتورة مبيعات وسند قبض محددان.

### اتجاهات الاعتماد

```text
POS checkout
  ├──> Sales cash-checkout application port
  │      ├──> Tax quote port
  │      ├──> Inventory catalog/stock ports
  │      └──> Core Accounting PostingEngine
  └──> Treasury receipt application port
         ├──> Treasury instrument port
         ├──> AR settlement port
         └──> Core Accounting PostingEngine
```

- يمنع POS من إنشاء أو تعديل `SalesInvoice`, `SalesInvoiceLine`, `ReceivableItem`, `Receipt`, `ReceiptAllocation`, `InventoryMovement`, `InventoryBalance`, `JournalEntry` أو `JournalLine` مباشرة.
- لا يحمل `PosSale` بنودًا أو مبالغ أو أرصدة أو نسخًا من بيانات الفاتورة؛ يعرضها عبر Query Port للمالكين.
- ينفذ Checkout داخل معاملة ACID واحدة ومفتاح Idempotency واحد. فشل التحصيل أو المخزون أو الترحيل يلغي سجل POS والفاتورة والسند والقيود والحركة كلها.
- لا Event أو Outbox في الشريحة الأولى لأن جميع الآثار حاكمة ومطلوبة قبل إرجاع النجاح. يمكن إضافة حدث `PosSaleCompleted` فقط عند وجود مستهلك لاحق حقيقي.

## حدود المرحلة الأولى

تدعم المرحلة الأولى بيعًا نقديًا حضوريًا واحدًا، بعملة واحدة وسعر صرف واحد، ومستودع واحد، وعميل مسجل واحد، وطريقة تحصيل واحدة، وتسوية كاملة لمبلغ الفاتورة. تحسب Sales الإجمالي ولا يقبله POS من العميل، وتحرك Inventory الأصناف المخزنية عند ترحيل الفاتورة، وتسجل Treasury سند قبض مخصصًا بالكامل لعنصر الذمة الناتج، وينشئ `PostingEngine` القيود.

خارج النطاق: تعليق السلة، العمل دون اتصال، أكثر من Tender، دفع جزئي، مرتجع POS مستقل، قارئ باركود أو طابعة/درج نقد خارجي، ورديات الصندوق والتسليم، خصومات الصلاحية، عميل نقدي مجهول، مزامنة فروع، وبرنامج ولاء.

## الترحيل والعكس

- الترحيل: Sales ينشئ الفاتورة ويرحلها عبر `PostingEngine`؛ Inventory يطبق حركة `ISSUE` في hook المالك؛ Treasury ينشئ سند القبض المخصص للذمة ويرحله عبر `PostingEngine`; ثم يحفظ POS رابط النتيجة.
- عكس الأعمال: لا ينشئ POS مسار عكس موازٍ في المرحلة الأولى. يعكس المستخدم سند القبض أولًا عبر Treasury ثم يعكس الفاتورة عبر Sales؛ كل مالك يحمي نسخه وتسوياته وحركة المخزون التاريخية. تعرض شاشة POS الحالة المشتقة من المستندين ولا تغيرها بنفسها. إضافة أمر عكس مركب تحتاج تصميم ترتيب أقفال مستقل واختبارًا فعليًا قبل اعتمادها.
- ترحيل قاعدة البيانات توسعي فقط. الرجوع البرمجي يعطل مسارات وشاشة POS مع إبقاء جدول الربط. إسقاط الجدول مسموح فقط بعد التأكد أنه لا يحتوي صفوفًا، كي لا تضيع سلسلة التدقيق.

## الصلاحيات

- `pos.view`: عرض شاشة POS والمبيعات الناتجة.
- `pos.checkout`: تنفيذ البيع النقدي، ولا يرث تلقائيًا صلاحيات CRUD العامة للمبيعات أو القبض.

تبقى صلاحيات عكس سند القبض والفاتورة `receipts.reverse` و`sales_invoices.reverse` عند مالكيهما. يمنح الدور الإداري الصلاحيتين الجديدتين عبر Migration وSeed؛ الأدوار المخصصة لا ترثهما تلقائيًا.

## التزامن والعزل

- `Idempotency-Key` إلزامي، والبصمة تشمل كل مدخلات Checkout بترتيب حتمي.
- كل صف وعلاقة يحمل `companyId`، وتمنع المفاتيح المركبة ربط فاتورة أو سند من شركة أخرى.
- تستخدم العملية `TransactionExecutor` بحد محاولات وdeadline واحد. لا Network I/O أو sleep داخل المعاملة.
- عنصر الذمة وسند القبض يولدان داخل المعاملة نفسها ولا يمكن لمعاملة منافسة رؤيتهما قبل الالتزام؛ لذلك لا يوجد مسار خارجي يستطيع قفل عنصر التسوية الجديد بين قيد البيع وقيد القبض. تبقى أقفال الموارد الموجودة مسبقًا — الفترة والمستند والمخزون — بترتيب مالكيها، وتعيد `TransactionExecutor` الأمر الكامل فقط عند خطأ قاعدة عابر مصنف.
- تفرد `(companyId, salesInvoiceId)` و`(companyId, receiptId)` دفاع إضافي ولا يستبدل Idempotency أو أقفال المالكين.
- يجب أن تثبت الاختبارات: إعادة المفتاح نفسه، رفض payload مختلف، rollback الكامل عند فشل Treasury، عدم تجاوز المخزون، عزل الشركات، وعدم وجود كتابة Ledger في POS.

## الاعتماديات

لا تضاف مكتبة خارجية. الحساب والحالات المالية موجودة لدى المالكين الحاليين، وإضافة SDK POS أو ERP خارجي ستكرر Ledger أو المخزون أو الفاتورة بلا ضرورة مثبتة.

## النتائج والتبعات

الإيجابي: رحلة بيع نقدي واحدة من الواجهة إلى القيد مع مصدر حقيقة واحد لكل مجال وخطة خروج بسيطة بحذف المنسق. التكلفة: المعاملة أطول من أمر فاتورة منفرد، ولذلك تبقى الشريحة محدودة البنود ويجب قياس زمنها واختبار التنافس على قاعدة فعلية. كما أن العكس المركب وورديات الصندوق مؤجلان عمدًا ولا يجوز تمثيلهما بتعديل مباشر لسجل POS.
