# نواة الرواتب المحايدة للدولة

## 1. وضع هذا المستند وحدوده

هذا المستند تصميم قابل للتحويل إلى مهام تنفيذ، وليس إعلانًا عن ميزة منفذة. لا تغيّر
هذه المهمة Prisma schema أو Migration أو OpenAPI أو API أو Posting Engine. يلزم قبل
التنفيذ ADR مقبول، وقرار خصوصية واحتفاظ، وسياسة حسابات، ومراجعة متطلبات الدولة
المستهدفة.

تعني «محايدة الدولة» هنا أن النواة لا تفترض بلدًا أو ضريبة دخل أو تأمينًا اجتماعيًا
أو مكافأة نهاية خدمة أو تقويمًا أو عملة بعينها. وهي لذلك **ليست محرك امتثال صالحًا
للإنتاج في كل الدول**. أي حساب إلزامي قانونًا يأتي في حزمة سياسة دولة مؤرخة ومختبرة
خلف Port مستقل، ولا يضاف كنسبة ثابتة أو شرط دولة داخل النواة.

نطاق الشريحة الأولى المقترحة:

- تعريف مكونات استحقاق واستقطاع داخل الشركة، ثم إسناد مبالغ ثابتة مؤرخة للموظف.
- إدخالات موجبة لمرة واحدة ضمن دورة رواتب، مع فصل الاستحقاق عن الاستقطاع.
- حساب لقطة رواتب ثابتة، وإرسالها إلى Approvals، واعتمادها بفصل Maker/Checker.
- ترحيل الدورة المعتمدة فقط إلى Core Accounting عبر Port و`PostingEngine`.
- عرض إجمالي الاستحقاقات والاستقطاعات وصافي المستحق لكل موظف وللدورة.

خارج الشريحة:

- الضرائب والتأمينات والمزايا الملزمة نظاميًا وأي تقرير أو ملف حكومي.
- الحضور والساعات الإضافية والإجازات والعمل بالقطعة والنسب والصيغ العامة.
- تحويل العملات داخل الدورة؛ تكون الدورة بعملة واحدة وتقبل اتفاقات العملة نفسها فقط.
- الحساب البنكي والهوية الوطنية وملفات الدفع والتحويل البنكي والتسوية في Treasury.
- السلف والقروض والحجز القضائي ومكافأة نهاية الخدمة والتسوية النهائية.
- بوابة موظف ذاتية أو كشف راتب PDF؛ كلاهما يحتاج قرار خصوصية وإخراج مستقلًا.

## 2. الملكية وحدود السياقات

يقترح ADR اللاحق سياقًا مستقلًا باسم `Payroll`. لا يوسّع HR ليملك الأموال؛ يبقى HR
مالك الموظف وحالة العمل والعقد غير المالي. يملك Payroll حقائق التعويض ودورة الحساب
ولقطاتها فقط، بينما تبقى الملكيات الأخرى كما يلي:

| الحقيقة | المالك | ما يراه Payroll |
|---|---|---|
| الموظف وحالة العمل وتاريخ الالتحاق/الإنهاء | Human Resources | مرجع أهلية محدود عبر Port |
| المستخدم والصلاحيات | Identity & Access | ActorContext فقط |
| العملة ودقتها وتمكينها | Tenant Configuration | مرجع عملة عبر Query Port |
| طلب وقرار الموافقة | Approvals | معرف الموضوع ونسخته وبصمته فقط |
| الفترة والحسابات والمستند والقيد | Core Accounting | جاهزية الترحيل ونتيجته عبر Ports |
| أداة الدفع والحركة البنكية | Treasury | لا اتصال في الشريحة الأولى |
| حقائق التعويض ودورة الرواتب ولقطة الحساب | Payroll | ملكية كتابة وحيدة |

لا يقرأ Payroll جداول HR أو Accounting أو Approvals مباشرة، ولا يكتب سياق آخر عبر
Prisma. لا يخزن قرار الموافقة أو أسطر Ledger نسخة ثانية. يجوز له حفظ معرف مرجع
المستند المحاسبي الناتج لإثبات الربط، بينما يجلب رقمه وحالته من Core Accounting عند
العرض.

## 3. النموذج المقترح

الأسماء أدناه أسماء تصميمية؛ لا تنشئ هذه المهمة جداولها.

### 3.1 تعريفات المكونات

`PayrollComponentDefinition` داخل الشركة:

- `publicId`, `companyId`, رمز خادمي ثابت، اسمان، `kind` يساوي `EARNING` أو
  `DEDUCTION`، حالة نشاط، و`version`.
- `calculationMethod=FIXED_AMOUNT` فقط في أول شريحة.
- `postingRole` دلالي لا يحمل رقم حساب، مثل `BASE_EARNING`, `ALLOWANCE`, أو معرف
  التزام استقطاع خاص بالمكوّن. تربط Core Accounting هذه الأدوار بحساباتها في ملف
  ترحيل مؤرخ تملكه هي.
- التعريف لا يحمل نسبة ضريبة أو شرط دولة أو معادلة قابلة للتنفيذ.

كل مبلغ داخل Payroll يمثل Decimal canonical string في العقود، ويخزن
`DECIMAL(27,8)`؛ فهذا يبقي 19 منزلة صحيحة وثماني منازل كسرية، ويغطي كامل نطاق
`currency.decimals` الحالي من 0 إلى 8 بلا إسقاط صامت. يمنع `Number` أو Float
للحساب النهائي. يرفض الإدخال منازل تتجاوز دقة عملة الدورة، وتنفذ المجاميع بDecimal
عند scale 8 ثم تعرض بالقيمة الدقيقة للعملة، من دون تقريب وسيط للأسطر.

يجب أن يثبت `PayrollPostingReadinessPort` أن `PostingPlan` وحقول Core Accounting
المقصودة تحفظ القيمة المكمّمة نفسها حتى ثماني منازل. إذا بقي أي مسار محاسبي على
scale أصغر، تكون توسعته Migration منسقة سابقة لإتاحة Payroll لتلك العملة؛ لا يسمح
المنفذ بالتقريب إلى أربع منازل ولا يعتبر فرق التقريب قيدًا متوازنًا.

### 3.2 اتفاق التعويض المؤرخ

`EmployeePayAgreement` يربط موظفًا بعملة ووتيرة دفع وفترة سريان ونسخة. يحتوي
`EmployeeRecurringPayLine` لكل مكوّن ومبلغ موجب. نوع المكوّن هو الذي يحدد هل السطر
استحقاق أم استقطاع؛ لا تقبل الاستقطاعات مبالغ سالبة ولا يسمح بقلب نوعها بالإشارة.

القواعد:

- اتفاق واحد نافذ للموظف في التاريخ نفسه لكل عملة/وتيرة، بلا تداخل.
- تعديل التعويض ينشئ نسخة مؤرخة جديدة؛ لا يعدل الاتفاق الذي استخدمته دورة محسوبة.
- الموظف المنتهي لا يبدأ له اتفاق بعد تاريخ الإنهاء، وتحدد أهلية جزء الفترة بسياسة
  مستقلة قبل دعم التجزئة؛ الشريحة الأولى لا تجزئ تلقائيًا.
- لا يحمل الاتفاق IBAN أو رقم هوية أو ضريبة أو رصيد إجازة.

### 3.3 الدورة والتشغيل

`PayrollCycle` يمثل شركة وعملة ووتيرة وحدي فترة شامل/حصري وتاريخ دفع مقترح. يمنع
تداخل دورتين غير ملغيتين للنطاق نفسه. يملك كل نطاق صف تنسيق دائمًا
`PayrollCycleScope(companyId, currencyId, frequency)` بمفتاح فريد، ولا يعتمد منع
التداخل على فحص بلا قفل أو Isolation افتراضي أو Partial Index غير متاح في
MySQL/MariaDB. يحتوي التشغيل على تشغيل واحد حاكم
`PayrollRun` وحالته ونسخته، مع إمكان محاولات حساب جديدة مؤرخة قبل الإرسال.

`PayrollRunEmployee` لقطة الموظف المستخدمة في الحساب: معرف الموظف ورقمه واسمه
وعملة الاتفاق ومعرف/نسخة الاتفاق. `PayrollRunLine` لقطة immutable بعد الحساب:
معرف تعريف المكوّن ونسخته ورمزه واسمه ونوعه والمبلغ ومصدره
`RECURRING | ONE_OFF`.

`PayrollOneOffInput` إدخال يدوي قبل الحساب لمكوّن موجود ومبلغ موجب وسبب. يحمل
Idempotency ونسخة ولا يتحول إلى تعريف دائم. لا تقبل الشريحة خصمًا سالبًا أو استحقاقًا
سالبًا؛ التصحيح يكون بسطر من النوع الصحيح وسبب واضح قبل الاعتماد.

المجاميع المشتقة من اللقطة:

```text
grossEarnings = sum(EARNING lines)
totalDeductions = sum(DEDUCTION lines)
netPayable = grossEarnings - totalDeductions
```

يرفض الحساب `netPayable < 0` في الشريحة الأولى. لا تخزن قيم مجمعة قابلة للتعديل؛
إذا حفظت لأداء القراءة فتوثّق كلقطة مشتقة وتتحقق مساواتها للأسطر عند كل انتقال.

## 4. دورة الحالة وفصل الواجبات

```text
DRAFT -> CALCULATED -> AWAITING_APPROVAL -> APPROVED -> POSTED
             |                 |
             v                 | reject
           DRAFT <-------------+

DRAFT | CALCULATED -> CANCELLED
POSTED -> REVERSAL_REQUIRED -> REVERSED
```

- `calculate`: يثبت الموظفين والاتفاقات والأسطر والمجاميع في محاولة حساب جديدة.
- أي تعديل إدخال بعد الحساب يعيد التشغيل إلى `DRAFT` ويلغي صلاحية اللقطة السابقة؛
  لا يغير صفوف لقطة سبق إرسالها.
- `submit`: يحسب SHA-256 canonical للموظفين والأسطر والمجاميع ونسخ الاتفاقات، ثم
  ينشئ موضوع `PAYROLL_RUN` في Approvals. يظل Payroll مالك حالة التشغيل.
- `approve/reject`: يملك Approvals الطلب والقرار ويطبق `PayrollApprovalSubjectAdapter`
  انتقال المالك داخل المعاملة. يعاد حساب البصمة ويرفض القرار عند تغير اللقطة أو النسخة.
- Maker الدورة لا يكون Checker. صلاحية `approvals.decide` لا تلغي صلاحية Payroll
  المطلوبة لرؤية بيانات التعويض.
- `post`: متاح لتشغيل `APPROVED` فقط وبالبصمة المعتمدة نفسها. لا يعني الاعتماد دفعًا،
  ولا تعني `POSTED` أن الموظف استلم المال.
- لا يعدل تشغيل مرحل. التصحيح بعكس Accounting موثّق ثم تشغيل فروقات جديد؛ تفاصيل
  off-cycle والعكس تحتاج بوابة قبول قبل التنفيذ.

## 5. المنافذ المطلوبة

الأنواع التالية عقود Application صريحة ولا تستخدم Prisma records:

### `PayrollEmployeePort` — يملكه Payroll ويطبقه HR Adapter

- `listEligibleEmployees(companyId, period, tx?)` يعيد مرجع الموظف والحالة وتواريخ
  الالتحاق/الإنهاء فقط.
- `lockEligibleEmployees(companyId, sortedEmployeeIds, period, tx)` يعيد اللقطة نفسها
  بعد القفل عند الحساب الحاكم.
- لا يعيد عقد العمل أو حساب الدخول أو بيانات هوية حساسة.

### `PayrollCurrencyPort` — يملكه Payroll ويطبقه Tenant Adapter

- يتحقق من أن العملة مفعلة للشركة ويعيد الرمز والدقة.
- لا يحول مبالغ ولا يخترع سعر صرف للدورة.

### `PayrollApprovalSubjectAdapter` — يطبقه Payroll لعقد Approvals

- `inspect` يعيد نوع الموضوع ومعرفه ونسخته وحالته والبصمة وفاعل الإنشاء.
- `approve/reject` ينفذ CAS لحالة Payroll فقط؛ لا يرحل ولا يدفع ضمن قرار Checker.
- يرفض اختلاف الشركة أو النسخة أو البصمة كـBusiness conflict بلا Retry.

### `PayrollPostingReadinessPort` — يملكه Payroll ويطبقه Core Accounting

- يتحقق قبل الإرسال/الترحيل من الفترة المفتوحة وملف ربط أدوار الاستحقاق والاستقطاع
  وحساب صافي المستحق، ويعيد `profileVersion/profileHash` وأسباب نقص مفهومة.
- لا يعيد شجرة حسابات كاملة ولا يسمح لـPayroll بتعديلها.

### `PayrollPostingPort` — يملكه Payroll ويطبقه Core Accounting

يقبل داخل `Prisma.TransactionClient` أمرًا idempotent يحمل:

- `companyId`, `payrollRunId`, `payrollRunVersion`, `approvedSnapshotHash`.
- `currencyCode`, `postingDate`, و`postingProfileVersion/hash`.
- مجاميع كل دور ترحيل كـDecimal strings، وإجمالي الاستحقاقات والاستقطاعات والصافي.

يتحقق Adapter من التطابق، ويبني `PostingPlan` متوازنًا، ويفوض الحفظ إلى
`PostingEngine`. التصور المحايد للقيد:

- مدين: مصروف كل دور استحقاق.
- دائن: التزام كل دور استقطاع.
- دائن: حساب صافي الرواتب المستحقة.

يجب أن يساوي مجموع المدين إجمالي الاستحقاقات، ومجموع الدائن الاستقطاعات + الصافي.
لا يرسل Payroll حسابات خامًا من العميل ولا ينشئ `JournalEntry/JournalLine` مباشرة.
يعيد المنفذ معرف `AccountingDocument` فقط. قراءة الرقم والحالة لاحقًا عبر
`PayrollAccountingDocumentQueryPort` صغير.

لا يوجد `TreasuryPaymentPort` في هذه الشريحة. إضافته قبل اعتماد ملكية تعليمات الدفع
وبيانات البنك والتسوية والعكس سيكون خرقًا صريحًا للنطاق.

## 6. المعاملة والتزامن

كل أمر كتابة يحمل Idempotency-Key، وكل تعديل يحمل `version`. لا يعاد Conflict أعمال
تلقائيًا. الترتيب المقترح:

- إنشاء/تعديل/إلغاء دورة: سجل Idempotency، ثم صف `PayrollCycleScope`، ثم الدورات
  المتداخلة، ثم الدورة وAudit.
- الحساب: سجل Idempotency، تشغيل الدورة، الموظفون مرتبين، اتفاقاتهم المرتبة،
  التعريفات، الإدخالات، ثم Audit.
- الإرسال: سجل Idempotency، التشغيل، ثم طلب الموافقة النشط.
- القرار: سجل Idempotency لدى Approvals، طلب الموافقة، ثم تشغيل Payroll؛ يطابق
  اتجاه ADR-005.
- الترحيل: سجل Idempotency، الفترة المحاسبية، تشغيل Payroll، ملف الربط، ثم
  AccountingDocument/Journal حسب ترتيب PostingEngine، ثم Audit.

لتحقيق ترتيب الترحيل لا يقفل Payroll التشغيل ثم يستدعي Core. يكون منسق الترحيل عند
حد `PayrollPostingPort` قادرًا على قفل الفترة أولًا ثم استدعاء CAS محدود يملكه Payroll
داخل المعاملة نفسها. يراجع هذا الترتيب مع PostingEngine قبل اعتماد ADR، ويضاف إلى
سياسة الأقفال. لا Network I/O أو توليد PDF أو إرسال بريد داخل المعاملة.

خوارزمية منع تداخل الدورة قابلة للإثبات على InnoDB في MySQL وMariaDB:

1. ينشأ صف النطاق مرة واحدة داخل المعاملة بـ`INSERT ... ON DUPLICATE KEY UPDATE`
   على المفتاح الفريد؛ عند السباق ينتظر الكاتب الآخر نتيجة المفتاح نفسه.
2. ينفذ `SELECT ... FOR UPDATE` لصف النطاق قبل أي فحص أو إدراج/تعديل/إلغاء دورة.
3. تحت القفل نفسه يبحث عن دورة غير ملغاة تحقق
   `existing.periodStart < proposed.periodEndExclusive AND
   existing.periodEndExclusive > proposed.periodStart`؛ وجودها يعيد Business
   conflict، وإلا تدرج الدورة ثم تثبت المعاملة.
4. لا يفرج عن قفل النطاق بين الفحص والكتابة، ولا ينشئ مسار آخر دورة أو يغير فترتها
   أو حالتها من دون هذا القفل. بذلك تتسلسل القرارات لكل شركة/عملة/وتيرة حتى تحت
   `READ COMMITTED`، ولا تعتمد السلامة على Gap Lock متغير السلوك.

اختبار التكامل يشغل اتصالين ومعاملتين مع Barrier قبل محاولة أخذ قفل النطاق، ثم يمسك
الأول بعد القفل عبر test hook بينما يثبت أن الثاني ينتظر، قبل تحرير الأول. لفترتين
متداخلتين يجب أن ينجح التزام واحد فقط ويرجع الآخر Conflict بعد رؤيته الصف المثبت؛
ولفترتين غير متداخلتين ينجح الاثنان بالتسلسل. يعاد الاختبار نفسه على MySQL وMariaDB،
ويغطي أيضًا create-vs-reschedule وcancel-vs-create مع timeout يثبت غياب deadlock.

تفردات إلزامية مستقبلًا:

- صف نطاق واحد لكل `(companyId, currencyId, frequency)`؛ وهو حارس كل فحوص التداخل.
- مفتاح request/idempotency يثبت إعادة إنشاء الفترة نفسها؛ لا يستخدم قيد status
  لمحاكاة Partial Unique، لأن حالات الإلغاء والتعديل لا تثبت منع التداخل.
- طلب موافقة نشط واحد لكل تشغيل.
- مستند ترحيل واحد لكل `(companyId, payrollRunId, approvedSnapshotHash)`.
- نتيجة واحدة لنفس Idempotency key والجسم؛ الجسم المختلف يعيد mismatch.

## 7. الصلاحيات والخصوصية

الصلاحيات المقترحة منفصلة ولا تمنحها صلاحيات HR تلقائيًا:

| الصلاحية | الغرض |
|---|---|
| `payroll.runs.view` | عرض الدورات والمجاميع المسموح بها |
| `payroll.runs.manage` | إنشاء الدورة والإدخالات والحساب |
| `payroll.runs.submit` | إرسال اللقطة للموافقة |
| `payroll.runs.post` | ترحيل تشغيل معتمد |
| `payroll.compensation.view` | عرض اتفاقات ومبالغ التعويض الحساسة |
| `payroll.compensation.manage` | إنشاء نسخ اتفاقات مؤرخة |
| `payroll.configuration.manage` | تعريف المكونات وربطها المحاسبي عبر واجهة Core |

صندوق Approvals لا يعرض مبالغ الرواتب العامة لمجرد `approvals.view`. يحتاج Query
من Payroll يطبق صلاحية التعويض ويرجع Review DTO محدودًا. تحفظ أسماء الموظفين والمبالغ
كبيانات حساسة؛ لا تدخل Logs أو Metrics أو Outbox payload. يجب قبل Migration اعتماد:

- من يستطيع رؤية راتب فردي مقابل مجاميع الدورة.
- تشفير الحقول/النسخ الاحتياطية، وسياسة الاحتفاظ والحذف القانوني والتصدير.
- منع تنزيلات CSV والتخزين المؤقت والمتصفح قبل تصميمها.
- Audit للأفعال الحساسة دون نسخ المبالغ أو البيانات البنكية في سجل عام.

## 8. العقود المستقبلية المقترحة

لا تنشئ هذه المهمة المسارات، لكنها تحدد شريحة OpenAPI اللاحقة:

- مكونات: `GET/POST /payroll/components` و`PATCH /payroll/components/{id}`.
- الاتفاقات: `GET/POST /payroll/employees/{employeeId}/agreements`.
- الدورات: `GET/POST /payroll/runs`, و`GET /payroll/runs/{id}`.
- الإدخالات: `POST/PATCH /payroll/runs/{id}/inputs` قبل الحساب فقط.
- الأوامر: `POST .../{id}/calculate`, `/submit`, `/post`, و`/request-reversal`.

تفصل DTOs دائمًا `earnings[]` و`deductions[]`، وتخرج Decimal وBigInt كنصوص. تحمل
الاستجابة `calculationSnapshotHash`, `version`, وحالة صريحة، ولا تعرض enum خامًا في
الواجهة. أجسام JSON تولد حراسها من OpenAPI؛ لا Zod موازٍ داخل Router.

## 9. خطة الترحيل والرجوع المستقبلية

تقسم إلى مرحلتين على الأقل:

1. Migration توسعي للتعريفات والاتفاقات والدورات واللقطات والصلاحيات، بلا تغيير HR.
2. بعد اعتماد ملف الحسابات، توسيع أنواع موضوع Approvals وAccountingDocument وربط
   Composition Ports، ثم إظهار Feature Flag لشركات تجريبية محددة.

الرجوع التشغيلي يعيد التطبيق السابق ويبقي بيانات الرواتب مشفرة وغير قابلة للكتابة.
يرفض rollback الإسقاط عند وجود اتفاق أو دورة أو لقطة أو طلب موافقة أو مستند محاسبي؛
لا يحذف التاريخ لاستعادة نسخة تطبيق.

## 10. مصفوفة الاختبارات المطلوبة للتنفيذ

- حساب ثابت يفصل الاستحقاقات والاستقطاعات ويثبت `gross - deductions = net` عند دقة
  كل عملة، مع حدود القيم ورفض الصافي السالب.
- منع اتفاقات متداخلة، مكوّن معطل، موظف منتهي، عملة غير مفعلة، أو عملة اتفاق مختلفة.
- منع دورتين متداخلتين باختبار اتصالين متزامنين على MySQL وMariaDB، مع حالات
  create-vs-create وcreate-vs-reschedule وcancel-vs-create وفترتين غير متداخلتين.
- حفظ مبالغ عملة ذات ثماني منازل من API إلى لقطة Payroll ثم PostingPlan بلا فقد أو
  تقريب وسيط، ورفض readiness إذا لم يحفظ Core Accounting الدقة نفسها.
- إعادة الحساب تنشئ لقطة جديدة ولا تعدل لقطة مرسلة؛ canonical hash ثابت لترتيب إدخال
  مختلف ومختلف عند تغير أي مبلغ/نسخة.
- عزل شركتين في كل قراءة وكتابة وعلاقة مركبة، وإخفاء وجود معرف شركة أخرى.
- Idempotency متزامن للحساب والإرسال والترحيل، ورفض payload مختلف.
- Maker/Checker، وقرار واحد، ورفض نسخة/بصمة قديمة، وعدم منح Approvals وصول التعويض.
- `post-vs-period-close`, و`post-vs-recalculate`, وترحيلين متزامنين؛ مستند وقيد واحد
  أو Conflict واضح بلا أثر جزئي على MySQL وMariaDB.
- توازن PostingPlan، ملف ربط ناقص/قديم، فترة مغلقة، عكس في فترة مفتوحة، وثبات POSTED.
- Migration من قاعدة فارغة وترقية ببيانات HR، وrollback guard مع بيانات فعلية.
- OpenAPI parity/guards، TypeScript، UI بأربع لغات وRTL/LTR وعروض
  390/768/1440/1920، واختبارات صلاحيات وعدم تسرب مبلغ.

## 11. بوابات البدء والقرار

لا يبدأ تنفيذ قاعدة البيانات قبل إغلاق هذه القرارات:

1. ADR ملكية Payroll واتجاه `PayrollPostingPort` وترتيب قفله.
2. دولة الإطلاق الأولى وحزمة سياساتها القانونية المؤرخة ومالك تحديثها.
3. سياسة الخصوصية والتشفير والاحتفاظ وصلاحيات الراتب الفردي.
4. ملف الحسابات الافتراضي وأدوار الاستحقاقات والاستقطاعات والصافي والعكس.
5. سياسة التجزئة والغياب والإنهاء والتصحيحات وoff-cycle.
6. تقييم build-versus-adopt لحزم حساب الرواتب/القوانين: الرخصة، نشاط المصدر، الأمن،
   قابلية العزل والتحديث والرجوع. لا Dependency مختارة في هذا التصميم.
7. قرار مستقل للدفع البنكي وTreasury؛ لا يعد نجاح الترحيل إذنًا بالدفع.
