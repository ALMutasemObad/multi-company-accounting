# هدف الفروع ومحطات نقاط البيع المتعددة

## الحالة الحالية

يدعم النظام عدة مستودعات وصناديق/حسابات وطرق دفع داخل الشركة، ويسمح لمستخدمين متعددين
بتنفيذ Checkout ذري. لكنه لا يملك كيان `Branch` أو `PosTerminal` أو وردية صندوق؛ لذلك
فهذا ليس دعمًا كاملًا للفروع ونقاط البيع المتعددة، حتى لو أمكن تشغيل عدة شاشات مع اختيار
المستودع والصندوق يدويًا.

## حد الكيان القانوني

- الموقع التشغيلي داخل نفس الكيان القانوني والدفتر والرقم الضريبي هو `Branch`.
- الكيان ذو دفاتر أو ضريبة أو ملكية قانونية مستقلة هو `Company`، لا فرعًا شكليًا.
- الفرع ليس دفتر أستاذ موازيًا ولا يكتب قيودًا؛ تبقى المحاسبة في الشركة، ويمكن إضافة
  بعد تحليلي للفرع بقرار مستقل ومتوافق مع مراكز التكلفة.

## الملكية المقترحة

- يملك Tenant/Company سجل الفرع ورمزه وحالته وعنوانه وتوقيته.
- يملك Inventory المستودع، ويقبل ربطه بفرع من الشركة نفسها دون نقل ملكية الكتابة.
- يملك Treasury الصندوق/الحساب وحقائق القبض والدفع وحركات النقد.
- يملك POS المحطة والوردية وربط البيع بالمحطة، ويظل منسقًا رفيعًا عبر Ports؛ لا ينسخ
  الفاتورة أو المخزون أو القبض أو Ledger.

## النموذج التشغيلي المستهدف

### الفرع

هوية ورمز يولده الخادم، اسم وعنوان وحالة، `companyId`، وتوقيت عند الحاجة. كل علاقة
عابرة تحمل مفتاح شركة مركب، ولا يسمح بنقل الفرع بين الشركات.

### محطة POS

تتبع فرعًا واحدًا وتحدد افتراضيًا:

- المستودع النشط.
- الصندوق/الحساب النقدي.
- طرق الدفع المسموحة.
- الطابعة وقالب الإيصال وإعداد قارئ الباركود عبر Device Adapter، لا داخل المجال.
- حالة التفعيل ونسخة optimistic وإعدادات لا تحتوي سرًا أو عنوان جهاز غير محمي.

هذه الافتراضات تزيل طلب المستودع والصندوق في كل Checkout، لكن الخادم يعيد التحقق منها
عند كل عملية، ويمكن منح صلاحية واضحة لتغييرها في حالة استثنائية.

### الوردية والصندوق

- فتح وردية لمستخدم ومحطة بعملة صندوق واحدة ورصيد افتتاحي.
- وردية نشطة واحدة كحد أقصى للمحطة، مع قفل يمنع السباق.
- ربط كل `PosSale` بالوردية والمحطة تاريخيًا.
- إغلاق بعد حساب المتوقع من حقائق Treasury، وإدخال الفعلي، وتسجيل الفرق والسبب
  والمراجعة. لا تنشئ POS حركة نقد موازية.
- لا hard delete ولا تعديل صامت لوردية مغلقة.

## القدرات المرحلية

1. `MBP-1`: الفروع والمحطات والإعدادات الافتراضية والصلاحيات والتدقيق.
2. `MBP-2`: فتح/إغلاق الوردية والتسليم والجرد والفروق عبر Treasury.
3. `MBP-3`: تقارير المبيعات والمخزون والنقد حسب الفرع/المحطة/الوردية.
4. `MBP-4`: أكثر من Tender والمرتجعات الخاصة بـPOS والطابعات والدرج.
5. العمل دون اتصال لا يدخل تلقائيًا؛ يحتاج ADR لـqueue وIdempotency والتعارض وترقيم
   المستندات ومزامنة المخزون.

## الأمان والعزل

- اختيار المحطة لا يرسل `companyId` موثوقًا؛ تستنتج الشركة من الجلسة وتتحقق كل
  المراجع منها.
- صلاحيات مستقلة لعرض الفروع وإدارتها، وتشغيل المحطة، وفتح/إغلاق الوردية، واعتماد فرق
  الصندوق، وتغيير الافتراضات.
- يمكن تقييد المستخدم بفروع/محطات مسماة؛ دور الشركة العام لا يمنحه كل المحطات ضمنيًا
  إذا فعلت الشركة هذا القيد.
- أسرار الطابعة أو الاتصال بالأجهزة تحفظ في بيئة الجهاز/Keychain أو وكيل محلي، لا في
  استجابة API عامة.
- لا تعتمد هوية المحطة على اسم متصفح قابل للتزوير؛ تحتاج enrollment/revocation عند
  تفعيل ربط الجهاز.

## الباركود والمخرجات

- تستخدم كل محطة Barcode Resolve نفسه المقيد بالشركة، مع قارئ HID أو كاميرا التطبيق.
- يظهر الفرع والمحطة والوردية في الإيصال عند اعتماد الحالة التجارية، وتبقى لقطة الطباعة
  التاريخية ثابتة.
- قالب الملصق والطابعة إعداد Presentation؛ تعريف باركود الصنف يبقى ملك Inventory.

## بوابات القبول

- شركتان تحملان رمز الفرع نفسه بلا تسرب، ومنع أي Warehouse/Cash Account أجنبي.
- سباق فتح ورديتين لمحطة واحدة ينتج وردية واحدة فقط.
- Checkout متزامن يحافظ على Idempotency والمخزون والنقد والقيد ويرتبط بمحطة ووردية.
- تعطيل فرع أو محطة له وردية مفتوحة مرفوض بسبب مستقر.
- حساب المتوقع والفعلي والفرق بـDecimal نصي، دون Float أو جمع عملات.
- OpenAPI وRBAC وCSRF وAudit والحراس المعمارية والاختبارات الوظيفية والحمل.
- اختبارات قارئ وملصق وطابعة على أجهزة فعلية، وMariaDB 10.11 وMySQL 8.4.

## الترتيب

لا يبدأ هذا التوسع داخل دفعة الأساس الحالية. بعد نجاح الباركود ومسار POS الأول وبوابات
الأداء، يقارن المنتج أولوية `MBP-1` مع `CRM-1` حسب نوع الشركات الأولى المستهدفة؛ تجارة
التجزئة ترجح الفروع والمحطات، والخدمات المهنية ترجح CRM. كلاهما يستخدم الأساس نفسه ولا
يجوز دمجهما في Migration أو PR واحدة.
