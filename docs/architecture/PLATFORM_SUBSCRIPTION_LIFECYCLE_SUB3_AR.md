# SUB-3: مركز إدارة الخطط ودورة حياة اشتراك الشركة

## تحليل الفجوة

أساس SUB-1/SUB-2 يملك كتالوج الموديولات والخطط ونسخ الخطط واشتراكًا واحدًا لكل
`Company` واستحقاقات مؤرخة، ويطبق تقاطع الاستحقاق مع RBAC. لكنه لا يملك حتى الآن:

- حالة DRAFT قابلة للتحرير أو أمر PUBLISH؛ كل النسخ الحالية مولودة كمنشورة.
- API أو واجهة لإدارة الكتالوج أو البحث والعد والترقيم من قاعدة البيانات.
- تمييز السعر غير المحسوم عن الرسم الصفري، أو سياسة واضحة للاختيار الذاتي.
- سجل طلب/قرار مؤرخ يبين التغيير الحالي والمجدول وتاريخ الخطط.
- اختيار موديولات اختيارية بسياسة سعر واضحة والتحقق من إغلاق الاعتماديات عند الأمر.
- صفحة مستقلة لمالك النشاط تبقى متاحة عند إغلاق موديولات الأعمال.

حقول `PlatformBillingAccount.planName` وفواتير المنصة الحالية ليست بديلًا عن هذه
الحقائق، ولا تنقل هذه الدفعة ملكيتها أو تغير إصدار الفواتير أو السداد اليدوي الحالي.

## الملكية والحدود

`Platform Subscriptions & Entitlements` هو مالك الكتابة الوحيد لكل جداول الكتالوج
والاشتراك والاستحقاق والتغيير. يستهلك بقية النظام `CompanyEntitlementQueryPort` فقط.
تبقى صلاحية مشغل المنصة مستقلة عن أدوار الشركة، بينما تستخدم صفحة مالك النشاط
`subscriptions.view/manage` داخل الشركة المختارة من الجلسة. تنتمي الصلاحيتان إلى
`PLATFORM_FOUNDATION` حتى لا تقطع حالة الاشتراك طريق الاستعادة وإدارة الاشتراك نفسه.

لا يكتب الموديول في Platform Billing أو Sales أو Treasury أو Ledger. لا توجد Network
I/O داخل المعاملة، ولا Outbox لعدم وجود مستهلك خارجي معروف في هذه الشريحة.

## نموذج الخطط

- `PlatformPlan` هو الهوية المستقرة والكود الدلالي وحالة الإتاحة.
- `PlatformPlanVersion.publishedAt = null` يعني DRAFT. يحمل الإصدار `version`
  متفائلة وهو وحده القابل للتعديل.
- PUBLISH يتحقق من اكتمال السعر والحدود والموديولات، ثم يثبت `publishedAt` والفاعل.
  لا يوجد أمر يعيد النسخة المنشورة إلى DRAFT، ويرفض كل تعديل لاحق خادميًا.
- `recurringFee = null` يعني أن التسعير لم يُحسم، وليس رسمًا صفريًا. الرسم المجاني
  يمثل بصفر صريح. لذلك تبقى مسودة Basic غير قابلة للنشر حتى إدخال سعر حقيقي.
- سياسة الاختيار الذاتي هي `DISABLED` أو `REQUEST_ONLY` أو `IMMEDIATE_FREE`.
  الأخيرة لا تنشر ولا تطبق خطة ذات رسم موجب.
- موديول النسخة إما `INCLUDED` أو `OPTIONAL`. الاختياري يحمل
  `additionalRecurringFee` صريحًا، ويجوز أن يكون صفرًا. لا ينشر خيار بلا سياسة سعر.

تضيف Migration مسودات قابلة للتهيئة لأكواد `FREE` و`TRIAL` و`BASIC`. لا تنشر أيًا
منها، ولا تخمن أيام تجربة أو حدًا أو سعر Basic. تبقى نسخ Legacy المنشورة واشتراكات
الشركات الحالية واستحقاقاتها `GRANDFATHERED` كما هي.

## دورة التغيير المؤرخ

يسجل `PlatformSubscriptionChange` المصدر والفاعل ونسخة الاشتراك المستند إليها ونسخة
الخطة المطلوبة ولقطة السعر والعملة والوقت الفعال والقرار. يثبت جدول ربط صغير حزمة
الموديولات المختارة ولا يعتمد التاريخ على كتالوج قابل للتغيير لاحقًا.

- طلب مالك النشاط المدفوع أو ذو سياسة `REQUEST_ONLY` يبقى `PENDING_APPROVAL` ولا
  يغير الاشتراك أو الاستحقاق ولا ينشئ سدادًا وهميًا.
- طلب `IMMEDIATE_FREE` صفري الرسم يمكن تطبيقه فورًا فقط بعد تحقق الخادم من السياسة
  ومن أن الشركة لم تستهلك تجربة سابقة عند وجود `trialDays`.
- مشغل المنصة يستطيع إنشاء/اعتماد تغيير بوقت `effectiveAt` صريح. يغلق الاستحقاقات
  الحالية عند ذلك الوقت وينشئ الحزمة الجديدة من الوقت نفسه داخل معاملة ACID واحدة.
- الخطة الفعالة هي آخر تغيير معتمد بدأ قبل وقت القراءة؛ والتغيير المعتمد المستقبلي
  هو التغيير المجدول. لا يحتاج الانتقال الزمني Worker أو Network I/O.
- قفل صف الاشتراك، و`version` الشرطية، ومفتاح Idempotency، وعدم وجود أكثر من تغيير
  معتمد مستقبلي مفتوح تحمي القرار المتزامن. اختلاف النسخة يعيد `VERSION_CONFLICT`.

تسجل تغييرات الشركة في Audit داخل المعاملة نفسها. لأن كتالوج الخطة عالمي ولا يملك
`companyId`، تحفظ حقول فاعل الإنشاء والتعديل والنشر على سجلاته بدل اختلاق شركة تدقيق.

## قواعد حزمة الموديولات

قبل النشر وقبل كل طلب تغيير يتحقق المالك من أن:

1. كل موديول نشط وموجود في نسخة الخطة.
2. كل اختيار إضافي معلن `OPTIONAL` وله رسم إضافي صريح.
3. الحزمة النهائية تساوي الموديولات المشمولة مضافًا إليها الاختيارات فقط.
4. كل اعتماد مباشر أو متعدٍ نشط وموجود في الحزمة نفسها، ولا توجد دورة.

تعيد واجهة المالك الموديولات المنشورة الصالحة فقط، لكن ذلك لا يستبدل التحقق الخادمي.
تظل `CompanyCapabilityService` تستهلك الاستحقاقات المؤرخة الناتجة، ولذلك تصبح نتيجة
التغيير فعالة في API والتنقل من الوقت نفسه.

## العقود والصفحات

- `#platformSubscriptions`: كتالوج خطط مستقل لمشغل المنصة، مع بحث وتصفية وعد وترقيم
  في قاعدة البيانات، ومحرر DRAFT ونشر صريح، ودليل اشتراكات الشركات وطلباتها.
- `#subscription`: خطة الشركة الحالية والتجربة والحدود والموديولات والتاريخ والتغيير
  المجدول، مع كتالوج منشور مرقم وخيارات مسموحة فقط.
- لا تكشف واجهة الشركة معرفات مستخدمي المنصة أو ملاحظات تشغيل داخلية أو بيانات شركة
  أخرى. مبالغ DECIMAL تظل نصوصًا canonical في OpenAPI والواجهة.

## الترحيل والرجوع

الترحيل توسعي: يضيف أعمدة حالة المسودة والسياسة والفاعل، وسياسة اختيار الموديول،
وسجلي التغيير والحزمة. تنشأ نقطة تاريخ أولية لكل اشتراك Legacy بلا تعديل حقول
Platform Billing أو الفواتير أو السداد. الرجوع DDL مسموح فقط قبل وجود مسودة معدلة أو
طلب/تغيير غير صف الـbackfill؛ بعد الاستخدام يحتفظ التاريخ ويكون الرجوع بتطبيق سابق
متوافق ثم Forward Migration.

## بوابات القبول

- نشر DRAFT ثم رفض PATCH مباشر للنسخة المنشورة.
- Idempotency لتغيير مجدول وتعارض `version`.
- عزل شركتين في القراءة والطلب والقرار.
- رفض موديول معطل أو غير متاح أو حزمة dependency ناقصة.
- بقاء التغيير المدفوع PENDING بلا مزود دفع أو سجل سداد.
- عد وتصفية وترقيم الخطط والاشتراكات من قاعدة البيانات، وحارس يمنع `slice/filter`
  في مسارات القوائم الجديدة.
- رفض API المباشر بلا صلاحية أو بلا أهلية مشغل المنصة.
- Prisma validate/generate وTypeScript وOpenAPI/Redocly والحراس وi18n/UI/build، ثم
  الترحيل من الصفر والترقية على MariaDB 10.11 وMySQL 8.4.
