# سياسة اعتماد الموديولات مفتوحة المصدر

## 1. القرار

الأصل عند إضافة قدرة جديدة هو تقييم موديول مفتوح المصدر ناضج قبل الموافقة على بنائها من الصفر. لا يعتمد أي موديول لمجرد توفره؛ يجب أن يقلل كلفة البناء والصيانة من دون إضعاف صحة القيود المحاسبية أو عزل الشركات أو أمن البيانات.

يبنى الحل داخليًا فقط عندما لا يحقق أي مرشح المتطلبات الإلزامية، أو عندما تكون طبقة التكييف المطلوبة أكبر وأخطر من تنفيذ نطاق صغير محليًا. يسجل القرار وبدائله في ADR أو مذكرة تقييم قابلة للمراجعة.

## 2. بوابة الاختيار الإلزامية

يجب قبل الاعتماد توثيق:

- الرخصة وملاءمتها لطريقة توزيع النظام واستضافته، مع تفضيل الرخص permissive مثل MIT وApache-2.0 وBSD وإحالة GPL/AGPL أو الرخص غير الواضحة إلى مراجعة قانونية.
- نشاط المشروع، انتظام الإصدارات، زمن معالجة الثغرات، جودة الاختبارات والتوثيق، وعدد المشرفين الفعليين؛ لا تكفي شهرة المستودع وحدها.
- توافق Node.js وقاعدة البيانات والمنصة، وحجم شجرة الاعتماديات، والثغرات المعروفة، ووجود إصدار مثبت يمكن إعادة بنائه حتميًا.
- قدرة الموديول على عزل الشركات، وتمثيل `DECIMAL` و`BIGINT` بأمان، وتطبيق الصلاحيات والتدقيق وIdempotency ومتطلبات العربية وRTL عند الصلة.
- خطة تحديث وخروج: مالك داخلي، دورية ترقية، مراقبة نشرات الأمان، طريقة تصدير البيانات، وبديل عند توقف upstream.

لا يقبل موديول يرسل بيانات مالية أو شخصية إلى خدمة خارجية من دون قرار صريح وعقد معالجة بيانات وضوابط أسرار واحتفاظ وموافقة تشغيلية.

## 3. طريقة الربط

- يربط الموديول عبر Port/Adapter أو Anti-Corruption Layer مملوكة للسياق المستهلك؛ لا تنتشر أنواعه أو مخططه داخل بقية النظام.
- لا يكتب الموديول مباشرة في `JournalEntry` أو `JournalLine` أو جداول سياق آخر. كل أثر محاسبي يمر بخطة معتمدة إلى `PostingEngine` داخل المعاملة الحاكمة.
- لا يشترك مع النظام في جداول تشغيلية بلا حدود ملكية واضحة. التكامل يكون بحزمة داخلية معزولة أو API أو أحداث موثقة بحسب الحاجة.
- تبقى قواعد التوازن والفترة والعملة والتقريب والعكس وعزل الشركة محلية وواجبة الاختبار حتى إذا وفر الموديول حسابات مشابهة.
- يمنع نسخ ملفات متفرقة من مشروع خارجي من دون حفظ إشعار الرخصة والمصدر والإصدار والبصمة وخطة التحديث. يفضل الاعتماد المثبت أو vendoring منظمًا عند الحاجة.

## 4. التحقق قبل الدمج

يلزم لكل اعتماد جديد:

1. مذكرة مقارنة بين مرشحين مناسبين على الأقل وبين البناء المحلي المحدود.
2. فحص الرخصة وSBOM والاعتماديات والثغرات وقفل الإصدار والبصمة.
3. Prototype مع بيانات غير إنتاجية يثبت أهم حالات الاستخدام والفشل والخروج.
4. اختبارات عقد وحدود وعزل شركة، واختبارات مالية على MariaDB وMySQL عند وجود أثر محاسبي.
5. توثيق التهيئة والترقية والنسخ الاحتياطي والاستعادة والمراقبة والرجوع.
6. نجاح جميع بوابات OpenAPI وTypeScript والبناء والأمان والإصدار الحالية.

## 5. قاعدة عملية للموديولات القادمة

تبدأ التسوية البنكية والدفعات المقدمة وإقفال السنة وإعادة تقييم العملات والضرائب والأصول الثابتة وأذونات المخزون بمرحلة اكتشاف مكونات مفتوحة المصدر. لا يبدأ تنفيذ دائم قبل تقديم نتيجة البوابة واختيار: اعتماد مباشر، تكييف عبر Adapter، أو بناء محلي مبرر.
