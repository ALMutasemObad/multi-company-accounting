# إدارة المشاريع — شرائح الخطة والتعاون والتحرير GPM-2 إلى GPM-5

## المنفذ محليًا حتى الآن

- أضيفت جداول مستقلة للمراحل والمهام وإسنادات أعضاء المشروع، مع مفاتيح مركبة تمنع ربط مهمة بمرحلة أو عضو من مشروع أو شركة أخرى، ونسخ لكل سجل وترتيب داخل المرحلة/المشروع.
- أضيفت صلاحية `general_projects.progress` دون تفعيل وحدة `GENERAL_PROJECTS` أو منحها اشتراكًا. ترحيل التراجع يرفض إسقاط الجداول إذا وجدت بيانات أو سجلات إعادة لأوامر الخطة.
- أصبح أمر إكمال المشروع يقرأ حالات المراحل والمهام الفعلية داخل المعاملة، ويرفض الإكمال إذا بقي أي عمل مفتوح. كانت شريحة السجل السابقة تمرر قائمتين فارغتين لأنها لم تكن تملك جداول خطة.
- أضيفت قراءة المراحل وإنشاؤها وتغيير حالتها بعقد OpenAPI وحراسة صلاحية الإدارة وCSRF ومفتاح إعادة المحاولة ونسخة الخطة ونسخة المرحلة. يظهر ذلك في صفحة «إدارة المشاريع» مع مفاتيح ترجمة في القواميس الأربع.
- حُرست حدود تواريخ المرحلة داخل حدود المشروع، ويُرفض تضييق حدود المشروع إذا أصبحت مرحلة موجودة خارجه. نُقل ترحيل الخطة إلى اسم يرتّب تنفيذه بعد ترحيل سجل المشاريع الذي يعتمد عليه.
- أضيفت قراءة مهام كل مرحلة وإنشاؤها بترتيب خادمي، وحراسة التاريخ ضمن المرحلة والمشروع، ونسخة الخطة والصلاحية ومفتاح إعادة المحاولة. تظهر قائمة المهام وإنشاؤها في واجهة إدارة المشاريع.
- أضيف عرض إسنادات المهمة، إسناد مسؤول أو مشارك من أعضاء فريق المشروع النشطين، سحب الإسناد بسبب ونسخة متفائلة، وانتقالات المهمة بإذن إدارة المشاريع. تمنع السياسة بدء مهمة بلا مسؤول نشط، وسحب آخر مسؤول عن مهمة جارية، وإكمال مرحلة أو مشروع مع مهام مفتوحة. واجهة المشروع تعرض هذه الخطوات، لكن صلاحية `general_projects.progress` المستقلة لم تُفعّل في مسار الموظف بعد.
- يتحقق أمر الإسناد من مرجع الموظف النشط قبل قفل المشروع ثم يعيد فحص عضوية الفريق بعد القفل؛ يمنع سحب عضو مسؤول من فريق المشروع ما دامت له مهمة غير نهائية.
- أضيف مسار `general_projects.progress` مستقل للموظف المسؤول النشط دون منحه إدارة المشروع؛ يرفض الخادم مهمة غير مسندة له دون كشف وجودها، ويحتفظ المدير بمسار override مدقق. تعرض قائمة المهام قرار `canProgress` المحسوب في الخادم لتوجيه أزرار الواجهة، ولا تسمح واجهة الموظف بإلغاء المهمة.
- أضيفت اعتماديات مهام من نوع «انتهاء السابقة ثم بدء التالية» ضمن المشروع نفسه. يمنع النموذج المرجعي ربط شركتين أو مشروعين، وتمنع السياسة الربط الذاتي والتكرار والحلقات والربط بمهمة نهائية. تقرأ نقلة بدء المهمة حالات السوابق من قاعدة البيانات، لا قائمة فارغة.
- يعرض API وواجهة إدارة المشاريع الاعتماديات والمهام السابقة القابلة للبحث، وينبهان إلى المهمة التي تنتظر سابقتها. إزالة الرابط تتطلب سببًا وتتحقق من نسخة الخطة والرابط؛ يمكن للمدير إزالة رابط سابقة ملغاة لإصلاح خطة عالقة مع تدقيق مختلف لهذا القرار. صلاحية الموظف لتقدم المهمة لا تتيح له تعديل الخطة.
- أضيفت متابعة ذاتية وتعليقات نصية للمشروع أو مهمة منه، بصلاحيتين منفصلتين `general_projects.follow/comment` لا تمنحان إدارة الخطة أو رؤية مشروع بلا `general_projects.view`. لا تقبل التعليقات على مهمة أو مشروع نهائي؛ إلغاء المتابعة الذاتية ممكن بعد نهائية المشروع. تعرض الواجهة مرشح «أتابعها» ونموذج التعليق وسجل التعليقات دون استخدام سجل التدقيق كواجهة نشاط.
- أصلح اختبار المتصفح عقد `/auth/me` ليقبل وحدة `GENERAL_PROJECTS` عند تفعيلها في قاعدة اختبار معزولة، وأصلح واجهة الإنشاء لتبقي المشروع المنشأ مختارًا بعد تحديث القائمة. اختُصرت بادئة مفاتيح إعادة المحاولة للمشاريع لأن جمع بادئة طويلة مع معرفي UUID كان يتجاوز حد API البالغ 100 حرف ويمنع إنشاء المراحل.
- أضيف تحرير بيانات المرحلة والمهمة وصفيًا وزمنيًا، وأولوية المهمة، بعقد وصلاحية إدارة المشروع وCSRF ومفتاح إعادة المحاولة ونسختي الخطة والسجل. يمنع تعديل مرحلة إلى حدود تستبعد تواريخ مهامها الحالية، ويمنع تعديل مهمة خارج حدود مرحلتها أو مشروعها أو بعد نهائيتها. تعرض الواجهة نماذج التحرير للمدير فقط مع قيم القواميس الأربع.

## دليل التحقق وحدوده

- نجح `prisma validate` وتوليد Prisma Client باستخدام عنوان قاعدة شكلي بلا اتصال فعلي، وفحص أنواع API واختباراته.
- أضيف اختبار تكامل لإكمال المشروع مع مهمة ومرحلة مفتوحتين؛ لم يُشغّل لأن MySQL/MariaDB المحلي غير متاح على `127.0.0.1:3306`.
- بعد إضافة مسار تقدم الموظف نجحت 51 حالة عقد وHTTP موجهة، وحزمة API الكاملة بـ1621 اختبارًا مع 211 متجاوزة، وحزمة الواجهة من إعدادها الصحيح بـ841 اختبارًا مع 35 متجاوزة. نجح فحص أنواع API والواجهة وفحص القواميس الأربع والعقد المولد. أُضيفت اختبارات تكامل للمراحل والمهام والإسناد وتقدم المسؤول والعزل والتواريخ لكنها لم تُشغّل لغياب قاعدة محلية على `127.0.0.1:3306`.
- أضيفت اختبارات سياسة ودخول HTTP لعقد الاعتماديات وخيار البحث، وحالة تكامل لعزل الاعتماديات ومنع الحلقة وإصلاح سابقة ملغاة؛ حالة التكامل لم تُشغّل لغياب قاعدة محلية. نجحت الحزمة العامة بعد التغيير بـ1625 اختبار API و212 متجاوزًا، و842 اختبار واجهة و35 متجاوزًا. انتهت مهلة اختبار جرد غير متعلق بالمشاريع مرة أثناء تشغيل الحزمتين بالتوازي؛ نجح منفردًا ثم نجحت حزمة API كاملة وحدها بمهلة 10 ثوانٍ للاختبار.
- كشف تشغيل الترحيلات على MariaDB 10.4 في قاعدة اختبار معزولة نقص فهرس مركب في ترحيل سجل الأعضاء؛ أضيف الفهرس إلى الترحيل غير المنشور، ثم نجح تطبيق 91 ترحيلًا من البداية على قاعدة معزولة ثانية. نجحت 8 حالات تكامل قاعدة للمشاريع، تشمل ربط الاعتماديات ومنع الدورات وإصلاحها، والتعليقات والمتابعة وإعادة الطلب والعزل بين المشاريع والشركات. قاعدة الاختبار الأولى فشلت عند الفهرس قبل الإصلاح وبقيت محفوظة كدليل، ولم تمس قاعدة تشغيلية.
- بعد إضافة التعاون نجحت حزمة API العامة بـ1627 اختبارًا و213 متجاوزًا، وحزمة الواجهة بـ842 اختبارًا و35 متجاوزًا، و8 اختبارات تكامل مشاريع على MariaDB 10.4. نجح فحص أنواع API والواجهة والقواميس الأربع والعقد المولد.
- نجح تطبيق 91 ترحيلًا من الصفر مرة ثانية في قاعدة اختبار ثالثة بعد إضافة تعليقات ومتابعة المشاريع وصلاحياتهما. اجتاز اختبار Chromium المتصل بالخادم وMariaDB مسار إنشاء المشروع والمرحلة والمهمتين والاعتمادية والتعليق على المشروع والمهمة والمتابعة وإلغائها (`1/1`). أعيدت حزمة الواجهة بعد إصلاحات المتصفح (`842` ناجحًا، `35` متجاوزًا)، وAPI (`1627` ناجحًا، `213` متجاوزًا)، وحالات تكامل المشاريع الثماني على قاعدة معزولة (`8/8`).
- بعد تحرير المرحلة والمهمة نجحت 10 حالات تكامل MariaDB تشمل إعادة الطلب والنسخ وتضييق الحدود والعزل وتعديلين متزامنين يتنافسان على النسخة نفسها؛ ينجح واحد فقط ثم تكتمل دورة مشروع حقيقية من التفعيل إلى إكمال المهمة والمرحلة والمشروع. نجح 42 فحصًا موجهًا لعقد API وحدود HTTP. نجح اختبارا Chromium متصلان بالخادم وقاعدة الاختبار (`2/2`): مسار التحرير والاعتماديات والتعليقات، ثم جلستا متصفح تتنافسان على تعديل مشروع واحد فيرجع `200` لأحدهما و`409` للآخر وتتطابق القراءة اللاحقة لديهما. نجحت حزمة API العامة بـ`1628` اختبارًا و`214` متجاوزًا، وحزمة الواجهة بـ`842` اختبارًا و`35` متجاوزًا، وكذلك بناء API والواجهة وفحص القواميس الأربع.
- شُغّل جزء الحراسة الفعلي من ملف رجوع ترحيل التعاون على قاعدتي اختبار معزولتين: رفض الرجوع عند وجود 6 متابعات و8 تعليقات و16 سجل إعادة (`exit 1`) وبقيت البيانات والصلاحيتان، وسمح بمرور الحارس على قاعدة خالية (`exit 0`). لم تُنفّذ أوامر الحذف من الرجوع على أي منهما. ما زالت الوحدة غير مفعلة في الإعداد الافتراضي وغير منشورة؛ نجاح الشريحة لا يعني اكتمال قبول النشر.
- نجح اختبار تكامل جديد على MariaDB المعزولة (`2/2`): نسخ باقة مجانية منشورة إلى إصدار جديد يضيف المشاريع دون تعديل الإصدار القديم، ثم إنشاء نسخ بداية مجانية واستحقاق `GENERAL_PROJECTS` لشركات تجريبية في العملات الإحدى عشرة الحالية برسوم استخدام صفرية. تحققت إعادة جميع سجلات الخطط والشركات التي أنشأها الاختبار إلى الصفر، ونجح فحص أنواع الاختبارات. لا يغيّر هذا الاختبار باقات الإنتاج أو إعداد ربط العملات ولا يثبت وصول الشركات القائمة إلى الميزة.

## البوابة التالية

مراجعة عزل الواجهة والصلاحيات، ثم ضبط ربط إصدارات باقة البداية في بيئة قبول فعلية واختبار إنشاء شركة جديدة عبر HTTP لكل العملات، قبل النشر. اختبار القاعدة المحلية لا يحل محل التحقق من إعداد الاستضافة.

## مسار الإتاحة دون تعديل الباقات المنشورة بصمت

ترحيل السجل ينشئ `GENERAL_PROJECTS` غير نشطة عمدًا. نجاح ترحيل الجداول وحده لا يُظهر النظام: تحتاج الشركة إلى وحدة نشطة واستحقاق `INCLUDED` في نسخة باقتها، مع تبعية `HUMAN_RESOURCES` وصلاحية `general_projects.view`. لا يجوز إدخال استحقاق جديد مباشرة في صف نسخة باقة منشورة؛ خدمة الباقات تعتبر النسخة المنشورة ثابتة. يجب أولًا في بيئة قبول معزولة تفعيل الوحدة بعد مراجعة الخطة، وإنشاء مسودة نسخة جديدة من كل باقة بداية مجانية منشورة، وإضافة الوحدة مجانًا مع تبعيتها، ونشر النسخ الجديدة بعد التحقق من الرسوم الصفرية والحصص والعملات الإحدى عشرة. ثم يُحدّث ربط إصدارات باقة البداية لكل عملة ويُختبر إنشاء شركة جديدة واستخدام المشاريع. الشركات القائمة لا تُنقل تلقائيًا إلى نسخة أخرى أو تُمنح استحقاقًا دون قرار نشر موثق؛ لا تدّعي هذه الشريحة إتاحة النظام لها بعد نشر الكود وحده.
