# مرشح محلي: تتبع إخفاق إنشاء شركة المجموعة

## دليل البيئة الحية وقرار المالك في 29 سبتمبر

بقراءة مخوّلة من cPanel وphpMyAdmin، ظهر أن تطبيق `accounting.doralashab.com` يعمل بالإصدار `0.1.0-381dfde8df9c`، وأن متغير `PLATFORM_SUBSCRIPTION_START_PLAN_VERSION_ID` غير موجود في قائمة متغيرات Node.js Selector. سُجّل الطلب `b1470737-f35d-46e0-9990-e88a245ba35c` في Passenger برد `503`؛ لم يرد معه سبب سياسة الباقة في السجل القديم، لذا لا نزعم أي شرط فشل أولًا. في قاعدة `doralash_mcapprod`، مسودة `FREE` هي الإصدار `8`: نشطة كخطة لكنها غير منشورة، بعملة `SAR` وسياسة `DISABLED`، دون حصص مستخدمين/موظفين/مستندات أو أسعار زيادة صريحة أو وحدات مشمولة. العملة العامة `AED` نشطة. بقيت مجموعة الاختبار ذات الرقم `6` بشركة واحدة وصفر سجلات لأمر `CREATE_GROUP_COMPANY`، فلا دليل على أثر جزئي للمحاولة الفاشلة. كانت كل استعلامات قاعدة الاستضافة `SELECT` فقط؛ لم تتغير أي خطة أو إعداد حي.

اختار المالك إتاحة البداية مجانًا مؤقتًا للشركات الجديدة بعملتي `SAR` و`AED`، مع جميع الميزات المتاحة دون رسوم زيادة. يتطلب ذلك **إصدارين منشورين مؤهلين**، أحدهما لكل عملة؛ لا يجوز استخدام إصدار `SAR` لشركة بعملة `AED`. أُضيف إعداد `PLATFORM_SUBSCRIPTION_START_PLAN_VERSION_IDS_BY_CURRENCY` بصيغة مثل `SAR:8,AED:9` بعد نشر الإصدارين والتحقق من أرقامهما الفعلية. الإعداد الجديد بديل كامل عن `PLATFORM_SUBSCRIPTION_START_PLAN_VERSION_ID` القديم ولا يجوز ضبطهما معًا. فحص الخيارات يرفض إعدادًا غير صالح أو إصدارًا غير مؤهل ويعرض العملتين فقط إذا اجتازتا التحقق، والإنشاء يعيد الفحص داخل معاملته. الأمثلة الرقمية هنا توضيحية؛ لا تُضبط في الاستضافة قبل التحقق من الإصدارين المنشورين.

الحصص الثلاث مطلوبة تقنيًا ولكنها **حسابية لا حدود منع** في التنفيذ الحالي؛ الأسعار الإضافية الثلاث يجب أن تكون صفرًا صريحًا. اعتماد جميع الوحدات النشطة يتطلب تضمين تبعياتها، وعدم تضمين `CRM` و`SERVICE_CATALOG` المعطلتين حاليًا. لا تُنشر مسودة `FREE` القديمة أو تُعدّل قاعدة الإنتاج بــSQL مباشر؛ يستخدم مشغل المنصة واجهة إدارة الباقات ذات سجل التدقيق بعد مراجعة الحصص والوحدات والرسوم، ثم يضبط متغير البيئة في Node.js Selector ويعيد تشغيل التطبيق بالطريقة المعتمدة ويفحص العملتين. لم يُنفذ هذا التشغيل الحي أو النشر بعد.

## المنجز

بُني هذا المرشح من `origin/main` عند `381dfde` وجمع فحص أهلية عملة خطة البداية وتشخيص إخفاقات `503` الآمن واختبارات HTTP، ثم سد فجوة معرّف الطلب بين الخادم والعقد والواجهة. تلتقط الواجهة `X-Request-ID` الآمن من الاستجابة، أو `requestId` من جسم الخطأ عند غياب الترويسة، وتعرضه بجانب رسالة تعذر تحميل خيارات الشركة أو إنشائها. يُزال الرقم عند إعادة المحاولة أو نجاح الطلب أو بدء شركة أخرى. لا تُعرض للمالك أسباب الخادم الداخلية أو بيانات حساسة، ولا تتغير سياسة مفتاح التكرار.

صار عقد OpenAPI يقبل معرّفات الطلب الآمنة المسموح بها في `requestLogger`، ومنها UUID، بطول 8–128 حرفًا من الحروف الإنجليزية والأرقام والنقطة والشرطة والشرطة السفلية. الحراس المولدة محدثة، ورسائل الواجهة مترجمة في العربية والإنجليزية والأردية والهندية.

## دليل التحقق المحلي

- `111` اختبار API مركز ناجح في الفحص دون قاعدة. تشمل رفض معرف غير آمن، وفحص خيارات العملة، وتسجيل `503` دون اسم الشركة أو رقم هاتفها أو جسم الطلب. يثبت اختبار HTTP بمنافذ مُحاكية أن مجموعة القيم المصوّرة تقبلها الخدمة إذا كانت باقة البداية بعملة `AED`، وتصدر `503` وسبب `PLAN_NOT_ELIGIBLE` إذا كانت بعملة `SAR`.
- أُنشئت قاعدة اختبار جديدة ومعزولة على `E:` وشُغّلت عليها الهجرات الـ`86` كلها ثم نجحت `11/11` حالة تكامل لإنشاء شركة المجموعة على MariaDB `10.4.32`. الحالة الجديدة تستخدم `YE` و`AED` و`Asia/Riyadh` ونشاط التصنيع وقالب الخدمات مع قاعدة فعلية: تفشل بباقة `SAR`، ولا تترك شركة أو سجل تكرار بعد rollback، ثم تنجح بالمفتاح نفسه وباقة `AED` وتنتج ملف الشركة والاشتراك الصحيحين. هذه نسخة أقدم من نسختي MariaDB `10.11` وMySQL `8.4` المستهدفتين؛ لا تحل محلهما.
- أُعيد اختبار ملف التكامل نفسه على **قاعدتين جديدتين منفصلتين** على `E:`: MariaDB `10.11.11` ثم MySQL `8.4.11`، بالتتابع لا بالتزامن. طُبقت الترحيلات الـ`86` على كل منهما، ونجحت الحالات الـ`11/11` على كل محرك، بما فيها تراجع الطلب ذي القيم المصوّرة عند باقة `SAR` ونجاح المفتاح نفسه عند باقة `AED`. أُوقف خادما الاختبار بعد التشغيل؛ بقيت بياناتهما الاختبارية المحلية دون حذف.
- أُضيفت حالة Chromium مشروطة داخل ملف تكامل إنشاء الشركة، تصل بالواجهة المبنية محليًا إلى `createApp` الحقيقي وMariaDB `10.11.11` المعزولة. يسجل مالك مجموعة اختبار دخوله، ويرسل إنشاء شركة مرة؛ يلتزم الخادم بالإنشاء ثم يحجب اعتراض المتصفح رد `201` ويعرض بدلًا منه `503` مع معرّف طلب. تعيد الواجهة الطلب بنفس الجسم والمفتاح؛ يرد الخادم بنفس معرّف الشركة، ويبقى في المجموعة سجل شركة واحد وسجل تكرار واحد واشتراك نشط صحيح. نجحت الحالة مرتين، ونجح الملف كاملًا `12/12` عند تفعيلها، مع فحص أنواع اختبارات API. لا تعمل افتراضيًا: تتطلب `RUN_DB_TESTS=true` و`RUN_GROUP_COMPANY_REAL_BROWSER_TESTS=true` واسم قاعدة محلية `test_*` مطابقًا لـ`GROUP_COMPANY_REAL_BROWSER_DISPOSABLE_DATABASE`؛ يتحقق الحارس منها قبل أي تهيئة اختبارية. تتطلب أيضًا بناء الواجهة المحلي مسبقًا.
- `5` اختبارات وحدة لعميل API و`8` حالات متصفح مُحاكية لتأسيس الشركة ناجحة، بما فيها إظهار رقم التتبع وإزالته عند إعادة المحاولة.
- حزمة الواجهة العامة: `834` ناجحة و`35` متجاوزة. نجح فحص أنواع API والواجهة وبناؤهما، و`contracts:check` و`i18n:check`.
- أُعيد تشغيل حزمة API العامة على هذا المرشح نفسه في 29 سبتمبر 2026 باستخدام Node المحلي `24.19.0`: نجح `1546` اختبارًا في `181` ملفًا، وتجاوز `204` اختبارات (منها اختبارات قاعدة البيانات غير المفعّلة في هذه الجولة). هذا فحص محلي إضافي، لا يحل محل بوابتي CI على Node الاستضافة وMariaDB/MySQL.
- لم يُشغّل CI بعيد أو تحقق على البيئة التي أنتجت صورة البلاغ؛ بيانات الشركات والاشتراكات الناتجة اصطناعية داخل قواعد الاختبار المعزولة فقط. اختبار المتصفح المتصل يغطي إعادة طلب **ناجح أخفي رده**، ولا يثبت تعافي إعداد باقة غير مؤهلة في الموقع. لا تثبت نجاحات المحركات المحلية أهلية باقة البداية الحية أو إعدادها الفعلي.

## حدّ النتيجة والخطوة التالية

هذا تحسين تشخيص وتجربة إخفاق ومنع اختيار عملة لا تقبلها باقة البداية، مع إثبات محلي للرجوع وإعادة المحاولة بالقيم المصوّرة. لا يثبت سبب الخطأ في الخادم ولا إصلاحه هناك؛ يبقى البلاغ P0 مفتوحًا. يحتاج مسؤول البيئة إلى ربط المحاولة المصوّرة أو سجل محفوظ بمعرّف طلبها بقراءة مخوّلة، والتحقق هل `PLATFORM_SUBSCRIPTION_START_PLAN_VERSION_ID` مهيأ وما عملة إصداره وحالته. إن كان الإعداد غائبًا أو غير مؤهل فلا يكفي إصلاح الواجهة: يلزم قرار تجاري/تشغيلي لإصدار بداية معتمد بدل اختراع خطة أو تسعير ضمن الكود. لا يُغيَّر كتالوج أو خطة حية ولا تُكرَّر محاولة حيّة بمفتاح جديد استنادًا إلى التخمين.

المرشح محلي وغير مدمج؛ لم يحدث push أو PR أو نشر، ولا ينقل نجاح Staging سابقًا إلى هذا التغيير.
