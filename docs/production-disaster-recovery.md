# التعافي من الكوارث والنسخ الخارجية للإنتاج

## الهدف والنطاق

تحمي هذه الخطة قاعدة إنتاج جوار المالية من فقدان حساب iFastNet كاملًا، لا من فشل إصدار التطبيق فقط. تنشئ `.github/workflows/production-backup-dr.yml` نقطة استعادة مشفرة يوميًا، تنقلها إلى GitHub Actions Artifact خارج حساب الاستضافة، وتعيد النسخة الفعلية شهريًا إلى MariaDB مؤقتة ومعزولة. لا تكتب تجربة الاستعادة في قاعدة الإنتاج ولا تعيد Migration إلى الخلف.

الحدود الحالية:

- هدف استمرارية نقاط الاستعادة: ألا يتجاوز العمر من `recoveryPointAt`/`snapshotStartedAt` **26 ساعة**؛ الجدول اليومي يجعل RPO الاسمي حتى 24 ساعة. لأن المراقب الساعي يرى `artifact.created_at` دون تنزيل قاعدة البيانات، يطبق حدًا محافظًا **25.5 ساعة** ويحتفظ بنصف ساعة لمهلة Job القصوى بين بدء Snapshot والرفع.
- هدف تمرين الاستعادة التقني: إكمال فك التشفير والإدخال والتحقق داخل `database-restore.mjs` خلال **900 ثانية**. لا يساوي ذلك RTO الحادث الكامل من الإعلان إلى عودة التطبيق؛ يُقاس الأخير ويسجل أثناء الحادث أو تمرين خدمة كامل.
- لا توفر الاستضافة الحالية binlogs، لذلك لا توجد استعادة إلى نقطة زمنية بين النسخ اليومية.
- Artifact مشفر، والـManifest الجانبي غير مشفر لكنه منقح: يحمل وقت الإنشاء وبدء Snapshot والحجم وSHA-256 وعدد الترحيلات وصيغة الحماية فقط، ولا يحمل اسم قاعدة المصدر أو إصدارها أو أعداد الصفوف أو المجاميع المالية.

## المسار الآلي

يعمل Workflow يوميًا عند `01:43 UTC` (`04:43 Asia/Riyadh`) ويمكن تشغيله يدويًا مع خيار `restore_drill`:

1. يفحص عمر Artifact السابق قبل صنع النسخة الجديدة.
2. يرفض أي ref غير `refs/heads/main` ويتحقق أن `github.sha` هو رأس `main` الحالي قبل قراءة أي سر، ثم يثبت Actions وصورة MariaDB ببصمات immutable، ويثبت هوية SSH وبصمة المضيف ويرفع مساعدًا مؤقتًا إلى مسار صريح تحت `incoming`.
3. يمرر `BACKUP_ENCRYPTION_PASSPHRASE` و`MIGRATION_DATABASE_URL` من أسرار بيئة `production` عبر `stdin`؛ لا يضعهما في Artifact أو سجل أو وسيطة أمر.
4. يمسك قفل الإنتاج البعيد نفسه، ويثبت أن حساب Passenger وحساب الترحيل يشيران إلى المضيف والمنفذ والقاعدة نفسها بصلاحياتهما المنفصلة، ثم يفحص قبل النسخ صحة تعدادات الجداول الأساسية ووجود مؤسسة وشركة ومستخدم واحد على الأقل واتزان دفتر اليومية. بعدها يشغّل `database-backup.mjs` من الإصدار النشط باسم ملف عام `mcap-production-*`، ويتحقق من المسار والصلاحية `0600` والحجم وSHA-256 وعدد الترحيلات وصيغة التشفير ومن اقتصار Manifest `mcap-backup-v2` على قائمة الحقول المنقحة؛ وإذا كان الإصدار المرجوع إليه ينتج v1 يحوله ذريًا إلى v2 منقحًا قبل النقل.
5. ينزّل `.jwb` والـManifest إلى Runner، ويعيد التحقق مستقلًا عبر `scripts/verify-backup-artifact.mjs`.
6. يرفع Artifact باسم `mcap-production-database-backup` مدة 90 يومًا وبلا ضغط إضافي؛ Artifact الإصدار الرابع immutable داخل المحاولة. إذا أعيد التشغيل نفسه، يسمح `overwrite` فقط عندما تكون `github.run_attempt > 1` كي يستبدل Artifact المحاولة السابقة بدل الاصطدام باسمه، وتبقى كل تشغيلات dispatch المستقلة منفصلة.
7. بعد نجاح الرفع فقط، يحذف من المسار المحلي الأزواج `mcap-production-*` الأقدم من سبعة أيام والمخلفات/الملفات اليتيمة الأقدم من يوم بمسار ثابت؛ لا يمس نسخ النشر الأخرى أو ملفًا حديثًا أو رابطًا رمزيًا، ويفشل التشغيل إذا تعذر التحقق أو التنظيف.
8. في اليوم الأول من كل شهر، أو عند الطلب اليدوي، ينزّل Artifact الذي أُنشئ في التشغيل نفسه ويعيده إلى خدمة MariaDB 10.11.11 مؤقتة بقاعدة فارغة.
9. تتحقق أداة الاستعادة من الجداول والترحيلات، ومن نجاح استعلام تعدادات الجداول المرجعية ووجود مؤسسة وشركة ومستخدم واحد على الأقل، ومن اتزان المجاميع في القاعدة المستعادة؛ أما النسخ القديمة `mcap-backup-v1` فتقارن حقائقها أيضًا للتوافق الخلفي. يحمي SHA-256 ومصادقة AES-GCM سلامة ملف dump نفسه، لكن v2 لا ينشر أعداد المصدر ولا يدّعي مقارنة عددية معه. ثم تحفظ دليلًا منقحًا باسم `mcap-production-restore-drill` يتضمن RPO/RTO والبصمات والنتيجة.

يشترك هذا المسار ووظيفة نشر الإنتاج في ملف القفل البعيد `.pipeline.lock` وينتظر كل منهما حتى 900 ثانية قبل الفشل الصريح؛ فلا يبدأ `mysqldump` أثناء تطبيق Prisma Migration ولا يبدأ نشر جديد أثناء أخذ النسخة. لا تستخدم الوظائف مجموعة GitHub `concurrency` مشتركة، لأن GitHub قد يستبدل الطلب المنتظر الأقدم بطلب أحدث حتى مع تعطيل الإلغاء؛ القفل البعيد هو مصدر التسلسل الحاسم ولا يسقط الطلبات بصمت.

يراقب `production-metrics-monitor.yml` كل ساعة Artifacts المربوطة حصريًا بتشغيلات `production-backup-dr.yml` على `main`: يفشل عند غياب النسخة أو تجاوز Artifact 25.5 ساعة، وعند غياب دليل استعادة ناجح أو تجاوزه 35 يومًا. كما يحفظ Workflow علامة فشل مستقلة لأي تمرين مطلوب فاشل؛ يبقى المراقب أحمر إذا كانت أحدث من آخر نجاح. هذا استقلال بين Workflowين داخل GitHub، لا استقلال منصة: تعطيل Actions أو نفاد الحصة قد يوقف النسخ والمراقب معًا، لذلك يبقى Heartbeat خارجي ضابطًا مستقبليًا مطلوبًا.

## تشغيل القبول أو التمرين يدويًا

يتطلب المسار أسرار بيئة `production`: ‏`CPANEL_SSH_PRIVATE_KEY` و`MIGRATION_DATABASE_URL` و`BACKUP_ENCRYPTION_PASSPHRASE`، ويتطلب قبول المراقبة اللاحق `METRICS_BEARER_TOKEN`. راجع قائمة الإعداد والتحقق في [دليل نشر iFastNet](ifastnet-cpanel-deployment.md) ولا تنقل أيًا منها إلى متغير Repository عادي أو إلى وسيطة أمر.

من واجهة GitHub Actions اختر `production backup and restore drill` ثم `Run workflow` واجعل `restore_drill=true`. ومن GitHub CLI بعد وجود Workflow على الفرع الافتراضي:

```bash
gh workflow run production-backup-dr.yml --ref main -f restore_drill=true
```

لا تعد القناة سليمة حتى ينجح ما يلي في التشغيل نفسه:

- `Create encrypted offsite production backup`.
- `Restore the production backup into isolated MariaDB`.
- `Enforce production recovery objectives`.
- وجود Artifact النسخة وArtifact الدليل `mcap-production-restore-drill`، وداخله الملف المنقح `dr-evidence.json`، ببصمة ومدة احتفاظ ظاهرتين.
- تشغيل المراقبة الساعي التالي من دون تنبيه missing/stale.

## مصفوفة الفشل والاستجابة

| الفشل | السلوك الآمن | الإجراء |
|---|---|---|
| تعذر SSH أو النسخ | لا يرفع Artifact جديدًا ويفشل التشغيل | افحص حالة iFastNet وبصمة المضيف والمفتاح، ولا توسع الصلاحيات قبل تحديد السبب |
| غياب/تقادم النسخة السابقة | تستمر محاولة صنع نسخة جديدة، لكن بوابة RPO تفشل بعد الحفظ والتمرين | تعامل معه كخرق RPO وسجل مدة الفجوة وسبب التشغيل المفقود |
| اختلاف الحجم أو SHA-256 أو Manifest | يرفض الملف قبل الرفع أو قبل فك التشفير | لا تحاول إصلاح Manifest يدويًا؛ أنشئ نسخة جديدة وحقق في التخزين/النقل |
| عبارة تشفير خاطئة أو ملف مبتور | تفشل مصادقة AES-GCM ولا تدخل بيانات جزئية معتمدة | استرجع إصدار المفتاح الصحيح من مدير الأسرار واستخدم Artifact سابقًا سليمًا |
| قاعدة الاستعادة غير فارغة | ترفض الأداة البدء | أنشئ قاعدة مؤقتة جديدة؛ لا تستخدم `--force` ولا تنظف هدفًا غير محسوم |
| غياب بيانات الهوية الأساسية أو اختلال دفتر المصدر قبل النسخ | لا ينشأ ملف جديد ولا يُرفع Artifact | تحقق من اختيار قاعدة الإنتاج ومن سلامة المؤسسة والشركة والمستخدم والقيود قبل إعادة المحاولة |
| فشل الترحيلات أو الجداول أو اتزان القاعدة المستعادة | يفشل التمرين وتُهدم خدمة Runner المؤقتة | صنف النسخة غير مقبولة وابحث عن اتساق dump أو تغير الأداة قبل اعتمادها |
| تجاوز 900 ثانية | يحفظ دليل فشل منفصل ويفشل هدف الاستعادة التقني | قس فك التشفير والإدخال والتحقق منفصلة، وراجع حجم القاعدة وسعة الهدف؛ لا تخلط القياس مع RTO الحادث الكامل |
| توقف الجدول اليومي مع استمرار Actions | المراقب الساعي يكتشف Artifact المتقادم | افحص schedule وحالة iFastNet، ثم شغّل تمرينًا يدويًا كاملًا |
| توقف GitHub Actions أو نفاد الحصة | قد يتوقف النسخ والمراقب الساعي معًا | افحص Heartbeat خارجيًا/يدويًا وحالة Actions، ولا تعتبر غياب التنبيه إثبات سلامة |

## استعادة الخدمة بعد فقدان الاستضافة

1. أوقف الكتابة إلى البيئة المتضررة وسجل وقت آخر عملية موثوقة؛ لا توجه تطبيقين قابلين للكتابة إلى القاعدة نفسها.
2. اختر أحدث `mcap-production-database-backup` من تشغيل ناجح. فضّل تشغيلًا يملك أيضًا دليل استعادة شهريًا ناجحًا، لكن أعد التحقق من النسخة المختارة دائمًا.
3. نزّل ملف `.jwb` والـManifest إلى محطة استجابة مشفرة ومقيدة. احصل على إصدار عبارة التشفير الموافق من مدير أسرار مستقل عن iFastNet.
4. شغّل `scripts/verify-backup-artifact.mjs` قبل فك التشفير، وأنشئ قاعدة MariaDB/MySQL فارغة متوافقة وهوية استعادة مؤقتة عليها فقط.
5. اضبط `DATABASE_URL` للقاعدة الفارغة و`BACKUP_FILE` و`BACKUP_ENCRYPTION_PASSPHRASE` من مدير الأسرار المستقل و`RESTORE_CONFIRM=RESTORE:<database>`، ثم شغّل `node scripts/database-restore.mjs`.
6. لا تعتبر نجاح استيراد SQL كافيًا؛ يجب نجاح فحص الجداول والترحيلات واستعلام تعدادات الجداول المرجعية ووجود بيانات الهوية الأساسية واتزان المدين والدائن. لا يقارن v2 التعدادات بعدد مصدر منشور، لذلك أكمل تحقق الحادث الوظيفي في الخطوة التالية. افحص حالة Prisma من Checkout مطابق للالتزام بعد `npm ci`، أو من محطة الاستجابة المعزولة عبر `npx --yes prisma@7.9.1 migrate status` داخل `apps/api`؛ أداة Prisma CLI محذوفة عمدًا من Release التشغيل المنقّى.
7. جهز حساب تشغيل DML فقط وحساب ترحيل مستقلًا، وشغّل الإصدار الموافق في عنوان معزول، ثم اختبر `/live` و`/ready` والدخول وتقارير ميزان المراجعة قبل تحويل DNS/Passenger.
8. وثق RPO الفعلي بدءًا من `recoveryPointAt` (وهو `snapshotStartedAt` في v2؛ يستخدم v1/التحويل القديم `createdAt` كبديل محدود الدقة) إلى آخر كتابة مفقودة، ووثق RTO الحادث من الإعلان إلى عودة الخدمة، وأبق البيئة الأصلية للطب الشرعي ما لم يشكل بقاؤها خطرًا.

استعادة شركة واحدة لا تدخل مباشرة فوق الإنتاج. تستعاد النسخة كاملة في بيئة معزولة، ثم يراجع استخراج الشركة وعلاقاتها وميزانها بخطة منفصلة.

## الاحتفاظ وتدوير المفتاح

- تحتفظ GitHub بالنسخ اليومية وأدلة التمرين 90 يومًا. تبقى Artifacts منفصلة حسب Run؛ لا يسمح المسار بالاستبدال في المحاولة الأولى، ويستخدم `overwrite` المقيد بمحاولة إعادة التشغيل فقط لمعالجة الاسم الموجود من المحاولة السابقة. سجل `run_attempt` عند التحقيق لأن Artifact المعاد رفعه يملك هوية وبصمة إنشاء جديدتين.
- يحتفظ Workflow بسبعة أيام محليًا من نسخ `mcap-production-*` ويحذف الأقدم بعد نجاح رفع النسخة الخارجية فقط، وينظف مخلفات النمط نفسه بعد مهلة يوم. لا يطابق هذا التنظيف نسخ ما قبل النشر ذات الأسماء الأخرى؛ تبقى سياسة مساحتها إجراءً مستقلًا حتى لا يحذف المسار الآلي أدلة رجوع لم توضع في نطاقه.
- تدوير `BACKUP_ENCRYPTION_PASSPHRASE` لا يعيد تشفير Artifacts القديمة. احتفظ بالمفتاح السابق، موسومًا بمدة صلاحيته، في مدير أسرار مستقل حتى انتهاء آخر Artifact يعتمد عليه.
- بعد كل تدوير شغّل نسخة وتمرين استعادة يدويين بالمفتاح الجديد قبل إيقافه عن الاستخدام، واختبر Artifact قديمًا بالمفتاح السابق في محطة معزولة.

## نموذج التهديد والحوكمة

يفصل هذا التصميم النسخة عن حساب iFastNet ويحمي المحتوى بتشفير مستقل. لكنه لا يفصل Artifact ومفتاح التشغيل عن سيطرة GitHub بالكامل: يستطيع مهاجم يملك تعديل Workflow منفذًا على `main` إساءة استخدام أسرار البيئة. لذلك يبقى إنفاذ حماية `main` عبر GitHub Pro أو مؤسسة Team/Enterprise ضابط P0 مستقلًا، ويجب حفظ نسخة من مفتاح التشفير في مدير أسرار خارج GitHub وiFastNet معًا.
