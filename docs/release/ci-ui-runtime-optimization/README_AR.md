# تحسين زمن بوابة واجهة CI

## النطاق

يخفض هذا التغيير زمن بوابة Playwright من دون حذف بوابات MySQL أو MariaDB أو ترقية قاعدة البيانات أو تغيير سير النشر. يقتصر التنفيذ على:

- تشغيل ملفّات Playwright بالتوازي على عاملين داخل CI، مع الإبقاء على عامل واحد محليًا.
- إزالة التكرار الخارجي فقط لملفي الاختبار اللذين يعرّفان قياسي `mobile-390` و`desktop-1440` داخليًا بأنفسهما.

تبقى `fullyParallel: false`، ولذلك لا تتوازى حالات الملف الواحد؛ التوازي الجديد يقع بين الملفات فقط.

تم إنشاء الدليل بالأمر:

```powershell
node node_modules/@playwright/test/cli.js test --config playwright.integration.config.ts --list
```

- بقيت حالات لوحة المعلومات الست، وتشمل عناوين `mobile-390` و`desktop-1440`.
- لا تزال بقية ملفات الواجهة تعمل على مشاريع القياسات الخارجية نفسها كما كانت.

## دليل التنفيذ المركّز

شُغّل الملفان المتأثران مع `CI=true`:

```text
Running 18 tests using 2 workers
18 passed (34.6s)
```

وشُغّلت عينة محلية مع غياب متغير `CI`:

```text
Running 2 tests using 1 worker
2 passed (5.3s)
```

يثبت ذلك أن فرع CI يستخدم عاملين، وأن التشغيل المحلي يبقى على عامل واحد، وأن القياسين الداخليين يعملان بعد إزالة التكرار الخارجي.

## الأثر الزمني المتوقع

كان الجزء المتسلسل المستهدف 31:39. بعد إزالة 6.28% من التنفيذات المتكررة وتشغيل الملفات على عاملين، التوقع المحافظ هو:

| القياس | قبل التغيير | المتوقع بعد التغيير |
|---|---:|---:|
| `subscription-qa:test` | 31:39 | 16–22 دقيقة |
| workflow الكامل مع النشر | 48:46 | 33–39 دقيقة |

هذه أرقام متوقعة وليست دليل نشر. القياس النهائي يتطلب تشغيل GitHub Actions على الفرع، لأن توازن الملفات وموارد runner يؤثران في مقدار التسريع.

## ما لم يتغير

- لم تتغير `.github/workflows/ci.yml`.
- لم تُحذف أي بوابة قاعدة بيانات أو ترقية أو نسخ احتياطي أو نشر.
- لم يتغير ترتيب حالات الاختبار داخل الملف الواحد.
- لم يُنفذ push أو PR أو نشر.
- لم تُشغّل المجموعة الكاملة محليًا؛ استغرقت 31 دقيقة في القياس السابق، واكتُفي بقائمة كاملة وتحقق فعلي مركّز للملفين المتأثرين.
