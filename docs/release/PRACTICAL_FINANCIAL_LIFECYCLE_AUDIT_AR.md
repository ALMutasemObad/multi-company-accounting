# تدقيق دورة المستخدم المالية الأساسية

التاريخ: 2026-09-08

الفرع: `task/practical-financial-lifecycle-audit`

خط الأساس: `731fc11f3635143558fcd6431b864afd0807ff53`

## النتيجة التنفيذية

اجتازت الواجهة رحلة محاسبية تركيبية كاملة على عرضي 390 و1440 بكسل: التحقق من السنة والفترة المفتوحة ودليل الحسابات، ظهور العميل والمورد، عرض تقريري التدفق النقدي وميزان المراجعة، ترحيل ثم عكس فاتورة بيع وفاتورة شراء وسند قبض وسند دفع، ثم ظهور المستندات الأربعة بحالة `REVERSED` في تقرير اليومية.

كُشفت في التدقيق الأصلي فجوة واحدة مؤكدة من الأولوية P1: كانت إجراءات العكس الأربعة تستخدم تاريخ UTC كتاريخ افتراضي بدل تاريخ الشركة. أُغلقت الفجوة في مرشح الموجة الرابعة، وحُوّل مسار إعادة إنتاجها نفسه إلى اختبار regression ناجح على عرضي 390 و1440 بكسل. لم تظهر فجوة P0 مؤكدة في النطاق المختبر.

## حدود الدليل

- البيانات تركيبية وآمنة بالكامل، ولا تستخدم أسرارًا أو حسابات أو بيانات حية.
- اعتراض الطلبات داخل Playwright يعزل الواجهة ويعيد استجابات متوافقة مع العقود المطلوبة للرحلة. لذلك يثبت هذا التدقيق سلوك الواجهة والطلبات والآثار الجانبية المرصودة، لكنه **لا** يثبت سلامة معاملات قاعدة البيانات أو القيود المحاسبية في خادم حقيقي.
- لم يُعدّل أي كود منتج أو API أو قاعدة بيانات، ولم يُستخدم أي خادم خارج النظام المحاسبي.
- حفظ الاختبار سجل JSON مرفقًا بكل نتيجة Playwright للقراءات والكتابات وفشل الطلبات وقيم تاريخ العكس الافتراضية.

## البيانات التركيبية

- سنة مالية 2026 وفترة سبتمبر مفتوحة من `2026-09-01` إلى `2026-09-30`.
- حسابات نقدية وذمم مدينة وذمم دائنة وإيراد ومصروف بالأكواد `1100` و`1200` و`2100` و`4100` و`5100`.
- عميل `CUS-000001` ومورد `SUP-000001`، وحساب صندوق وطريقة دفع نقدية وعملة `SAR`.
- مستندات مترابطة تبدأ بحالة `DRAFT`: `SI-2026-0001` و`PI-2026-0001` و`REC-2026-0001` و`PAY-2026-0001`.

## الرحلات والنتائج

| الرحلة | 390px | 1440px | الدليل |
|---|---:|---:|---|
| المتطلبات + العميل/المورد + التدفق النقدي + ميزان المراجعة | ناجح | ناجح | لا توجد كتابة؛ الحسابات الخمسة ظاهرة؛ تقرير التدفق متوازن؛ ميزان المراجعة يعرض الحساب `1100` |
| ترحيل وعكس المستندات الأربعة + تقرير اليومية | ناجح | ناجح | ثمانية طلبات كتابة مرتبة؛ الإصدارات `0` للترحيل ثم `1` للعكس؛ المستندات الأربعة ظاهرة `REVERSED` |

تحقق الاختبار كذلك من عدم وجود أخطاء JavaScript، وعدم وجود طلب كتابة فاشل، وعدم تجاوز المحتوى عرض الشاشة في المقاسين.

## سجل الآثار الجانبية المتوقع والمثبت

```text
POST /sales-invoices/sales-1/post
POST /sales-invoices/sales-1/reverse
POST /purchase-invoices/purchase-1/post
POST /purchase-invoices/purchase-1/reverse
POST /receipts/receipt-1/post
POST /receipts/receipt-1/reverse
POST /payments/payment-1/post
POST /payments/payment-1/reverse
```

- حمل كل طلب رمز CSRF، وحملت أوامر الترحيل والعكس مفاتيح idempotency غير فارغة.
- أرسلت أوامر الترحيل `{ version: 0 }`.
- أرسلت أوامر العكس بعد الإصلاح `{ version: 1, reason: "Synthetic lifecycle reversal", reversalDate: "2026-09-09" }`، وهو تاريخ الشركة عند اللحظة المثبتة.
- لم ترسل رحلة القراءة الأولى أي `POST` أو `PATCH` أو `DELETE`.

ظهرت إلغاءات `net::ERR_ABORTED` لنسخ أولية من قراءات بدء التشغيل في وضع Vite التطويري (`auth/me` و`auth/companies` و`platform/capabilities` و`organizations/workspaces`) بسبب تنظيف تأثيرات React في وضع التطوير، ثم نجحت القراءات البديلة. لم تُلغَ أي كتابة ولم يُصنف ذلك كفجوة منتج.

## الفجوات المؤكدة وإغلاقها

### FIN-LIFE-P1-001 — تاريخ العكس الافتراضي لا يتبع المنطقة الزمنية للشركة

الأولوية الأصلية: **P1** — الحالة في مرشح الموجة الرابعة: **مغلقة باختبار regression**

النطاق: فواتير البيع، فواتير الشراء، سندات القبض، سندات الدفع.

خطوات إعادة الإنتاج الآلية:

1. اجعل المنطقة الزمنية للشركة `Asia/Riyadh`.
2. ثبّت اللحظة عند `2026-09-08T22:30:00.000Z`؛ تاريخ الشركة حينها `2026-09-09`.
3. افتح مستندًا مرحلًا واضغط العكس.
4. راقب القيمة الافتراضية لحقل تاريخ العكس ثم اقبلها.

المتوقع: `2026-09-09`، أي تاريخ الشركة.

الفعلي قبل الإصلاح: `2026-09-08` في نافذة الإدخال وفي جسم طلب العكس.

السبب المرصود في الواجهة هو استخدام `new Date().toISOString().slice(0, 10)`، أي يوم UTC، بدل تحويل اللحظة إلى `selectedCompany.timezone`. يستطيع المستخدم تعديل التاريخ يدويًا، لكن قبول القيمة الافتراضية قد يرحّل العكس إلى يوم أو فترة مالية غير مقصودة، ولذلك صُنفت P1.

الإغلاق: تستخدم الصفحات الأربع الآن المساعد المركزي `companyCalendarDate(selectedCompany.timezone)` مع fallback حتمي إلى UTC عند غياب المنطقة أو عدم صلاحيتها. يثبت الاختبار نفسه أن قيم النوافذ الأربع وأجسام طلبات العكس الأربعة أصبحت `2026-09-09` عند اللحظة المثبتة، على المقاسين 390 و1440 بكسل.

## ما لم يثبته هذا التدقيق

- لم تُختبر قاعدة بيانات حقيقية أو قيود `PostingEngine` أو إنشاء قيود دفتر الأستاذ الفعلية.
- لم تُختبر سلامة الاسترداد بعد انقطاع خادم حقيقي أو فشل جزئي في معاملة.
- لم يُختبر إنشاء العميل والمورد والمستندات من النماذج؛ استُخدمت مسودات تركيبية ثابتة للتركيز على دورة الترحيل والعكس والتقارير.
