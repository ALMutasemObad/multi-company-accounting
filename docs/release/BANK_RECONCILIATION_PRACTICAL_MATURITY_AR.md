# نضج رحلة المطابقة البنكية عمليًا

التاريخ: 2026-09-08
النطاق: واجهة المطابقة البنكية فقط، ببيانات تركيبية واعتراضات API محلية معزولة. لم تُستخدم بيانات حية ولم يحدث دفع أو نشر.

## النتيجة

اكتملت رحلة عملية متصلة من ملف كشف CSV إلى إقفال جلسة المطابقة على عرضي 390 و1440 بكسل. شملت الرحلة المعاينة، اعتماد الاستيراد، إنشاء الجلسة، توليد الاقتراح، اعتماد الاقتراح ثم فكه، المطابقة اليدوية، تصنيف الاستثناء، والإقفال بعد زوال البنود غير المحسومة.

أثبت التدقيق فجوة P1 في حدود الإجراءات: كانت الواجهة تُبقي زر توليد الاقتراحات وزر الإقفال وبعض مدخلات الإقفال مركبة في DOM بحالة معطلة عند غياب القدرة، كما لم تكن معالجات الكتابة نفسها تعيد التحقق من القدرة المستقلة قبل الطلب. عولجت الفجوة بإزالة سطح الكتابة غير المسموح من DOM وربط كل handler بسياسة القدرة المقابلة قبل أي POST.

## مصفوفة القدرات المعتمدة

| القدرة | الإجراءات التي تسمح بها | حد الخادم المقارن |
|---|---|---|
| `canImport` | معاينة ملف الكشف واعتماد الاستيراد | `bank_reconciliation.import` في مرحلة `SHADOW` |
| `canSuggest` | إنشاء جلسة من كشف معتمد وتوليد الاقتراحات | `bank_reconciliation.review` في مرحلة `SHADOW` |
| `canReview` | المطابقة اليدوية، اعتماد الاقتراح، فك المطابقة، وتصنيف الاستثناء | `bank_reconciliation.review` في مرحلة `REVIEW` |
| `canClose` | إقفال جلسة مستوفية الشروط | `bank_reconciliation.close` في مرحلة `CLOSE` |

تظل قائمة الاستيرادات والجلسات، تفاصيل الجلسة، الحركات الدفترية، مشاهدة الاقتراح، وتصدير CSV المحلي ضمن سطح القراءة. لا ينشئ التصدير طلب كتابة للخادم.

## حدود الواجهة بعد المعالجة

- مستخدم القراءة فقط يرى التاريخ والتفاصيل والاقتراحات المقروءة، ولا يرى تبويب كشف جديد أو مدخل نافذة الاقتراح أو أزرار التوليد/المراجعة/الإقفال.
- قدرة الاستيراد وحدها تعرض ملف الكشف والمعاينة والاعتماد فقط؛ لا تنشئ جلسة تلقائيًا إذا كانت `canSuggest=false`.
- قدرة الاقتراح وحدها تعرض بدء الجلسة وتوليد الاقتراحات، مع إبقاء الاقتراح للقراءة دون إجراءات اعتماد.
- قدرة المراجعة وحدها تعرض إجراءات المراجعة ولا تعرض توليد الاقتراحات أو الإقفال.
- قدرة الإقفال وحدها تعرض الإقفال عند استيفاء شروط الجلسة ولا تعرض أسطح الاستيراد أو الاقتراح أو المراجعة.
- الحماية ثنائية: التحكم غير المخول غير مركب، والـhandler يرفض العمل أيضًا إن أصبحت القدرة قديمة أو تغيرت قبل التنفيذ.

## أدلة الاختبار

- اختبار الوحدة `apps/web/src/bank-reconciliation.test.ts`: أربع حالات، منها مصفوفة مستقلة تربط كل إجراء بقدرته.
- اختبار Playwright العملي `tests/visual/bank-reconciliation-practical-maturity.spec.ts`: 12 حالة؛ رحلة كاملة وخمس حالات قدرة مستقلة على كل من 390 و1440.
- يسجل الاختبار مسارات POST البنكية ويقارنها حرفيًا بالطلبات المسموح بها لكل حالة؛ حالات القراءة لا تسجل أي طلب كتابة.
- نجحت typechecks الخاصة بالويب وPlaywright، وبناء واجهة الويب، وفحص `git diff --check` عند التسليم.

## ما لم يُختبر

- لم تُشغّل قاعدة بيانات حقيقية أو مزود بنك خارجي؛ بيانات الرحلة تركيبية والطلبات معترضة داخل Playwright.
- لم يُختبر CAMT.053 في هذه المهمة؛ اختبر المسار العملي CSV فقط.
- لم تُغيّر أو تُختبر عقود API أو schema أو OpenAPI، ولم تُفحص وحدات خارج الخزينة والمطابقة البنكية.
- لم تُختبر صلاحيات خادم حقيقية هنا؛ جرى مقارنة أعلام القدرة التي تعيدها الواجهة مع متطلبات router قراءةً فقط، بينما ركز الاختبار العملي على امتناع الواجهة عن إصدار كتابة غير مسموح بها.

## المتبقي

لا توجد فجوة P0/P1 أخرى مؤكدة ضمن النطاق المملوك بعد هذه المعالجة. يبقى تشغيل الرحلة نفسها على تكامل API/قاعدة بيانات حقيقية بوابة مستقلة مستقبلية، وليس دليل نقص في fixture المحلي المستخدم هنا.
