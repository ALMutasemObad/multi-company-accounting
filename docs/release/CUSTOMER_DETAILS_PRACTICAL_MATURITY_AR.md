# نضج رحلة تفاصيل العملاء عمليًا

التاريخ: 2026-09-08

الفرع: `task/customer-details-practical-maturity`

خط الأساس: `731fc11f3635143558fcd6431b864afd0807ff53`

## النتيجة

اجتازت شاشة العملاء ست حالات متصفح على عرضي 390 و1440 بكسل: القائمة والبحث والتفاصيل لمستخدم العرض فقط، دورة الإدارة الكاملة، وإعادة تحميل التفويض بعد سحب الصلاحية أثناء فتح نموذج العميل أو نموذج العنوان.

ثبتت فجوة P1 واحدة وأُصلحت: كانت تفاصيل العميل تعرض المعرّف الداخلي الخام لحساب الذمم عندما لا يملك المستخدم `accounts.view`. أصبحت القيمة المحايدة `—` تظهر بدلًا منه، من دون طلب قراءة حسابات غير مخوّل.

لم تظهر فجوات P0 أو P1 إضافية ضمن المسارات المختبرة.

## حدود الاختبار

- استخدمت الرحلة بيانات تركيبية واعتراضات Playwright محلية فقط؛ لا أسرار ولا بيانات أو خوادم حية.
- لم يتغير API أو OpenAPI أو schema أو i18n أو الاعتمادات.
- اختبار سحب الصلاحية يحاكي تغير التفويض في الخادم ثم إعادة تحميل التطبيق للحصول على `/auth/me` المحدث. لا يزعم وجود بث فوري لتغير الصلاحيات إلى جلسة مفتوحة.
- يحفظ كل اختبار سجل JSON مرفقًا للطلبات الفعلية ورؤوس CSRF وIdempotency وأجسام الكتابة.

## مصفوفة الرحلات

| الرحلة | 390px | 1440px | الدليل |
|---|---:|---:|---|
| عرض فقط: قائمة، بحث، تفاصيل | ناجح | ناجح | لا `/accounts`، لا أفعال إدارة، لا معرّف حساب خام، وصفر كتابات عملاء |
| إدارة: إنشاء وتعديل وتعطيل وعناوين | ناجح | ناجح | ست كتابات مقصودة فقط بأجسام دقيقة وCSRF صحيح |
| سحب الصلاحية والنماذج مفتوحة | ناجح | ناجح | اختفاء CustomerForm وAddressForm بعد تحديث التفويض وصفر كتابات عملاء |

تحقق الاختبار كذلك من غياب أخطاء JavaScript، وغياب فشل الطلبات غير الإلغاءات المتوقعة عند إعادة التحميل، وعدم تجاوز المحتوى عرض الشاشة في المقاسين.

## الآثار الجانبية المثبتة

```text
POST /customers
PATCH /customers/2
POST /customers/2/addresses
PATCH /customers/2/addresses/21
DELETE /customers/2/addresses/21
POST /customers/2/deactivate
```

- أرسل الإنشاء حساب الذمم والاسمين والهاتف والبريد والرقم الضريبي وعنوان الفوترة الأولي، مع تحويل رمز الدولة `sa` إلى `SA`.
- أرسل تعديل العميل الحقول القابلة للتعديل فقط، ولم يرسل رقمًا ضريبيًا فارغًا يمسح القيمة القائمة.
- أرسلت عمليات العنوان الحقول السبعة المتوقعة، وحولت `ae` إلى `AE`، وحافظت على `isPrimary`.
- أرسل التعطيل `{ reason: "Lifecycle deactivation" }`.
- حملت الكتابات الست `X-CSRF-Token: customer-maturity-csrf`.
- لم تحمل العمليات `Idempotency-Key` لأن مسارات العملاء الحالية لا تطلب هذا الرأس في عقد OpenAPI أو customer router؛ سُجل الغياب ولم يُعامل كادعاء idempotency.
- لم ترسل حالتا العرض فقط أو سحب الصلاحية أي كتابة تحت `/customers`.

## الفجوة المؤكدة والإصلاح

### CUSTOMER-P1-001 — كشف معرّف حساب داخلي في تفاصيل العرض فقط

قبل الإصلاح، نفذ المستخدم ذو `customers.view` فقط الرحلة التالية:

1. فتح قائمة العملاء والبحث عن `CUS-000001`.
2. فتح تفاصيل العميل من زر الاسم.
3. لم تطلب الشاشة `/accounts` لغياب `accounts.view`، وهذا هو السلوك الصحيح.
4. عرض حقل حساب الذمم القيمة الخام `account-ar-internal-opaque` بدل اسم مفهوم أو قيمة محايدة.

أثبت تشغيل Playwright الأول الفشل عند توقع عدم وجود المعرف، وكان عدد ظهوره في DOM واحدًا. عدّل الإصلاح fallback داخل `CustomerDetails` إلى `—`. بعده نجحت الحالة في المقاسين مع بقاء `/accounts` غير مطلوب وصفر كتابات.

صُنفت P1 لأنها تكشف تفصيل تنفيذ داخلي غير مفيد للمستخدم وقد يُنسخ أو يُعتمد عليه خطأ، بينما لا تمنح صلاحية قراءة الحساب نفسه ولا تنفذ كتابة غير مخولة.

## حراسة الصلاحيات

- `customers.view` يكفي للقائمة والبحث وفتح التفاصيل.
- `customers.manage` وحده يكشف إنشاء العميل وتعديله وتعطيله وإضافة العناوين وتعديلها وحذفها.
- الحراسة قائمة عند العرض، وتركيب النماذج، وداخل submit/handlers.
- عند إعادة تحميل تفويض بلا `customers.manage` والنموذج مفتوح، لا يعاد تركيب النموذج ولا يظهر زر الإدارة ولا يرسل طلب عميل.
