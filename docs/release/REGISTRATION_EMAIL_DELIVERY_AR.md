# تسليم موثوقية بريد التسجيل

## التشخيص المثبت محليًا

- التسجيل ببريد مستخدم موجود لا ينشئ `RegistrationRequest` ولا حدث Outbox ولا يرسل بريدًا عمدًا؛ يعيد المسار العام النتيجة نفسها لمنع تعداد الحسابات.
- التسجيل الجديد يكتب `RegistrationRequest` و`RegistrationVerificationRequested` ذريًا، ثم يعالج العامل البريد بعد commit. لذلك `202 PENDING_VERIFICATION` يثبت قبول الطلب فقط، ولا يثبت أن مزود البريد قبله أو أن صندوق المستخدم استلمه.
- معالج التحقق القائم يحفظ `PENDING` قبل استدعاء المرسل، ثم `SENT` بعد قبول adapter، أو `FAILED` عند الخطأ. يعيد عامل Outbox الأخطاء المؤقتة بعد backoff محدود، وينقلها إلى `FAILED` عند آخر محاولة.
- رمز التحقق مشتق من `eventId` ولا يخزن خامًا في Outbox. إعادة محاولة الحدث نفسه تستخدم الرمز نفسه، وإعادة الإرسال الصريحة تزيد `deliveryGeneration` وتبطل عمل أحداث الجيل السابق.
- مسارات التسجيل وإعادة الإرسال والتحقق تشترك في محدد معدل خادمي مسجل في `app.ts`. لم تضف هذه المهمة polling أو API أو محددًا موازيًا.

## ما نُفذ

- ثُبت رد HTTP العام داخل router إلى `{ status: "PENDING_VERIFICATION" }` بعد نجاح الخدمة بدل تمرير أي حقول مستقبلية منها؛ وبذلك لا يمكن أن يتسرب `deliveryStatus` أو `lastErrorCode` أو اختلاف وجود الحساب من هذا الحد.
- استبدلت واجهة الانتظار بوصف صادق: الطلب استُلم ويعالج في الخلفية، والنتيجة واحدة لكل بريد. أضيف توجيه عام لتسجيل الدخول/استعادة كلمة المرور للحساب الموجود دون تأكيد وجوده.
- نجاح زر إعادة الإرسال يعرض أن **الطلب** قُبل ولا يدعي وصول البريد. يبقى الفشل ظاهرًا مع زر إعادة محاولة، ويعطل الزر أثناء الطلب المتزامن؛ ويظل الحد الحقيقي خادميًا.
- أضيفت نسخة محلية كاملة للعربية والإنجليزية والأردية والهندية داخل نطاق المهمة، دون تعديل قواميس i18n المشتركة.
- أضيف اختبار مركّز يثبت انتقالات `PENDING/SENT/FAILED`، تجاهل الجيل القديم والتسليم المكرر، retry محدود وdead-letter، وثبات الاستجابة العامة وعدم كشف تفاصيل المزود. وأضيف اختبار عرض لحالات القبول والفشل وإعادة المحاولة.

## التحقق المنفذ

- فحص أنواع API عبر `tsc -p apps/api/tsconfig.test.json --noEmit`: ناجح.
- فحص أنواع Web عبر `tsc -p apps/web/tsconfig.json --noEmit`: ناجح.
- ستة ملفات Vitest ذات صلة (`registration-email-delivery`, `registration-mailer`, `registration-verification-handler`, `outbox-worker` واختبارا الواجهة): 20 اختبارًا ناجحًا.
- حزمة Web الكاملة: 48 ملفًا و662 اختبارًا ناجحًا.
- حزمة API الكاملة: 127 ملفًا و1233 اختبارًا ناجحًا، و40 ملفًا/161 اختبارًا متجاوزة بشرط بيئي (ومنها اختبارات قاعدة البيانات).
- بوابات `contracts:check` وWeb i18n وWeb UI: ناجحة.
- ولّد Prisma Client محليًا من المخطط الحالي لتشغيل الاختبارات؛ لم يتغير schema أو migration.

## ما لم يُختبر والقيود

- لم يُرسل بريد فعلي، ولم تُقرأ أسرار أو رسائل أو بيانات مستخدمين حية.
- لم تُشغّل اختبارات MariaDB التكاملية لأن المهمة لم تُمنح اتصال قاعدة اختبار أو `DATABASE_URL`. الاختبارات القائمة في `self-registration.integration.test.ts` تغطي الذرية والتكرار والاستعادة عند توفر البيئة، لكنها لم تُحسب كدليل منفذ في هذه الجولة.
- `SENT` يعني أن adapter تلقى قبول مزود النقل، وليس إثبات فتح الرسالة أو وصولها إلى inbox. لا يوجد webhook تسليم ضمن النطاق الحالي، ولم يُضف ادعاء أعلى من الدليل المتاح.
- لم يُختر مزود جديد، ولم تتغير متغيرات البيئة أو OpenAPI أو الملفات المولدة أو `app.ts`.
- أظهر `npm ci` تدقيقًا آليًا بوجود ثغرتين في شجرة الاعتماد الحالية (واحدة متوسطة وواحدة عالية). لم يُنفذ `audit fix` لأنه تغيير اعتماد خارج نطاق المهمة.
- لا push ولا PR ولا دمج ولا نشر.
