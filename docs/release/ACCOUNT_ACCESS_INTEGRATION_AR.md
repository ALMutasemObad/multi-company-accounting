# تسليم تكامل الوصول إلى الحساب

## النتيجة

دُمجت محليًا المرشحات المقبولة التالية فوق `origin/main` عند `9be397c`:

- `account-onboarding-integration` حتى `8ae2eaf`.
- `registration-email-integration` حتى `638810d`.
- `social-login-implementation` حتى `3056d8f`.

السلاسل ليست مستقلة بالكامل: يحتوي مرشح البريد كامل مرشح onboarding، ويبدأ مرشح
الدخول الاجتماعي من رأس onboarding نفسه. لذلك طُبقت السلسلة المشتركة مرة واحدة، ثم
التزاما البريد الفريدان، ثم التزامات الدخول الاجتماعي الأربعة الفريدة. لم ينسخ شيء
من الأرشيف ولم يحدث push أو PR أو دمج بعيد أو نشر.

حافظ التكامل على استجابة التسجيل وإعادة الإرسال العامة
`PENDING_VERIFICATION` بلا `deliveryStatus` أو تفاصيل مزود، ولا تكشف الاستجابة وجود
البريد أو تعطيل الحساب ولا تدعي أن البريد أُرسل أو وصل. يظل إنشاء شركة إضافية مسارًا
واضحًا للحساب المسجل من مساحة مالك المجموعة وبصلاحية `OWNER` النشطة.

Google وApple معطلان افتراضيًا، ولا تعرض واجهة الدخول أزرارهما إلا وفق نتيجة
`/auth/social/providers`. الدخول والربط الخادميان يعتمدان الهوية الموثقة
`issuer + subject` فقط؛ البريد صفة اتصال ولا يربط حسابًا قائمًا تلقائيًا. يتطلب
`LINK` جلسة حديثة وموافقة صريحة، ويستهلك معاملة التفويض مرة واحدة ثم يدور الجلسة.

## فجوة P1 التالية — التسجيل والربط الاجتماعي غير مكتملين واجهيًا

لا يعني هذا التسليم أن إنشاء حساب جديد بواسطة Google أو Apple مكتمل. عندما تعود
الخدمة بـ`onboarding_required` يحول `App` المستخدم بأمان إلى نموذج التسجيل العام،
لكنه يزيل نتيجة callback ولا يحمل هوية المزود الموثقة إلى طلب التسجيل أو التحقق
اللاحق. لذلك ينشأ الحساب الحالي عبر البريد وكلمة المرور فقط، ولا ينشأ
`ExternalIdentity` له تلقائيًا. كذلك لا توجد شاشة إعدادات مكتملة تبدأ رحلة `LINK`
للمستخدم المصادق عليه، رغم أن عقد الخدمة الخادمي واختباره موجودان.

أصغر عقد استمرار آمن مقترح، وغير منفذ في هذه المهمة:

1. يصدر callback الناجح لِهوية جديدة continuation opaque أحادي الاستخدام وقصير
   العمر، مرتبطًا بمتصفح PRE_AUTH. لا تُرسل `issuer` أو `subject` أو رموز المزود إلى
   JavaScript أو حقول النموذج.
2. يستهلك أمر تسجيل اجتماعي صريح هذا continuation مع بيانات onboarding وموافقة
   المستخدم، وينشئ `RegistrationRequest` عامًا بلا اختلاف قابل للرصد عن التسجيل
   العادي. البريد الموثق من المزود لا يثبت ملكية حساب محلي قائم ولا يتجاوز تحقق
   البريد المعتمد إلا بقرار أمني مستقل.
3. عند اكتمال التحقق والتجهيز، ينشئ Identity المستخدم و`ExternalIdentity` ذات
   `issuer + subject` في المعاملة نفسها عبر Identity port، مع unique conflict آمن
   يمنع ربط الهوية بمستخدمين أو دمج الحسابات بالبريد.
4. تضيف شاشة إعدادات الحساب رحلة `LINK` منفصلة: إعادة إثبات حديثة، موافقة صريحة،
   عرض المزود المرتبط، وإلغاء الربط بسياسة تمنع حبس المستخدم خارج الحساب. تبقى
   الأزرار مخفية عند تعطيل المزود.

يلزم قبل تنفيذ هذا العقد تحديد مدة continuation وسياسة الاحتفاظ والإلغاء، وحماية
CSRF/Rate Limit، وسلوك التعارض المتزامن، وتحديث OpenAPI والترحيل والواجهة واختبارات
MySQL/MariaDB. لا يجوز تمرير البريد كدليل ربط أو تخزين access/refresh tokens لمجرد
إكمال هذه الرحلة.

  ونجحت الحالات المذكورة.

  الجاهزية الأول بصيغة arguments فسرتها PowerShell خطأ. لم يبدأ listener في المحاولة
  الأولى؛ أعيد تشغيل datadir المهيأ نفسه قبل أي migration بوسائط صريحة، ثم نجحت
  البوابة وأُغلق المحرك طبيعيًا.
