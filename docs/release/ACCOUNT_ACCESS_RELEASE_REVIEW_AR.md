# مراجعة إصدار الوصول إلى الحساب

## القرار

راجعت مرشح الوصول إلى الحساب مراجعة مستقلة بعد إعادة بناء السلسلة الخطية من
`origin/main` عند `9be397c` حتى المرشح `c3cbc0cb566f8b733d6a0cf1dc043656f46e8dd3`
مرة واحدة وبالترتيب. نتجت 18 التزامًا محليًا مكافئًا وانتهت السلسلة المعاد بناؤها
عند `9c56eed` قبل إصلاحات هذه المراجعة. لا توجد نتيجة فشل مفتوحة ضمن النطاق بعد
الإصلاح والتحقق المحلي، والمرشح صالح للانتقال إلى مراجعة الدمج، مع بقاء بوابات
المزودين والبريد والـCI والنشر الحية خارج هذا الإثبات.

لم يحدث push أو PR أو دمج بعيد أو نشر، ولم تستخدم أسرار أو حسابات مزودين أو بريد
حي. هذه الوثيقة تفرق عمدًا بين ما أعيد تشغيله هنا وبين أدلة التسليمات السابقة.

## ما روجع

- التسجيل: الاستجابة العامة غير المعددة للحسابات، وعدم إنشاء بريد للهوية الموجودة،
  وذرية `RegistrationRequest` مع Transactional Outbox، وعدم تسريب حالة المزود.
- إنشاء الحساب والشركة: تجهيز المالك والشركة والاشتراك والحسابات ذريًا، وإنشاء شركة
  إضافية عبر عضوية `OWNER` نشطة، والعزل والتكرار والـrollback عند فشل الآثار التابعة.
- الدخول والتسجيل الاجتماعي: `state` و`nonce` وPKCE وربط المتصفح، حماية القيم
  الحساسة وتخزين الـhash، الاستهلاك الأحادي، عدم الدمج بالبريد، continuation معتم
  ومشفّر ومرتبط بمتصفح PRE_AUTH، وتجهيز الهوية والمستخدم والشركة والجلسة ذريًا.
- حسابات المزود: لا يعيد API `issuer` أو `subject` أو البريد أو claims أو tokens؛
  ويعرض فقط المزود والحالة ووقت الربط للمزودين المهيأين.
- الربط والفك: recent-auth وCSRF والموافقة، تدوير الجلسة وسياق الشركة، القفل
  `FOR UPDATE` ومعاملة `Serializable`، حماية آخر وسيلة دخول، السباقات، وأحداث الأمان.
- callbacks: إلغاء المزود، أخطاء التبادل والتحقق، return path الآمن، ربط Apple
  `form_post`، إزالة cookie، ومنع replay.
- الترحيلات 71–74: ترتيبها، علاقات الملكية، تفرد `issuer + subject` ثم
  `user + provider`، وعدم تعديل البيانات خلسة، ورفض rollback عند وجود بيانات لا يمكن
  تمثيلها بأمان.
- OpenAPI والحراس المولدة وتكافؤ المسارات؛ والواجهة بأربع لغات واتجاهي RTL/LTR،
  وعرض هاتف 390px وعرض مكتبي 900px، وعدم إظهار المزود غير المهيأ. لا ينطبق مسار
  barcode على نطاق الهوية والوصول ولم يُعدّل.

## عيوب اكتشفتها مراجعة الإصدار وأصلحتها

هذه إصلاحات جديدة نتجت من المراجعة الحالية، وليست أدلة منقولة من التسليمات السابقة:

1. كان فشل تبادل المزود أو تحقق callback يعيد خطأ عامًا ويمسح cookie، لكنه يترك
   معاملة التفويض المترابطة قابلة لإعادة التشغيل حتى الانتهاء. أصبح الخطأ يستهلك
   المعاملة بشرط تطابق `state + provider + browser binding` فقط، وبـ`updateMany`
   أحادي الاستخدام. يؤخذ `returnPath` الآمن من السجل الصحيح قبل الحرق؛ الربط الخاطئ
   لا يحرق الطلب، ومحاولة replay بعد فشل exchange تُرفض.
2. كان LINK لحساب مصادق عليه بلا أي إسناد شركة نشط قادرًا على إنشاء الهوية من دون
   `SecurityEvent` لأن سجل الأمان شركة-النطاق. أصبح وجود الإسناد يعاد فحصه داخل
   المعاملة قبل إنشاء الهوية أو تدوير الجلسة، والفشل العام يتراجع بالمعاملة كاملة.

أضيفت اختبارات رجعية لمسار HTTP بعد فشل exchange ثم replay، ولمطابقة الحرق، ولحساب
منفصل بلا شركة يثبت عدم إنشاء الهوية وعدم إبطال الجلسة.

## أدلة سابقة اعتمدت عليها ولم أعد تشغيلها

- وثائق `GROUP_COMPANY_ONBOARDING_AR.md` و`REGISTRATION_EMAIL_INTEGRATION_AR.md`
  تثبت fresh/upgrade/rollback على MySQL 8.4.11 وMariaDB 10.11.16 للتغييرات حتى 71،
  واختبارات التسجيل وOutbox والعزل وإنشاء الشركة الفعلية.
- `SOCIAL_LOGIN_IMPLEMENTATION_AR.md` يثبت fresh/upgrade/rollback لترحيل 72 على
  المحركين واختبارات OIDC التشفيرية المحلية.
- `SOCIAL_ONBOARDING_AR.md` يثبت fresh وrollback/reapply لترحيل 73 على المحركين
  واختبارات DB 12/12 لكل محرك.
- `SOCIAL_ACCOUNT_LINKING_AR.md` يثبت fresh/upgrade/rollback/reapply لترحيل 74،
  وتفرد `user + provider` ورفض البيانات المكررة fail-closed، على MySQL 8.4.11
  وMariaDB 10.11.16، إضافة إلى الحزم الكاملة المسجلة هناك.

لا أنسب هذه الأدلة إلى تشغيل المراجعة الحالية، ولم أعد بوابات DB الثقيلة كاملة بعد
الإصلاح؛ شُغلت MariaDB المستهدفة لأن العيبين الجديدين احتاجا إثباتًا فعليًا.

## محاولات لم تحسب نجاحًا وحدود الإثبات

- فشل seed الأول لأن `SEED_ADMIN_PASSWORD` لم يكن مضبوطًا، ثم ضُبطت قيمة اختبارية
  محلية وأعيد seed بنجاح قبل احتساب اختبارات DB. أي تشغيل قبل نجاح seed لا يُحسب.
- تشغيل browser harnesses الأربعة معًا كشف اختلاف cwd بينها وتنافس Vite على مخزن
  التحسين؛ أوقف بأمان، ثم شُغل كل ملف بالتتابع من جذره الصحيح ونجحت 16/16.
- محاولة موسعة لاحقة لاختبارات API لم تُخرج ملخص Vitest النهائي عبر جلسة التشغيل،
  فلا تُحسب كنجاح؛ الأعداد المحتسبة أعلاه فقط هي التي ظهر لها ملخص نهائي أو نتيجة
  DB صريحة.
- أظهر `git log --check` أربع نهايات فارغة مرحلية في بعض التزامات المرشح المعاد
  بناؤها، بينما ظل الفرق الصافي وفحص التزام المراجعة نظيفين. لم تُعد كتابة التزامات
  المرشح التاريخية لإخفاء نتيجة الفحص.
- لم يُعد اختبار MySQL بعد إصلاحي المراجعة، ولم يتصل الاختبار بـGoogle أو Apple
  أو Resend/SMTP حي، ولم يختبر callback عامًا أو أسرار إنتاج أو CI/Linux/cPanel أو
  Staging/Production. تفعيل المزودين يظل قرارًا تشغيليًا منفصلًا ومغلقًا افتراضيًا.
