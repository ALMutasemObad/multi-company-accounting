# تسليم تكامل التسجيل وإنشاء شركات المجموعة

## النتيجة

جُمعت محليًا، دون دفع أو نشر، تسليمات الجلسة وCRM والمصروفات والوحدات الاختيارية، ثم إنشاء شركة داخل المجموعة، ثم أدوات النشر المقفلة. بدأ الفرع من `main` عند `9be397c`، وتقدّم fast-forward إلى `61c5056`، ثم أُعيد تطبيق `b06574a` و`5a636a8` بالترتيب.

حافظ المسار المجمع على استجابة تسجيل موحدة لا تكشف وجود البريد، ثم يتيح لصاحب حساب قائم تسجيل الدخول وإنشاء شركة جديدة داخل مجموعته. الإنشاء مقيد بعضوية `OWNER` نشطة، ذري مع التأسيس المحاسبي والخزينة والاشتراك والتدقيق، ويمنح المستخدم إدارة الشركة الجديدة فقط. تظهر الشركة في قائمة الشركات ويمكن اختيار سياقها، وتُنشأ استحقاقات خطة البداية.

صححت مراجعة التكامل اختبار سباق سحب `OWNER`: أصبح توقع رفض وعد الإنشاء مربوطًا فور إنشاء الوعد. كان MariaDB ينفذ الرفض بسرعة تكفي لتسجيل `unhandled rejection` مؤقت رغم نجاح assertion المتأخر؛ بعد التصحيح نجح الاختبار بلا أخطاء غير معالجة على المحركين.

## تحقق مثبت

- `npm ci` مستقل من `package-lock.json` بمخزن `E:/DevelopmentCaches/npm`: نجح، 358 حزمة، ولا ثغرات مدققة. لم تُشارك `node_modules` أو Prisma مع مهمة أخرى.
- Prisma Client: توليد ناجح بالإصدار `7.9.1`. `contracts:check` نجح: 182 جسم طلب و2336 جسم استجابة متزامنة. بوابة i18n نجحت.
- TypeScript: نجح فحص API للمصدر والاختبارات، وفحص Web. نجح بناء API، ونجح بناء Web الإنتاجي؛ بقي تحذير chunk للمصروفات أكبر من 500kB، وليس فشلًا.
- اختبارات API الكاملة غير المتصلة بقاعدة: 1234 ناجحًا، 170 متجاوزًا لأنها بوابات DB غير مفعلة في تلك الجولة، عبر 128 ملفًا ناجحًا و41 متجاوزًا.
- اختبارات Web الكاملة: 702 ناجحة و4 متجاوزة، عبر 51 ملفًا ناجحًا وملف واحد متجاوز.
- بوابات أدوات النشر: 22/22 ناجحة، وتشمل lock الحزمة المعزولة، رفض المنصة غير المعروفة، سلامة التغليف، وتمرير نتيجة CLI. أثبت التشغيل الفعلي Prisma `7.9.1` و`mysql2 3.23.1` في أداة الترحيل المعزولة.
- رحلة Playwright المجسمة على عرض 390: 20/20 ناجحة. شملت التسجيل والدخول بأربع لغات، RTL للعربية والأردية، الوحدات الاختيارية، CSRF/401، تغير الصلاحيات، الاستجابات القديمة، وعدم إعادة إرسال الأمر المقر به. البريد والـAPI في هذه الجولة مجسمان داخل الرحلة المتصفحية وليسا خدمة بريد حقيقية.

## قواعد البيانات الفعلية

استُخدمت برامج MySQL 8.4.11 وMariaDB 10.11.16 الموجودة مسبقًا، مع data directories وقواعد جديدة معزولة على `E:`. لم يُنزّل محرك قاعدة بيانات ولم تُستخدم قواعد الأرشيف للتنفيذ.

- Fresh: طبقت جميع الترحيلات الـ71 بنجاح على كل محرك، ومنها `20260906120000_organization_idempotency`.
- Integration: نجحت 9/9 حالات على كل محرك. غطت إنشاء الشركة وعزلها، الاستحقاقات، ظهورها والتبديل إليها عبر المصادقة، replay المتزامن وبعد 24 ساعة، mismatch، عزل المفتاح بين المستخدم/المجموعة، رفض ADMIN وVIEWER والعضوية/الهوية المعطلة، رفض replay بعد سحب OWNER، rollback عند فشل الاشتراك أو التدقيق، وتسلسل سحب OWNER مع الإنشاء.
- Upgrade 70→71: استعيدت لقطة بيانات الإصدار السابق إلى قواعد جديدة، حُذفت علامة 71 الزائدة من metadata الخاصة باللقطة، ثم طبق Prisma الترحيل 71 وحده. بقيت checksums للجداول القائمة مطابقة قبل/بعد على كل محرك، وظهر سجل migration والجدول الجديد مرة واحدة.
- Rollback: نجح حذف الجدول عندما كان فارغًا، ثم نجحت إعادة تطبيق migration. بعد إنشاء سجل replay رفض rollback على المحركين بالرمز `organization_idempotency_rollback_refused_records_exist`، وبقي السجل محفوظًا.

## ما لم يُثبت

- لم يُشغّل نشر، أو استضافة حية، أو PR/push، ولم يُعطّل أي guard.
- اختبارات أدوات النشر الحالية محاكاة محلية على Windows. تبقى بوابة Linux/OpenSSL/cPanel والتطبيق الكامل على Linux مفتوحة، كما تنص تعليمات المهمة؛ لم تُعتبر الأرشيفات السابقة حزمة release نهائية.
- لم تُرسل رسالة بريد حقيقية. المثبت هو عدم اختلاف الاستجابة بين البريد القديم وغير الموجود، وعدم جدولة بريد للهوية الموجودة في اختبار الخدمة.
- لم تُختبر خدمات أو خوادم خارج النظام المحاسبي.
