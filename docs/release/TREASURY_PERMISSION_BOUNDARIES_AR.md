# تسليم حدود صلاحيات الخزينة

المهمة: `treasury-permission-boundaries`، الفرع `task/treasury-permission-boundaries`، والأساس المتحقق منه `731fc11f3635143558fcd6431b864afd0807ff53`. التنفيذ محلي داخل worktree المسجل فقط.

## ما نُفذ

- ثُبتت سياسة القراءة `cash_bank_accounts.view` وسياسة الإدارة `cash_bank_accounts.manage` في ملف محلي واحد للحسابات النقدية والبنكية وطرق الدفع.
- بقيت الحسابات وطرق الدفع قابلة للقراءة لمستخدم العرض فقط، لكن أزرار الإنشاء والتعديل والتعطيل لا تظهر له.
- حُرست الكتابات بثلاث طبقات: العرض عبر `Can`، وتركيب نماذج الحساب/طريقة الدفع عبر `allows`، والتنفيذ داخل handlers/submits قبل التحقق أو prompt أو طلب الشبكة.
- عند غياب مرجع حساب دفتر الأستاذ، تعرض خلية الحساب `—` ولا تعود إلى `ledgerAccountId` الداخلي. دالة العرض لا تستقبل المعرّف الخام أصلًا.
- لم تتغير API أو OpenAPI أو قاعدة البيانات أو i18n، ولم يُمس نطاق مصروفات الموظفين أو المخزون أو الاستيراد.

## دليل الاختبار

- اختبار الوحدة `treasury-permission-policies.test.ts`: `2/2` ناجح؛ يثبت استقلال القراءة والإدارة، ويثبت `—` عند غياب المرجع مع عرض الرمز والاسم عند وجوده.
- اختبار المتصفح `treasury-permission-boundaries.spec.ts`: شُغل على `390×844` و`1440×900` وكانت النتيجة **4/4 ناجحة في 31.0s**.
- مستخدم `cash_bank_accounts.view` وحدها رأى الحساب وطريقة الدفع، ولم ير `New/Edit/Disable` في أي من التبويبين، ولم يركب نموذج، ولم يظهر prompt/confirm، ولم يخرج طلب كتابة.
- خلية مرجع دفتر الأستاذ للمستخدم الذي لا يملك `accounts.view` عرضت `—`، وثبت غياب قيمة `ledger-internal-raw-secret` الاختبارية من DOM.
- مستخدم `cash_bank_accounts.view + cash_bank_accounts.manage` رأى أفعال الحسابات وطرق الدفع القائمة، وفتح نماذج الإنشاء والتعديل في التبويبين، دون كتابة غير مقصودة أثناء فحص العرض والتركيب.
- سُجلت reads ذات الصلة وتأكد أن `/accounts` لم يُطلب دون صلاحية الحسابات؛ بقيت قراءتا `/cash-bank-accounts` و`/payment-methods` المصرح بهما فقط.
